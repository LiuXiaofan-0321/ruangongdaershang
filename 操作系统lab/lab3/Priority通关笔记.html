CHAPTER 1

零基础先导：CPU、线程、调度、优先级

这一章不看代码，只建立直觉。

1.1 CPU 一次只能干一件事

电脑里同时“在跑”的程序有很多，但 Pintos 运行在单核 CPU 上：任何一个时刻，CPU 只在执行一段代码。看起来“同时”，是因为 CPU 在不同任务之间来回切换得很快（每秒上百次），人感觉不出来。

每一个可以被 CPU 单独执行、单独切换的“任务”，在 Pintos 里叫一个线程（thread）。你可以把线程理解成“一份正在进行的工作”：它有自己做到哪一步了（寄存器、栈），被切走之后还能从原地接着做。

比喻：只有一个医生的诊室

CPU 是诊室里唯一的医生，线程是病人。医生一次只能看一个病人（RUNNING），其他能看病的人在走廊排队（READY），还有人去拍片子了，结果出来之前叫到也没用（BLOCKED）。调度器就是护士站：决定下一个叫谁进来。

1.2 调度：下一个轮到谁？

“调度”就是回答一个问题：当 CPU 空出来（或者该换人了），从排队的线程里选哪一个？

  • 先来先服务 / 轮转（Round-Robin）：谁先排队叫谁，每人最多连续看 4 个时间单位，没看完就回到队尾。Pintos 原始代码就是这样。
  • 优先级调度（Priority Scheduling）：每个线程有一个优先级数字，永远先叫优先级最高的。这就是 Lab3 priority 部分要实现的。

1.3 Pintos 里的优先级

PRI_MIN = 0　≤　priority　≤　PRI_MAX = 63 数字越大越优先；默认 PRI_DEFAULT = 31。测试里经常出现 31、32、33……就是“比默认高一点”。

Lab3 课件第 10 页把要做的事总结成三条，这也是整份笔记的主线：

  1. 选谁跑：从就绪队列里选优先级最高的。→ 第 7 章
  2. 抢占：新来的线程比正在跑的高，正在跑的要马上让出 CPU。→ 第 8 章
  3. 锁和信号量：从等待者里叫醒优先级最高的；为锁解决“优先级反转”（捐赠）。→ 第 9–11 章
诊室比喻的延伸
  • 选谁跑 = 急诊病人优先。
  • 抢占 = 来了一个更急的病人，医生立刻停下手里的普通病人去看急诊。
  • 捐赠 = 急诊病人要用的仪器被一个普通病人占着，那就先让这个普通病人“插队”用完仪器，急诊病人才能尽快用上。
CHAPTER 2

Pintos 的线程机器

看懂 thread.c 里最核心的几十行：线程长什么样、有哪几种状态、怎么切换。

2.1 一个线程 = 一页 4 KB 内存

Pintos 给每个线程分配一页（4 KB）。页的最底部放 struct thread（线程的“档案”），剩下的空间是这个线程的内核栈，从页顶往下长。

struct thread 里和 priority 有关的字段（带 ★ 的是我们加的）：

struct thread  {    tid_t tid;                     /* 线程编号 */    enum thread_status status;     /* RUNNING / READY / BLOCKED / DYING */    char name[16];                 /* 名字，调试用 */    int priority;                  /* 实际优先级（含捐赠） */    struct list_elem elem;         /* 挂在 ready_list 或某个 waiters 上的“钩子” */    int base_priority;             /* ★ 自己设置的原始优先级 */    struct list locks;             /* ★ 当前持有的所有锁 */    struct lock *waiting_lock;     /* ★ 正在等的那一把锁，没有就是 NULL */    unsigned magic;                /* 检测栈溢出用的“魔数” */  };

2.2 四种状态

状态意思在哪
RUNNING正在 CPU 上执行就是 thread_current()
READY随时可以跑，只是 CPU 被占着ready_list
BLOCKED在等某件事（信号量、锁、睡眠到点）某个信号量的 waiters，或 sleep_list
DYING已经结束，等下一个线程替它释放那一页内存—

2.3 换人的唯一入口：schedule()

不管因为什么要换线程，最后都走到 schedule()：

static voidschedule (void){  struct thread *cur = running_thread ();  struct thread *next = next_thread_to_run ();   /* 选下一个 */  struct thread *prev = NULL;   ASSERT (intr_get_level () == INTR_OFF);        /* 必须关着中断 */  ASSERT (cur->status != THREAD_RUNNING);        /* 调用者已经改好了自己的状态 */  ASSERT (is_thread (next));   if (cur != next)    prev = switch_threads (cur, next);           /* 汇编：保存/恢复寄存器和栈 */  thread_schedule_tail (prev);} static struct thread *next_thread_to_run (void){  if (list_empty (&ready_list))    return idle_thread;                          /* 没人可跑就跑 idle */  else    return list_entry (list_pop_front (&ready_list), struct thread, elem);}
老师可能问

“你改了 next_thread_to_run 吗？”没有。它一直是“取队首”。我们改的是放进 ready_list 的方式（按优先级排好），所以队首自然就是最高优先级。另一种做法是放的时候随便放、取的时候遍历找最大，两种都对，第 14 章难题区有对比。

调用 schedule() 的三个函数，记住它们把当前线程变成什么：

函数当前线程变成什么时候用
thread_yield()READY（重新排进 ready_list）主动让出 CPU、时间片用完、被抢占
thread_block()BLOCKED（不进 ready_list）等信号量、等锁、睡眠

还有一个相关函数 thread_unblock(t)：把一个 BLOCKED 的线程变成 READY，放进 ready_list。它不会切换线程（原始代码的注释专门强调了这一点，第 8 章会讲为什么这很重要）。

2.4 idle 线程和 main 线程

  • main 线程：Pintos 启动时正在跑的那段代码被“包装”成第一个线程，叫 main，优先级 31。测试代码就跑在 main 线程里，所以测试里说的“主线程”就是它。
  • idle 线程：优先级 0。ready_list 空了没人可跑时，CPU 就跑 idle，它只做一件事：执行 hlt 指令让 CPU 休息到下一次中断。idle 不会出现在 ready_list 里，是 next_thread_to_run 的特例。

2.5 原始代码为什么“不认优先级”

/* thread_unblock() 和 thread_yield() 里，原始代码： */list_push_back (&ready_list, &t->elem);      /* 插到队尾 */ /* next_thread_to_run() 里： */list_pop_front (&ready_list);                /* 从队首取 */

队尾进、队首出 = 先来先服务。priority 字段虽然存在、thread_create 也会设置它，但调度时根本没人看它。sema_up 叫醒等待者也是 list_pop_front，同样不看优先级。这就是 lab2 结束时 make check 还挂着 19 个测试的原因（其中 12 个是 priority）。

CHAPTER 3

时钟中断、时间片、中断上下文

这一章是老师最容易“往深里问”的地方，也是我踩过 kernel panic 的地方。

3.1 中断是什么

CPU 正在执行线程 A 的代码，硬件（比如定时器）发来一个信号：“有事！”CPU 会暂停A，跳去执行一段专门的处理函数（中断处理程序），处理完再回到 A 被打断的地方继续。

比喻

医生正在看病人 A，护士敲门递进来一张纸条（中断）。医生看完纸条、做个记录（中断处理），再继续给 A 看病。纸条可能写着“该换下一位了”，但医生不会在看纸条的过程中站起来换人，而是看完纸条、回到座位上之后再换。

3.2 时钟中断和时间片

定时器每秒中断 100 次（TIMER_FREQ = 100），每一次叫一个 tick。处理函数 timer_interrupt 做三件事：

static voidtimer_interrupt (struct intr_frame *args UNUSED){  ticks++;              /* 全局计时 +1 */  thread_tick ();       /* 统计 + 检查时间片 */  thread_wake (ticks);  /* lab2 加的：叫醒睡到点的线程 */} /* thread_tick() 里检查时间片的部分 */  if (++thread_ticks >= TIME_SLICE)   /* TIME_SLICE = 4 */    intr_yield_on_return ();

每个线程连续跑满 4 个 tick 就要让出 CPU，这就是“时间片”。注意这里用的不是 thread_yield()，而是 intr_yield_on_return()。

3.3 中断上下文 vs 线程上下文

线程上下文

普通代码，属于某个线程。可以睡眠（sema_down）、可以切换线程（thread_yield）。

中断上下文

正在执行中断处理程序。CPU 只是“借用”被打断线程的栈，不能睡眠、不能切换线程。intr_context() 返回 true。

所以 thread_yield() 的第一行就是：

ASSERT (!intr_context ());

在中断里想换人，只能“预约”：

voidintr_yield_on_return (void){  ASSERT (intr_context ());  yield_on_return = true;          /* 只是设一个标志 */} /* interrupt.c 的 intr_handler() 末尾，处理完外部中断后： */      in_external_intr = false;    /* 从这一刻起 intr_context() 为 false */      pic_end_of_interrupt (frame->vec_no);      if (yield_on_return)        thread_yield ();           /* 这里才真正让出，已经不算中断上下文了 */
我踩过的坑

做抢占时，我想让睡醒的高优先级线程马上运行，就在 thread_wake()（在时钟中断里被调用）里直接写了 thread_yield()，结果 alarm-priority 一跑就 Kernel PANIC ... assertion `!intr_context ()' failed。改成 intr_yield_on_return() 就好了。详细排查过程见第 13 章。

3.4 关中断 = 原子操作

Pintos 是单核的。只要把中断关掉，就不会有时钟中断来打断当前代码，也就不会切到别的线程。所以“关中断”就能保证一段代码不被打断地一口气执行完（原子性）。内核里修改共享数据（ready_list、等待队列、优先级）的标准写法：

enum intr_level old_level = intr_disable ();   /* 关中断，并记住原来的状态 *//* …… 修改共享数据 …… */intr_set_level (old_level);                    /* 恢复成原来的状态 */
老师可能问

“为什么恢复用 intr_set_level(old_level) 而不是直接 intr_enable()？”因为调用者可能本来就关着中断（比如 lock_release 关着中断去调 sema_up）。如果 sema_up 结束时直接开中断，就把调用者的“原子区”提前打破了。恢复成原来的状态才不会影响外层。

“为什么锁的实现里不用锁保护，而用关中断？”锁本身就是要实现的东西，用锁保护锁会无限递归；而且信号量、锁要能在单核上原子地检查和修改 value / 等待队列，关中断是最底层的手段。

4.1 侵入式链表：钩子长在结构体里

平时学的链表是“节点里存数据的指针”。Pintos 反过来：链表节点 struct list_elem 嵌在 struct thread 里面，就是那个 elem 字段。链表只把这些“钩子”串起来。

倒推用的宏 list_entry：

struct thread *t = list_entry (e, struct thread, elem);/* 意思：e 是某个 struct thread 里的 elem 字段，请给我那个 struct thread 的地址。   原理：elem 在 struct thread 里的偏移量是固定的（offsetof），         用 e 的地址减去这个偏移量，就是结构体开头的地址。 */
一个 elem 只能挂一个链表

每个线程只有一个 elem，所以同一时刻只能挂在一个链表上。READY 的线程挂在 ready_list；BLOCKED 的线程挂在某个信号量的 waiters 或 sleep_list。这两种状态互斥，所以够用。（allelem 是另一个字段，挂在所有线程的 all_list 上。）同理，struct lock 里我们加的 elem 用来挂在持有者的 locks 链表上，一把锁同一时刻只有一个持有者，也够用。

4.2 比较函数：把“怎么比大小”交给调用者

链表的排序、找最大最小都要比较两个元素。Pintos 不知道你想按什么比，所以让你传一个函数指针进去：

/* list.h 里的类型定义：一个“判断 a 是否小于 b”的函数 */typedef bool list_less_func (const struct list_elem *a,                             const struct list_elem *b,                             void *aux); /* 我们写的：a 的优先级是否“大于”b（注意是严格大于） */boolthread_priority_more (const struct list_elem *a, const struct list_elem *b,                      void *aux UNUSED){  return list_entry (a, struct thread, elem)->priority         > list_entry (b, struct thread, elem)->priority;}

名字里叫“less”，但链表只关心“谁排前面”。我们把“优先级更高”当成“更小（排前面）”传进去，就得到降序排列。aux 是额外参数，我们用不到，所以标 UNUSED。

4.3 要用到的 6 个链表函数

函数作用我们在哪用
list_push_back(list, e)插到队尾持有者的 locks
list_pop_front(list)取出并删除队首next_thread_to_run、thread_wake
list_insert_ordered(list, e, less, aux)从头找第一个满足 less(e, x) 的 x，插在 x 前面；找不到就插到最后ready_list、sema 的 waiters、sleep_list

CHAPTER 5

同步原语：信号量、锁、条件变量

priority 测试里一半在考“等待者被叫醒的顺序”，所以先搞懂这三样东西本来怎么工作。

5.1 为什么需要同步

两个线程同时执行 count = count + 1，这一行在 CPU 上其实是三步：读 count、加 1、写回。如果 A 读完还没写回就被切走，B 也读了同一个旧值，最后两次加法只生效一次。这叫竞态条件。需要一种机制保证“同一时刻只有一个线程在改 count”，这就是锁和信号量的用处。

5.2 信号量 semaphore

一个非负整数 value 加一个等待队列 waiters：

voidsema_down (struct semaphore *sema)        /* P 操作：要一个资源 */{  enum intr_level old_level = intr_disable ();  while (sema->value == 0)                /* 没资源：排队并睡下 */    {      list_insert_ordered (&sema->waiters, &thread_current ()->elem,                           thread_priority_more, NULL);   /* 原来是 push_back */      thread_block ();    }  sema->value--;                          /* 醒来后再拿走一个 */  intr_set_level (old_level);} voidsema_up (struct semaphore *sema)          /* V 操作：还一个资源 */{  enum intr_level old_level = intr_disable ();  if (!list_empty (&sema->waiters))    /* 原来：thread_unblock (list_pop_front (...))，第 9 章改成挑最高优先级 */    ...  sema->value++;  intr_set_level (old_level);}
老师可能问

“sema_down 里为什么是 while 不是 if？”被叫醒只说明“有人 up 过”，不保证轮到自己时 value 还大于 0：在被叫醒到真正运行之间，可能有别的线程（比如调用 sema_try_down 的，或者刚好执行 sema_down 没阻塞的）先把 value 拿走了。所以醒来要重新检查。这是 Mesa 风格的典型写法。

“sema_up 能在中断里调用吗？”能，它不会睡眠。这一点决定了我们在 sema_up 里做抢占时要区分中断上下文（第 8 章）。

5.3 锁 lock

锁 = 初值为 1 的信号量 + 一个 holder（谁拿着它）。

struct lock  {    struct thread *holder;      /* 持有者 */    struct semaphore semaphore; /* 初值为 1 的信号量 */    struct list_elem elem;      /* ★ 挂在持有者的 locks 链表上 */    int max_priority;           /* ★ 正在等这把锁的线程中的最高优先级 */  };
信号量锁
值可以大于 1只有 0/1
谁能释放谁都能 up只有持有者能 release
有没有“主人”没有有 holder
Pintos 要求捐赠吗不要求要求
关键直觉

正因为锁有主人，才能做优先级捐赠：我知道是谁挡住了我，才能把优先级借给它。信号量没有主人，不知道该捐给谁，所以 Pintos 文档只要求对锁做捐赠。

5.4 条件变量 condition

条件变量用来“等某个条件成立”：cond_wait(cond, lock) 释放锁、睡下去等信号、醒来后重新拿锁；cond_signal 叫醒一个等的人。

Pintos 的实现很巧：每个等待者在自己的栈上建一个只属于自己的信号量（struct semaphore_elem），把它挂到 cond->waiters 上，然后在这个私人信号量上 sema_down。cond_signal 就是从 cond->waiters 里挑一个，对它的私人信号量 sema_up。

struct semaphore_elem  {    struct list_elem elem;              /* 挂在 cond->waiters 上 */    struct semaphore semaphore;         /* 这个等待者的私人信号量，初值 0 */    struct thread *thread;              /* ★ 是哪个线程在等 */  }; voidcond_wait (struct condition *cond, struct lock *lock){  struct semaphore_elem waiter;  sema_init (&waiter.semaphore, 0);  waiter.thread = thread_current ();  /* ★ */  list_push_back (&cond->waiters, &waiter.elem);  lock_release (lock);                /* 先放锁 */  sema_down (&waiter.semaphore);      /* 再睡 */  lock_acquire (lock);                /* 醒来重新拿锁 */}
老师可能问

“Mesa 和 Hoare 管程有什么区别？Pintos 是哪种？”Hoare：signal 之后被唤醒的线程立刻运行，条件一定成立。Mesa：signal 只是把等待者放回就绪状态，它要重新竞争锁，等它真正运行时条件可能又不成立了，所以使用者要用 while 重新检查条件。Pintos 是 Mesa（synch.c 注释原话）。

CHAPTER 7

实现①：就绪队列按优先级排序

对应测试：所有测试的基础；priority-fifo 专门考同优先级的顺序。

7.1 改两个地方

往 ready_list 里放线程只有两处：thread_unblock（BLOCKED → READY）和 thread_yield（RUNNING → READY）。都从 list_push_back 改成按优先级有序插入：

voidthread_unblock (struct thread *t){  enum intr_level old_level;  ASSERT (is_thread (t));  old_level = intr_disable ();  ASSERT (t->status == THREAD_BLOCKED);  list_insert_ordered (&ready_list, &t->elem, thread_priority_more, NULL);  t->status = THREAD_READY;  intr_set_level (old_level);} voidthread_yield (void){  struct thread *cur = thread_current ();  enum intr_level old_level;  ASSERT (!intr_context ());  old_level = intr_disable ();  if (cur != idle_thread)    list_insert_ordered (&ready_list, &cur->elem, thread_priority_more, NULL);  cur->status = THREAD_READY;  schedule ();  intr_set_level (old_level);}

这样 ready_list 永远从高到低排好，next_thread_to_run() 照旧取队首，取到的就是最高优先级。

7.2 为什么必须是 > 而不是 >=

回忆 list_insert_ordered：找到第一个满足 less(新元素, x) 的 x，插在 x 前面。

  • 用 >：同优先级时 32 > 32 为假，一路找不到，就插到所有 32 的后面 → 轮转（FIFO）。
  • 用 >=：32 >= 32 为真，第一个就停，插到所有 32 的最前面 → 刚 yield 的线程又排在队首，下一次又选中它，thread_yield 等于没让。

CHAPTER 8

实现②：抢占——什么时候必须马上让出 CPU

对应测试：priority-preempt、priority-change，以及所有“唤醒后要立刻运行”的测试。

8.1 只排序为什么不够

排序只决定“下次换人时选谁”。如果当前线程不主动让出，高优先级线程只能等到时间片用完（最多 4 个 tick）。Pintos 文档要求：一个比当前线程优先级高的线程进入 ready_list 时，当前线程必须立即让出 CPU；当前线程降低自己的优先级、不再是最高时，也要立即让出。

8.2 thread_preempt：一个公共函数

/* 如果就绪队列里有比当前线程优先级更高的线程，就让出 CPU。 */voidthread_preempt (void){  enum intr_level old_level = intr_disable ();   if (!list_empty (&ready_list)      && list_entry (list_front (&ready_list), struct thread, elem)->priority         > thread_current ()->priority)    {      if (intr_context ())        intr_yield_on_return ();   /* 中断里只能预约 */      else        thread_yield ();    }  intr_set_level (old_level);}
  • 因为 ready_list 有序，只看队首就知道有没有比我高的。
  • 用严格 >：同优先级不抢占，让当前线程把时间片用完，保持轮转。
  • 判断 intr_context()：sema_up 可能在中断处理程序里被调用，那时不能 thread_yield。

8.3 在哪里调用

原则：任何可能让“ready_list 里出现比我更高的线程”的地方，或者“我自己变低”的地方。

位置为什么对应测试
thread_create() 末尾（thread_unblock 之后）新线程可能比我高priority-preempt、priority-change、donate-*
thread_set_priority() 末尾我降低了自己的优先级priority-change、priority-fifo、donate-lower
sema_up() 末尾（value++ 之后）被叫醒的线程可能比我高priority-sema、condvar、所有锁的测试（lock_release 里调用 sema_up）
thread_wake()（时钟中断里）睡醒的线程可能比当前线程高alarm-priority 的语义；这里直接用 intr_yield_on_return()

8.4 为什么不直接在 thread_unblock 里抢占

看起来最省事的做法是：thread_unblock 把线程放进 ready_list 后顺手检查一下。但原始代码的注释专门说了：“This function does not preempt the running thread. This can be important: if the caller had disabled interrupts itself, it may expect that it can atomically unblock a thread and update other data.”

举个我们代码里的真实例子，sema_up：

  if (!list_empty (&sema->waiters))    thread_unblock (被选中的线程);   /* ① 先叫醒 */  sema->value++;                     /* ② 再加 1 */  thread_preempt ();                 /* ③ 最后才检查抢占 */
老师可能问

“如果 thread_unblock 里就抢占，会出什么问题？”在 ① 就切走的话，被叫醒的高优先级线程立刻运行，回到 sema_down 的 while (sema->value == 0) 检查——这时 ② 还没执行，value 还是 0，它又睡回去了，而且这次没人再叫醒它。所以抢占必须放在“调用者把相关数据都改完之后”。这也是我们把抢占写成单独的 thread_preempt()、放在各个函数末尾的原因。

8.5 不抢占会怎样（真实输出）

把 thread_create 末尾的 thread_preempt() 删掉，priority-preempt 输出变成：

(priority-preempt) (priority-preempt) Thread high-priority iteration 0
(priority-preempt) Thread high-priority iteration 1
...
(priority-preempt) Thread high-priority done!
The high-priority thread should have already completed.

main 没让出 CPU，接着去打印 “The high-priority thread should have…”，刚打印了前缀 (priority-preempt) 就被时钟中断打断（时间片到了），高优先级线程这才上 CPU，于是两行输出搅在一起。这个现象说明：没有立即抢占，高优先级线程最多要等一个时间片。

实现③：信号量和条件变量按优先级唤醒

对应测试：priority-sema、priority-condvar、donate-sema，以及所有锁（锁的底层就是信号量）。

9.1 sema_up：取出时重新找最高的

voidsema_up (struct semaphore *sema){  enum intr_level old_level;  ASSERT (sema != NULL);   old_level = intr_disable ();  if (!list_empty (&sema->waiters))    {      struct list_elem *e = list_min (&sema->waiters,                                      thread_priority_more, NULL);      list_remove (e);      thread_unblock (list_entry (e, struct thread, elem));    }  sema->value++;  thread_preempt ();          /* 叫醒的线程可能比我高 */  intr_set_level (old_level);}
只在插入时排序为什么不够

sema_down 时我们已经按优先级插入了，为什么 sema_up 还要重新找？因为线程在等待期间优先级可能被捐赠改变，插入时排好的顺序就“过期”了。donate-sema 就是这样：L 插入时是 32 排在 M(34) 后面，之后被捐赠成 36，位置却没变。取队首会叫醒 M。（第 12 章推演器里有这个场景。）

list_min 配“大于”比较函数有点绕：list_min(list, less) 返回“没有谁比它更 less”的那个元素，我们传进去的 less 其实是“优先级更高”，所以“最 less”的就是优先级最高的；有并列时返回最前面的，也就是最早来的，同优先级仍然先来先服务。写一个“小于”比较函数配 list_max 效果一样，我只是想少写一个函数。

老师可能问

“为什么不直接看每个私人信号量 waiters 的队首线程，而要加一个 thread 字段？”因为 cond_wait 是先 lock_release 再 sema_down 的，中间可能被抢占。另一个线程拿到锁、调用 cond_signal 时，这个等待者可能还没来得及 sema_down，它的私人信号量等待队列是空的，取队首会出错。直接存线程指针最稳。

CHAPTER 10

优先级反转与优先级捐赠：原理

这是 PPT 的重点，也是老师最可能深挖的地方。

10.1 什么是优先级反转

优先级反转：高优先级线程 H 在等低优先级线程 L 手里的资源（锁），而中优先级线程 M 又一直抢占 L，结果 H 实际上被 M 卡住了，表现得好像 H 的优先级比 M 还低。

  • 有界反转：只有 H 和 L，H 等 L 放锁，等待时间不超过 L 的临界区长度。这是用锁就不可避免的，可以接受。
  • 无界反转：中间插进来 M（甚至很多个 M），H 的等待时间和锁完全无关、没有上限。这才是真正的问题，捐赠解决的就是它。
真实事故：1997 年火星探路者号

探路者号用的是 VxWorks 实时操作系统。低优先级的气象数据任务拿着“信息总线”的互斥锁，高优先级的总线管理任务等这把锁，而一个运行时间较长的中优先级通信任务一直抢占气象任务。总线管理任务长时间没运行，看门狗认为系统出错，于是整个系统反复重启。工程师在地面复现后，远程打开了那个互斥锁的“优先级继承”选项（默认是关的），问题解决。课件第 16–21 页讲的就是这个。

10.2 解决：优先级捐赠（优先级继承）

H 等 L 的锁时，把自己的优先级“借”给 L。L 变得和 H 一样高，M 就抢不了它了；L 尽快跑完临界区放锁，放锁时把借来的优先级还回去，H 立刻拿到锁。

要处理三种情况：

单一捐赠

一个线程等一把锁。
donate-one

多重捐赠

一个线程同时拿着几把锁，每把锁上都有人等。优先级取这些捐赠里最高的；放掉一把锁时只收回这把锁带来的。
donate-multiple(2)

嵌套捐赠

H 等 M 的锁，M 又在等 L 的锁。H 的优先级要沿着链一路传到 L，否则 L 还是会被别人抢占。
donate-nest、donate-chain

10.3 理论补充：继承协议 vs 天花板协议

优先级继承 Priority Inheritance（Pintos 要求的）优先级天花板 Priority Ceiling
什么时候提升有人来等的时候，持有者临时继承等待者的优先级一拿到锁就提升到这把锁预先设定的“天花板”（所有可能用它的线程里最高的优先级）
需要预先知道什么什么都不用每把锁会被哪些线程用
能防死锁吗不能（两个线程互相等对方的锁，捐赠也救不了）经典的天花板协议可以防止死锁和链式阻塞

实现④：优先级捐赠，逐行讲代码

11.1 设计：按“锁”记账

课件第 22 页建议给线程维护一个“捐赠者线程列表”。我想了一下：捐赠总是按锁收回的，放掉哪把锁，就收回因为这把锁得到的捐赠。所以换了个记法：

字段在哪记什么

老师可能问：为什么不用捐赠者列表？

两种都能过测试。记锁的好处：放锁时只要 list_remove 这把锁再重算；记捐赠者的话，放锁时要遍历捐赠者列表，把所有“在等这把锁的”删掉，嵌套时还要想清楚间接捐赠者算谁的，更容易错。而且实际优先级永远由一个公式算出来，不在各处“加一点、减一点”，多重、嵌套、捐赠期间改优先级这几种情况都不用写特判。

11.2 thread_update_priority：唯一“算优先级”的地方

voidthread_update_priority (struct thread *t){  int priority = t->base_priority;  struct list_elem *e;   ASSERT (intr_get_level () == INTR_OFF);   if (thread_mlfqs)            /* MLFQS 模式不做捐赠 */    return;   for (e = list_begin (&t->locks); e != list_end (&t->locks);       e = list_next (e))    {      struct lock *l = list_entry (e, struct lock, elem);      if (l->max_priority > priority)        priority = l->max_priority;    }  t->priority = priority;   /* 如果 T 在就绪队列里，优先级变了，位置也要跟着变 */  if (t->status == THREAD_READY)    {      list_remove (&t->elem);      list_insert_ordered (&ready_list, &t->elem, thread_priority_more, NULL);    }}
最后那段很容易漏

被捐赠的线程如果正处于 READY，它在 ready_list 里的位置是按旧优先级排的。不挪的话，调度器取队首还是取不到它，捐赠就白做了。（如果它是 BLOCKED，挂在信号量的 waiters 上，就靠 sema_up 取出时重新找最高的来兜底。）

11.3 lock_acquire：捐出去

voidlock_acquire (struct lock *lock){  struct thread *cur = thread_current ();  enum intr_level old_level;   ASSERT (lock != NULL);  ASSERT (!intr_context ());  ASSERT (!lock_held_by_current_thread (lock));   old_level = intr_disable ();                           /* ① */   if (!thread_mlfqs && lock->holder != NULL)             /* ② 锁被占用 */    {      struct lock *l = lock;      int depth = 0;       cur->waiting_lock = lock;                          /* ③ */      while (l != NULL && l->holder != NULL && depth < DONATE_DEPTH_MAX             && l->max_priority < cur->priority)         /* ④ */        {          l->max_priority = cur->priority;               /* ⑤ 捐给这把锁 */          thread_update_priority (l->holder);            /* ⑥ 持有者重算 */          l = l->holder->waiting_lock;                   /* ⑦ 往下一层 */          depth++;        }    }   sema_down (&lock->semaphore);                          /* ⑧ 真正等锁 */   cur->waiting_lock = NULL;                              /* ⑨ 拿到了 */  lock->holder = cur;  if (!thread_mlfqs)    {      lock->max_priority = PRI_MIN;                      /* ⑩ */      if (!list_empty (&lock->semaphore.waiters))        lock->max_priority = list_entry (list_min (&lock->semaphore.waiters,                                                   thread_priority_more, NULL),                                         struct thread, elem)->priority;      list_push_back (&cur->locks, &lock->elem);      thread_update_priority (cur);    }  intr_set_level (old_level);}
  1. ① 整个函数关中断：捐赠要同时改好几个线程和锁，中途被打断的话别的线程会看到“改了一半”的数据。
  2. ② 只在锁被占用时捐赠；MLFQS 模式下 Pintos 规定不捐赠。
  3. ③ 记下自己在等哪把锁：以后别人沿链捐赠到我时，要通过它继续往下走。
  4. ④ 循环的四个停止条件：
    • l == NULL：链到头了，最后一个持有者没在等别的锁。
    • l->holder == NULL：这把锁刚被释放、新持有者还没设上（见下面“窗口期”）。
    • depth >= 8：防止链太长或出现环时死循环。Pintos 文档允许设一个合理的上限（比如 8 层）；donate-chain 是 7 层，够用。
    • l->max_priority >= cur->priority：这把锁上已经有同样高或更高的捐赠了，再往下也不用捐（11.6 节证明为什么可以提前停）。
  5. ⑤⑥ 捐赠：只改锁的 max_priority，再让持有者按公式重算。不直接写 holder->priority = cur->priority，是为了让“放锁时收回”变得简单。
  6. ⑦ 嵌套：持有者如果也在等别的锁，就沿着它继续捐。
  7. ⑧ sema_down 可能阻塞；被叫醒、拿到锁才往下走。
  8. ⑩ 拿到锁后重算这把锁的 max_priority：锁上剩下的等待者原来是捐给上一个持有者的，现在应该改为捐给我。上一个持有者在 lock_release 时已经把这把锁从它的 locks 里删掉了，不会再受影响。
窗口期：为什么要判断 l->holder != NULL

A 刚 lock_release，把 holder 置成 NULL 并叫醒了等待者 B；但 B 还没被调度、还没执行到 ⑨，它的 waiting_lock 仍然指着这把锁。如果这时另一个线程 C 沿链捐赠到 B，再往下一步就会访问 NULL->waiting_lock。测试里没有触发，但这是对着代码推演交错情况时发现的隐患，加上判断更安全。

11.4 lock_release 和 lock_try_acquire

voidlock_release (struct lock *lock){  enum intr_level old_level;  ASSERT (lock != NULL);  ASSERT (lock_held_by_current_thread (lock));   old_level = intr_disable ();  if (!thread_mlfqs)    {      list_remove (&lock->elem);                   /* 这把锁不再算我的 */      thread_update_priority (thread_current ());  /* 按剩下的锁重算 */    }  lock->holder = NULL;  sema_up (&lock->semaphore);   /* 叫醒最高的等待者；末尾 thread_preempt 负责让出 */  intr_set_level (old_level);} boollock_try_acquire (struct lock *lock){  bool success = sema_try_down (&lock->semaphore);  if (success)    {      enum intr_level old_level = intr_disable ();      lock->holder = thread_current ();      if (!thread_mlfqs)        {          lock->max_priority = PRI_MIN;   /* 一次就拿到，说明没人在等 */          list_push_back (&thread_current ()->locks, &lock->elem);        }      intr_set_level (old_level);    }  return success;}

lock_release 只做两件事：把锁从 locks 里删掉、按公式重算。只收回这把锁带来的捐赠，别的锁上的还在。然后 sema_up 叫醒最高的等锁线程，而且因为我的优先级刚降，sema_up 末尾的 thread_preempt() 会让我马上让出。

lock_try_acquire 不会等待，所以不捐赠；但拿到了也要挂进 locks，否则以后有人来等这把锁、捐赠给我时，我重算优先级会漏掉它。

11.5 thread_set_priority 和 init_thread

voidthread_set_priority (int new_priority){  struct thread *cur = thread_current ();  enum intr_level old_level;   if (thread_mlfqs)                    /* MLFQS 下优先级由调度器算，忽略 */    return;   old_level = intr_disable ();  cur->base_priority = new_priority;   /* 只改 base */  thread_update_priority (cur);        /* 实际优先级按公式重算 */  intr_set_level (old_level);   thread_preempt ();                   /* 降低后可能有人比我高了 */} /* init_thread() 里新增的初始化 */  t->priority = priority;  t->base_priority = priority;  list_init (&t->locks);  t->waiting_lock = NULL;

如果直接写 cur->priority = new_priority，被捐赠期间就会把捐赠“覆盖”掉，donate-lower 会输出 Actual priority: 21（期望 41）。thread_get_priority() 不用改，它返回的就是含捐赠的实际优先级，这也是 Pintos 文档的要求。

11.6 进阶：这套设计为什么是对的

下面两条是“不变式”推理，老师问“你怎么保证……”时可以用。

不变式 1：每把锁的 max_priority ≥ 每个正在等它的线程的当前优先级。

  • 线程开始等锁时，④⑤ 保证了这一点。
  • 等待中的线程优先级只可能变高：它被阻塞了，不能自己调 thread_set_priority；它持有的锁也不会被释放（释放要它自己运行）。唯一的变化是有人沿链捐赠给它，而沿链捐赠时 ⑦ 会走到它的 waiting_lock，顺手更新这把锁的 max_priority。
  • 所以等待期间 max_priority 不需要降低。

不变式 2：持有者的 priority ≥ 它持有的每把锁的 max_priority。每次改 max_priority 后都立刻调用 thread_update_priority(holder)。

由此，提前停止是安全的：如果某把锁的 max_priority 已经 ≥ 我的优先级，说明之前有人用同样高的优先级捐赠过这条链，那次捐赠已经沿链传下去了（如果链后来又变长，是因为链上某个线程后来又去等别的锁，那时它会用自己含捐赠的优先级往下捐）。所以我再走下去不会让任何人更高。

和 MLFQS 的关系

-o mlfqs 模式下优先级由 recent_cpu 和 nice 自动计算，Pintos 规定这时不做捐赠、thread_set_priority 无效。所以每个相关函数开头都判断 thread_mlfqs。priority-* 测试开头都有 ASSERT (!thread_mlfqs);，只在普通模式下跑。

老师难题区

先遮住答案自己说一遍，再展开。基础 进阶 难

调度与抢占

基础你改了哪些地方让调度器“认优先级”？

往 ready_list 放线程的两处（thread_unblock、thread_yield）改成按优先级降序有序插入；next_thread_to_run 没改，还是取队首。再加一个 thread_preempt()，在 thread_create、thread_set_priority、sema_up 末尾调用，中断里用 intr_yield_on_return。

进阶插入时排序 vs 取出时找最大，哪个好？复杂度呢？

插入时排序：插入 O(n)，取出 O(1)；取出时找最大：插入 O(1)，取出 O(n)。线程数很少，都可以。

区别在于“优先级会变”：插入时排序的话，线程在队列里时优先级一变（被捐赠、MLFQS 每 4 tick 重算），顺序就过期，必须手动挪位置（我们在 thread_update_priority 里挪，MLFQS 里 list_sort）。取出时找最大永远用最新的优先级，反而更不容易出错。我们选有序插入是跟着课件的提示，并且在所有改优先级的地方都处理了重新排序。

基础同优先级的线程怎么调度？

轮转。比较函数用严格 >，新入队的线程排在同优先级线程最后；时间片用完（4 tick）就 thread_yield 回到同优先级的队尾。thread_preempt 也用严格 >，同优先级不抢占。

进阶为什么不在 thread_unblock 里直接抢占？

调用者可能关着中断，还要在叫醒之后继续改数据。sema_up 是先 thread_unblock 再 value++：如果在 unblock 里就切走，被叫醒的线程回到 sema_down 的 while 检查时 value 还是 0，又会睡回去，而且没人再叫醒它。所以抢占放在函数末尾。原始代码的注释也专门说了 thread_unblock 不抢占。

进阶intr_yield_on_return 之后，什么时候真正让出？那时还算中断上下文吗？

在 intr_handler 的末尾：先把 in_external_intr 置为 false、给中断控制器发 EOI，然后检查 yield_on_return，为真才调用 thread_yield()。那时 intr_context() 已经返回 false，所以 thread_yield 的断言能通过。

进阶thread_preempt 里为什么要关中断？

“看队首优先级”和“让出”要作为一个整体。如果检查完、还没 yield 时来一次时钟中断，ready_list 可能已经变了（比如有线程被 thread_wake 放进来），判断就不准了。关中断保证这一小段原子执行。thread_yield 本身也会关中断，嵌套关中断没问题，因为都用 intr_set_level(old) 恢复。

基础严格优先级调度会不会让低优先级线程饿死？

会。只要一直有高优先级线程可运行，低优先级的就永远轮不到。Pintos 的 priority 部分不要求解决饥饿；第三部分 MLFQS 通过动态优先级解决：一个线程用 CPU 越多，recent_cpu 越大，优先级越低；不用 CPU 时 recent_cpu 衰减、优先级回升，相当于“老化（aging）”。

进阶donate-chain 里 main 的优先级是 0，和 idle 一样，为什么不会和 idle 抢？

idle 从来不在 ready_list 里。thread_yield 里专门判断了 cur != idle_thread 才入队；next_thread_to_run 只有在 ready_list 为空时才返回 idle。所以只要 main 是 READY，就一定先选 main。

进阶priority-fifo 里 main 为什么先把自己升到 33 再创建线程？priority-sema 里为什么先降到 0？

fifo：16 个线程都是 32，main 升到 33 后创建它们不会被抢占，16 个线程按创建顺序整整齐齐排进 ready_list，然后 main 降回 31，它们才一起开始轮转，这样才能检验“每轮顺序一样”。

sema：main 降到 0，每个新线程一创建就比 main 高，立刻运行并在 sema_down 睡下；之后每次 sema_up 叫醒的线程也都比 main 高，必须立刻抢占，输出才会和 “Back in main thread.” 交替。

进阶thread_create 返回之前，新线程可能已经运行完了吗？

可能。新线程优先级更高时，thread_create 末尾的 thread_preempt 就切过去了，它甚至可能跑完、退出、页面被释放，然后 thread_create 才返回 tid。所以调用者不能再访问那个线程的 struct thread，Pintos 的注释也写了要用信号量之类的同步来保证顺序。priority-preempt 就是利用这一点：“The high-priority thread should have already completed.”

信号量、锁、条件变量

基础为什么只对锁做捐赠，信号量不捐？

锁有持有者 holder，知道是谁挡住了我，可以捐给它；信号量没有持有者，任何线程都可以 up，等信号量的线程不知道该把优先级借给谁。Pintos 文档也只要求锁的捐赠。

进阶为什么 sema_up 要重新找最高的？能不能用 list_sort？

线程在等待期间可能被捐赠（donate-sema 的 L），插入时的顺序过期了。用 list_sort 再取队首也可以，但要 O(n log n)，而且要确认排序是稳定的；list_min 线性扫一遍 O(n)，并列时返回最前面那个，天然保持先来先服务。

难为什么捐赠发生时，不顺便把被捐赠线程在信号量等待队列里的位置也调整好？

捐赠时只知道“持有者是谁”，不知道它此刻挂在哪个链表上：elem 只有一个，可能在 ready_list、某个信号量的 waiters、条件变量私人信号量的 waiters 或 sleep_list 里，struct thread 没有记录它属于哪个链表。我们只处理了 READY 的情况（ready_list 是全局的，知道在哪）；BLOCKED 的情况交给 sema_up 取出时重新找最高的。如果要做，就得在 thread 里再记一个“我在哪个等待队列上”的指针。

进阶条件变量需要捐赠吗？

不需要，也做不了。cond_wait 等的是“某个条件成立”，没有一个具体的持有者在挡着它；而且 cond_wait 先释放了锁才睡。条件变量只需要 cond_signal 按优先级唤醒。被唤醒后重新 lock_acquire 时，如果锁被占用，那时才会正常捐赠。

基础lock_release 之后当前线程一定会让出 CPU 吗？

不一定。放锁后它按剩下的锁重算优先级，sema_up 叫醒最高的等锁线程，然后 thread_preempt 比较 ready_list 队首和自己：只有队首更高才让出。比如 donate-multiple2 里 main 放锁 a 后还是 36，被叫醒的 a(34) 就要等着。

进阶中断处理程序里能调用 lock_acquire 或 sema_down 吗？

不能。它们可能阻塞，而中断上下文不能睡眠；lock_acquire 和 sema_down 开头都有 ASSERT (!intr_context ())。中断里可以用 sema_up 和 sema_try_down、lock_try_acquire（不会阻塞）。

优先级捐赠

基础用一句话说清你的捐赠设计。

线程记录持有的锁，锁记录正在等它的线程里最高的优先级，线程的实际优先级 = max(原始优先级, 每把锁的 max_priority)；等锁时沿着 waiting_lock → holder 链把优先级捐到锁上，放锁时把这把锁从列表里删掉，任何变化都调用 thread_update_priority 按公式重算。

进阶你的设计和课件建议的“捐赠者列表”有什么区别？

课件：线程维护一个“捐赠给我的线程”列表，放锁时删掉等这把锁的捐赠者，再在剩下的捐赠者里取最大。我们：维护“我持有的锁”，每把锁自带 max_priority。两者等价；我们放锁时只要删一个锁，不用遍历捐赠者筛选“谁等的是这把锁”。嵌套时，间接捐赠也自然体现在中间那把锁的 max_priority 里。

进阶拿到锁之后为什么要重算这把锁的 max_priority？

这把锁上可能还有别人在等，它们之前是捐给上一个持有者的，现在应该改为捐给我。如果不重算，max_priority 可能还是我自己等锁时捐的值（我已经不在等了），或者是上一轮留下的旧值。重算成“剩余等待者的最高优先级”，没人等就是 PRI_MIN。donate-one 里 acquire2 拿到锁后，锁上 acquire1(32) 还在等，所以 max 是 32。

难捐赠循环为什么可以在 l->max_priority >= cur->priority 时提前停？会不会漏捐？

不会。两个不变式：(1) 每把锁的 max_priority ≥ 每个等它的线程的当前优先级；(2) 持有者的优先级 ≥ 它持有的每把锁的 max_priority。如果某把锁的 max 已经 ≥ 我的优先级，说明之前有优先级不低于我的线程捐过这把锁，那次捐赠已经沿链传下去了，链上后面的线程都已经 ≥ 这个值。链如果后来变长，是因为链上某个线程后来又去等新的锁，那时它会用自己含捐赠的优先级继续往下捐。所以我再往下走不会让任何人变高。

难线程在等锁期间，它的优先级会降低吗？max_priority 要不要降？

不会降。等锁的线程被阻塞了，不能调用 thread_set_priority；它持有的锁也不会被释放（释放要它自己运行）。它的优先级只可能因为别人沿链捐赠而升高，而沿链捐赠时循环会经过它的 waiting_lock，顺手把那把锁的 max_priority 也抬高。所以等待期间 max_priority 只升不降，不需要“降低”的逻辑；只有拿到锁、放锁这两个时刻才需要重算。

进阶嵌套深度限制 8 层有什么代价？超过 8 层会怎样？

超过 8 层后，更深处的持有者拿不到捐赠，可能又出现优先级反转。这是在“正确性”和“防止死循环”之间的取舍：如果线程之间形成了等待环（死锁），没有上限的话理论上可能一直绕圈。Pintos 文档允许设一个合理的上限，比如 8；测试里最深的是 donate-chain 的 7 层。

难如果两个线程死锁（A 等 B 的锁，B 等 A 的锁），你的代码会怎样？捐赠能解决死锁吗？

捐赠解决不了死锁，两个线程都会永远阻塞。但我们的循环不会卡死：设 A(40) 持 la、B(30) 持 lb。A 等 lb：lb.max = 40，B 变 40，B 没在等锁，停。B 再等 la：la.max = 40，A 重算还是 40；沿 A 的 waiting_lock 到 lb，lb.max 已经是 40，不小于 B 的 40，停。即使条件没让它停，depth < 8 也会兜底。

进阶被捐赠的线程如果在 READY / 在睡觉（timer_sleep）/ 在等信号量，分别会怎样？
  • READY：thread_update_priority 把它从 ready_list 摘下来按新优先级重新插入。
  • 在 sleep_list 里睡觉：只改优先级，不动 sleep_list（那里按唤醒时间排序）；睡醒时 thread_unblock 按新优先级插入 ready_list。
  • 在信号量上等：位置不动，sema_up 取出时重新找最高的（donate-sema）。
进阶为什么 lock_acquire 里关中断，sema_down 里也关中断，嵌套会不会有问题？

不会。每一层都用 old = intr_disable() 和 intr_set_level(old)：sema_down 进来时中断已经关了，它记下的 old 就是“关”，出去时恢复成“关”，外层 lock_acquire 最后才恢复成真正的原状态。sema_down 里阻塞时会切到别的线程，每个线程切回来时恢复的都是它自己的中断状态，Pintos 的设计允许“关着中断调用 thread_block”。

进阶线程拿着锁就退出了会怎样？

Pintos 没有替你处理：锁永远不会被释放，等它的线程永远阻塞，而且 holder 会指向已经被释放的页。这属于使用错误，内核线程退出前必须释放持有的锁。测试里不会出现这种情况。

难如果 Pintos 是多核的，你的实现还成立吗？

不成立。关中断只对当前 CPU 有效，另一个 CPU 照样能同时修改 ready_list 和锁的状态。多核下要用自旋锁保护这些数据结构；沿链捐赠要同时访问好几个线程和锁，还要规定加锁顺序避免死锁；“只看 ready_list 队首决定是否抢占”也要变成给别的 CPU 发处理器间中断。我们的实现基于“单核 + 关中断就是原子操作”这个前提。

进阶MLFQS 模式下，锁和信号量还按优先级唤醒吗？

按。Pintos 要求优先级调度“在所有情况下”都生效，只是 MLFQS 模式下优先级由公式计算、不做捐赠。我们的 sema_up 和 cond_signal 照样挑优先级最高的，thread_update_priority 和捐赠循环在 MLFQS 下直接跳过。

难火星探路者号是死锁吗？为什么会重启？

不是死锁，是无界优先级反转。高优先级的总线管理任务等低优先级气象任务手里的互斥锁，而中优先级的通信任务一直抢占气象任务，总线管理任务迟迟不能运行。系统里的看门狗发现总线管理任务没有按时完成，判定系统故障，于是复位重启。修复方法是打开那个互斥锁的优先级继承选项。

难优先级继承和优先级天花板协议有什么区别？

继承：有高优先级线程来等时，持有者临时继承它的优先级，不需要预先知道什么，但防不了死锁，也可能出现一个线程依次被好几把锁挡住（链式阻塞）。天花板：每把锁预先设定一个天花板（可能使用它的线程中的最高优先级），线程拿到锁就提升到天花板；经典的天花板协议能防止死锁和链式阻塞，代价是要静态知道每把锁会被谁用。Pintos 要求的是继承。
