### （二）今年新版课件（Lesson 2–7）高频命题判断清单（24 道核心陷阱）

#### 【Lesson 2–3：系统调用、内核结构、进程与 IPC】
1. **“应用程序每调用一次 `printf()`，就会立即触发一次 `write()` 系统调用。”**
   - **×**。`printf()` 是标准库函数，数据常先写入**用户态缓冲区**，缓冲刷新（满、换行、`fflush` 或退出）时才调用 `write()`，多次输出可能合并为一次系统调用。
2. **“CPU 从用户态切换到内核态，就意味着发生了进程上下文切换。”**
   - **×**。系统调用或中断进入内核只是**模式切换（Mode Switch）**，内核处理完毕后可直接返回原进程继续运行，不一定切换进程。
3. **“Linux 支持动态加载内核模块（`.ko`），因此 Linux 属于微内核操作系统。”**
   - **×**。Linux 是结合了模块化的**单体内核**；加载后的模块直接运行在**内核地址空间**并通过函数调用交互，而非微内核的用户态独立进程 + 消息传递。
4. **“等待 I/O 的进程在 I/O 操作完成后，会立即由等待态直接进入运行态。”**
   - **×**。I/O 完成后进程只能由**等待态转为就绪态**（进入就绪队列），必须经 CPU 调度器选中分派后才能进入运行态。
5. **“`fork()` 之后，父子进程各自的普通全局变量与继承的已打开文件偏移量都彼此独立、互不影响。”**
   - **×**。虚拟地址空间（普通变量）各自独立（写时复制）；但继承的文件描述符指向同一个内核**打开文件描述**，因此**共享文件读写偏移量（file offset）**。
6. **“父进程尚未调用 `wait()`，此时它创建的正在运行的子进程就是僵尸进程；一旦父进程退出，子进程也会自动终止。”**
   - **×**。只有**已终止**但尚未被父进程 `wait` 回收的子进程才是**僵尸进程**；父进程先退出会使子进程成为**孤儿进程**，被 `init`/`systemd`（PID 1）收养并继续运行。
7. **“当匿名管道（pipe）内已经没有数据时，阻塞模式的 `read()` 一定会立即返回 `0`（EOF）。”**
   - **×**。仅当管道已空**且系统中所有指向该管道的写端描述符（含读进程自身继承未关的写端）均已关闭**时才返回 `0`；只要仍有任一写端打开，`read()` 就会阻塞等待。
8. **“客户端发起 RPC 远程过程调用发生超时，可以断定服务端没有执行该请求，直接重试总是安全的。”**
   - **×**。超时可能是响应报文在网络丢失而**服务端实际已执行完毕**；对非幂等操作（如扣款）直接重试会导致重复执行。

#### 【Lesson 4–5：线程模型、并发与 CPU 调度】
9. **“同一进程内的每个线程拥有各自独立的栈，因此一个线程绝对无法读写同进程另一线程栈上的变量。”**
   - **×**。同进程线程**共享同一个虚拟地址空间**，硬件不隔离各线程栈；若将某线程有效栈变量的地址（指针）传给另一线程，后者可以直接访问。
10. **“在多对一（Many-to-One）线程模型中，即使运行在 8 核处理器上，同一进程的多个用户线程也无法并行执行，且任一线程发起阻塞系统调用会阻塞整个进程。”**
    - **√**。（内核只感知那唯一一个内核线程，同一时刻只能在一个核上调度，阻塞即全组停摆。）
11. **“调用 `pthread_cancel(tid)` 成功返回后，说明目标线程已经终止并释放了所有资源。”**
    - **×**。`pthread_cancel` 仅发出取消请求；若目标线程禁用取消或处于默认的**延迟取消（Deferred）**模式，需运行到**取消点**才退出，且需 `pthread_join` 确认回收。
12. **“在线程池中复用工作线程处理请求时，线程局部存储（TLS）变量会在每个新任务开始时自动清空重置。”**
    - **×**。TLS 生命周期随工作线程而非随任务；工作线程复用时 TLS 会保留上一个任务遗留的旧值，新任务必须显式覆盖或清理。
13. **“某任务在时刻 0 到达并立刻获得 CPU，响应时间为 0，说明它的总等待时间也一定为 0。”**
    - **×**。响应时间只看**首次**获得 CPU 的等待；在抢占式调度（如 RR、SRTF）下，该任务后续可能被多次抢占回就绪队列排队，累计总等待时间可以大于 0。
14. **“在时间片轮转（RR）调度中，每当定时器时间片到期，CPU 一定会切换到另一个进程运行。”**
    - **×**。若时间片到期时就绪队列中**没有其他可运行的同级或更高优先级进程**（仅剩当前进程自己），该进程将继续占用下一个时间片，无需切换。
15. **“四核八线程（开启超线程）的处理器等价于拥有八个独立的物理 CPU 核心。”**
    - **×**。它是 4 个物理核向 OS 呈现 8 个**逻辑 CPU**，利用访存停顿（Memory stall）切换硬件线程；同核两个逻辑线程仍共享执行单元与缓存，不等同于 8 个独立物理核。
16. **“在 Linux 系统中，普通进程的 `nice` 值越大优先级权重越高；单核周期任务的 CPU 利用率超过 $n(2^{1/n}-1)$ 时一定无法用 RM（速率单调）算法调度。”**
    - **×**。两处均错：① Linux `nice` 范围 $-20 \sim 19$，**数值越小权重越高**；② $U \le n(2^{1/n}-1)$ 是 RM 可调度的**充分非必要条件**，超过该界限但 $\le 1$ 时仍可能可调度。

#### 【Lesson 6–7：同步原语、管程与经典同步问题】
17. **“两个线程各自执行一次‘原子读取 `count`，再原子写回旧值加 1’，最终 `count` 一定精确增加 2。”**
    - **×**。单次读和单次写虽各自原子，但**读—改—写整体不原子**；两线程可能同时读到旧值 5，各自写回 6（丢失更新），需用原子读改写指令（如 CAS / `atomic_fetch_add`）或互斥锁。
18. **“两进程严格轮换法（用 `turn` 交替进入）能保证互斥，因此是临界区问题的合格解决方案。”**
    - **×**。严格轮换虽然满足互斥，但当轮到的进程留在剩余区不想进临界区时，另一想进入的进程也会被挡在外面，**违反了‘前进（Progress）’准则**。
19. **“Peterson 算法在理想顺序一致模型下满足互斥、前进和有限等待，但在现代多核处理器上若不加内存屏障可能因指令重排而破坏互斥。”**
    - **√**。（若 `flag[i] = true` 与后续写入/读取发生乱序可见，两个进程可能同时观察到对方 `flag` 为 `false` 而双双进入临界区。）
20. **“直接用 `while (test_and_set(&lock)) ;` 或朴素 CAS 自旋实现的互斥锁，能同时满足临界区的互斥、前进和有限等待三项要求。”**
    - **×**。满足互斥和前进，但**违反有限等待（Bounded waiting）**——锁释放时新到来的线程可能反复抢先，导致某个等待线程饥饿。
21. **“单核处理器上保护较长临界区时，使用忙等自旋锁（Spinlock）比睡眠阻塞互斥锁更高效。”**
    - **×**。单核上自旋线程占着唯一 CPU 空转期间，持有锁的线程根本没有机会上 CPU 执行解锁；自旋锁仅适用于**多核系统且持锁时间极短**（或不可睡眠的中断处理程序）。
22. **“在 POSIX 条件变量中，为什么必须用 `while` 而不是 `if` 检查条件？因为通知线程调用 `pthread_cond_signal` 后等待线程立即直接运行且状态不可能改变。”**
    - **×**。POSIX 采用 **Signal-and-Continue** 语义：通知者仍持锁，等待者在重新竞争获得 `mutex` 前，共享状态可能已被其他线程抢先改写，且可能存在**虚假唤醒**，故必须用 `while` 重查。
23. **“哲学家就餐问题的管程方案（仅当左右两根筷子都可用时才置 `EATING`）彻底消除了死锁，因此保证了每位哲学家都能有限等待。”**
    - **×**。消除死锁不等于消除**饥饿**；若某哲学家的左右两位邻居交替进餐，每次一方放下筷子时另一方仍在进餐，中间这位哲学家仍可能长期饥饿。
24. **“在第一类读者-写者问题（读者优先）中，每个进入的读者都必须执行一次 `wait(rw_mutex)` 以防止写者写入。”**
    - **×**。只有**第一个进入的读者**（`read_count == 1`）执行 `wait(rw_mutex)`，**最后一个退出的读者**（`read_count == 0`）执行 `signal(rw_mutex)`；若每个读者都申请 `rw_mutex` 会导致读者之间相互阻塞，无法并发读取。

### （二）Lesson 2–7 九组高频易混概念秒杀对照表

#### 第 1 组：进程虚拟地址空间五段映射（L3 P.5–6，必考！）
```text
低地址 0  ┌─────────────────────────┐
          │ text（代码段）           │ ← 编译后的可执行机器指令（只读）
          ├─────────────────────────┤
          │ data（已初始化数据段）   │ ← 已初始化的全局变量、static 静态变量（如全局 int y = 15;）
          ├─────────────────────────┤
          │ bss（未初始化数据段）    │ ← 未显式初始化的全局变量、static 变量（如全局 int x; 装载清零）
          ├─────────────────────────┤
          │ heap（堆，向上增长 ↑）   │ ← malloc / new 动态分配的内存块本体
          │           ...           │   （中间空闲区及 mmap 共享库/共享内存映射）
          │ stack（栈，向下增长 ↓）  │ ← 函数调用帧：局部变量、形参、返回地址（注：局部指针变量 int *p 本身在栈，p 指向的对象在堆！）
高地址 max└─────────────────────────┘ ← 顶部含命令行参数 argc/argv 与环境变量
```

#### 第 2 组：同一进程内多线程“共享资源 vs 私有资源”（L4 P.4–5，多选最爱考！）
- **全进程线程共享**：**代码段（`text`）**、**全局/静态数据段（`data`/`bss`）**、**堆（`heap`）**、**虚拟地址空间**、**已打开文件描述符表（open files）**、**信号处置表（signal handlers）**、进程当前工作目录与用户权限、进程组/TGID。
- **每个线程各自私有**：**程序计数器（`PC`）**、**CPU 寄存器集合（含栈指针 SP）**、**栈（`stack`，含用户栈与内核栈）**、**线程局部存储（`TLS`）**、**线程号（`TID`）与调度状态/优先级**、**信号屏蔽字（`signal mask`）**。

#### 第 3 组：四种线程映射模型与底层结构对比（L4 P.19–22, P.57–60）

| 模型 / 平台 | 映射特征 | 一个线程阻塞系统调用时 | 多核并行能力 | 典型实例与课件细节 |
| :--- | :--- | :--- | :--- | :--- |
| **多对一 (Many-to-One)** | 多个用户线程 $\to$ 1 个内核线程 | **整个进程全部阻塞** | **不能多核并行** | GNU Pth（纯用户态库切换极快） |
| **一对一 (One-to-One)** | 1 个用户线程 $\to$ 1 个内核线程 | 其他线程仍可正常运行 | **支持真正并行** | **Linux NPTL**、**常规 Windows 线程**（创建过多耗内核资源） |
| **多对多 (Many-to-Many)** | $M$ 个用户线程复用 $N$ 个内核线程 | 运行时可将其他协程/虚拟线程切到可用内核线程 | **支持并行且轻量** | **Go goroutine**、**Java 21 虚拟线程** |
| **双层模型 (Two-Level)** | 多对多基础上允许单独绑定某个内核线程/LWP | 视是否绑定及 LWP 池而定 | 支持并行 | Solaris 8（注：LWP 是连接用户与内核线程的执行实体） |

- *底层补充*：Windows 线程结构含内核态 **`ETHREAD`、`KTHREAD`（含内核栈）** 与用户态 **`TEB`（含用户栈、TLS）**；Linux 不区分进程与线程结构体，统一用 **`task_struct`**，通过 `clone()` 传递 `CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_SIGHAND | CLONE_THREAD` 共享资源。

#### 第 4 组：五种内核结构与 API / ABI 辨析（L2 P.39–51）
- **API vs ABI**：**API** 是**源代码级**编程接口（管重新编译能否通过）；**ABI** 是**二进制级**接口（管寄存器传参、栈布局、系统调用约定、ELF/PE/Mach-O 格式，决定编译好的二进制能否直接运行）。
- **单体内核（Linux/传统 UNIX）**：核心子系统同处**内核地址空间**直接函数调用，效率高但故障隔离弱；Linux 可加载模块仍在内核态运行，属于**模块化单体内核**。
- **微内核（Mach/QNX/seL4）**：仅 **IPC + 基本内存 + CPU 调度**留在内核，文件系统/驱动作为**用户态进程**靠 **消息传递** 通信，隔离强但跨态切换与 IPC 开销大。
- **混合内核**：**macOS/iOS XNU**（同一内核空间融合 Mach + BSD + I/O Kit）；**Android**（Linux 内核 + **Bionic** C 库 + HAL + **ART** 运行时，非 glibc 桌面环境）。

#### 第 5 组：IPC 进程间通信对比（L3 P.35–66）
- **共享内存 vs 消息传递**：共享内存（`shm_open` + `ftruncate` + `mmap(MAP_SHARED)`）建立映射后读写最快、无需每次进内核，但**必须自行加同步互斥**，且**内部不能存进程本地虚拟地址指针（应存相对偏移量）**；消息传递由内核收发（适合小数据或跨网络），注意有缓冲时 `send/write` 返回仅代表写入本机内核缓冲。
- **匿名管道 `pipe(fd)` vs 命名管道 `FIFO` vs TCP Socket**：
  - `pipe(fd)`：**`fd[0]` 读端、`fd[1]` 写端**，单向字节流，用于父子亲缘进程。
  - `FIFO`：有文件系统路径名，可用于无亲缘本机进程，**数据在内核内存流转不落盘**。
  - `TCP Socket`：有序字节流（**无内置消息边界**，需应用层自定义长度或分隔符）；服务端 `accept()` 返回**新的已连接 socket**，原监听 socket 继续监听。

#### 第 6 组：八大 CPU 调度算法核心特征速查（L5 P.15–44）

| 算法 | 是否抢占 | 核心选择依据 | 突出优点 | 核心缺陷 / 专属考点 |
| :--- | :---: | :--- | :--- | :--- |
| **FCFS** | 非抢占 | 先进入就绪队列者先运行 | 实现最简单、零额外抢占切换开销 | 平均等待长，出现**护航效应（Convoy effect）** |
| **SJF** | 非抢占 | **下一段 CPU burst** 最短者 | 同时到达时**平均等待时间理论最优** | 难以精确预知下一段 CPU 长度；长任务可能**饥饿** |
| **SRTF** | **抢占** | **剩余 CPU burst** 最短者 | 分批到达时平均等待/周转时间更短 | 需预测长度、切换开销多、长任务可能**饥饿** |
| **优先级** | 均可 | 优先级最高者（看清大小方向！） | 区分任务轻重缓急 | 低优先级任务可能**饥饿** $\rightarrow$ 用**老化（Aging）**解决 |
| **RR** | **抢占** | FIFO + 固定时间片 $q$ 轮转 | **响应时间有上界** $(n-1)q$，无饥饿 | 平均等待常长于 SJF；$q$ 太大退化为 FCFS，$q$ 太小切换开销剧增 |
| **MLQ** | 队间可抢占 | 按任务性质固定入不同队列 | 区分前台交互（RR）与后台批处理（FCFS） | **进程固定在原队列不移动**，不够灵活 |
| **MLFQ** | **抢占** | 按运行消耗时间片动态升降队列 | **无需预知长度**即可优待短/交互任务 | 参数设计最复杂（需配老化升级防低队列饥饿） |
| **HRRN** *(往年卷)* | 非抢占 | 响应比 $R_p = \frac{W + B}{B}$ 最高者 | 兼顾短作业与长作业等待时间，防饥饿 | 每次调度需计算所有就绪进程响应比 |

#### 第 7 组：临界区准则与同步工具达标对照（L6 P.8–57）
- **临界区三准则**：① **互斥**（最多 1 人在临界区）；② **前进**（空闲有人申时，剩余区进程不得阻拦且不能无限推迟选择）；③ **有限等待**（发出申请后被他人抢先的次数有上界）。
  - *严格轮换*：满足互斥，**违反前进**。
  - *Peterson 算法*：双进程顺序一致模型下**三项全满足**（等待上界 1 次）；现代乱序多核需加**内存屏障 / Acquire-Release**。
  - *简单 TAS / 简单 CAS 自旋锁*：满足互斥与前进，**违反有限等待**；带 `waiting[n]` 环形交接的改进版 CAS 锁**三项全满足**（等待上界 $n-1$ 次）。
- **互斥量（Mutex） vs 信号量（Semaphore） vs 条件变量（Condition Variable）**：
  - **互斥量**：有明确**持有者**概念，必须**同一线程加锁、同一线程解锁**，保护临界区多字段一致性。
  - **信号量**：维护整型计数值，可由**一个线程 `P/wait`，另一个线程 `V/signal`**；既能控多实例并发名额（初值 $N$），又能做前驱同步（初值 $0$）。
  - **条件变量**：**本身不保存计数状态**（无人等时 `signal` 为空操作），必须配合共享状态变量与互斥锁使用。

### （三）选择题必背 4 大“小计算”秒杀公式

1. **Amdahl 定律（L4 P.13–15，2020 真题）**
   - 设固定任务中**串行部分占比为 $S$**（$0 \le S \le 1$），并行占比为 $1 - S$，$N$ 个 CPU 核的**理想加速比**：
     $$\text{Speedup}(N) = \frac{1}{S + \frac{1 - S}{N}}, \qquad \lim_{N \to \infty} \text{Speedup}(N) = \frac{1}{S}$$
   - *课件原题速算*：
     - $S = 25\%,\ N = 2 \implies \frac{1}{0.25 + 0.75/2} = \frac{1}{0.625} = \mathbf{1.6}$；$N \to \infty$ 上限为 $\mathbf{4}$。
     - $S = 20\%,\ N = 4 \implies \frac{1}{0.20 + 0.80/4} = \frac{1}{0.40} = \mathbf{2.5}$；$N \to \infty$ 上限为 $\mathbf{5}$。

2. **下一段 CPU Burst 指数平均预测（L5 P.24–26）**
   $$\tau_{n+1} = \alpha t_n + (1 - \alpha)\tau_n \quad (0 \le \alpha \le 1)$$
   - 其中 $t_n$ 为刚结束的**实际** CPU 长度，$\tau_n$ 为上次**预测**长度。
   - *课件例题*：$\alpha = 0.5,\ \tau_0 = 10,\ t_0 = 6 \implies \tau_1 = 0.5 \times 6 + 0.5 \times 10 = \mathbf{8}$。

3. **单核实时周期任务可调度性判据（L5 P.54–56，独立可抢占且截止期 $D_i = T_i$）**
   - 总 CPU 利用率：$U = \sum_{i=1}^{n} \frac{C_i}{T_i}$（$C_i$ 为执行时间，$T_i$ 为周期）。
   - **EDF（最早截止时间优先，动态优先级）充要条件**：$U \le 1$。
   - **RM（速率单调，周期越短静态优先级越高）充分条件**：$U \le n\left(2^{1/n} - 1\right)$（记住特殊值：$n=2$ 时约 **$0.828$**，$n=3$ 时约 **$0.780$**，$n \to \infty$ 趋近 $\ln 2 \approx \mathbf{0.693}$）。
   - *课件例题*：$A(C=1, T=4)$，$B(C=2, T=5) \implies U = \frac{1}{4} + \frac{2}{5} = \mathbf{0.65} \le 0.828 \le 1$，RM 与 EDF 均可调度。

4. **Little 定律（L5 P.70）与记录型信号量计数（L6 P.40–42，2018/2019/2020 真题）**
   - **Little 定律**：稳态队列平均等待人数 $L_q = \lambda W_q$（课件：每秒到达 $\lambda = 7$ 个，平均排队 $L_q = 14$ 个 $\implies$ 平均等待时间 $W_q = 14 / 7 = \mathbf{2\text{ 秒}}$）。
   - **记录型信号量 $S$（初值 $S_0$）**：
     - $S > 0$：表示当前**尚余 $S$ 个可用资源许可**，等待进程数为 $0$；
     - $S = 0$：表示资源**恰好分完**，且等待进程数为 $0$；
     - $S < 0$：表示资源已用尽，且当前正有 **$|S|$ 个进程阻塞在该信号量的等待队列中**！

## 三、简答题 / 名词辨析题专项突破（直接可默写的卷面满分答案）

> [!TIP]
> **简答与辨析满分三步法**（2018/2019/2023 均设“辨析题”）：
> 1. **先下定义**：分别用一句话写清概念 A 是什么、概念 B 是什么（*2023 年 96 分高分卷唯一扣分处就是把“管程”错答成“一块共享内存空间”，务必背准管程三要素！*）；
> 2. **再列核心区别**：从作用对象、资源边界、执行时机或开销角度点出 2～3 条差异；
> 3. **补一句联系或场景例子**：如用“生产者—消费者”把两者串起来，阅卷老师一眼给满分。

### （一）往年真题高频简答 / 辨析题标准答案（10 道母题）

#### 1. 比较核心态（内核态）与用户态；区分模式切换与上下文切换 *(2018 真题 + L2 P.19 / L3 P.18–20)*
- **核心态（Kernel Mode）**：操作系统内核运行时的受保护特权状态，可执行全部指令（含特权指令）并访问系统全部内存与硬件资源。
- **用户态（User Mode）**：普通用户进程执行时的非特权状态，只能执行非特权指令、访问本进程受限的用户虚拟地址空间。
- **转换与切换区别**：用户态程序必须通过**系统调用（访管指令/Trap）、外设中断或异常**才能受控进入核心态——这称为**模式切换（Mode Switch）**，执行主体仍是当前进程/线程，处理完可直接返回原线程；而**上下文切换（Context Switch）**是 CPU 从一个进程/线程切换到另一个进程/线程，需将旧任务寄存器与 PC 保存进 PCB、恢复新任务 PCB（跨进程还需切换页表并承受 **Cache 失效与 TLB 刷新**的间接开销）。

#### 2. 描述进程（Process）与线程（Thread）的关系与区别 *(2018 真题 + L3 P.13 / L4 P.4–8, P.62)*
- **定位关系**：在引入内核级线程的现代操作系统中，**进程是资源分配与隔离保护的基本单位**，而**线程是 CPU 调度和分派的基本执行单位**（对于传统单线程进程，进程既是资源单位也是调度单位）。
- **核心区别**：
  1. **地址空间与资源**：不同进程拥有独立的虚拟地址空间和系统资源；同一进程内的多个线程**共享**进程的代码段、全局数据、堆和打开文件表，仅**私有**各自的 `PC`、寄存器集合、栈（Stack）与 `TLS`。
  2. **并发开销**：进程创建、销毁、跨进程 IPC 和切换地址空间开销大；同进程线程创建与切换无需更换地址空间，开销显著更小。
  3. **隔离与健壮性**：进程间有硬件内存隔离，一个进程崩溃不影响其他进程（如 Chrome 多进程标签页架构）；同进程内一个线程非法写内存或崩溃会导致整个进程终止。

#### 3. 比较并发（Concurrent）与并行（Parallel）；区分数据并行与任务并行 *(2018 真题 + L4 P.9–12)*
- **并发（Concurrency）**：在**同一时间间隔内**有多个任务交替推进（宏观上同时，微观上可在单核 CPU 上通过时间片快速切换交替执行）。
- **并行（Parallelism）**：在**同一时刻（瞬间）**有多个任务在多个物理执行单元（多核/多处理器）上真正同时执行（微观上同时，必须有多执行硬件支持）。
- **两种并行模式**：**数据并行**是将同一数据集切分成多个子集，各核对不同数据子集执行**相同操作**（如分块滤镜）；**任务并行**是将不同功能模块分配到不同核，执行**不同操作**（如解码、渲染、编码流水线）。

#### 4. 辨析进程间的同步（Synchronization）与互斥（Mutual Exclusion），并解释为何多处理器不能靠关中断实现同步原语 *(2019、2023 简答+综合双考！)*
- **互斥**：指多个并发进程访问同一临界资源时具有排他性，**同一时刻最多只允许一个进程进入临界区**，但不限制谁先谁后的访问次序（无序排他）。
- **同步**：指并发进程因合作而产生的**直接制约关系**，要求各进程的操作必须按特定**先后顺序**推进（有序协调）。
- **举例联系（生产者-消费者）**：多个生产者和消费者不能同时修改缓冲区及读写指针，这属于**互斥**；当缓冲区为空时消费者必须等生产者先放入产品才能取、满时生产者必须等消费者先取走才能放，这属于**同步**。
- **为何多处理器（SMP）不能靠关中断实现同步原语**：关中断指令只能屏蔽**执行该指令的当前单个 CPU 核**的中断；其他 CPU 核并不受影响，运行在其他核上的线程依然可以并行读写同一块共享内存中的信号量或临界资源。若通过核间通信强制关闭所有 CPU 核的中断，则通信代价极高、严重损害多核并行效率并阻塞系统时钟与外部响应，因此多核必须依赖硬件原子指令（如 `TAS`、`CAS`）与锁机制。

#### 5. 辨析进程（Process）与管程（Monitor） *(2019、2023 两考！易丢分题)*
- **定义**：**进程**是程序的一次动态执行过程，是操作系统中主动申请资源和参与并发执行的**活动实体**；**管程**是一种高级同步抽象数据类型（ADT / 被动语法模块），将**私有共享数据结构**、**对该数据的一组公开操作过程**以及**初始化代码与条件变量同步规则**封装在一起。
- **区别与联系**：
  1. **主动 vs 被动**：进程是主动运行的执行流；管程本身不主动运行，是供多个并发进程调用的受保护共享资源管理模块。
  2. **互斥机制**：管程由编译器/运行时自动保证**任一时刻最多只有一个进程在管程内部活跃执行**（其余调用者在入口队列等待）；若管程内进程发现条件不满足调用 `x.wait()`，会挂起并**自动让出管程互斥权**。
  3. **协作联系**：多个并发进程（如生产者进程和消费者进程）通过调用同一个“有界缓冲区管程”的 `insert()` / `remove()` 过程实现安全通信与同步。

#### 6. 辨析互斥量（Mutex）与信号量（Semaphore） *(2019 真题)*
1. **设计语义不同**：互斥量专用于保护临界区的**独占互斥访问**；信号量通过整型许可计数，既能控制多实例资源的并发访问上限，又能协调线程间的**先后同步顺序**。
2. **取值范围不同**：互斥量只有未加锁/已加锁两种状态（对应 `0/1`）；计数信号量可取任意非负初值 $N$（阻塞实现下等待时可为负值，$|S|$ 表等待人数）。
3. **所有权（加解锁主体）不同**：互斥量具有严格的**持有者（Owner）**概念，**必须由加锁的同一个线程负责解锁**；而信号量没有持有者限制，完全可以**由线程 A 执行 `P(wait)`，由线程 B 执行 `V(signal)`**（如生产者 `V(full)` 唤醒消费者 `P(full)`）。

#### 7. 比较多级队列（MLQ）、多级反馈队列（MLFQ）与先来先服务（FCFS），并举例说明 MLFQ 优点 *(2018、2019、2023 三考 + L5 P.38–44)*
- **FCFS**：单一就绪队列，严格按到达先后非抢占执行到底；长任务排在队首会引发**护航效应**，拖慢短交互任务响应。
- **多级队列（MLQ）**：按进程固定属性（如交互、批处理）划分为多个队列，进程**一旦入队终身固定不跨队移动**。
- **多级反馈队列（MLFQ）原理与 30ms 实例（L5 P.43–44）**：设置多个优先级递减而时间片递增的就绪队列（如课件实例：`Q0` 用 RR $8\text{ ms}$，`Q1` 用 RR $16\text{ ms}$，`Q2` 用 FCFS），**允许进程根据运行行为在队列间动态升降**：
  - *短交互作业*：进入最高级 `Q0`，在 $8\text{ ms}$ 内迅速完成并响应终端用户；
  - *30ms 长计算作业*：无需事先知道长度，先在 `Q0` 跑 $8\text{ ms}$（快速获得首次响应），未完降入 `Q1` 跑 $16\text{ ms}$，仍剩 $6\text{ ms}$ 降入 `Q2` 按 FCFS 跑完最后 $6\text{ ms}$；
  - *防饥饿机制*：若最低级队列中的进程长期得不到 CPU，通过**老化（Aging）/ 周期性优先级提升**将其移回高优先级队列，兼顾短响应、高周转且不饥饿。

#### 8. 辨析死锁（Deadlock）与饥饿（Starvation） *(2019、2023 两考 + L6 P.44 / L7 P.15, P.23)*
- **死锁**：一组并发进程各自占有部分资源，同时又循环等待组内其他进程所持有的资源，在无外力干涉下**组内所有进程都永久阻塞、无法推进**的现象。
- **饥饿（无限期阻塞）**：系统整体仍在正常推进（没有全员卡死），但**某一个或少数进程因调度或分配策略不公，长期得不到所需资源或 CPU 而迟迟无法执行**的现象。
- **联系与实例**：死锁中的进程必然处于无限等待状态，但**饥饿不一定发生死锁**！例如在**第一类读者-写者问题（读者优先）**中，若新读者源源不断在旧读者离开前进入（`read_count > 0` 持续成立），系统一直在正常读取（无死锁），但等待写锁的写者会一直等下去，发生**饥饿**。

#### 9. 列出三态（Ready / Running / Waiting）全部合法转换及条件；如何减少上下文切换开销？SRTF 与 FCFS 指标比较 *(2020 真题三连问)*
- **三态全部 4 条合法转换（注意：绝无 `Waiting -> Running` 和 `Ready -> Waiting`！）**：
  1. `Ready` $\to$ `Running`：CPU 调度程序从就绪队列选中该线程并分派 CPU；
  2. `Running` $\to$ `Ready`：时间片用完（时钟中断）或被更高优先级/更短剩余时间的就绪线程抢占；
  3. `Running` $\to$ `Waiting`：运行线程主动请求尚未就绪的事件（如发起阻塞 I/O、申请被占用的锁/信号量、`waitpid`）；
  4. `Waiting` $\to$ `Ready`：所等待的外部事件发生（如 I/O 完成中断、其他线程释放锁并发出 `signal`/`wakeup`）。
- **减少上下文切换开销的 3 种方法**：① 控制活跃内核线程数量（采用**有界线程池**或异步**事件驱动 I/O** 复用替代“每连接一线程”）；② 减少跨核/内核态调度切换（采用协程/用户态调度如多对多 goroutine，保持 CPU 亲和性）；③ 选用切换频率更低的调度参数或策略（适当调大 RR 时间片 $q$，或批处理用 FCFS）。
- **SRTF 与 FCFS 指标优劣**：在已知执行长度且忽略切换开销下，**SRTF 在平均等待时间与平均周转时间上最优**；而 **FCFS 相比 RR 没有时间片抢占，节省了频繁上下文切换的开销，有利于整体吞吐量**。

#### 10. 比较死锁预防（Prevention）与死锁避免（Avoidance） *(2018 真题)*
- **死锁预防**：通过制定静态资源申请限制规则，直接**破坏死锁产生的四个必要条件之一**（① 互斥、② 占有并等待、③ 不可抢占、④ 循环等待——工程上最常用**规定全局统一的加锁编号递增顺序**破坏循环等待）。优点是实现简单、无需运行时复杂计算；缺点是限制过于严格，资源利用率和并发度较低。
- **死锁避免**：允许前三个必要条件存在，要求事先声明最大资源需求，在运行时每次分配资源前**动态检查分配后系统是否仍处于“安全状态”**（单实例资源用**资源分配图环检测**，多实例资源用**银行家算法**寻找安全序列）。优点是资源利用率更高；缺点是需要预知最大需求且动态计算开销大。

### （二）今年新版课件（Lesson 2–7）高概率新增简答题精编（8 题）

1. **描述一次 `read(fd, buf, count)` 系统调用的过程，并说明内核为什么不能直接信任用户传入的指针参数？（L2 P.19–24, P.59）**
   - *过程*：应用调用库封装函数准备好系统调用号与参数（寄存器传参），执行受控陷阱指令（`syscall`）从用户态切入内核态；内核检查调用号并查系统调用表分派到对应处理函数，校验参数后读取数据（若未就绪则阻塞等待 I/O），完成后将数据拷回用户 `buf`，返回实际读取字节数（`>0` 字节数，`0` 表 EOF，`-1` 表出错）并恢复用户态。
   - *为何必须校验用户指针*：用户程序可能有 Bug 或恶意构造——指针可能是空指针/未映射非法地址（引发内核崩溃）、只读内存（写回违规）、长度越界/整数溢出，甚至**伪造指向内核空间的地址企图诱导拥有高特权的内核泄露或覆写篡改内核关键数据**。

2. **什么是操作系统的“机制与策略分离”原则？请举例说明。（L2 P.42）**
   - **机制（Mechanism）**解决“**如何做（How）**”的底层技术手段（如时钟定时器中断、保存与恢复 PCB 上下文）；**策略（Policy）**解决“**选谁做、何时做（What/Who/When）**”的决策规则（如采用 RR 还是优先级算法、时间片定多大）。两者分离使得更换或调优调度策略时无需重写底层切换机制，提高系统灵活性与可维护性。

3. **从按下电源到出现命令行 Shell 经过哪些主要引导阶段？两台相同 CPU 的机器为何可能无法运行同一可执行文件？（L2 P.39, P.54–55, P.59）**
   - *引导 6 阶段*：① **固件（BIOS/UEFI）**上电自检并选择启动项 $\to$ ② **引导加载程序（Bootloader 如 GRUB）**加载内核映像与 `initramfs` $\to$ ③ **内核初始化**内存、中断、调度与驱动 $\to$ ④ **挂载根文件系统** $\to$ ⑤ 启动首个用户态进程 **`init`（PID 1，如 `systemd`）** $\to$ ⑥ 启动后台服务与登录会话，运行用户态 **Shell**。
   - *同 CPU 不能直接运行同一二进制的原因*：除指令集（ISA）外，还可能因**可执行文件格式不同**（ELF vs PE vs Mach-O）、**系统调用号与内核接口不同**、**ABI 调用约定/结构体对齐不同**，或**缺失兼容版本的动态共享库（如 glibc vs Bionic）**而无法装载运行。

4. **多线程程序调用 `fork()` 和 `exec()` 有何特殊语义与风险？（L4 P.48）**
   - POSIX 中多线程进程调用 `fork()` 时，**子进程只复制保留调用 `fork()` 的那一个线程**，其他线程在子进程中消失；但整个地址空间（含**其他线程当时正持有的互斥锁加锁状态**）会被原样复制到子进程，若子进程不立即 `exec()` 而尝试获取那些无人解锁的互斥锁就会**死锁**！调用 `exec()` 成功后则会替换整个进程映像并终止所有其他线程。

5. **无同步时“写线程 `x=100; flag=true;`，读线程 `while(!flag); print(x);`”为何可能打印 `0`？如何修复？（L6 P.17–21）**
   - *原因*：现代编译器和乱序执行多核 CPU 会对无依赖读写进行**指令重排**或写缓冲延迟刷新，导致读线程所在核先观察到 `flag == true` 跳出循环，却读到旧缓存值 `x == 0`。
   - *修复*：在写线程 `x=100` 与 `flag=true` 之间插入**写内存屏障**（或用 `memory_order_release` 原子写 `flag`），并在读线程用**读内存屏障**（或 `memory_order_acquire` 原子读 `flag`），强制保证 `x=100` 对读线程先可见。

6. **自旋锁（Spinlock）与阻塞互斥锁（Blocking Mutex）各自适用什么场景？（L6 P.33, L7 P.27）**
   - **自旋锁**在等待时留在 CPU 上忙等轮询，省去了线程睡眠与唤醒的两次上下文切换开销，但空耗 CPU，仅适用于**多核处理器且持锁临界区极短**的场景，或**禁止睡眠的中断处理程序**。
   - **阻塞互斥锁**在获取失败时将线程挂起睡眠并让出 CPU，适用于**持锁时间较长**或**单核处理器**（单核自旋会饿死持锁线程使其无法上 CPU 解锁）。

7. **管程条件变量的 `Signal-and-Wait` 与 `Signal-and-Continue` 有何区别？POSIX `pthread_cond_wait(&cond, &mutex)` 为何必须传 `mutex` 且用 `while` 循环？（L6 P.50, L7 P.34–35）**
   - *两种语义*：`Signal-and-Wait`（Hoare）下通知者立即暂停把管程让给被唤醒者先运行；`Signal-and-Continue`（Mesa / POSIX / Java）下通知者继续持锁执行，直到它退出解锁后被唤醒者再去竞争锁。
   - *为何传 `mutex`*：① 保护共享条件变量的读写互斥；② 内核**原子地执行“释放 `mutex` 并挂入等待队列”**，防止在检查条件与睡眠之间的空隙发生 `signal` 造成**丢失唤醒（Lost Wakeup）**，并在返回前自动重新拿回 `mutex`。
   - *为何必须用 `while`*：在 POSIX `Signal-and-Continue` 下，从发出 `signal` 到等待线程真正重新抢到 `mutex` 之间，**共享条件可能已被其他插队线程再次改写为不成立**，且系统允许偶发**虚假唤醒**，必须用 `while` 重新验证条件。

8. **第一类读者-写者问题（读者优先）中，`mutex` 和 `rw_mutex` 各起什么作用？为何只在首尾读者操作 `rw_mutex`？（L7 P.12–15, P.53）**
   - `mutex` 保护共享计数器 `read_count` 的互斥增减；`rw_mutex` 用于实现**整个活跃读者组与写者之间、以及写者与写者之间的互斥**。
   - 因为多个读者只读不写，允许同时并发访问：第一个进入的读者（`read_count == 1`）执行 `wait(rw_mutex)` 替全体读者挡住写者，随后释放 `mutex` 让后续读者无需等待直接并行执行 `read_data()`；最后一个离开的读者（`read_count == 0`）执行 `signal(rw_mutex)` 归还写权限。

### 题型一【100% 必考】：CPU 调度甘特图绘制与等待 / 周转 / 响应时间计算

#### 1. 考场零失误四步公式模板
动笔前先用笔圈出四个条件：**① 到达时刻 $A_i$ 是否全为 0？ ② 优先级数字“越小越高”还是“越大越高”？ ③ 抢占还是非抢占？ ④ 求“等待时间”还是“周转时间”？**

对每个进程记录：到达时刻 $A$、CPU 总执行时长 $B$、首次上 CPU 时刻 $S$、最终完成时刻 $C$：
- **周转时间（Turnaround）** $= C - A$
- **响应时间（Response）** $= S - A$（只看第一次上 CPU！）
- **等待时间（Waiting）** $= \text{各段就绪排队时间之和} = (C - A) - B$ *(无 I/O 阻塞且忽略切换开销时恒成立，用此式验算最快最准！)*

#### 2. 真题实战 1（2019 & 2023 完全重题！）：四进程四算法对比
> **原题**：四个进程 $P_1, P_2, P_3, P_4$ 在时刻 $0$ 按序到达，需要 CPU 时间依次为 $(9, 2, 3, 2)\text{ ms}$，优先级依次为 $(3, 1, 2, 4)$（**数值越小优先级越高**），RR 时间片 $q = 1\text{ ms}$。a) 画 FCFS、SJF、RR、非抢占优先级甘特图；b) 求各进程等待时间；c) 哪种算法平均等待时间最少？

| 调度算法 | 标准甘特图（竖线数字为时刻 ms） | 各进程等待时间 $(P_1, P_2, P_3, P_4)$ | 平均等待时间 |
| :--- | :--- | :---: | :---: |
| **1. FCFS** | `0 \| P1 \| 9 \| P2 \| 11 \| P3 \| 14 \| P4 \| 16` | $0,\ 9,\ 11,\ 14$ | $\frac{0+9+11+14}{4} = \mathbf{8.5\text{ ms}}$ |
| **2. 非抢占 SJF** | `0 \| P2 \| 2 \| P4 \| 4 \| P3 \| 7 \| P1 \| 16` | $7,\ 0,\ 4,\ 2$ | $\frac{7+0+4+2}{4} = \mathbf{3.25\text{ ms}}$ |
| **3. RR ($q=1$)** | `0\|P1\|1\|P2\|2\|P3\|3\|P4\|4\|P1\|5\|P2\|6\|P3\|7\|P4\|8\|P1\|9\|P3\|10\| P1 \|16` | $7,\ 4,\ 7,\ 6$ | $\frac{7+4+7+6}{4} = \mathbf{6\text{ ms}}$ |
| **4. 非抢占优先级** | `0 \| P2 \| 2 \| P3 \| 5 \| P1 \| 14 \| P4 \| 16` | $5,\ 0,\ 2,\ 14$ | $\frac{5+0+2+14}{4} = \mathbf{5.25\text{ ms}}$ |

- **c) 结论**：**SJF（短作业优先）**使平均等待时间最少（$3.25\text{ ms}$）。
- **RR 防错验算**：$P_1$ 在 $C=16$ 完成，$B=9 \implies$ 等待 $= 16 - 0 - 9 = \mathbf{7\text{ ms}}$（千万别只看首次响应 $0$ 或漏算 $[9,10]$ 那 $1\text{ ms}$，2019 旧参考答案曾误算为 6，按 $C-A-B$ 验算永不出错！）。

#### 3. 真题实战 2（2018 原题）：改考“大数优先 + 平均周转时间”
> **原题**：5 个任务 $A, B, C, D, E$ 在时刻 $0$ 同时到达，运行时间为 $(10, 6, 2, 4, 8)\text{ ms}$，优先级为 $(3, 5, 2, 1, 4)$（**5 为最高优先级**）。求 FCFS、优先级、RR（$q = 2\text{ ms}$）的**平均周转时间**。

1. **FCFS**：`0 [A] 10 [B] 16 [C] 18 [D] 22 [E] 30` $\implies$ 完成（周转）时间 $(10, 16, 18, 22, 30)$，平均周转 $= \frac{96}{5} = \mathbf{19.2\text{ ms}}$。
2. **优先级（5>4>3>2>1，即 B→E→A→C→D）**：`0 [B] 6 [E] 14 [A] 24 [C] 26 [D] 30` $\implies$ 周转时间 $(6, 14, 24, 26, 30)$，平均周转 $= \frac{100}{5} = \mathbf{20\text{ ms}}$。
3. **RR ($q=2\text{ ms}$)**：轮转轮次为 `(A,B,C,D,E) [0~10] -> (A,B,D,E) [10~18] -> (A,B,E) [18~24] -> (A,E) [24~28] -> (A) [28~30]`。
   - 按 $A \sim E$ 完成时刻（周转时间）：$T_A = 30,\ T_B = 22,\ T_C = 6,\ T_D = 16,\ T_E = 28$；平均周转 $= \frac{30+22+6+16+28}{5} = \mathbf{20.4\text{ ms}}$。

#### 4. 今年课件必练变式（L5 P.23 分批到达 SRTF & L5 P.36 课堂练习）
- **变式 A（分批到达的抢占式 SRTF，L5 P.23）**：
  - 数据：$P_1(A=0, B=8),\ P_2(A=1, B=4),\ P_3(A=2, B=9),\ P_4(A=3, B=5)$。
  - 抢占推演：时刻 `0` $P_1$ 先跑；时刻 `1` $P_2$ 到达，**比较 $P_1$ 剩余 $7$ 与 $P_2$ 所需 $4$**，$4 < 7$ 故 **$P_2$ 抢占 $P_1$**；时刻 `2`（$P_2$ 剩 $3 < 9$）、时刻 `3`（$P_2$ 剩 $2 < 5$）均不抢占；时刻 `5` $P_2$ 结束，就绪队列有 $P_1(\text{剩}7), P_3(9), P_4(5)$，选最短的 $P_4$！
  - 甘特图：`0 | P1 | 1 | P2 | 5 | P4 | 10 | P1 | 17 | P3 | 26`
  - 等待时间 $(C-A-B)$：$P_1 = 17-0-8 = 9,\ P_2 = 5-1-4 = 0,\ P_3 = 26-2-9 = 15,\ P_4 = 10-3-5 = 2 \implies$ 平均等待 $= \mathbf{6.5\text{ ms}}$。
- **变式 B（课件 L5 P.36 五进程练习核对值）**：$P_1 \sim P_5$ 时刻 $0$ 到达，长度 $(2,1,8,4,5)$，优先级 $(2,1,4,2,3)$（大数优先，$q=2$）。自测核对答案：平均等待时间依次为 **FCFS $6.2\text{ ms}$、非抢占 SJF $4.6\text{ ms}$、非抢占优先级 $11.0\text{ ms}$、RR $7.2\text{ ms}$**。

### 题型二【95%+ 必考】：同步与互斥代码编写与填空（P/V 信号量 + 条件变量）

#### 1. 真题母题 A：有界缓冲区 / 单槽多生产者-多消费者 P/V 代码 *(2019 & 2023 真题 + L7 P.5–9)*
> **原题**：一个初始为空的缓冲区（容量 $N=1$；若考一般有界缓冲区则设为 $N$），多个生产者与多个消费者不断并发放/取产品。只有空时生产者能放，只有有数据时消费者能取，且缓冲区不允许同时操作。用 P、V（或 `wait`/`signal`）写出完整代码。

```c
// 1. 定义信号量与初值（单槽题令 N = 1；一般有界缓冲区保留 N）
semaphore mutex = 1;   // 互斥信号量：保护缓冲区的互斥访问
semaphore empty = 1;   // 同步信号量：当前空槽位数（一般容量为 N）
semaphore full  = 0;   // 同步信号量：当前可取产品数

// 2. 生产者进程（共 m 个）          // 3. 消费者进程（共 n 个）
void Producer() {                    void Consumer() {
    while (true) {                       while (true) {
        item = produce_item();               P(full);       // ① 先等有产品（绝不能先 P(mutex)!）
        P(empty);      // ① 先等空位          P(mutex);      // ② 再申请互斥锁
        P(mutex);      // ② 再拿互斥锁        item = get_item();
        put_item(item);                      V(mutex);      // ③ 释放互斥锁
        V(mutex);      // ③ 释放互斥锁        V(empty);      // ④ 归还空槽位！（切勿错写成 V(full)!）
        V(full);       // ④ 通知有新产品      consume_item(item);
    }                                    }
}                                    }
```
- **必背三个高频追问**：
  1. **信号量取值范围**（设 $m$ 个生产者、$n$ 个消费者、容量 $N=1$）：`empty` $\in [-m, 1]$，`full` $\in [-n, 1]$，`mutex` $\in [-(m+n-1), 1]$。
  2. **为什么两个 `P` 顺序绝不能颠倒？** 若生产者先 `P(mutex)` 再 `P(empty)`，当缓冲区已满（`empty == 0`）时，生产者持有 `mutex` 阻塞在 `P(empty)`；此时消费者想取走产品释放空位，却在 `P(mutex)` 处等待生产者手里的锁，双方永久互等发生**死锁**！
  3. **2023 阅卷扣分警示**：消费者取出产品后腾出的是**空位**，最后一步必定是 **`V(empty)`**，千万别顺手抄成 `V(full)`！

#### 2. 真题母题 B：车站售票厅计数信号量问题 *(2018 真题)*
> **原题**：某车站售票厅任何时刻最多容纳 20 名购票者进入，少于 20 人立即进入，否则在厅外等待。共有最多 $n$ 名购票者进程 $P_i$。

1. **信号量定义、初值与正负零含义**：
   - 定义计数信号量 `semaphore S = 20;`（初值为 $20$）。
   - **$S > 0$**：表示售票厅内尚可继续进入的空余名额数；
   - **$S = 0$**：表示售票厅内恰好已有 20 名购票者（已满），且厅外暂无等待者；
   - **$S < 0$**：$|S|$ 的值表示当前正在售票厅外排队等待进入的购票者人数。
2. **填入 P、V 操作**：
   ```text
   Cobegin PROCESS Pi (i = 1, 2, ...)
       Begin
           P(S);
           进入售票厅;
           购票;
           退出;
           V(S);
       End;
   Coend
   ```
3. **信号量 $S$ 的变化范围（最大值与最小值）**：最大值为 **`20`**（无人进入时），最小值为 **`20 - n`**（当 $n$ 名购票者同时申请进入时，20 人在厅内，$n-20$ 人在厅外等待；若 $n < 20$ 则最小值为 $20-n$）。

#### 3. 🔥 今年极高概率新题：厨师与服务员共用传菜位（POSIX 条件变量填空） *(L7 P.54–55 原题)*
> **课件原题**：一个厨师、一个服务员共用单传菜位（容量 1，初始为空）。布尔变量 `full`（初值 `false`）表示是否有菜；共用互斥锁 `mutex` 和条件变量 `not_empty`、`not_full`。补全六处空白并说明锁交接过程。

```c
/* 厨师：放入一份菜 */                      /* 服务员：取走一份菜 */
pthread_mutex_lock(&mutex);                 pthread_mutex_lock(&mutex);
while ( full )              // 空(1)        while ( !full )             // 空(4)
    pthread_cond_wait(                          pthread_cond_wait(
        &not_full, &mutex); // 空(2)                &not_empty, &mutex);// 空(5)
放入菜品;                                   取走菜品;
full = true;                                full = false;
pthread_cond_signal(&not_empty); // 空(3)   pthread_cond_signal(&not_full); // 空(6)
pthread_mutex_unlock(&mutex);               pthread_mutex_unlock(&mutex);
```
- **标准追问满分答法（当服务员先运行时）**：
  1. **何时释放锁**：服务员先拿到 `mutex`，检查发现无菜（`!full` 为真），进入 `pthread_cond_wait(&not_empty, &mutex)` 时**由系统原子地释放 `mutex` 锁并进入 `not_empty` 等待队列睡眠**。
  2. **厨师通知谁**：厨师随后获得 `mutex` 锁，放入菜品并置 `full = true`，调用 `pthread_cond_signal(&not_empty)` **唤醒等待在 `not_empty` 上的服务员**（注意此时厨师仍持有 `mutex` 锁，直到执行 `unlock` 才释放）。
  3. **何时从 `wait` 返回**：厨师 `unlock` 释放锁后，服务员**重新竞争并获得 `mutex` 锁之后**才从 `pthread_cond_wait` 返回，经 `while (!full)` 复查确认 `full == true` 后取菜、置 `full = false`、通知 `not_full` 并解锁。

#### 4. 经典同步拓展速记：读者-写者 & 哲学家就餐破死锁代码框架 *(L7 P.12–22)*
- **读者优先（第一类读者-写者）核心模板**：
  - 初值：`int read_count = 0; semaphore mutex = 1, rw_mutex = 1;`
  - 写者：`P(rw_mutex); write(); V(rw_mutex);`
  - 读者：`P(mutex); read_count++; if (read_count == 1) P(rw_mutex); V(mutex);` $\to$ `read();` $\to$ `P(mutex); read_count--; if (read_count == 0) V(rw_mutex); V(mutex);`
- **哲学家就餐（5 人共用 `chopstick[0..4] = 1`）破除死锁三种代码写法**：
  1. **至多 4 人同时拿筷子**：加 `semaphore seats = 4;`，每人 `P(seats) -> P(chopstick[i]) -> P(chopstick[(i+1)%5]) -> eat() -> V(左) -> V(右) -> V(seats)`。
  2. **奇偶非对称（或全局锁序）**：奇数号先 `P(i)`（左）再 `P((i+1)%5)`（右）；偶数号先 `P((i+1)%5)`（右）再 `P(i)`（左）。
  3. **管程 `pickup/putdown/test` 法**：仅当左右邻居均 `!= EATING` 且自己 `== HUNGRY` 时才置 `state[i] = EATING` 并 `self[i].signal()`，放筷子时依次 `test` 左右两位邻居。

### 题型三【高概率】：`fork()` / `exec()` / `pthread` 与文件偏移共享程序推演

#### 1. 真题实战（2020 综合题 1 原题）：三段写文件程序输出全解
> **共同前提**：`file.txt` 初始为空，无 `O_APPEND`，所有系统调用成功，调度先后任意，所有进程结束后判断 `file.txt` 可能的内容。

| 程序代码核心逻辑 | 标准答案 | 底层内核机制推演（得分关键！） |
| :--- | :---: | :--- |
| **程序一（先 `fork`，父子各自 `open`）**：<br>`if (fork() == 0) { fd1 = open("file.txt", O_WRONLY); write(fd1, "a", 1); }`<br>`else { fd2 = open("file.txt", O_WRONLY); write(fd2, "b", 1); }` | **`a` 或 `b`**<br>*(选 BC)* | 父子分别独立调用 `open()`，在内核中创建**两个独立的打开文件描述**，各自的读写偏移量 `offset` **均从 `0` 开始**！后执行 `write` 的进程在偏移 `0` 处直接覆盖先写入的字节。 |
| **程序二（先 `open` 一次，再 `fork`）**：<br>`fd = open("file.txt", O_WRONLY);`<br>`if (fork() == 0) buffer = 'a'; else buffer = 'b';`<br>`write(fd, &buffer, 1);` | **`ab` 或 `ba`**<br>*(选 EF)* | ① 普通全局变量 `buffer` 在 `fork` 后父子地址空间各自独立（子为 `'a'`、父为 `'b'`）；<br>② 继承的 `fd` 指向**同一个内核打开文件描述，共享同一个 `offset`**！先写者写在偏移 `0` 并把共享偏移推进到 `1`，后写者接着写在偏移 `1`。 |
| **程序三（主线程 `open`，建子线程写 `'a'`，主线程写 `'b'` 后直接结束 `main` 未 `join`）**：<br>`fd = open(...); pthread_create(&t, NULL, helper_write_a, NULL);`<br>`write(fd, "b", 1); /* main 直接返回退出 */` | **`b`、`ab` 或 `ba`**<br>*(选 CEF)* | 同进程线程共享 `fd` 与文件偏移；`main` 返回等价于调用 `exit()` 终止整个进程，因此主线程的 `'b'` **必定已写入**！若子线程在进程销毁前未来得及跑 `write` 则只留 **`b`**；若赶在退出前完成，则按先后得 **`ab`** 或 **`ba`**。*(注：若在 `write("b")` 后加 `pthread_join`，则只有 `ab` 或 `ba`)* |

#### 2. 今年课件重磅代码题（L3 P.27）：`fork` + `execlp` + `waitpid` 打印顺序
```c
pid_t pid = fork();
printf("[0] Hello from %d\n", pid);                   // 语句 [0]：父打印子PID(记0_P)，子打印0(记0_C)
if (pid == 0) {
    printf("[1] [Child] before exec\n");              // 语句 [1]
    execlp("echo", "echo", "[2] Hello echo!", NULL);  // 语句 [2]
    printf("[3] [Child] after exec\n");               // 语句 [3]（陷阱！）
} else {
    waitpid(pid, &status, 0);
    printf("[4] [Parent] child exited...\n");         // 语句 [4]
}
```
- **三大必答结论**：
  1. **`[3]` 绝不会打印**（`execlp` 成功时直接用 `echo` 程序映像覆盖子进程原代码段，永不返回原程序）；
  2. **`[4]` 必定在最后打印**（父进程阻塞在 `waitpid` 直到子进程执行完 $0_C \to [1] \to [2]$ 退出后才恢复）；
  3. **共有 4 种合法打印顺序**（取决于父进程的 $0_P$ 插在子进程三句的哪个间隙）：
     - $0_P \to 0_C \to [1] \to [2] \to [4]$
     - $0_C \to 0_P \to [1] \to [2] \to [4]$
     - $0_C \to [1] \to 0_P \to [2] \to [4]$
     - $0_C \to [1] \to [2] \to 0_P \to [4]$

### 题型四【高概率】：多线程多把锁死锁执行序列构造与破除分析 *(2020 综合题 2 原题，25 分)*

> **原题代码特征**：共三把互斥锁 `x, y, z`，三个并发线程：
> - 线程 `a`：依次 `lock(&y) -> lock(&z) -> unlock(&y) -> unlock(&z)`
> - 线程 `b`：依次 `lock(&z) -> lock(&x) -> unlock(&z) -> unlock(&x)`
> - 线程 `c`：依次 `lock(&x) -> lock(&y) -> unlock(&x) -> unlock(&y)`

1. **（1）写出一种导致死锁的执行序列**：
   ```text
   a 调用 lock_acquire(&y)   // a 持有 y
   b 调用 lock_acquire(&z)   // b 持有 z
   c 调用 lock_acquire(&x)   // c 持有 x  <-- 至此进入首个不安全状态！
   a 调用 lock_acquire(&z)   // a 阻塞等待 b 持有的 z
   b 调用 lock_acquire(&x)   // b 阻塞等待 c 持有的 x
   c 调用 lock_acquire(&y)   // c 阻塞等待 a 持有的 y（形成等待环 a → b → c → a，死锁！）
   ```
2. **（2）上述序列中第一个“不安全（unsafe）”状态是什么？出现在哪里？**
   - 出现在**前三条语句执行完毕之后**，状态为：**`a` 持有 `y`、`b` 持有 `z`、`c` 持有 `x`**。此时每个线程都已拿走第一把锁，后续无论调度器先调度谁执行下一条加锁指令，都必然全部阻塞死锁（而在第 2 条语句后若继续调度 `b` 拿 `x` 则仍可顺利跑完，故前两步仍安全）。
3. **（3）能否通过改变每个线程 `unlock` 解锁互斥锁的顺序来解决死锁？**
   - **不能！** 因为死锁发生在所有线程获取第二把锁的阶段，此时**还没有任何一个线程能执行到第一条 `unlock` 语句**。
   - *附：正确的修改方法（L6 P.44）*：**规定全局一致的加锁顺序**，例如规定 `x < y < z`，将线程 `b` 的加锁顺序改为先 `lock(&x)` 再 `lock(&z)`，即可彻底破坏**循环等待**条件！
4. **（4）若底层使用单核非抢占 FCFS 线程调度器，该程序容易死锁吗？**
   - **不会死锁**。非抢占 FCFS 会让第一个上 CPU 的线程一口气拿齐两把锁并解锁运行到结束，再运行下一个线程，锁完全无竞争，所有 `lock` 都不会阻塞。
5. **（5）使用抢占式线程调度器会消除死锁的可能性吗？**
   - **不会消除**（反而使上述交错死锁更容易发生）。因为抢占式调度器**只能从线程手中抢占 CPU，绝不能强行抢占（剥夺）该线程已经持有的互斥锁**！

### 题型五【5 分钟防超纲兜底】：银行家算法安全性检查与资源等待图 *(2018 & 2023 旧卷压轴题)*

> [!NOTE]
> 今年考试通知范围列至 Lesson 7（未列死锁专章），但因 2018、2023 两套试卷最后一题均出现了银行家算法表格题，花 3 分钟记住下面三步即可 100% 稳妥兜底：
> 1. 算尚需矩阵：$\text{Need}[i] = \text{Max}[i] - \text{Allocation}[i]$；
> 2. 设工作向量 $\text{Work} = \text{Available}$，找满足 **$\text{Need}[i] \le \text{Work}$**（每一维都小于等于！）的未完成进程 $P_i$；
> 3. 找到后假定 $P_i$ 运行完毕归还资源：**$\text{Work} = \text{Work} + \text{Allocation}[i]$**，将 $P_i$ 加入序列并重复第 2 步。若所有进程都能完成则处于**安全状态**（写出安全序列）；若中途没有任何剩余进程满足 $\text{Need}[i] \le \text{Work}$，则处于**不安全状态（无安全序列）**！

- **2018 真题速核**：$\text{Available} = (0, 2, 1)$。
  - 先选 $P_1$（$\text{Need}=(0,0,1) \le (0,2,1)$）$\implies \text{Work} = (0,2,1)+(2,0,0) = (2,2,1)$；
  - 再选 $P_4$（$\text{Need}=(2,0,0) \le (2,2,1)$）$\implies \text{Work} = (2,2,1)+(0,0,1) = (2,2,2)$；
  - 剩余 $P_2$（$\text{Need}=(1,3,2)$）和 $P_3$（$\text{Need}=(1,3,1)$）的 $R_2$ 均需 $3 > 2$，无法满足 $\implies$ **答：不处于安全状态（安全序列不存在）**。
- **2023 真题速核**：5 进程 $P_0 \sim P_4$，算出 $\text{Need}$ 依次为 $P_0(7,4,3), P_1(1,2,2), P_2(6,0,0), P_3(0,1,1), P_4(4,3,1)$。
  - 卷面印 $\text{Available} = (2, 3, 0)$：$P_0, P_1, P_3, P_4$ 均需 $C \ge 1 > 0$，$P_2$ 需 $A = 6 > 2$，**一步都走不动 $\implies$ 不处于安全状态**，可能卷入死锁的进程为 $P_0, P_1, P_2, P_3, P_4$。*(注：若考场把 Available 印为教材原值 `(3, 3, 2)`，则安全，序列为 `P1 -> P3 -> P4 -> P2 -> P0`)*。
  - **经典第 b 问：“当前不安全状态是否一定会发生死锁？为什么？”**
    - **答：不一定！** 不安全状态只代表存在导致死锁的潜在最坏请求序列（当各进程后续真的请求达到各自的 `Max` 时无法避免死锁）；如果各进程后续不再申请新资源或提前释放已占资源，系统并不会发生死锁。

## 五、考场 60 分钟冲刺与交卷前 5 分钟防丢分 Checklist

1. **【判断题】** 凡是打 **`×`** 的题，**100% 检查是否写了一句理由**（没写理由直接丢一半分！）。
2. **【判断题文字坑】** 看到 `$S = -6$` 看清写的是“等待**该信号量**的进程有 6 个”（√）还是“**全系统**共有 6 个等待进程”（×）。
3. **【选择题】** 先看大题标题是**单选**还是**不定项选择**；问“CPU 执行内核代码处于什么态”选**内核态**（别选执行态）；信号量初值 $2$ 当前值 $-1$，等待进程数是 **$|-1| = 1$ 个**（别选 $3$ 个！）。
4. **【CPU 调度题】** 交卷前重核四件事：
   - 甘特图末尾总长度是否等于 $\sum B_i$（无空闲段时）？
   - 优先级究竟是**小数字优先**（2019/2023）还是**大数字优先**（2018 / L5 P.36）？
   - 题目问的是**等待时间**（$C - A - B$）、**周转时间**（$C - A$）还是**响应时间**（$S - A$）？
   - RR 中多次运行的进程，是否用 $C - A - B$ 算齐了中途所有排队片段？
5. **【P/V 同步题】** 检查生产者和消费者是否都是**先 `P(资源 empty/full)`，再 `P(mutex)`**（顺序反了必死锁扣大分！）；检查消费者最后一行是否是 **`V(empty)`**（绝不是 `V(full)`！）。
6. **【条件变量题】** 检查 `wait` 外面套的是不是 **`while` 循环**（不能写 `if`），`pthread_cond_wait` 是否传了 `&mutex`，以及修改 `full` 标志后是否调用了唤醒**对方**条件变量的 `signal`。
