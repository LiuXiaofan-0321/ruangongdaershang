### 第一讲（考纲起点）：Lesson 2 — 操作系统服务与内核结构（OS Services）

#### 1. 操作系统的两类核心服务（P.3–8）
操作系统介于应用程序与硬件之间，提供的服务按服务对象分为两大类：
- **面向用户与支持程序运行的服务**：
  1. **用户界面（UI）**：命令行（CLI/Shell）、图形界面（GUI，源于 Xerox PARC）、触控界面（Touch）。界面只决定“怎样表达请求”，底层调用的系统服务能力相同。
  2. **程序执行**：将程序装入内存创建进程，支持正常结束或异常终止。
  3. **I/O 操作**：因安全与效率原因，用户程序不能直接操纵外设硬件，必须由 OS 统一代理完成读写与设备控制。
  4. **文件系统操作**：文件的创建、删除、读写、定位、目录组织与权限管理。
  5. **通信（IPC）**：为本机或跨网络进程提供**共享内存**或**消息传递**两种数据交换途径。
  6. **错误检测**：监控 CPU/内存硬件故障（如非法地址访问）、I/O 设备错误和用户程序异常（除零、越界），返回错误码、记日志或终止故障进程（*注意：OS 并非能自动恢复一切错误*）。
- **面向系统整体高效安全共享资源的服务**：
  1. **资源分配**：多任务并发时利用调度与分配策略分配 CPU 周期、物理内存、磁盘和外设。
  2. **记录与统计（Accounting/Logging）**：统计各用户/进程占用了多少资源，用于审计、计费与性能调优。
  3. **保护（Protection） vs 安全（Security）**：**保护**聚焦系统**内部**访问控制（确保并发进程互不越界干扰）；**安全**聚焦抵御**外部**非法入侵、认证用户身份与保障系统完整性。

#### 2. 双重特权模式（用户态 vs 内核态）与 Shell 的本质（P.9–14，衔接往年真题）
- **用户态（User Mode）与内核态（Kernel Mode / 核心态）**：CPU 硬件通过模式位（Mode bit）区分当前执行权限。用户程序运行在非特权的用户态，只能访问自己的虚拟地址空间且禁止执行关中断、改页表、直接 I/O 等**特权指令**；操作系统内核运行在受保护的内核态，拥有最高硬件权限。从用户态进入内核态**只有三条受控通道**：**① 系统调用（Trap / 访管指令）、② 外部硬件中断（Interrupt）、③ 内部异常（Exception，如缺页、除零）**。
- **Shell（命令解释器）的定位**：Shell 是运行在**用户态**的普通系统程序（并非内核的一部分！）。用户输入命令后：
  - **内建命令（Built-in，如 `cd /tmp`）**：由 Shell 进程直接调用自身函数修改自己的当前工作目录（若派生子进程执行 `cd`，子进程改完目录退出后父 Shell 的目录根本不会变！）。
  - **外部程序（如 `/bin/ls`）**：Shell 通过 `fork()` 创建子进程并调用 `exec()` 加载磁盘上的可执行文件运行，因此新增外部工具无需修改 Shell 代码。

#### 3. API、库函数与系统调用的关系及 I/O 陷阱（P.14–33）
- **三者层级关系**：应用程序通常调用高级语言或标准库的 **API**（如 C 库 `printf`、`strlen`，POSIX API，Windows API），而不是直接手写汇编触发**系统调用（System Call，内核对外的受控二进制服务入口）**。
  - **核心规律**：**一次库函数 API 调用可能对应 0 次、1 次或多次系统调用**！例如 `strlen()` 纯在用户态算长度（**0 次**系统调用）；`printf("hi")` 先把字符写进**用户态 C 库缓冲区**，未满或全缓冲未换行时也是 **0 次**系统调用，直到缓冲区满、`fflush()` 或程序正常退出时才合并调用底层的 `write()` 系统调用。因此用 `strace` 跟踪系统调用时，只能看到 `write()`，看不到纯用户态的 `printf()`。
- **底层 I/O 三大陷阱**：
  1. **短读 / 短写（Short read/write）**：`read(fd, buf, count)` 或 `write` 返回正整数 $k < \text{count}$ 并不代表出错（如管道缓冲有限、网络分包），必须根据返回值用循环继续读写剩余的 `count - k` 字节；普通文件 `read` 返回 `0` 代表到达文件尾（**EOF**），返回 `-1` 代表出错并置 `errno`。
  2. **`write` 成功 $\neq$ 落盘持久化**：`write()` 返回成功仅说明数据已从用户缓冲区拷贝到**内核页缓存（Page Cache）**，若此刻突然断电仍可能丢失，真正刷入磁盘需调用 `fsync()`。
  3. **进入内核 $\neq$ 进程切换**：执行系统调用从用户态陷入内核态只是当前线程发生了**模式切换（Mode Switch）**；如果请求无需阻塞等待，内核做完直接返回原线程继续跑，并未切换到其他进程。

#### 4. 系统调用传参机制与内核参数安全校验（P.22–24）
- **三种传参方式**：① **寄存器传参**（最快，Linux x86-64 默认用约定的寄存器传调用号和前几个参数，受寄存器数量限制）；② **内存块/表传参**（参数较多时存放在用户内存块中，只把该块首地址放入寄存器传给内核）；③ **栈传参**（压入用户栈由内核读取）。
- **为什么内核绝不能直接信任用户传来的指针参数（如 `read(fd, buf, count)` 中的 `buf`）？**
  因为内核拥有最高特权，而用户态参数不可信：若 `buf` 是空指针/未映射虚拟地址会导致内核页错误崩溃；若指向只读代码段会违背写权限；若 `count` 过大可能引发整数溢出越界；最危险的是恶意程序可能**伪造一个指向内核地址空间的指针传给 `read`**，诱骗内核把文件数据直接覆盖到内核关键数据结构上实现提权攻击！因此内核必须先检查 `fd` 有效性、地址范围是否落在合法用户空间、页表读写权限及长度边界。

#### 5. 编译、链接、装载与跨平台二进制限制（P.34–40）
- **从代码到进程的四步链路**：
  1. **编译（Compiler，`gcc -c`）**：单源文件译为目标文件 `.o`，跨文件调用的函数此时地址未知，仅留未定义符号和重定位表项。
  2. **链接（Linker，`gcc -o`）**：合并多个 `.o` 与库，完成**符号解析**（把函数名绑到定义处）和**地址重定位**（填入/修正指令引用地址），生成可执行文件。
     - **静态链接**：把库代码直接打包进可执行文件——独立易部署，但磁盘/内存体积大，库修补漏洞需重新链接所有程序。
     - **动态链接**：运行时由动态加载器（`ld.so`）映射共享库（`.so`/`.dll`）——多进程可在物理内存中**共享同一份只读代码页**，且能独立升级共享库（前提是保持 ABI 兼容；注意共享库的可写全局变量在各进程中依然写时复制隔离！）。
  3. **装载（Loader）**：内核解析可执行文件头建立虚拟地址空间，采用**按需调页（Demand Paging）**机制——无需在启动时把整个文件一次性拷入物理内存，运行到哪一页缺页时再调入。
- **API vs ABI 与跨平台限制**：
  - **API（应用编程接口）**约束**源码层**函数签名（决定换系统重新编译能否过）；**ABI（应用二进制接口）**约束**编译后机器码层**的交互细节（寄存器谁传参、栈帧怎么摆、结构体怎么对齐、系统调用号是多少）。
  - **即便两台电脑都是 x86-64 CPU，同一个编译好的程序仍无法通跑**，因为：① 可执行格式不同（Linux 用 **ELF**，Windows 用 **PE**，macOS 用 **Mach-O**）；② 系统调用号与内核接口不同；③ ABI 约定不同；④ 依赖的动态共享库不同。

#### 6. “机制与策略分离”原则及五类内核架构对比（P.41–51）
- **机制（Mechanism） vs 策略（Policy）**：**机制**回答“**怎么做（How）**”（如提供定时器中断硬件支持和保存/恢复上下文的操作）；**策略**回答“**选谁做、做多久（What/Who/When）**”（如决定给交互进程 8ms 时间片还是按优先级选人）。把两者解耦，修改调度策略时就不必改动底层机制代码。
- **五种内核组织结构核心原理**：
  1. **单体内核（Monolithic，如传统 UNIX）**：进程调度、文件系统、网络协议栈、设备驱动**全部放在同一个内核地址空间**里，彼此直接通过C函数调用交互。**优点**是调用极快、性能高；**缺点**是无内部硬件隔离，一个劣质显卡/网卡驱动空指针崩溃就会引发整个内核 Panic。
  2. **分层结构（Layered）**：严格划分为第 $0$ 层（硬件）到第 $N$ 层（用户接口），每层只允许调用紧邻下层的接口。逻辑清晰易验证，但跨层传递参数开销大且很难划清严格的单向依赖（如虚拟内存和磁盘驱动互相依赖）。
  3. **微内核（Microkernel，如 Mach、QNX、seL4）**：把内核裁剪到极致，**内核态只保留最基本的 IPC（进程间通信）、基本内存管理和 CPU 调度**；把文件系统、设备驱动、网络服务统统移到**用户态作为独立服务进程**运行，服务间只能靠内核转发**消息传递（Message Passing）**协作。**优点**是隔离性极强（驱动崩了重启该用户进程即可，内核不倒）、高可靠易扩展；**缺点**是一次文件读写要经历多次跨地址空间消息拷贝与用户态/内核态切换，通信性能损耗大。
  4. **可加载内核模块（Modular，如现代 Linux）**：允许在运行时动态插入（`insmod` `.ko`）或卸载驱动与文件系统模块，无需重编重启内核。**必考辨析**：**模块化 Linux 依然是单体内核而不是微内核**！因为 `.ko` 模块加载后直接进入**同一个内核地址空间**，通过直接函数调用运行在最高特权级，没有微内核的用户态进程隔离。
  5. **混合结构（Hybrid）**：工程折中——**Apple Darwin/XNU** 在同一内核空间融合了 Mach（管调度/IPC/虚拟内存）+ BSD（管 POSIX 接口/进程/文件系统/网络）+ I/O Kit；**Android** 底层用 Linux 内核，但用户空间换用了轻量 **Bionic C 库**（非桌面 glibc）、**HAL** 硬件抽象层与 **ART 虚拟机运行时**。

#### 7. 系统引导（Boot）与调试性能观测（P.54–57）
- **开机引导 6 阶段**：通电执行非易失存储中的 **① 固件（BIOS/UEFI）** 自检硬件 $\to$ 加载 **② 引导程序（Bootloader，如 GRUB）** $\to$ 将内核映像与初始内存盘 `initramfs` 读入内存，完成 **③ 内核子系统初始化** $\to$ **④ 挂载真实根文件系统** $\to$ 启动第一个用户态祖先进程 **⑤ `init`（PID = 1，如 `systemd`）** $\to$ 拉起后台守护服务并提供 **⑥ 登录界面或命令行 Shell**。
- **调试 vs 性能观测**：调试（GDB、`core dump`、`dmesg`）查“哪里算错/崩了”；性能分析查“慢在哪里”，分**计数**（`perf stat` 统计总次数）、**采样**（`perf record` 周期抽查调用栈找热点）和**跟踪**（`strace` 逐条记录事件，注意跟踪本身会显著拖慢程序！且**CPU 利用率低不代表没瓶颈**，很可能正卡在慢速磁盘/网络 I/O 阻塞或锁等待上）。

### 第二讲：Lesson 3 — 进程管理与进程间通信（Process & IPC）

#### 1. 进程本质与虚拟内存五段布局（P.3–6）
- **程序 vs 进程**：**程序**是躺在磁盘里的静态可执行文件（被动实体）；**进程**是运行中的程序实例（主动实体），不仅有代码，还有动态变化的程序计数器 `PC`、寄存器、堆栈和打开的文件资源。同一个程序连开两次就是两个完全独立的进程。
- **进程虚拟地址空间（从低地址 `0` 到高地址 `max`）**：
  1. **`text`（代码段）**：只读机器指令；
  2. **`data`（已初始化数据段）**：给了初值的全局变量和 `static` 变量（如全局 `int a = 10;`）；
  3. **`bss`（未初始化数据段）**：没写初值的全局变量和 `static` 变量（如全局 `int b;`，装载时自动清零，在磁盘文件里不占实体的零字节空间）；
  4. **`heap`（堆，向高地址 $\uparrow$ 增长）**：运行时 `malloc` / `new` 动态申请出的内存块本体；
  5. **`stack`（栈，向低地址 $\downarrow$ 增长）**：每次函数调用压入一个栈帧，存放**局部变量、函数形参、返回地址**（*高频考点*：函数里写 `int *p = malloc(20);`，指针变量 `p` 自身是局部变量住在 **`stack`** 上，`malloc` 出来的那 20 字节才住在 **`heap`** 上！）。最高地址处还存有命令行参数 `argc/argv` 和环境变量。

#### 2. 进程状态转换、PCB 与上下文切换（P.7–20）
- **五状态与核心禁区**：`New`（新建） $\xrightarrow{\text{准入}}$ `Ready`（就绪：万事俱备只欠 CPU） $\xleftrightarrow[\text{时间片完/被抢占}]{\text{调度分派}}$ `Running`（运行） $\xrightarrow{\text{exit}}$ `Terminated`（终止）；若运行中发起阻塞 I/O 或等锁未果，则 `Running` $\to$ `Waiting`（等待/阻塞：给它 CPU 也跑不了）；当外设中断报告 I/O 完成时，只能 **`Waiting` $\to$ `Ready`**（回到就绪队列排队，**绝不可能从 `Waiting` 一步跳到 `Running`**，因为此刻 CPU 可能正跑着别的进程！）。
- **PCB（进程控制块，Linux 中为 `struct task_struct`）**：进程存在的唯一内核标志，记录 PID/PPID、当前状态（注意 Linux `ps` 中状态码 **`R` 同时代表 Running 和 Ready**，`S` 为睡眠等待，`Z` 为僵尸）、**`PC` 与 CPU 寄存器保存区**、调度优先级、页表基址、已打开文件描述符表与记账信息。
- **进程上下文切换（Context Switch）的双重代价**：当调度器把 CPU 从进程 $P_0$ 换给 $P_1$ 时，除了**直接开销**（将 $P_0$ 的寄存器和 PC 存入 $\text{PCB}_0$、切换页表基址寄存器、从 $\text{PCB}_1$ 恢复寄存器和 PC），还有极易被忽视的**间接硬件开销**——切换地址空间会导致 **TLB（快表）刷新失效**，且新进程的数据不在 **CPU 高速缓存（Cache）**中，刚切过去的一段时间会频繁发生 Cache Miss 拖慢访存。

#### 3. 进程生命周期原语：`fork` / `exec` / `wait` 与僵尸、孤儿进程（P.21–33）
- **`fork()` 机制精髓**：
  - **一次调用，两次返回**：内核复制父进程创建子进程，两者从 `fork()` 下一行同时起步——**父进程拿到子进程的 `PID (>0)`**，**子进程拿到 `0`**（失败返 `-1`），谁先上 CPU 完全由调度器决定。
  - **写时复制（Copy-On-Write, COW）与共享边界**：`fork()` 时内核并不立刻傻傻拷贝全部物理内存页，而是让父子页表先指向同一组物理页并标为**只读**；一旦任一方试图修改某个变量（如 `x = 2`），触发写保护缺页异常，内核才为修改方单独分配一页新物理内存拷过去改——所以逻辑上**父子所有普通变量（全局/栈/堆）完全独立互不影响**！但**唯一默认共享的例外**是：子进程复制了父进程的文件描述符表，对应的 `fd` 指向**同一个内核“打开文件描述”结构**，因此父子**共享同一个文件读写偏移量 `offset`**！
- **`exec()` 系列**：在当前进程躯壳里“借尸还魂”——**PID 保持不变**，但把原程序的代码、数据、堆栈彻底清空替换成新可执行文件，从新程序的 `main` 重新开始。因此**只要 `exec` 成功，原程序写在 `exec` 后面的代码永远不会执行**！
- **僵尸进程（Zombie） vs 孤儿进程（Orphan）**：
  - **僵尸进程**：子进程**已经终止退出**，内核释放了它的内存和文件，但必须保留它的最小 PCB（装着退出码等父进程查验）。如果父进程一直不调 `wait()`/`waitpid()` 收尸，该死掉的子进程就一直占着内核进程表项和 PID，呈 `Z` 状态。*(注意：还在活蹦乱跳运行的子进程绝不是僵尸！)*
  - **孤儿进程**：父进程比子进程**先死掉了**，还在运行的子进程变成孤儿，会被内核立即过继给 **`init`/`systemd`（PID = 1）** 收养；等子进程将来退出时，`PID 1` 会自动调 `wait` 把它干净回收，不会变永久僵尸。

#### 4. 进程间通信（IPC）：共享内存、消息传递、管道、Socket 与 RPC（P.34–66）
- **共享内存 vs 消息传递**：
  - **共享内存**（POSIX 用 `shm_open` $\to$ `ftruncate` $\to$ `mmap(..., MAP_SHARED, ...)`）：将同一块物理内存映射进两个进程各自的虚拟地址空间。**最快**（读写就像访问普通数组，无需每次进出内核拷贝），但有两条铁律：① 内核不管同步，**必须由程序员自己配信号量/锁防读写冲突**；② 同一块共享内存映射到进程 A 和进程 B 的虚拟起始地址可能不同，因此**共享内存里只能存相对偏移量（offset），绝不能直接存某进程的本地虚拟地址指针**！
  - **消息传递**：调用 `send/receive` 由内核转发（适合少量数据或跨网络）。寻址分**直接通信**（指名道姓 `send(P, msg)`）和**间接通信**（发往共享邮箱 `send(Mailbox, msg)`，多进程同时收同一邮箱时默认择一接收而非广播）；缓冲分**零容量**（无缓冲，发送方必须死等接收方到场当面交接 Rendezvous）、**有界容量**（满则发送阻塞）和**无界容量**。
- **管道（Pipe & FIFO）与必考 EOF 定律**：
  - **匿名管道 `pipe(fd)`**：半双工单向字节流（无消息边界），**`fd[0]` 固定为读端、`fd[1]` 固定为写端**，仅用于 `fork` 继承描述符的亲缘进程。
  - **管道阻塞与 EOF 铁律**：当管道已空时，阻塞 `read(fd[0])` 会不会返回 `0`（EOF）？**取决于全系统还有没有未关闭的写端 `fd[1]`**！只要还有**任何一个进程**（哪怕是读进程自己 `fork` 继承来却忘了 `close(fd[1])` 的那个写端！）没关掉 `fd[1]`，内核就认为未来还可能有人写数据，`read` 就会**永久阻塞死等**；只有**管道数据读光 且 所有写端引用计数归 0** 时，`read` 才立即返回 `0`！
  - **命名管道（FIFO）**：在文件系统里挂个路径名让无亲缘关系的本机进程也能打开通信，但**传输的字节只在内核内存缓冲区走，绝不会写到磁盘文件里**。
- **Socket 与 RPC（远程过程调用）**：
  - **TCP Socket**：由（源IP, 源端口, 目的IP, 目的端口）四元组唯一标识一条连接；服务端 `accept()` 会返回一个**全新的已连接 socket** 服务该客户，原监听 socket 继续接客；TCP 是无边界字节流，应用层必须自己定协议切分消息。
  - **RPC 与超时幂等性**：RPC 用客户端/服务端存根（Stub）把跨网调用伪装成本地函数调用，用序列化（Marshalling / XDR）消除不同机器的大小端与字节对齐差异。**最大痛点是网络超时二义性**：客户端超时没收到回复时，**根本分不清是“请求包在路上丢了（服务端执行了 0 次）”还是“服务端早已执行成功，只是回执包在路上丢了（已执行 1 次）”**！因此衍生出**至多一次（At-most-once，带请求 ID 服务端去重）**与**至少一次（At-least-once，超时只管重发，仅适用于纯查询、定值覆盖等执行多次结果不变的“幂等操作 Idempotent”；像转账扣款这种非幂等操作盲目重试会扣两次钱！）**。

### 第三讲：Lesson 4 — 线程与并发编程（Threads & Concurrency）

#### 1. 线程的资源划分与四大优势（P.3–8）
- **核心思想**：把传统进程拆解开——**进程只管“占资源与圈地隔离”，线程专门管“上 CPU 跑指令流”**。
- **为什么这些共享、那些私有？**
  - **同进程线程共享**：代码段（`text`）、全局/静态变量（`data`/`bss`）、堆（`heap`）、打开文件描述符表、信号处理函数表、工作目录。因为大家在同一个进程地址空间里干活，直接读写全局变量和堆对象无需繁琐 IPC。
  - **每个线程必须私有**：**程序计数器 `PC`**（记我自己跑到哪一行指令了）、**CPU 寄存器集合**（记我自己算到一半的临时值和栈顶指针 `SP`）、**栈 `stack`**（记我自己的函数调用链和局部变量，否则 A 调函数把 B 的返回地址冲了）、**线程局部存储 `TLS`** 和 **信号屏蔽字**。
  - *易错透视*：虽然每个线程各用各的栈，但因为全进程共用同一张页表（同一虚拟地址空间），**线程栈之间没有硬件内存保护墙**——如果线程 A 把自己局部变量的地址 `&local_var` 传给线程 B，线程 B 完全能顺着指针过来读写（一旦线程 A 函数提前返回销毁栈帧，B 就踩到悬空野指针了！）。
- **多线程四大优势**：① **响应性**（后台线程阻塞等网络时 UI 线程照样响应点击）；② **资源共享**；③ **经济性**（建线程比 `fork` 进程快得多、切换不换页表）；④ **多核可扩展性**（不同线程真正在多个物理核上同时跑）。

#### 2. 并发 vs 并行、Amdahl 定律与四种线程映射模型（P.9–22）
- **并发 vs 并行**：单核 CPU 靠毫秒级快速轮换在 1 秒内同时推进听歌、打字、下载，叫**并发（宏观同时、微观交替）**；双核 CPU 在同一纳秒核 0 跑听歌、核 1 跑打字，叫**并行（微观真正同时）**。
- **Amdahl 定律（加速比天花板）**：任何程序都有无法并行化的串行占比 $S$（如初始化、汇总写入），并行部分 $1-S$ 平分给 $N$ 个核后，耗时从 $1$ 缩为 $S + \frac{1-S}{N}$，故理想加速比 $\text{Speedup}(N) = \frac{1}{S + (1-S)/N}$。哪怕买一万颗核（$N \to \infty$），加速比也绝不可能超过 **$1/S$**（例如 20% 串行代码直接把极限锁死在 5 倍以内，且实际还有建线程、锁争用和缓存同步损耗）。
- **用户线程（ULT）到内核线程（KLT）的四种映射模型**：
  1. **多对一**：纯用户态库在 1 个内核线程上轮换多个用户线程。切换不进内核极快；但内核眼里只有 1 个线程，**任一用户线程调阻塞 `read` 全进程一起卡死，且在多核机上永远只能用 1 个核**。
  2. **一对一**（Linux NPTL、Windows 默认）：每建 1 个用户线程就在内核建 1 个调度实体（Linux 中都是 `task_struct`，同进程各线程 `TID` 不同但共享同一个线程组号 `TGID = PID`）。一个阻塞不影响别人、真多核并行；代价是建太多线程耗内核栈内存，故需用线程池限流。
  3. **多对多**（Go `goroutine`、Java 21 虚拟线程）：$M$ 个超轻量用户态协程动态调度复用 $N$ 个内核线程，兼顾高并发规模与多核并行。
  4. **双层模型**：多对多基础上允许关键用户线程单独绑死一个专属内核线程（LWP）。

#### 3. 隐式线程（线程池 / Fork-Join / OpenMP）与多线程四大系统陷阱（P.30–55）
- **隐式线程**：把“建/管线程”交给运行时库，程序员只管交任务：
  - **线程池**：预先养固定数量工作线程循环从任务队列领活，省去反复创建销毁开销并防内存撑爆。（*CPython GIL 补充*：因全局解释器锁限制同一时刻仅一线程跑字节码，Python 多线程适合重叠 I/O 等待，纯计算密集需用多进程或 C 扩展）。
  - **Fork-Join 分治**：大任务递归对半拆分子任务并行算完再 `join` 合并（切忌让固定小线程池里的父任务占着工作线程干等队列里的子任务，会引发池饥饿死锁！）。
  - **OpenMP**：`#pragma omp parallel for` 自动并行拆循环；累加共享变量用 `reduction(+:sum)` 让各线程算私有副本最后安全汇总，或用 `#pragma omp critical` 自动加解锁。
- **多线程系统管理四大高频陷阱**：
  1. **多线程中调 `fork()`**：子进程**只保留调用 `fork` 的那一个线程**，其他兄弟线程全蒸发，但兄弟线程在父进程里锁住的 `mutex` 却保持“已上锁”状态被拷进了子进程！若子进程不立刻 `exec()` 而去碰那把锁，没人能给它解锁，当场死锁。
  2. **多线程信号递送**：信号处理函数表（收到信号干什么）是**全进程共享**的，但信号屏蔽字（堵住哪些信号不收）是**每线程私有**的；异步发给进程的信号会挑**一个**未屏蔽它的线程接收（`SIGKILL`/`SIGSTOP` 不可捕获或屏蔽）。
  3. **线程取消（`pthread_cancel`）**：调完函数目标线程并未立刻死！默认是**延迟取消（Deferred）**，目标线程一直跑到安全的**取消点**（如阻塞 I/O 或 `pthread_testcancel()`）才触发清理函数退出（若设为异步取消可在任意机器指令处暴毙，极易导致锁没解、内存泄漏）。
  4. **线程局部存储（TLS，`__thread` / `_Thread_local`）**：变量名像全局，但每个线程各有一份持久私有拷贝。**线程池大坑**：线程池里的工作线程做完任务 A 不会销毁，紧接着领任务 B，如果任务 B 不主动重置 TLS，就会读到任务 A 留下的脏数据！

### 第四讲：Lesson 5 — CPU 调度（CPU Scheduling）

#### 1. CPU-I/O 突发周期、抢占时机与评价指标（P.3–13）
- **为什么需要调度？** 进程一生都在“跑一段 CPU 计算（CPU burst）$\to$ 等一段慢速 I/O（I/O burst）”之间循环。绝大多数交互/I/O 密集型进程的 CPU burst 都很短，少量计算型进程有很长的 CPU burst。
- **四类状态转换时机定性（抢占 vs 非抢占的分水岭）**：
  - 当进程发生 **① 运行 $\to$ 等待**（自己去等 I/O 了）或 **④ 运行 $\to$ 终止**（跑完了），原进程自己没法占着 CPU 了，任何调度器都必须换人——**只在这两种情况换人的叫“非抢占式调度（Nonpreemptive）”**（如 FCFS、非抢占 SJF）。
  - 当发生 **② 运行 $\to$ 就绪**（时钟中断宣告时间片到）或 **③ 等待 $\to$ 就绪**（某个高优先级或极短任务刚做完 I/O 醒来入队，或新进程刚到达），原运行进程本来还能继续跑，调度器强行把它摘下来换别人上——**允许在 ②、③ 换人的叫“抢占式调度（Preemptive）”**（如 RR、SRTF、抢占式优先级）。
- **分派程序（Dispatcher）**：调度器选好人后，真正动手完成“存旧 PCB 现场 $\to$ 切页表 $\to$ 恢复新 PCB 现场并切回用户态跳到新 PC”的模块，耗时称**分派延迟**。
- **五大评价指标**：CPU 利用率、吞吐量（单位时间完成进程数）、**周转时间**（完成 $C - \text{到达 } A$）、**等待时间**（在就绪队列干等的总时长，不含跑 CPU 和等 I/O 的时间！）、**响应时间**（首次上 CPU 时刻 $S - \text{到达 } A$）。

#### 2. 经典调度算法核心思想与优劣权衡（P.15–44）
- **FCFS（先来先服务）**：谁先就绪谁跑完。致命伤是**护航效应（Convoy Effect）**：1 个大长计算进程排前头霸占 CPU，后面跟一串只需 1ms CPU 就能去发磁盘请求的小进程全被堵死在就绪队列，导致 I/O 设备闲死；等长进程终于去 I/O，小进程瞬间跑完又全去等 I/O，轮到 CPU 闲死。
- **SJF（非抢占短作业优先）与 SRTF（抢占式最短剩余时间优先）**：
  - **为什么 SJF 平均等待最短？** 邻项交换原理：长任务 $a$ 和短任务 $b$ 挨着时，先跑短任务 $b$ 能让 $b$ 少等 $a$ 毫秒，而 $a$ 只多等较小的 $b$ 毫秒，净赚 $a - b > 0$，且后面所有人的开工时刻不变！
  - **怎么猜下一次 CPU 跑多久？** 用**指数平均法** $\tau_{n+1} = \alpha t_n + (1-\alpha)\tau_n$ 综合“刚跑完的实际值 $t_n$”和“上次预测值 $\tau_n$”。
  - **SRTF**：新进程到达瞬间，拿它的需要时间跟当前运行进程的**剩余时间**比，更短立刻抢占。SJF/SRTF 的共同软肋是长任务可能被源源不断的短任务插队致**饥饿**。
- **优先级调度 & HRRN**：按优先级挑人，软肋同样是低优先级**饥饿**，标准解药是**老化（Aging）**——在就绪队列等得越久，系统自动一点点调高它的优先级。**高响应比优先（HRRN，往年真题常客）**正是老化的数学化体现：响应比 $R_p = \frac{W + B}{B} = 1 + \frac{W}{B}$，服务时间 $B$ 短则分母小优先（像 SJF），长作业等待时间 $W$ 变大后分子飙升也能拿到最高响应比（绝不饥饿）！
- **RR（时间片轮转）**：专为分时交互设计，每次最多跑一个时间片 $q$，没跑完去就绪队尾重排。$n$ 个任务下任何人距下次响应不超过 $(n-1)q$。**$q$ 的黄金法则**：$q \to \infty$ 退化成 FCFS；$q$ 太小（接近上下文切换耗时）则 CPU 全花在切换保存寄存器和刷 Cache 上，系统有效效率暴跌（经验上让约 80% 的短 CPU burst 能在 1 个 $q$ 内跑完最佳）。
- **MLQ（多级队列） vs MLFQ（多级反馈队列）**：MLQ 按进程身份定终身（前台交互队用 RR、后台批处理队用 FCFS，永不换队）；**MLFQ** 最聪明——不用预知进程长短，所有新进程一律先放进最高优先级短时间片队列 $Q_0$（如 $q=8\text{ ms}$）：如果是交互短任务，一下就跑完走了；如果跑完 $8\text{ ms}$ 还没完，说明偏计算型，降级丢进 $Q_1$（$q=16\text{ ms}$）；再跑不完降进底层 $Q_2$（FCFS），配合定期把底层老进程提回高层防饥饿，完美兼顾响应与周转！

#### 3. 多核调度、实时调度与 Linux / Windows 实例（P.45–73）
- **多核 SMP 四大机制**：① **每核私有就绪队列**（比全局共享单队列少了多核抢队列锁的开销）；② **负载均衡**（空闲核主动偷活 Pull migration + 忙核定期推活 Push migration）；③ **CPU 亲和性与 NUMA**（尽量让线程留在上次跑过的核上复用热 Cache 称软亲和性；用 `taskset` 绑死核集合称硬亲和性；NUMA 下调度器尽量让线程在离它物理内存最近的节点核上跑）；④ **超线程**（1 个物理核配两套寄存器装成 2 个逻辑核，趁线程 A 等内存 Cache Miss 停顿时切线程 B 用算术单元）。
- **实时调度（RM vs EDF）**：硬实时错过截止期即事故。单核独立周期任务（周期 $T_i$，计算量 $C_i$，默认截止期 $D_i = T_i$，总负载 $U = \sum C_i/T_i$）：
  - **RM（速率单调）**：周期越短（频率越高）静态优先级越高；当 $U \le n(2^{1/n}-1)$ 时**必定可调度**（充分条件，$n=2$ 约 $82.8\%$，无穷多任务趋于 $69.3\%$）。
  - **EDF（最早截止期优先）**：谁眼下这一轮离绝对截止时刻最近谁先跑（动态优先级）；**当且仅当 $U \le 100\%$ 时可调度**（充要条件，理论利用率拉满）。
- **Linux 与 Windows 调度精要**：
  - **Linux**：实时类（`SCHED_DEADLINE` > `SCHED_FIFO`/`SCHED_RR`，用户态实时优先级 `1~99` 越大越高）永远压制普通公平类（`SCHED_OTHER`）。普通进程看 **`nice` 值（`-20 ~ +19`，注意越负代表越“不谦让”，权重越高！）**：CFS 按权重折算累计**虚拟运行时间 `vruntime`**（高权重涨得慢，每次挑红黑树里 `vruntime` 最小的跑）；Linux 6.6+ 演进为 **EEVDF**，在未超支份额（Eligible）的任务中挑**虚拟截止时间**最早者。
  - **Windows**：`0~31` 共 32 级（越大越高，`16~31` 为实时固定级，`1~15` 为动态级——线程刚等完键盘/鼠标 I/O 醒来时会获临时优先级加分以保证丝滑交互）。

### 第五讲：Lesson 6 — 同步工具（Synchronization Tools）

#### 1. 竞争条件、临界区三准则与关中断局限（P.4–10）
- **为什么会有竞争条件（Race Condition）？** C 语言里看似一行的 `counter++`，编译成机器码其实是三条分立指令：`① 读内存到寄存器 -> ② 寄存器加 1 -> ③ 写回内存`。若线程 A 刚做完 ① 读出 `5` 就被时钟中断切走，线程 B 上来一口气读 `5` 加成 `6` 写回，等线程 A 恢复执行时手里寄存器还是旧的 `5`，加 1 后又把 `6` 写回去——两次自增硬生生吞掉了一次（**丢失更新**）。结果取决于调度先后，即为竞争条件。
- **临界区问题三项黄金准则（缺一不可！）**：
  1. **互斥（Mutual Exclusion）**：同一时刻最多 **1 个**执行流在临界区内。
  2. **前进 / 空闲让进（Progress）**：当临界区**空着**且有人想进时，那些待在“剩余区”（根本不想进临界区）的无关进程绝不能掺和阻拦，且必须在有限时间内选出一个人进去（系统不能干瞪眼卡死）。
  3. **有限等待（Bounded Waiting）**：某进程举手申请进入后，在它获准进入之前，**允许其他进程插队先行的总次数必须有个明确上限**（防止个体饿死）。
- **为什么多核不能靠“关中断”互斥？** 单核内核态关掉本地中断，时钟中断进不来就不会发生调度切换，天然原子；但在多核 SMP 上，**CPU 0 关中断只捂住了 CPU 0 自己的耳朵，CPU 1 照样在另一条物理通路上全速并发读写同一块共享内存**！且绝不能把关中断指令开放给用户态（恶意死循环关中断整机直接死机）。

#### 2. 软件解法（严格轮换 vs Peterson）与现代多核内存屏障（P.9–21）
- **严格轮换法（`turn = 0/1`）为什么不及格？** 每次 $P_0$ 出来把令牌改成 `turn = 1`；万一 $P_1$ 去喝茶了（一直在剩余区不进临界区），哪怕临界区空无一人，$P_0$ 想再进第二次也被 `while (turn == 1)` 死死挡在门外——**满足互斥，但直接违反“前进”准则**！
- **Peterson 算法为什么精妙？** 结合了 `flag[2]`（表达“我想不想进”）和 `turn`（表达“同时想进时我礼貌让谁先走”）：
  - $P_i$ 进门三步：`flag[i] = true; turn = j; while (flag[j] && turn == j);`
  - 若只有 $P_0$ 想进，`flag[1]` 为假，直接进（满足**前进**）；若两人同时想进，`turn` 这块黑板最后被谁改写，谁就把通行权让给对方（例如 $P_1$ 后写 `turn = 0`，则 $P_0$ 进、$P_1$ 等，满足**互斥**）；$P_0$ 出来设 `flag[0] = false` 放 $P_1$ 进，就算 $P_0$ 立刻回马枪重申，它也会乖乖把 `turn = 1` 让给正在等的 $P_1$（至多让对方先走 1 次，满足**有限等待**）。
- **现代硬件指令重排与内存屏障（Memory Barrier / Acquire-Release）**：现代 CPU 为提速会把写操作暂存写缓冲、让后面的读操作超车先跑！在 Peterson 中，若 $P_0$ 的 `flag[0] = true` 还没刷出写缓冲，后面的读 `flag[1]` 先跑了，看到 `false` 直接冲进临界区；与此同时 $P_1$ 也同样先读到 `flag[0] == false` 冲进临界区——**互斥瞬间崩塌**！同理，`x = 100; ready = true;` 若无同步，读线程看到 `ready == true` 后可能读到旧的 `x == 0`。必须用**内存屏障**或 C11 **`memory_order_release`（写发布：保证前面的写绝不排到后面）+ `memory_order_acquire`（读获取：保证后面的读绝不排到前面）**配对锁住可见顺序。

#### 3. 硬件原子指令（TAS / CAS）、自旋锁与信号量机制（P.22–44）
- **TAS 与 CAS 硬件基石**：硬件总线锁或缓存一致性协议保证一条指令周期内不可打断地完成“读旧值+改新值”：
  - **`test_and_set(&lock)`**：无条件把目标改成 `true` 并返回原来的旧值（谁拿到返回值 `false` 说明抢到了原先空闲的锁）。
  - **`compare_and_swap(&val, expected, new)`**：看当前值是不是我预期的 `expected`，是才改成 `new`，**无论改没改都返回旧值**。既能做锁，又能写无锁原子累加 `do { old = count; } while (CAS(&count, old, old+1) != old);`。
  - *有限等待缺陷*：朴素 `while(TAS(&lock))` 自旋抢锁全凭运气，刚来的线程可能一直抢赢老实排队的线程（违反有限等待）；需加 `waiting[n]` 数组，解锁者按 `(i+1)%n` 环形点名直接把入场券递给下一个等待者（保持 `lock=1` 不放外人插队）才能满足有限等待。
- **自旋锁（Spinlock） vs 阻塞互斥锁（Mutex）**：自旋锁拿不到锁就在原地死循环烧 CPU，省掉了“挂起睡眠 + 唤醒调度”两次上下文切换开销，**仅适合多核且持锁只有几条指令的超短临界区（以及不能睡眠的中断处理程序）**；持锁时间长或单核环境必须用睡眠让出 CPU 的阻塞互斥锁。
- **信号量（Semaphore）底层透视**：
  - **记录型（无忙等阻塞版）实现**：内部含整型 `value` 和等待链表 `list`。
    - `P(S) / wait(S)`：先做 `S->value--`；若减完发现 **`S->value < 0`**，说明没名额了，把自己挂进 `S->list` 并调 `block()` 睡眠让出 CPU。
    - `V(S) / signal(S)`：先做 `S->value++`；若加完发现 **`S->value <= 0`**，说明加之前必然 `< 0`（链表里肯定有人在睡！），从 `S->list` 摘出一个进程调 `wakeup()` 移入就绪队列。
    - 由此直接导出必考公式：当 $S < 0$ 时，**$|S|$ 精确等于正排在 $S$ 等待队列里的阻塞进程数**！
  - **优先级反转与继承**：高优先级 $H$ 等低优先级 $L$ 手里的锁，结果中优先级 $M$ 抢走了 $L$ 的 CPU 一直跑，害得 $H$ 被不如自己的 $M$ 间接卡死（**优先级反转**）；解法是让持锁的 $L$ **临时继承**等待者 $H$ 的高优先级赶紧跑完解锁（**优先级继承协议**）。

#### 4. 管程（Monitor）与条件变量的灵魂辨析（P.45–57）
- **管程设计初衷**：手写信号量极易把 `P/V` 写反或漏写导致死锁。管程像一个“带自动门禁的房间”（面向对象类的雏形）：把共享变量藏成私有，外部只能调用管程公开函数，且**管程自动保证同一时刻房间里最多只有 1 个线程在执行**。
- **条件变量（`condition x`）与信号量的本质差异**：
  - 走进管程房间的线程如果发现业务条件不满足（比如消费者进屋发现盘子是空的），不能在屋里干坐着（否则生产者进不了屋放菜！），于是调用 `x.wait()`——**把自己挂到条件队列 `x` 上睡觉，同时把管程房间钥匙交出来让别人进**！
  - **最核心考点**：条件变量 `x` **自己肚子里没有任何整数计数值**！如果当前根本没人在 `x` 上睡觉，你调 `x.signal()` **就像按门铃屋里没人——声音直接消散，什么也不会留下（空操作）**！而信号量的 `V(S)` 就像往储蓄罐投硬币，没人等也会把 `value` 加 1 存着给后来的人用。
  - **唤醒后的“一山不容二虎”抉择**：通知者 $P$ 叫醒了等待者 $Q$，但房间只能留一个人活跃：
    - **Hoare（Signal-and-Wait）**：好人做到底，$P$ 立刻暂停自己，把房间直接让给刚醒的 $Q$ 跑，等 $Q$ 出门了 $P$ 再接着跑（此时条件 100% 没变）。
    - **Mesa（Signal-and-Continue，POSIX 与 Java 真实采用！）**：$P$ 只是拍一下 $Q$ 喊“起来去门口重排拿锁”，$P$ 自己继续把屋里剩下的活干完出门解锁；等 $Q$ 重新挤进门拿到锁时，中间可能早被小三线程 $R$ 先进屋把菜抢光了！所以 **Mesa 语义下醒来第一件事必须用 `while` 循环重新检查条件，绝不能用 `if`**！

### 第六讲：Lesson 7 — 经典同步实例、系统 API 与死锁核心

#### 1. 三大经典同步模型核心精髓（P.3–23）
1. **有界缓冲区（生产者-消费者）**：1 把互斥锁 `mutex = 1` 护住缓冲区指针 + 2 个计数信号量 `empty = N`（空位数）和 `full = 0`（产品数）管同步等待。铁律：**永远先申请资源信号量（`empty`/`full`），拿到名额后再锁 `mutex`**，否则拿着锁等空位必死锁。
2. **读者-写者问题**：“读读可共享，读写/写写必互斥”。第一类**读者优先**用 `read_count` 记录屋里共有几个读者：**第 1 个进门的读者负责抢写锁 `P(rw_mutex)` 替所有读者把写者挡在门外，最后 1 个出门的读者负责还写锁 `V(rw_mutex)`**，中间进出的读者只用小锁 `mutex` 改一下人数就进屋并行读。代价是只要读者不断流，写者就会活活**饿死**。
3. **哲学家就餐问题**：5 人围桌各需左右两支筷子。若全员同时先拿左筷再等右筷，5 把锁全被占死形成闭环死锁。破局思路就是**打破对称性或限制并发抢锁条件**：① 至多放 4 人上桌（抽屉原理必有一人凑齐一双）；② 奇数号先左后右、偶数号先右后左（消除环形等待）；③ 用管程 `test()` 检查只有左右邻居都没在吃（两支筷子全在）才一次性批给状态 `EATING`（注意：此管程法虽绝无死锁，但若 0 号和 2 号轮流无缝接力吃饭，夹在中间的 1 号仍可能**饥饿**！）。

#### 2. 内核、POSIX 与 Java 同步实战要点（P.24–51）
- **Linux 内核选锁口诀**：单整数增减用无锁 `atomic_t`；**中断处理程序绝不能睡眠阻塞**，只能用**自旋锁**；内核线程长临界区允许睡眠，用**互斥锁/信号量**。Windows 则统一抽象为有信号（Signaled 可通行）/ 无信号（Nonsignaled 需等待）的**分派器对象**。
- **POSIX 信号量**：`sem_open("/name", ...)` 创建**有名信号量**，靠名字天然跨无亲缘进程共享；`sem_init(&s, pshared, val)` 创建**无名信号量**，`pshared=0` 供同进程多线程用，若设 `pshared=1` 跨进程用，**必须把 `sem_t` 变量本身放进 `MAP_SHARED` 共享内存里**（否则 `fork` 后各自写时复制改自己的副本，完全不起同步作用！）。
- **Java 同步两处细节**：① 每个对象只有 1 个等待集（Wait set），生产者消费者混住在一起时若调单次 `notify()` 可能叫醒同行引发假死，故常用 **`notifyAll()` + `while`**；② `java.util.concurrent.Semaphore` 中，`permits.acquire()` **必须写在 `try` 块外面之前**——若写进 `try` 里面，等锁期间被打断抛 `InterruptedException`（根本没拿到许可）却还会进 `finally` 执行 `release()`，就会凭空多造出一个假许可！

#### 3. 死锁核心理论衔接（往年真题必备知识闭环）
- **死锁产生的四个必要条件（同时成立才可能死锁）**：① **互斥**（资源独占）；② **占有并等待**（手里攥着资源 A 不放，同时排队等资源 B）；③ **不可抢占**（别人手里的锁不能强剥夺，只能等他自己释放）；④ **循环等待**（存在 $P_0 \to P_1 \to \dots \to P_0$ 的首尾闭合等待环）。
- **资源分配图判环定律**：如果每类资源**只有 1 个实例**（如每把互斥锁只有 1 把），等待图里**出现环 $\iff$ 必定死锁**；如果某类资源有**多个相同实例**，有环只是必要条件，若环外某个进程用完释放出同类实例就能把环解开，故**有环不一定死锁**！

### （二）今年新版课件（Lesson 2–7）高频命题判断清单（24 道核心陷阱）

#### 【Lesson 2–3：系统调用、内核结构、进程与 IPC】
1. **“应用程序每调用一次 `printf()`，就会立即触发一次 `write()` 系统调用。”**
   - **×**。`printf()` 是标准库函数，数据常先写入**用户态缓冲区**，缓冲刷新（满、换行、`fflush` 或退出）时才调用 `write()`，多次输出可能合并为一次系统调用。
2. **“CPU 从用户态切换到内核态，就意味着发生了进程上下文切换。”**
   - **×**。系统调用或中断进入内核只是**模式切换（Mode Switch）**，内核处理完毕后可直接返回原进程继续运行，不一定切换进程。
3. **“Linux 支持动态加载内核模块（`.ko`），因此 Linux 属于微内核操作系统。”**
   - **×**。Linux 是结合了模块化的**单体内核**；加载后的模块直接运行在**内核地址空间**并通过函数调用交互，而非微内核的用户态独立进程 + 消息传递。
4. **“等待 I/O 的进程在 I/O 操作完成后，会立即由等待态直接进入运行态。”**
   - **×**。I/O 完成后进程只能由**等待态转为就绪态**（进入就绪队列），必须经 CPU 调度器选中分派后才能进入运行态。
5. **“`fork()` 之后，父子进程各自的普通全局变量与继承的已打开文件偏移量都彼此独立、互不影响。”**
   - **×**。虚拟地址空间（普通变量）各自独立（写时复制）；但继承的文件描述符指向同一个内核**打开文件描述**，因此**共享文件读写偏移量（file offset）**。
6. **“父进程尚未调用 `wait()`，此时它创建的正在运行的子进程就是僵尸进程；一旦父进程退出，子进程也会自动终止。”**
   - **×**。只有**已终止**但尚未被父进程 `wait` 回收的子进程才是**僵尸进程**；父进程先退出会使子进程成为**孤儿进程**，被 `init`/`systemd`（PID 1）收养并继续运行。
7. **“当匿名管道（pipe）内已经没有数据时，阻塞模式的 `read()` 一定会立即返回 `0`（EOF）。”**
   - **×**。仅当管道已空**且系统中所有指向该管道的写端描述符（含读进程自身继承未关的写端）均已关闭**时才返回 `0`；只要仍有任一写端打开，`read()` 就会阻塞等待。
8. **“客户端发起 RPC 远程过程调用发生超时，可以断定服务端没有执行该请求，直接重试总是安全的。”**
   - **×**。超时可能是响应报文在网络丢失而**服务端实际已执行完毕**；对非幂等操作（如扣款）直接重试会导致重复执行。

#### 【Lesson 4–5：线程模型、并发与 CPU 调度】
9. **“同一进程内的每个线程拥有各自独立的栈，因此一个线程绝对无法读写同进程另一线程栈上的变量。”**
   - **×**。同进程线程**共享同一个虚拟地址空间**，硬件不隔离各线程栈；若将某线程有效栈变量的地址（指针）传给另一线程，后者可以直接访问。
10. **“在多对一（Many-to-One）线程模型中，即使运行在 8 核处理器上，同一进程的多个用户线程也无法并行执行，且任一线程发起阻塞系统调用会阻塞整个进程。”**
    - **√**。（内核只感知那唯一一个内核线程，同一时刻只能在一个核上调度，阻塞即全组停摆。）
11. **“调用 `pthread_cancel(tid)` 成功返回后，说明目标线程已经终止并释放了所有资源。”**
    - **×**。`pthread_cancel` 仅发出取消请求；若目标线程禁用取消或处于默认的**延迟取消（Deferred）**模式，需运行到**取消点**才退出，且需 `pthread_join` 确认回收。
12. **“在线程池中复用工作线程处理请求时，线程局部存储（TLS）变量会在每个新任务开始时自动清空重置。”**
    - **×**。TLS 生命周期随工作线程而非随任务；工作线程复用时 TLS 会保留上一个任务遗留的旧值，新任务必须显式覆盖或清理。
13. **“某任务在时刻 0 到达并立刻获得 CPU，响应时间为 0，说明它的总等待时间也一定为 0。”**
    - **×**。响应时间只看**首次**获得 CPU 的等待；在抢占式调度（如 RR、SRTF）下，该任务后续可能被多次抢占回就绪队列排队，累计总等待时间可以大于 0。
14. **“在时间片轮转（RR）调度中，每当定时器时间片到期，CPU 一定会切换到另一个进程运行。”**
    - **×**。若时间片到期时就绪队列中**没有其他可运行的同级或更高优先级进程**（仅剩当前进程自己），该进程将继续占用下一个时间片，无需切换。
15. **“四核八线程（开启超线程）的处理器等价于拥有八个独立的物理 CPU 核心。”**
    - **×**。它是 4 个物理核向 OS 呈现 8 个**逻辑 CPU**，利用访存停顿（Memory stall）切换硬件线程；同核两个逻辑线程仍共享执行单元与缓存，不等同于 8 个独立物理核。
16. **“在 Linux 系统中，普通进程的 `nice` 值越大优先级权重越高；单核周期任务的 CPU 利用率超过 $n(2^{1/n}-1)$ 时一定无法用 RM（速率单调）算法调度。”**
    - **×**。两处均错：① Linux `nice` 范围 $-20 \sim 19$，**数值越小权重越高**；② $U \le n(2^{1/n}-1)$ 是 RM 可调度的**充分非必要条件**，超过该界限但 $\le 1$ 时仍可能可调度。

#### 【Lesson 6–7：同步原语、管程与经典同步问题】
17. **“两个线程各自执行一次‘原子读取 `count`，再原子写回旧值加 1’，最终 `count` 一定精确增加 2。”**
    - **×**。单次读和单次写虽各自原子，但**读—改—写整体不原子**；两线程可能同时读到旧值 5，各自写回 6（丢失更新），需用原子读改写指令（如 CAS / `atomic_fetch_add`）或互斥锁。
18. **“两进程严格轮换法（用 `turn` 交替进入）能保证互斥，因此是临界区问题的合格解决方案。”**
    - **×**。严格轮换虽然满足互斥，但当轮到的进程留在剩余区不想进临界区时，另一想进入的进程也会被挡在外面，**违反了‘前进（Progress）’准则**。
19. **“Peterson 算法在理想顺序一致模型下满足互斥、前进和有限等待，但在现代多核处理器上若不加内存屏障可能因指令重排而破坏互斥。”**
    - **√**。（若 `flag[i] = true` 与后续写入/读取发生乱序可见，两个进程可能同时观察到对方 `flag` 为 `false` 而双双进入临界区。）
20. **“直接用 `while (test_and_set(&lock)) ;` 或朴素 CAS 自旋实现的互斥锁，能同时满足临界区的互斥、前进和有限等待三项要求。”**
    - **×**。满足互斥和前进，但**违反有限等待（Bounded waiting）**——锁释放时新到来的线程可能反复抢先，导致某个等待线程饥饿。
21. **“单核处理器上保护较长临界区时，使用忙等自旋锁（Spinlock）比睡眠阻塞互斥锁更高效。”**
    - **×**。单核上自旋线程占着唯一 CPU 空转期间，持有锁的线程根本没有机会上 CPU 执行解锁；自旋锁仅适用于**多核系统且持锁时间极短**（或不可睡眠的中断处理程序）。
22. **“在 POSIX 条件变量中，为什么必须用 `while` 而不是 `if` 检查条件？因为通知线程调用 `pthread_cond_signal` 后等待线程立即直接运行且状态不可能改变。”**
    - **×**。POSIX 采用 **Signal-and-Continue** 语义：通知者仍持锁，等待者在重新竞争获得 `mutex` 前，共享状态可能已被其他线程抢先改写，且可能存在**虚假唤醒**，故必须用 `while` 重查。
23. **“哲学家就餐问题的管程方案（仅当左右两根筷子都可用时才置 `EATING`）彻底消除了死锁，因此保证了每位哲学家都能有限等待。”**
    - **×**。消除死锁不等于消除**饥饿**；若某哲学家的左右两位邻居交替进餐，每次一方放下筷子时另一方仍在进餐，中间这位哲学家仍可能长期饥饿。
24. **“在第一类读者-写者问题（读者优先）中，每个进入的读者都必须执行一次 `wait(rw_mutex)` 以防止写者写入。”**
    - **×**。只有**第一个进入的读者**（`read_count == 1`）执行 `wait(rw_mutex)`，**最后一个退出的读者**（`read_count == 0`）执行 `signal(rw_mutex)`；若每个读者都申请 `rw_mutex` 会导致读者之间相互阻塞，无法并发读取。

#### 第 2 组：同一进程内多线程“共享资源 vs 私有资源”（L4 P.4–5，多选最爱考！）
- **全进程线程共享**：**代码段（`text`）**、**全局/静态数据段（`data`/`bss`）**、**堆（`heap`）**、**虚拟地址空间**、**已打开文件描述符表（open files）**、**信号处置表（signal handlers）**、进程当前工作目录与用户权限、进程组/TGID。
- **每个线程各自私有**：**程序计数器（`PC`）**、**CPU 寄存器集合（含栈指针 SP）**、**栈（`stack`，含用户栈与内核栈）**、**线程局部存储（`TLS`）**、**线程号（`TID`）与调度状态/优先级**、**信号屏蔽字（`signal mask`）**。

#### 第 3 组：四种线程映射模型与底层结构对比（L4 P.19–22, P.57–60）

| 模型 / 平台 | 映射特征 | 一个线程阻塞系统调用时 | 多核并行能力 | 典型实例与课件细节 |
| :--- | :--- | :--- | :--- | :--- |
| **多对一 (Many-to-One)** | 多个用户线程 $\to$ 1 个内核线程 | **整个进程全部阻塞** | **不能多核并行** | GNU Pth（纯用户态库切换极快） |
| **一对一 (One-to-One)** | 1 个用户线程 $\to$ 1 个内核线程 | 其他线程仍可正常运行 | **支持真正并行** | **Linux NPTL**、**常规 Windows 线程**（创建过多耗内核资源） |
| **多对多 (Many-to-Many)** | $M$ 个用户线程复用 $N$ 个内核线程 | 运行时可将其他协程/虚拟线程切到可用内核线程 | **支持并行且轻量** | **Go goroutine**、**Java 21 虚拟线程** |
| **双层模型 (Two-Level)** | 多对多基础上允许单独绑定某个内核线程/LWP | 视是否绑定及 LWP 池而定 | 支持并行 | Solaris 8（注：LWP 是连接用户与内核线程的执行实体） |

- *底层补充*：Windows 线程结构含内核态 **`ETHREAD`、`KTHREAD`（含内核栈）** 与用户态 **`TEB`（含用户栈、TLS）**；Linux 不区分进程与线程结构体，统一用 **`task_struct`**，通过 `clone()` 传递 `CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_SIGHAND | CLONE_THREAD` 共享资源。

#### 第 4 组：五种内核结构与 API / ABI 辨析（L2 P.39–51）
- **API vs ABI**：**API** 是**源代码级**编程接口（管重新编译能否通过）；**ABI** 是**二进制级**接口（管寄存器传参、栈布局、系统调用约定、ELF/PE/Mach-O 格式，决定编译好的二进制能否直接运行）。
- **单体内核（Linux/传统 UNIX）**：核心子系统同处**内核地址空间**直接函数调用，效率高但故障隔离弱；Linux 可加载模块仍在内核态运行，属于**模块化单体内核**。
- **微内核（Mach/QNX/seL4）**：仅 **IPC + 基本内存 + CPU 调度**留在内核，文件系统/驱动作为**用户态进程**靠 **消息传递** 通信，隔离强但跨态切换与 IPC 开销大。
- **混合内核**：**macOS/iOS XNU**（同一内核空间融合 Mach + BSD + I/O Kit）；**Android**（Linux 内核 + **Bionic** C 库 + HAL + **ART** 运行时，非 glibc 桌面环境）。

#### 第 5 组：IPC 进程间通信对比（L3 P.35–66）
- **共享内存 vs 消息传递**：共享内存（`shm_open` + `ftruncate` + `mmap(MAP_SHARED)`）建立映射后读写最快、无需每次进内核，但**必须自行加同步互斥**，且**内部不能存进程本地虚拟地址指针（应存相对偏移量）**；消息传递由内核收发（适合小数据或跨网络），注意有缓冲时 `send/write` 返回仅代表写入本机内核缓冲。
- **匿名管道 `pipe(fd)` vs 命名管道 `FIFO` vs TCP Socket**：
  - `pipe(fd)`：**`fd[0]` 读端、`fd[1]` 写端**，单向字节流，用于父子亲缘进程。
  - `FIFO`：有文件系统路径名，可用于无亲缘本机进程，**数据在内核内存流转不落盘**。
  - `TCP Socket`：有序字节流（**无内置消息边界**，需应用层自定义长度或分隔符）；服务端 `accept()` 返回**新的已连接 socket**，原监听 socket 继续监听。

#### 第 6 组：八大 CPU 调度算法核心特征速查（L5 P.15–44）

| 算法 | 是否抢占 | 核心选择依据 | 突出优点 | 核心缺陷 / 专属考点 |
| :--- | :---: | :--- | :--- | :--- |
| **FCFS** | 非抢占 | 先进入就绪队列者先运行 | 实现最简单、零额外抢占切换开销 | 平均等待长，出现**护航效应（Convoy effect）** |
| **SJF** | 非抢占 | **下一段 CPU burst** 最短者 | 同时到达时**平均等待时间理论最优** | 难以精确预知下一段 CPU 长度；长任务可能**饥饿** |
| **SRTF** | **抢占** | **剩余 CPU burst** 最短者 | 分批到达时平均等待/周转时间更短 | 需预测长度、切换开销多、长任务可能**饥饿** |
| **优先级** | 均可 | 优先级最高者（看清大小方向！） | 区分任务轻重缓急 | 低优先级任务可能**饥饿** $\rightarrow$ 用**老化（Aging）**解决 |
| **RR** | **抢占** | FIFO + 固定时间片 $q$ 轮转 | **响应时间有上界** $(n-1)q$，无饥饿 | 平均等待常长于 SJF；$q$ 太大退化为 FCFS，$q$ 太小切换开销剧增 |
| **MLQ** | 队间可抢占 | 按任务性质固定入不同队列 | 区分前台交互（RR）与后台批处理（FCFS） | **进程固定在原队列不移动**，不够灵活 |
| **MLFQ** | **抢占** | 按运行消耗时间片动态升降队列 | **无需预知长度**即可优待短/交互任务 | 参数设计最复杂（需配老化升级防低队列饥饿） |
| **HRRN** *(往年卷)* | 非抢占 | 响应比 $R_p = \frac{W + B}{B}$ 最高者 | 兼顾短作业与长作业等待时间，防饥饿 | 每次调度需计算所有就绪进程响应比 |

#### 第 7 组：临界区准则与同步工具达标对照（L6 P.8–57）
- **临界区三准则**：① **互斥**（最多 1 人在临界区）；② **前进**（空闲有人申时，剩余区进程不得阻拦且不能无限推迟选择）；③ **有限等待**（发出申请后被他人抢先的次数有上界）。
  - *严格轮换*：满足互斥，**违反前进**。
  - *Peterson 算法*：双进程顺序一致模型下**三项全满足**（等待上界 1 次）；现代乱序多核需加**内存屏障 / Acquire-Release**。
  - *简单 TAS / 简单 CAS 自旋锁*：满足互斥与前进，**违反有限等待**；带 `waiting[n]` 环形交接的改进版 CAS 锁**三项全满足**（等待上界 $n-1$ 次）。
- **互斥量（Mutex） vs 信号量（Semaphore） vs 条件变量（Condition Variable）**：
  - **互斥量**：有明确**持有者**概念，必须**同一线程加锁、同一线程解锁**，保护临界区多字段一致性。
  - **信号量**：维护整型计数值，可由**一个线程 `P/wait`，另一个线程 `V/signal`**；既能控多实例并发名额（初值 $N$），又能做前驱同步（初值 $0$）。
  - **条件变量**：**本身不保存计数状态**（无人等时 `signal` 为空操作），必须配合共享状态变量与互斥锁使用。

### （三）选择题必背 4 大“小计算”秒杀公式

1. **Amdahl 定律（L4 P.13–15，2020 真题）**
   - 设固定任务中**串行部分占比为 $S$**（$0 \le S \le 1$），并行占比为 $1 - S$，$N$ 个 CPU 核的**理想加速比**：
     $$\text{Speedup}(N) = \frac{1}{S + \frac{1 - S}{N}}, \qquad \lim_{N \to \infty} \text{Speedup}(N) = \frac{1}{S}$$
   - *课件原题速算*：
     - $S = 25\%,\ N = 2 \implies \frac{1}{0.25 + 0.75/2} = \frac{1}{0.625} = \mathbf{1.6}$；$N \to \infty$ 上限为 $\mathbf{4}$。
     - $S = 20\%,\ N = 4 \implies \frac{1}{0.20 + 0.80/4} = \frac{1}{0.40} = \mathbf{2.5}$；$N \to \infty$ 上限为 $\mathbf{5}$。

2. **下一段 CPU Burst 指数平均预测（L5 P.24–26）**
   $$\tau_{n+1} = \alpha t_n + (1 - \alpha)\tau_n \quad (0 \le \alpha \le 1)$$
   - 其中 $t_n$ 为刚结束的**实际** CPU 长度，$\tau_n$ 为上次**预测**长度。
   - *课件例题*：$\alpha = 0.5,\ \tau_0 = 10,\ t_0 = 6 \implies \tau_1 = 0.5 \times 6 + 0.5 \times 10 = \mathbf{8}$。

3. **单核实时周期任务可调度性判据（L5 P.54–56，独立可抢占且截止期 $D_i = T_i$）**
   - 总 CPU 利用率：$U = \sum_{i=1}^{n} \frac{C_i}{T_i}$（$C_i$ 为执行时间，$T_i$ 为周期）。
   - **EDF（最早截止时间优先，动态优先级）充要条件**：$U \le 1$。
   - **RM（速率单调，周期越短静态优先级越高）充分条件**：$U \le n\left(2^{1/n} - 1\right)$（记住特殊值：$n=2$ 时约 **$0.828$**，$n=3$ 时约 **$0.780$**，$n \to \infty$ 趋近 $\ln 2 \approx \mathbf{0.693}$）。
   - *课件例题*：$A(C=1, T=4)$，$B(C=2, T=5) \implies U = \frac{1}{4} + \frac{2}{5} = \mathbf{0.65} \le 0.828 \le 1$，RM 与 EDF 均可调度。

4. **Little 定律（L5 P.70）与记录型信号量计数（L6 P.40–42，2018/2019/2020 真题）**
   - **Little 定律**：稳态队列平均等待人数 $L_q = \lambda W_q$（课件：每秒到达 $\lambda = 7$ 个，平均排队 $L_q = 14$ 个 $\implies$ 平均等待时间 $W_q = 14 / 7 = \mathbf{2\text{ 秒}}$）。
   - **记录型信号量 $S$（初值 $S_0$）**：
     - $S > 0$：表示当前**尚余 $S$ 个可用资源许可**，等待进程数为 $0$；
     - $S = 0$：表示资源**恰好分完**，且等待进程数为 $0$；
     - $S < 0$：表示资源已用尽，且当前正有 **$|S|$ 个进程阻塞在该信号量的等待队列中**！

> **简答与辨析满分三步法**（2018/2019/2023 均设“辨析题”）：
> 1. **先下定义**：分别用一句话写清概念 A 是什么、概念 B 是什么（*2023 年 96 分高分卷唯一扣分处就是把“管程”错答成“一块共享内存空间”，务必背准管程三要素！*）；

### （一）往年真题高频简答 / 辨析题标准答案（10 道母题）

#### 1. 比较核心态（内核态）与用户态；区分模式切换与上下文切换 *(2018 真题 + L2 P.19 / L3 P.18–20)*
- **核心态（Kernel Mode）**：操作系统内核运行时的受保护特权状态，可执行全部指令（含特权指令）并访问系统全部内存与硬件资源。
- **用户态（User Mode）**：普通用户进程执行时的非特权状态，只能执行非特权指令、访问本进程受限的用户虚拟地址空间。
- **转换与切换区别**：用户态程序必须通过**系统调用（访管指令/Trap）、外设中断或异常**才能受控进入核心态——这称为**模式切换（Mode Switch）**，执行主体仍是当前进程/线程，处理完可直接返回原线程；而**上下文切换（Context Switch）**是 CPU 从一个进程/线程切换到另一个进程/线程，需将旧任务寄存器与 PC 保存进 PCB、恢复新任务 PCB（跨进程还需切换页表并承受 **Cache 失效与 TLB 刷新**的间接开销）。

#### 2. 描述进程（Process）与线程（Thread）的关系与区别 *(2018 真题 + L3 P.13 / L4 P.4–8, P.62)*
- **定位关系**：在引入内核级线程的现代操作系统中，**进程是资源分配与隔离保护的基本单位**，而**线程是 CPU 调度和分派的基本执行单位**（对于传统单线程进程，进程既是资源单位也是调度单位）。
- **核心区别**：
  1. **地址空间与资源**：不同进程拥有独立的虚拟地址空间和系统资源；同一进程内的多个线程**共享**进程的代码段、全局数据、堆和打开文件表，仅**私有**各自的 `PC`、寄存器集合、栈（Stack）与 `TLS`。
  2. **并发开销**：进程创建、销毁、跨进程 IPC 和切换地址空间开销大；同进程线程创建与切换无需更换地址空间，开销显著更小。
  3. **隔离与健壮性**：进程间有硬件内存隔离，一个进程崩溃不影响其他进程（如 Chrome 多进程标签页架构）；同进程内一个线程非法写内存或崩溃会导致整个进程终止。

#### 3. 比较并发（Concurrent）与并行（Parallel）；区分数据并行与任务并行 *(2018 真题 + L4 P.9–12)*
- **并发（Concurrency）**：在**同一时间间隔内**有多个任务交替推进（宏观上同时，微观上可在单核 CPU 上通过时间片快速切换交替执行）。
- **并行（Parallelism）**：在**同一时刻（瞬间）**有多个任务在多个物理执行单元（多核/多处理器）上真正同时执行（微观上同时，必须有多执行硬件支持）。
- **两种并行模式**：**数据并行**是将同一数据集切分成多个子集，各核对不同数据子集执行**相同操作**（如分块滤镜）；**任务并行**是将不同功能模块分配到不同核，执行**不同操作**（如解码、渲染、编码流水线）。

#### 4. 辨析进程间的同步（Synchronization）与互斥（Mutual Exclusion），并解释为何多处理器不能靠关中断实现同步原语 *(2019、2023 简答+综合双考！)*
- **互斥**：指多个并发进程访问同一临界资源时具有排他性，**同一时刻最多只允许一个进程进入临界区**，但不限制谁先谁后的访问次序（无序排他）。
- **同步**：指并发进程因合作而产生的**直接制约关系**，要求各进程的操作必须按特定**先后顺序**推进（有序协调）。
- **举例联系（生产者-消费者）**：多个生产者和消费者不能同时修改缓冲区及读写指针，这属于**互斥**；当缓冲区为空时消费者必须等生产者先放入产品才能取、满时生产者必须等消费者先取走才能放，这属于**同步**。
- **为何多处理器（SMP）不能靠关中断实现同步原语**：关中断指令只能屏蔽**执行该指令的当前单个 CPU 核**的中断；其他 CPU 核并不受影响，运行在其他核上的线程依然可以并行读写同一块共享内存中的信号量或临界资源。若通过核间通信强制关闭所有 CPU 核的中断，则通信代价极高、严重损害多核并行效率并阻塞系统时钟与外部响应，因此多核必须依赖硬件原子指令（如 `TAS`、`CAS`）与锁机制。

#### 5. 辨析进程（Process）与管程（Monitor） *(2019、2023 两考！易丢分题)*
- **定义**：**进程**是程序的一次动态执行过程，是操作系统中主动申请资源和参与并发执行的**活动实体**；**管程**是一种高级同步抽象数据类型（ADT / 被动语法模块），将**私有共享数据结构**、**对该数据的一组公开操作过程**以及**初始化代码与条件变量同步规则**封装在一起。
- **区别与联系**：
  1. **主动 vs 被动**：进程是主动运行的执行流；管程本身不主动运行，是供多个并发进程调用的受保护共享资源管理模块。
  2. **互斥机制**：管程由编译器/运行时自动保证**任一时刻最多只有一个进程在管程内部活跃执行**（其余调用者在入口队列等待）；若管程内进程发现条件不满足调用 `x.wait()`，会挂起并**自动让出管程互斥权**。
  3. **协作联系**：多个并发进程（如生产者进程和消费者进程）通过调用同一个“有界缓冲区管程”的 `insert()` / `remove()` 过程实现安全通信与同步。

#### 6. 辨析互斥量（Mutex）与信号量（Semaphore） *(2019 真题)*
1. **设计语义不同**：互斥量专用于保护临界区的**独占互斥访问**；信号量通过整型许可计数，既能控制多实例资源的并发访问上限，又能协调线程间的**先后同步顺序**。
2. **取值范围不同**：互斥量只有未加锁/已加锁两种状态（对应 `0/1`）；计数信号量可取任意非负初值 $N$（阻塞实现下等待时可为负值，$|S|$ 表等待人数）。
3. **所有权（加解锁主体）不同**：互斥量具有严格的**持有者（Owner）**概念，**必须由加锁的同一个线程负责解锁**；而信号量没有持有者限制，完全可以**由线程 A 执行 `P(wait)`，由线程 B 执行 `V(signal)`**（如生产者 `V(full)` 唤醒消费者 `P(full)`）。

#### 7. 比较多级队列（MLQ）、多级反馈队列（MLFQ）与先来先服务（FCFS），并举例说明 MLFQ 优点 *(2018、2019、2023 三考 + L5 P.38–44)*
- **FCFS**：单一就绪队列，严格按到达先后非抢占执行到底；长任务排在队首会引发**护航效应**，拖慢短交互任务响应。
- **多级队列（MLQ）**：按进程固定属性（如交互、批处理）划分为多个队列，进程**一旦入队终身固定不跨队移动**。
- **多级反馈队列（MLFQ）原理与 30ms 实例（L5 P.43–44）**：设置多个优先级递减而时间片递增的就绪队列（如课件实例：`Q0` 用 RR $8\text{ ms}$，`Q1` 用 RR $16\text{ ms}$，`Q2` 用 FCFS），**允许进程根据运行行为在队列间动态升降**：
  - *短交互作业*：进入最高级 `Q0`，在 $8\text{ ms}$ 内迅速完成并响应终端用户；
  - *30ms 长计算作业*：无需事先知道长度，先在 `Q0` 跑 $8\text{ ms}$（快速获得首次响应），未完降入 `Q1` 跑 $16\text{ ms}$，仍剩 $6\text{ ms}$ 降入 `Q2` 按 FCFS 跑完最后 $6\text{ ms}$；
  - *防饥饿机制*：若最低级队列中的进程长期得不到 CPU，通过**老化（Aging）/ 周期性优先级提升**将其移回高优先级队列，兼顾短响应、高周转且不饥饿。

#### 8. 辨析死锁（Deadlock）与饥饿（Starvation） *(2019、2023 两考 + L6 P.44 / L7 P.15, P.23)*
- **死锁**：一组并发进程各自占有部分资源，同时又循环等待组内其他进程所持有的资源，在无外力干涉下**组内所有进程都永久阻塞、无法推进**的现象。
- **饥饿（无限期阻塞）**：系统整体仍在正常推进（没有全员卡死），但**某一个或少数进程因调度或分配策略不公，长期得不到所需资源或 CPU 而迟迟无法执行**的现象。
- **联系与实例**：死锁中的进程必然处于无限等待状态，但**饥饿不一定发生死锁**！例如在**第一类读者-写者问题（读者优先）**中，若新读者源源不断在旧读者离开前进入（`read_count > 0` 持续成立），系统一直在正常读取（无死锁），但等待写锁的写者会一直等下去，发生**饥饿**。

#### 9. 列出三态（Ready / Running / Waiting）全部合法转换及条件；如何减少上下文切换开销？SRTF 与 FCFS 指标比较 *(2020 真题三连问)*
- **三态全部 4 条合法转换（注意：绝无 `Waiting -> Running` 和 `Ready -> Waiting`！）**：
  1. `Ready` $\to$ `Running`：CPU 调度程序从就绪队列选中该线程并分派 CPU；
  2. `Running` $\to$ `Ready`：时间片用完（时钟中断）或被更高优先级/更短剩余时间的就绪线程抢占；
  3. `Running` $\to$ `Waiting`：运行线程主动请求尚未就绪的事件（如发起阻塞 I/O、申请被占用的锁/信号量、`waitpid`）；
  4. `Waiting` $\to$ `Ready`：所等待的外部事件发生（如 I/O 完成中断、其他线程释放锁并发出 `signal`/`wakeup`）。
- **减少上下文切换开销的 3 种方法**：① 控制活跃内核线程数量（采用**有界线程池**或异步**事件驱动 I/O** 复用替代“每连接一线程”）；② 减少跨核/内核态调度切换（采用协程/用户态调度如多对多 goroutine，保持 CPU 亲和性）；③ 选用切换频率更低的调度参数或策略（适当调大 RR 时间片 $q$，或批处理用 FCFS）。
- **SRTF 与 FCFS 指标优劣**：在已知执行长度且忽略切换开销下，**SRTF 在平均等待时间与平均周转时间上最优**；而 **FCFS 相比 RR 没有时间片抢占，节省了频繁上下文切换的开销，有利于整体吞吐量**。

#### 10. 比较死锁预防（Prevention）与死锁避免（Avoidance） *(2018 真题)*
- **死锁预防**：通过制定静态资源申请限制规则，直接**破坏死锁产生的四个必要条件之一**（① 互斥、② 占有并等待、③ 不可抢占、④ 循环等待——工程上最常用**规定全局统一的加锁编号递增顺序**破坏循环等待）。优点是实现简单、无需运行时复杂计算；缺点是限制过于严格，资源利用率和并发度较低。
- **死锁避免**：允许前三个必要条件存在，要求事先声明最大资源需求，在运行时每次分配资源前**动态检查分配后系统是否仍处于“安全状态”**（单实例资源用**资源分配图环检测**，多实例资源用**银行家算法**寻找安全序列）。优点是资源利用率更高；缺点是需要预知最大需求且动态计算开销大。

### （二）今年新版课件（Lesson 2–7）高概率新增简答题精编（8 题）

1. **描述一次 `read(fd, buf, count)` 系统调用的过程，并说明内核为什么不能直接信任用户传入的指针参数？（L2 P.19–24, P.59）**
   - *过程*：应用调用库封装函数准备好系统调用号与参数（寄存器传参），执行受控陷阱指令（`syscall`）从用户态切入内核态；内核检查调用号并查系统调用表分派到对应处理函数，校验参数后读取数据（若未就绪则阻塞等待 I/O），完成后将数据拷回用户 `buf`，返回实际读取字节数（`>0` 字节数，`0` 表 EOF，`-1` 表出错）并恢复用户态。
   - *为何必须校验用户指针*：用户程序可能有 Bug 或恶意构造——指针可能是空指针/未映射非法地址（引发内核崩溃）、只读内存（写回违规）、长度越界/整数溢出，甚至**伪造指向内核空间的地址企图诱导拥有高特权的内核泄露或覆写篡改内核关键数据**。

2. **什么是操作系统的“机制与策略分离”原则？请举例说明。（L2 P.42）**
   - **机制（Mechanism）**解决“**如何做（How）**”的底层技术手段（如时钟定时器中断、保存与恢复 PCB 上下文）；**策略（Policy）**解决“**选谁做、何时做（What/Who/When）**”的决策规则（如采用 RR 还是优先级算法、时间片定多大）。两者分离使得更换或调优调度策略时无需重写底层切换机制，提高系统灵活性与可维护性。

3. **从按下电源到出现命令行 Shell 经过哪些主要引导阶段？两台相同 CPU 的机器为何可能无法运行同一可执行文件？（L2 P.39, P.54–55, P.59）**
   - *引导 6 阶段*：① **固件（BIOS/UEFI）**上电自检并选择启动项 $\to$ ② **引导加载程序（Bootloader 如 GRUB）**加载内核映像与 `initramfs` $\to$ ③ **内核初始化**内存、中断、调度与驱动 $\to$ ④ **挂载根文件系统** $\to$ ⑤ 启动首个用户态进程 **`init`（PID 1，如 `systemd`）** $\to$ ⑥ 启动后台服务与登录会话，运行用户态 **Shell**。
   - *同 CPU 不能直接运行同一二进制的原因*：除指令集（ISA）外，还可能因**可执行文件格式不同**（ELF vs PE vs Mach-O）、**系统调用号与内核接口不同**、**ABI 调用约定/结构体对齐不同**，或**缺失兼容版本的动态共享库（如 glibc vs Bionic）**而无法装载运行。

4. **多线程程序调用 `fork()` 和 `exec()` 有何特殊语义与风险？（L4 P.48）**
   - POSIX 中多线程进程调用 `fork()` 时，**子进程只复制保留调用 `fork()` 的那一个线程**，其他线程在子进程中消失；但整个地址空间（含**其他线程当时正持有的互斥锁加锁状态**）会被原样复制到子进程，若子进程不立即 `exec()` 而尝试获取那些无人解锁的互斥锁就会**死锁**！调用 `exec()` 成功后则会替换整个进程映像并终止所有其他线程。

5. **无同步时“写线程 `x=100; flag=true;`，读线程 `while(!flag); print(x);`”为何可能打印 `0`？如何修复？（L6 P.17–21）**
   - *原因*：现代编译器和乱序执行多核 CPU 会对无依赖读写进行**指令重排**或写缓冲延迟刷新，导致读线程所在核先观察到 `flag == true` 跳出循环，却读到旧缓存值 `x == 0`。
   - *修复*：在写线程 `x=100` 与 `flag=true` 之间插入**写内存屏障**（或用 `memory_order_release` 原子写 `flag`），并在读线程用**读内存屏障**（或 `memory_order_acquire` 原子读 `flag`），强制保证 `x=100` 对读线程先可见。

6. **自旋锁（Spinlock）与阻塞互斥锁（Blocking Mutex）各自适用什么场景？（L6 P.33, L7 P.27）**
   - **自旋锁**在等待时留在 CPU 上忙等轮询，省去了线程睡眠与唤醒的两次上下文切换开销，但空耗 CPU，仅适用于**多核处理器且持锁临界区极短**的场景，或**禁止睡眠的中断处理程序**。
   - **阻塞互斥锁**在获取失败时将线程挂起睡眠并让出 CPU，适用于**持锁时间较长**或**单核处理器**（单核自旋会饿死持锁线程使其无法上 CPU 解锁）。

7. **管程条件变量的 `Signal-and-Wait` 与 `Signal-and-Continue` 有何区别？POSIX `pthread_cond_wait(&cond, &mutex)` 为何必须传 `mutex` 且用 `while` 循环？（L6 P.50, L7 P.34–35）**
   - *两种语义*：`Signal-and-Wait`（Hoare）下通知者立即暂停把管程让给被唤醒者先运行；`Signal-and-Continue`（Mesa / POSIX / Java）下通知者继续持锁执行，直到它退出解锁后被唤醒者再去竞争锁。
   - *为何传 `mutex`*：① 保护共享条件变量的读写互斥；② 内核**原子地执行“释放 `mutex` 并挂入等待队列”**，防止在检查条件与睡眠之间的空隙发生 `signal` 造成**丢失唤醒（Lost Wakeup）**，并在返回前自动重新拿回 `mutex`。
   - *为何必须用 `while`*：在 POSIX `Signal-and-Continue` 下，从发出 `signal` 到等待线程真正重新抢到 `mutex` 之间，**共享条件可能已被其他插队线程再次改写为不成立**，且系统允许偶发**虚假唤醒**，必须用 `while` 重新验证条件。

8. **第一类读者-写者问题（读者优先）中，`mutex` 和 `rw_mutex` 各起什么作用？为何只在首尾读者操作 `rw_mutex`？（L7 P.12–15, P.53）**
   - `mutex` 保护共享计数器 `read_count` 的互斥增减；`rw_mutex` 用于实现**整个活跃读者组与写者之间、以及写者与写者之间的互斥**。
   - 因为多个读者只读不写，允许同时并发访问：第一个进入的读者（`read_count == 1`）执行 `wait(rw_mutex)` 替全体读者挡住写者，随后释放 `mutex` 让后续读者无需等待直接并行执行 `read_data()`；最后一个离开的读者（`read_count == 0`）执行 `signal(rw_mutex)` 归还写权限。

### 题型一【100% 必考】：CPU 调度甘特图绘制与等待 / 周转 / 响应时间计算

#### 0. 底层算法精讲：事件驱动时间轴模拟法（不管怎么改条件都能一次画对！）

任何 CPU 调度题，本质上都是在模拟一个随时间 $t$ 推进的状态机。永远记住铁律：**在时刻 $t$ 做选择时，你的视野里只能看到“已经到达（$A_i \le t$）且尚未跑完”的就绪进程，绝不能提前偷看 $A_i > t$ 还没出生的未来进程！**

##### （1）七种调度算法一步步怎么跑？（核心算法逻辑拆解）
1. **FCFS（先来先服务 · 非抢占）**：
   - **算法**：就绪队列就是普通先入先出（FIFO）队列。谁先到达谁先上 CPU，一旦上去就一口气把自己的 $B_i$ 全跑完才下来。
   - *变式防坑*：若前一个进程在 $t=3$ 跑完，下一个进程 $A=5$ 才到达，则 `[3, 5]` 这段 CPU 空转，甘特图要诚实画出 `3 | Idle | 5`。
2. **非抢占 SJF vs 抢占式 SRTF（最容易混的一对，盯紧“什么时候重新选人”！）**：
   - **非抢占 SJF 算法**：**只有当前进程彻底跑完下台的那一瞬间**，才看一眼此刻已经排在就绪队列里的进程（$A_i \le t$），挑**需要时间 $B_i$ 最小**的上去跑完（若长度并列，按先到达者优先）。哪怕它刚跑了 $1\text{ ms}$，外面来了一个超短进程，也绝不中途换人！
   - **抢占式 SRTF（最短剩余时间优先）算法**：除了进程跑完时刻外，**每当有一个新进程在时刻 $t = A_{\text{new}}$ 到达时，必须立刻暂停比大小**！
     - 先算当前台上进程还剩多少没跑：$\text{Rem}_{\text{cur}} = \text{原剩余} - \text{刚跑掉的时长}$；
     - 拿新来进程的 $B_{\text{new}}$ 跟 $\text{Rem}_{\text{cur}}$ 比：
       - 若 **$B_{\text{new}} < \text{Rem}_{\text{cur}}$（严格小于！）** $\implies$ **立即抢占**！原进程带着剩余时间 $\text{Rem}_{\text{cur}}$ 退回就绪队列，新进程马上接管 CPU；
       - 若 **$B_{\text{new}} \ge \text{Rem}_{\text{cur}}$（注意相等不抢占，保持原进程先来先服务）** $\implies$ 新进程乖乖进就绪队列等，原进程继续跑。
3. **优先级调度（非抢占 vs 抢占，及同级处理）**：
   - **算法完全同构于 SJF / SRTF**，只是把比较标尺从“谁剩余更短”换成“谁优先级更高”！
   - *考场第一眼必查*：题目写的是**“小数字高优先级”**（如 `1 > 2 > 3`）还是**“大数字高优先级”**（如 `5 > 4 > 3`）！
   - 若出现两个同为最高优先级的就绪进程：题目未特别声明时按 **FCFS（到达早/编号小者先跑）**；若题目声明“同优先级采用 RR”，则仅在这几个并列最高级进程之间按时间片 $q$ 轮转，跑完它们再轮下一优先级（见课件 L5 P.35）。
4. **时间片轮转 RR（“草稿纸显式队列法”——彻底攻克分批到达难题！）**：
   - 全在 `t=0` 到达时按圈轮转谁都会；一旦考**分批到达**（如 $A = 0, 1, 2$），心算极易把队尾顺序搞反！请在草稿纸上画一条真实的队列 `Queue`，严格按以下 4 步循环执行：
     - **Step 1**：弹出队首进程 $P$，它本次实际跑的时长为 $\Delta t = \min(\text{Rem}_P,\ q)$，时钟从 $t$ 走到 $t' = t + \Delta t$（*注意：如果它只剩 $1\text{ ms}$ 而时间片 $q=4\text{ ms}$，它跑 $1\text{ ms}$ 就提前完工下台，时钟只加 $1$ 而不是加 $4$！*）。
     - **Step 2（入队先后黄金法则）**：先检查在刚刚这段 $(t,\ t']$ 期间有没有新到达的进程——**让所有新到达的进程按到达先后先排入 `Queue` 队尾**！
     - **Step 3**：更新 $\text{Rem}_P \leftarrow \text{Rem}_P - \Delta t$。若 $\text{Rem}_P == 0$，记录完成时刻 $C_P = t'$；若 $\text{Rem}_P > 0$（没跑完），**最后才把刚退下来的 $P$ 追加到 `Queue` 最末尾**！
     - **Step 4**：若此时 `Queue` 里只剩它自己一个人，下个时间片继续跑它自己。
     - *举个 30 秒小例子验证*：$A(0, 5\text{ms}), B(1, 3\text{ms}), C(2, 1\text{ms})$，$q=2$：
       - `t=0`：`Queue=[A]` $\to$ `A` 跑 `[0,2]`（剩 3）；期间 `t=1` 的 `B`、`t=2` 的 `C` **先入队**，未完的 `A` **后入队** $\implies$ `Queue=[B, C, A]`！
       - `t=2`：弹 `B` 跑 `[2,4]`（剩 1），无新到，`B` 排队尾 $\implies$ `Queue=[C, A, B]`；
       - `t=4`：弹 `C` 只剩 $1 < 2$，只跑 `[4,5]` 完工！$\implies$ `Queue=[A, B]`；后续 `[5,7]A -> [7,8]B(完) -> [8,9]A(完)`。只要画队列，100% 零失误！
5. **多级反馈队列 MLFQ 与高响应比 HRRN 模拟法**：
   - **MLFQ**：画三级队列 $Q_0(q_0), Q_1(q_1), Q_2(\text{FCFS})$。新进程进 $Q_0$；高队列绝对压制低队列（$Q_0$ 空才轮到 $Q_1$；跑 $Q_1/Q_2$ 中途若新来进程进 $Q_0$ 则抢占）；在 $Q_k$ 耗尽配额 $q_k$ 仍未结束就降入 $Q_{k+1}$ 队尾。
   - **HRRN**：非抢占，每次在时刻 $t$ 挑人时，现场给每个已到达进程算分 $R_p = 1 + \frac{t - A_i}{B_i}$，分最高者跑到底。

##### （2）为什么时间公式这么算？（吃透本质，有 I/O 也不怕）
把一个进程从到达时刻 $A$ 到彻底完成时刻 $C$ 的生命总长度（即**周转时间 $T_{\text{turn}} = C - A$**）切开看，它在这段时间里只可能处于三种状态之一：
$$\underbrace{C - A}_{\text{周转总时间}} = \underbrace{B}_{\text{真正在 CPU 上跑的总时长}} + \underbrace{I}_{\text{去外设阻塞做 I/O 的总时长}} + \underbrace{W}_{\text{在就绪队列干等的总时长}}$$
移项立刻得到万能等待时间公式：**$W = (C - A) - B - I$**！常规考题没有 I/O（$I = 0$），所以直接算 **$W = C - A - B$** 比一段段加甘特图空白格快得多，而且绝不会漏掉 RR 中间某一段等待！

#### 1. 考场零失误四步公式模板
动笔前先用笔圈出四个条件：**① 到达时刻 $A_i$ 是否全为 0？ ② 优先级数字“越小越高”还是“越大越高”？ ③ 抢占还是非抢占？ ④ 求“等待时间”还是“周转时间”？**

对每个进程记录：到达时刻 $A$、CPU 总执行时长 $B$、首次上 CPU 时刻 $S$、最终完成时刻 $C$：
- **周转时间（Turnaround）** $= C - A$
- **响应时间（Response）** $= S - A$（只看第一次上 CPU！）
- **等待时间（Waiting）** $= \text{各段就绪排队时间之和} = (C - A) - B$ *(无 I/O 阻塞且忽略切换开销时恒成立，用此式验算最快最准！)*

#### 2. 真题实战 1（2019 & 2023 完全重题！）：四进程四算法对比
> **原题**：四个进程 $P_1, P_2, P_3, P_4$ 在时刻 $0$ 按序到达，需要 CPU 时间依次为 $(9, 2, 3, 2)\text{ ms}$，优先级依次为 $(3, 1, 2, 4)$（**数值越小优先级越高**），RR 时间片 $q = 1\text{ ms}$。a) 画 FCFS、SJF、RR、非抢占优先级甘特图；b) 求各进程等待时间；c) 哪种算法平均等待时间最少？

| 调度算法 | 标准甘特图（竖线数字为时刻 ms） | 各进程等待时间 $(P_1, P_2, P_3, P_4)$ | 平均等待时间 |
| :--- | :--- | :---: | :---: |
| **1. FCFS** | `0 \| P1 \| 9 \| P2 \| 11 \| P3 \| 14 \| P4 \| 16` | $0,\ 9,\ 11,\ 14$ | $\frac{0+9+11+14}{4} = \mathbf{8.5\text{ ms}}$ |
| **2. 非抢占 SJF** | `0 \| P2 \| 2 \| P4 \| 4 \| P3 \| 7 \| P1 \| 16` | $7,\ 0,\ 4,\ 2$ | $\frac{7+0+4+2}{4} = \mathbf{3.25\text{ ms}}$ |
| **3. RR ($q=1$)** | `0\|P1\|1\|P2\|2\|P3\|3\|P4\|4\|P1\|5\|P2\|6\|P3\|7\|P4\|8\|P1\|9\|P3\|10\| P1 \|16` | $7,\ 4,\ 7,\ 6$ | $\frac{7+4+7+6}{4} = \mathbf{6\text{ ms}}$ |
| **4. 非抢占优先级** | `0 \| P2 \| 2 \| P3 \| 5 \| P1 \| 14 \| P4 \| 16` | $5,\ 0,\ 2,\ 14$ | $\frac{5+0+2+14}{4} = \mathbf{5.25\text{ ms}}$ |

- **c) 结论**：**SJF（短作业优先）**使平均等待时间最少（$3.25\text{ ms}$）。
- **RR 防错验算**：$P_1$ 在 $C=16$ 完成，$B=9 \implies$ 等待 $= 16 - 0 - 9 = \mathbf{7\text{ ms}}$（千万别只看首次响应 $0$ 或漏算 $[9,10]$ 那 $1\text{ ms}$，2019 旧参考答案曾误算为 6，按 $C-A-B$ 验算永不出错！）。

#### 3. 真题实战 2（2018 原题）：改考“大数优先 + 平均周转时间”
> **原题**：5 个任务 $A, B, C, D, E$ 在时刻 $0$ 同时到达，运行时间为 $(10, 6, 2, 4, 8)\text{ ms}$，优先级为 $(3, 5, 2, 1, 4)$（**5 为最高优先级**）。求 FCFS、优先级、RR（$q = 2\text{ ms}$）的**平均周转时间**。

1. **FCFS**：`0 [A] 10 [B] 16 [C] 18 [D] 22 [E] 30` $\implies$ 完成（周转）时间 $(10, 16, 18, 22, 30)$，平均周转 $= \frac{96}{5} = \mathbf{19.2\text{ ms}}$。
2. **优先级（5>4>3>2>1，即 B→E→A→C→D）**：`0 [B] 6 [E] 14 [A] 24 [C] 26 [D] 30` $\implies$ 周转时间 $(6, 14, 24, 26, 30)$，平均周转 $= \frac{100}{5} = \mathbf{20\text{ ms}}$。
3. **RR ($q=2\text{ ms}$)**：轮转轮次为 `(A,B,C,D,E) [0~10] -> (A,B,D,E) [10~18] -> (A,B,E) [18~24] -> (A,E) [24~28] -> (A) [28~30]`。
   - 按 $A \sim E$ 完成时刻（周转时间）：$T_A = 30,\ T_B = 22,\ T_C = 6,\ T_D = 16,\ T_E = 28$；平均周转 $= \frac{30+22+6+16+28}{5} = \mathbf{20.4\text{ ms}}$。

#### 4. 今年课件必练变式（L5 P.23 分批到达 SRTF & L5 P.36 课堂练习）
- **变式 A（分批到达的抢占式 SRTF，L5 P.23）**：
  - 数据：$P_1(A=0, B=8),\ P_2(A=1, B=4),\ P_3(A=2, B=9),\ P_4(A=3, B=5)$。
  - 抢占推演：时刻 `0` $P_1$ 先跑；时刻 `1` $P_2$ 到达，**比较 $P_1$ 剩余 $7$ 与 $P_2$ 所需 $4$**，$4 < 7$ 故 **$P_2$ 抢占 $P_1$**；时刻 `2`（$P_2$ 剩 $3 < 9$）、时刻 `3`（$P_2$ 剩 $2 < 5$）均不抢占；时刻 `5` $P_2$ 结束，就绪队列有 $P_1(\text{剩}7), P_3(9), P_4(5)$，选最短的 $P_4$！
  - 甘特图：`0 | P1 | 1 | P2 | 5 | P4 | 10 | P1 | 17 | P3 | 26`
  - 等待时间 $(C-A-B)$：$P_1 = 17-0-8 = 9,\ P_2 = 5-1-4 = 0,\ P_3 = 26-2-9 = 15,\ P_4 = 10-3-5 = 2 \implies$ 平均等待 $= \mathbf{6.5\text{ ms}}$。
- **变式 B（课件 L5 P.36 五进程练习核对值）**：$P_1 \sim P_5$ 时刻 $0$ 到达，长度 $(2,1,8,4,5)$，优先级 $(2,1,4,2,3)$（大数优先，$q=2$）。自测核对答案：平均等待时间依次为 **FCFS $6.2\text{ ms}$、非抢占 SJF $4.6\text{ ms}$、非抢占优先级 $11.0\text{ ms}$、RR $7.2\text{ ms}$**。

### 题型二【95%+ 必考】：同步与互斥代码编写与填空（P/V 信号量 + 条件变量）

#### 0. 底层算法精讲：陌生情景一招拆解——“P/V 四步万能建模法”与“条件变量五步法”

千万别死背代码！不管考场把题目包装成“货架补货”“切菜传菜”“阅览室借书”还是“爸爸放水果”，只要按下面这套**通用建模算法**拆解，5 分钟必写出满分程序：

##### （1）信号量 P/V 四步万能建模法
- **第 1 步：圈出所有并发主体（有几类人就写几个函数）**。例如 `Producer()` 和 `Consumer()`。
- **第 2 步：判断是否需要互斥锁 `mutex = 1`（极关键避坑点！）**
  - **什么时候要加 `mutex = 1`？** 当多个进程要**操作同一个共享数据结构**（如往共享缓冲区数组移动下标放/取东西、修改同一个计数器 `read_count`）时，必须加 `mutex = 1`，在读写动作紧贴前后包上 `P(mutex) ... V(mutex)`。
  - **什么时候绝不能加 `mutex = 1`？** 当题目只是**限制某空间同时容纳的人数上限**（如“售票厅最多进 20 人”“阅览室有 50 个座位”，人进去后各买各的票、各看各的书，没去改同一个数组指针）时，**只需一个计数信号量 `S = 20`，千万别画蛇添足套 `P(mutex)`**——否则 20 人的售票厅被你锁成每次只能进 1 个人了！
- **第 3 步：找同步制约关系——口诀“缺啥设啥，初值看开局，谁消耗谁 P，谁创造谁 V”**
  把所有“等待条件”统统翻译成**可消耗的许可证**，一共只有 4 种基础积木（考场新题全是它们的组合）：
  1. **【限流积木】**（最多同时进 $K$ 人）：设 `S = K`，进场消耗名额 `P(S)`，离场归还名额 `V(S)`。
  2. **【前驱积木】**（动作 A 必须发生在动作 B 之前）：设信号 `done = 0`（开局 A 还没做，故为 0），A 做完发许可 `V(done)`，B 开始前等许可 `P(done)`。
  3. **【供需仓库积木】**（容量 $N$ 的缓冲区/盘子）：把**“空位”也当成一种给生产者消耗的许可证**！
     - 开局有 $N$ 个空位、$0$ 件产品 $\implies$ `empty = N, full = 0`；
     - 生产者：**消耗 1 个空位 `P(empty)`** $\to$ 放货 $\to$ **创造 1 件产品 `V(full)`**；
     - 消费者：**消耗 1 件产品 `P(full)`** $\to$ 取货 $\to$ **创造（腾出）1 个空位 `V(empty)`**！
     - *融会贯通变式*：如果考“一个盘子最多放 1 个水果，爸爸只放苹果、妈妈只放橘子，儿子只吃苹果、女儿只吃橘子”怎么办？空位大家都抢同一个 `empty = 1`，产品分两类就拆成两个信号量 `apple = 0, orange = 0`！爸爸 `P(empty)->放->V(apple)`，儿子 `P(apple)->取->V(empty)`；妈妈与女儿同理换成 `orange`（单槽下 `empty=1` 自身已天然保证爸爸妈妈不会同时放，连 `mutex` 都可省，加了也不错）——是不是瞬间通透？
  4. **【抱团共享积木】**（同类可并行、异类需互斥，如读者-写者 / 独木桥同向同行）：给同类阵营配一个人数计数器 `count = 0`（配小锁 `mutex = 1` 专门护住 `count`）+ 一把大场地锁 `rw = 1`。口诀：**“本队第 1 个人进场时 `if (++count == 1) P(rw)` 替全队抢场地，本队最后 1 个人退场时 `if (--count == 0) V(rw)` 替全队交场地；中间真正的 `read()` 干活代码一定要写在 `V(mutex)` 外面才能多人并行！”**
- **第 4 步：排定 P/V 先后顺序（防死锁生死线！）**
  - **双 `P` 铁律**：当一个进程既要 `P(资源 empty/full)` 又要 `P(mutex)` 时，**永远先 `P(资源)`，后 `P(mutex)`**！（想通道理：先在门外确认仓库里有货/有空位了，再拿钥匙进屋搬货；如果先拿钥匙锁死屋门再在屋里傻等别人进屋送货，门外送货的人拿不到钥匙，两人当场死锁！）
  - **双 `V` 规律**：`V` 操作只是归还增加计数，**永远不会阻塞**，所以先 `V(mutex)` 还是先 `V(资源)` 逻辑都正确（先 `V(mutex)` 早点放锁并发度更高）。

##### （2）如何把任意 P/V 题一秒改写成“POSIX 条件变量 / 管程”代码？（五步转换通法）
为什么有些题让你写 `pthread_cond_wait` 而不是 `P/V`？抓准两者唯一核心区别：**信号量自己肚子里装着整数计数器，而条件变量肚子里没有数（只是一个睡眠队列 + 门铃）！**
所以任何同步题用条件变量写，全宇宙统一套这**五步标准死模板**：
1. **显式声明普通状态变量**：比如缓冲区当前产品数 `int count = 0;`（若容量为 1 可用 `bool full = false;`），配一把 `pthread_mutex_t mutex` 保护它；
2. **按“等待原因”建条件变量**：生产者因“满”而等建 `not_full`，消费者因“空”而等建 `not_empty`；
3. **任何角色函数一律照抄以下 5 行骨架**：
   ```c
   pthread_mutex_lock(&mutex);                    // 第1步：进门先加互斥锁
   while ( 我还不能行动的条件 )                   // 第2步：用 while（绝不用 if！）检查普通状态变量
       pthread_cond_wait(&我等的条件变量, &mutex);// 第3步：条件不满足则原子放锁睡眠；醒来重获锁后再回 while 复查
   执行操作并更新普通状态变量 (如 count++ / full=true); // 第4步：持锁安全干活改状态
   pthread_cond_signal(&对方在等的条件变量);      // 第5步：按门铃叫醒对方（然后 unlock 解锁出门）
   pthread_mutex_unlock(&mutex);
   ```

#### 1. 真题母题 A：有界缓冲区 / 单槽多生产者-多消费者 P/V 代码 *(2019 & 2023 真题 + L7 P.5–9)*
> **原题**：一个初始为空的缓冲区（容量 $N=1$；若考一般有界缓冲区则设为 $N$），多个生产者与多个消费者不断并发放/取产品。只有空时生产者能放，只有有数据时消费者能取，且缓冲区不允许同时操作。用 P、V（或 `wait`/`signal`）写出完整代码。

```c
// 1. 定义信号量与初值（单槽题令 N = 1；一般有界缓冲区保留 N）
semaphore mutex = 1;   // 互斥信号量：保护缓冲区的互斥访问
semaphore empty = 1;   // 同步信号量：当前空槽位数（一般容量为 N）
semaphore full  = 0;   // 同步信号量：当前可取产品数

// 2. 生产者进程（共 m 个）          // 3. 消费者进程（共 n 个）
void Producer() {                    void Consumer() {
    while (true) {                       while (true) {
        item = produce_item();               P(full);       // ① 先等有产品（绝不能先 P(mutex)!）
        P(empty);      // ① 先等空位          P(mutex);      // ② 再申请互斥锁
        P(mutex);      // ② 再拿互斥锁        item = get_item();
        put_item(item);                      V(mutex);      // ③ 释放互斥锁
        V(mutex);      // ③ 释放互斥锁        V(empty);      // ④ 归还空槽位！（切勿错写成 V(full)!）
        V(full);       // ④ 通知有新产品      consume_item(item);
    }                                    }
}                                    }
```
- **必背三个高频追问**：
  1. **信号量取值范围**（设 $m$ 个生产者、$n$ 个消费者、容量 $N=1$）：`empty` $\in [-m, 1]$，`full` $\in [-n, 1]$，`mutex` $\in [-(m+n-1), 1]$。
  2. **为什么两个 `P` 顺序绝不能颠倒？** 若生产者先 `P(mutex)` 再 `P(empty)`，当缓冲区已满（`empty == 0`）时，生产者持有 `mutex` 阻塞在 `P(empty)`；此时消费者想取走产品释放空位，却在 `P(mutex)` 处等待生产者手里的锁，双方永久互等发生**死锁**！
  3. **2023 阅卷扣分警示**：消费者取出产品后腾出的是**空位**，最后一步必定是 **`V(empty)`**，千万别顺手抄成 `V(full)`！

#### 3. 🔥 今年极高概率新题：厨师与服务员共用传菜位（POSIX 条件变量填空） *(L7 P.54–55 原题)*
> **课件原题**：一个厨师、一个服务员共用单传菜位（容量 1，初始为空）。布尔变量 `full`（初值 `false`）表示是否有菜；共用互斥锁 `mutex` 和条件变量 `not_empty`、`not_full`。补全六处空白并说明锁交接过程。

```c
/* 厨师：放入一份菜 */                      /* 服务员：取走一份菜 */
pthread_mutex_lock(&mutex);                 pthread_mutex_lock(&mutex);
while ( full )              // 空(1)        while ( !full )             // 空(4)
    pthread_cond_wait(                          pthread_cond_wait(
        &not_full, &mutex); // 空(2)                &not_empty, &mutex);// 空(5)
放入菜品;                                   取走菜品;
full = true;                                full = false;
pthread_cond_signal(&not_empty); // 空(3)   pthread_cond_signal(&not_full); // 空(6)
pthread_mutex_unlock(&mutex);               pthread_mutex_unlock(&mutex);
```
- **标准追问满分答法（当服务员先运行时）**：
  1. **何时释放锁**：服务员先拿到 `mutex`，检查发现无菜（`!full` 为真），进入 `pthread_cond_wait(&not_empty, &mutex)` 时**由系统原子地释放 `mutex` 锁并进入 `not_empty` 等待队列睡眠**。
  2. **厨师通知谁**：厨师随后获得 `mutex` 锁，放入菜品并置 `full = true`，调用 `pthread_cond_signal(&not_empty)` **唤醒等待在 `not_empty` 上的服务员**（注意此时厨师仍持有 `mutex` 锁，直到执行 `unlock` 才释放）。
  3. **何时从 `wait` 返回**：厨师 `unlock` 释放锁后，服务员**重新竞争并获得 `mutex` 锁之后**才从 `pthread_cond_wait` 返回，经 `while (!full)` 复查确认 `full == true` 后取菜、置 `full = false`、通知 `not_full` 并解锁。

- **读者优先（第一类读者-写者）核心模板**：

### 题型三【高概率】：`fork()` / `exec()` / `pthread` 与文件偏移共享程序推演

#### 0. 底层算法精讲：“内核三级文件表模型”与“并发偏序树推演法”

遇到多进程/多线程读写文件或打印输出的程序阅读题，只要画出下面两张图，任何代码变形都能一眼看穿所有可能输出：

##### （1）判断文件是“覆盖”还是“追加拼接”——画内核三级文件表！
Linux 内核管理打开文件分三级：**① 每进程私有的 `fd` 描述符表 $\longrightarrow$ ② 系统级“打开文件表项”（这里面存着当前读写偏移量 `offset`！） $\longrightarrow$ ③ 磁盘文件 `inode`**。
```text
【情况 A：先 open 一次，再 fork】            【情况 B：先 fork，父子再各自 open】
 父进程 fd[3] ──┐                             父进程 fd1 ──► 打开文件表项#1 (offset=0) ──┐
                ├──► 同一个打开文件表项        子进程 fd2 ──► 打开文件表项#2 (offset=0) ──┼──► file.txt
 子进程 fd[3] ──┘     (共享同一个 offset!)                                                │
 结论：先写者写0推到1，后写者写1 → 拼接(ab/ba)  结论：各从自己的 offset=0 写，后写覆盖先写 → 覆盖(a/b)
```
- **如果是同进程多线程（`pthread_create`）**：所有线程本来就共用**同一张进程 `fd` 表**，所以天然等同于【情况 A】（共享 `offset` 顺序拼接）！

##### （2）推演并发打印/写出结果的通用三步算法
1. **查变量是否分家**：`fork()` 之后父子修改任何普通 C 变量（全局/局部/堆）互不相干；`pthread_create()` 之后各线程读写同一个全局/堆变量会互相看见（若无锁则存在竞争）。
2. **查进程是否提前销毁杀线程（致命细节！）**：
   - 多进程下：父进程 `return 0` 结束自己，**不会杀死子进程**，子进程一定会跑完自己的 `write`！
   - 多线程下：**主线程一旦从 `main()` 执行 `return`（或任一线程调 `exit()`），整个进程当场灰飞烟灭**！如果主线程在 `return` 前**没写 `pthread_join`**，那么子线程就多出一种可能——**还没排上 CPU 执行 `write` 就随着进程一起被强杀了**！
3. **画偏序图（DAG）做插空排列**：
   - 把每条线程/进程内部的语句按先后连成直线；
   - 若有 `execlp(...)`：一旦成功，该分支在 `exec` 下面的原程序语句**直接打叉删掉（永不执行）**；
   - 若有 `waitpid` 或 `pthread_join`：从“子分支的最后一步”画一条箭头指向“`wait/join` 的下一句”（保证子分支全部跑完后才执行这句）；
   - 没有箭头约束的两条并行支路，直接用高中排列组合“插空法”列出所有先后交错！

#### 1. 真题实战（2020 综合题 1 原题）：三段写文件程序输出全解

| :--- | :---: | :--- |

#### 2. 今年课件重磅代码题（L3 P.27）：`fork` + `execlp` + `waitpid` 打印顺序
```c
pid_t pid = fork();
printf("[0] Hello from %d\n", pid);                   // 语句 [0]：父打印子PID(记0_P)，子打印0(记0_C)
if (pid == 0) {
    printf("[1] [Child] before exec\n");              // 语句 [1]
    execlp("echo", "echo", "[2] Hello echo!", NULL);  // 语句 [2]
    printf("[3] [Child] after exec\n");               // 语句 [3]（陷阱！）
} else {
    waitpid(pid, &status, 0);
    printf("[4] [Parent] child exited...\n");         // 语句 [4]
}
```
- **三大必答结论**：
  1. **`[3]` 绝不会打印**（`execlp` 成功时直接用 `echo` 程序映像覆盖子进程原代码段，永不返回原程序）；
  2. **`[4]` 必定在最后打印**（父进程阻塞在 `waitpid` 直到子进程执行完 $0_C \to [1] \to [2]$ 退出后才恢复）；
  3. **共有 4 种合法打印顺序**（取决于父进程的 $0_P$ 插在子进程三句的哪个间隙）：
     - $0_P \to 0_C \to [1] \to [2] \to [4]$
     - $0_C \to 0_P \to [1] \to [2] \to [4]$
     - $0_C \to [1] \to 0_P \to [2] \to [4]$
     - $0_C \to [1] \to [2] \to 0_P \to [4]$

### 题型四【高概率】：多线程多把锁死锁执行序列构造与破除分析 *(2020 综合题 2 原题，25 分)*

#### 0. 底层算法精讲：两轮构造死锁法、“首个不安全状态”判别法与全局锁序法

只要题目给出一组线程各自申请多把互斥锁的代码，按以下三板斧通杀所有设问：
1. **怎么 10 秒写出死锁序列？（“每人先领第一把锁”两轮构造法）**
   - 先找出哪些线程的加锁顺序构成了环（画**等待图 Wait-for Graph**：若线程 $T_1$ 手握锁 $L_a$ 还要申锁 $L_b$，而 $L_b$ 在 $T_2$ 手里，就画有向边 **$T_1 \longrightarrow T_2$**，箭头永远从**等待者指向持有者**！）。
   - **第 1 轮**：依次调度环上的每个线程各执行完它的**第 1 条 `lock`** 语句就暂停切换；
   - **第 2 轮**：再依次调度每个线程去执行它的**第 2 条 `lock`** 语句——因为目标锁全在下一家手里，全员阻塞成环，死锁完成！
2. **怎么找序列中的“第一个不安全（Unsafe）状态”？（上帝偏心检验法）**
   - 切勿把“不安全状态”和“已经全部阻塞的死锁状态”混为一谈！
   - 顺着你写的序列一步步停下来问：**“假设从这一行刚跑完的瞬间起，我当上帝偏心某一个线程让它一直跑，有没有哪一个线程能顺利拿齐它剩下的锁、做完解锁释放出来救活大家？”**
   - 只要**还存在哪怕 1 个线程能跑通释放锁**，当前状态就是**安全（Safe）**的；一旦执行完某一行（必然是环上最后一个线程刚拿走它第 1 把锁的那一行！），发现**哪怕上帝想偏心谁，每个人缺的第 2 把锁都已经在别人兜里了（死局已定、无路可逃）**——这一行刚结束的状态就是**第一个不安全状态**！
3. **怎么改代码彻底消除死锁？（全局锁编号递增法）**
   - 给程序中出现的所有锁随便定一个固定大小顺序，例如 **`x < y < z`**（或按内存地址从小到大）。
   - 检查每个线程：只要求它把**所有 `lock()` 获取语句**调整为严格按 `x -> y -> z` 从小到大拿锁（比如原本先拿 `z` 再拿 `x` 的线程，改成先 `lock(&x)` 再 `lock(&z)`）。
   - *为什么 100% 不会再成环？（反证法一句话写卷面）*：若还存在等待环 $T_1 \to T_2 \to \dots \to T_1$，由于每人都是“拿着小号锁去等大号锁”，所持锁编号必满足 $L_1 < L_2 < \dots < L_1$，得出 $L_1 < L_1$ 矛盾！注意：**只改 `unlock()` 顺序毫无意义**，因为死锁在第一句 `unlock` 之前就已经卡死了！

> **原题代码特征**：共三把互斥锁 `x, y, z`，三个并发线程：
> - 线程 `a`：依次 `lock(&y) -> lock(&z) -> unlock(&y) -> unlock(&z)`
> - 线程 `b`：依次 `lock(&z) -> lock(&x) -> unlock(&z) -> unlock(&x)`
> - 线程 `c`：依次 `lock(&x) -> lock(&y) -> unlock(&x) -> unlock(&y)`

1. **（1）写出一种导致死锁的执行序列**：
   ```text
   a 调用 lock_acquire(&y)   // a 持有 y
   b 调用 lock_acquire(&z)   // b 持有 z
   c 调用 lock_acquire(&x)   // c 持有 x  <-- 至此进入首个不安全状态！
   a 调用 lock_acquire(&z)   // a 阻塞等待 b 持有的 z
   b 调用 lock_acquire(&x)   // b 阻塞等待 c 持有的 x
   c 调用 lock_acquire(&y)   // c 阻塞等待 a 持有的 y（形成等待环 a → b → c → a，死锁！）
   ```
2. **（2）上述序列中第一个“不安全（unsafe）”状态是什么？出现在哪里？**
   - 出现在**前三条语句执行完毕之后**，状态为：**`a` 持有 `y`、`b` 持有 `z`、`c` 持有 `x`**。此时每个线程都已拿走第一把锁，后续无论调度器先调度谁执行下一条加锁指令，都必然全部阻塞死锁（而在第 2 条语句后若继续调度 `b` 拿 `x` 则仍可顺利跑完，故前两步仍安全）。
3. **（3）能否通过改变每个线程 `unlock` 解锁互斥锁的顺序来解决死锁？**
   - **不能！** 因为死锁发生在所有线程获取第二把锁的阶段，此时**还没有任何一个线程能执行到第一条 `unlock` 语句**。
   - *附：正确的修改方法（L6 P.44）*：**规定全局一致的加锁顺序**，例如规定 `x < y < z`，将线程 `b` 的加锁顺序改为先 `lock(&x)` 再 `lock(&z)`，即可彻底破坏**循环等待**条件！
4. **（4）若底层使用单核非抢占 FCFS 线程调度器，该程序容易死锁吗？**
   - **不会死锁**。非抢占 FCFS 会让第一个上 CPU 的线程一口气拿齐两把锁并解锁运行到结束，再运行下一个线程，锁完全无竞争，所有 `lock` 都不会阻塞。
5. **（5）使用抢占式线程调度器会消除死锁的可能性吗？**
   - **不会消除**（反而使上述交错死锁更容易发生）。因为抢占式调度器**只能从线程手中抢占 CPU，绝不能强行抢占（剥夺）该线程已经持有的互斥锁**！

### 题型五【5 分钟防超纲兜底】：银行家算法安全性检查与资源等待图 *(2018 & 2023 旧卷压轴题)*

#### 0. 底层算法精讲：“滚雪球放贷思想”与银行家全套手算步骤

虽然今年通知列至 Lesson 7，但 2018、2023 真题压轴均考了银行家算法，它原理极其直观——把它想成**银行行长用有限现金 `Available` 救活所有贷款企业**：

##### （1）安全性检查算法（Safety Algorithm —— 判断当前状态安不安全）
1. **第 1 步（列尚需表）**：如果卷面给的是最大需求 `Max` 和已分配 `Allocation`，先逐行相减算出每个进程**最多还差多少资源才能完工**：
   $$\text{Need}[i] = \text{Max}[i] - \text{Allocation}[i]$$
   *(注意：像 2018 卷有时直接印好了“尚需资源 Need”，看清表头别重复减！)*
2. **第 2 步（挑能救活的人）**：把手头可用流动资金记为 $\text{Work} = \text{Available}$。从上到下扫描还没完工的进程，找满足 **$\text{Need}[i] \le \text{Work}$** 的进程 $P_i$——**注意向量比较必须每一类资源（A、B、C 每一列）都同时小于等于 $\text{Work}$ 才算够！哪怕有一列差 1 个都不行！**
3. **第 3 步（完工连本带利回收滚雪球）**：一旦找到这样的 $P_i$，把钱借给它让它跑完，它完工后会把**之前借走的本金 `Allocation[i]` 全额退还给银行**！于是你的流动资金变多了（注意是加 `Allocation`，千万别加错成 `Max` 或 `Need`！）：
   $$\text{Work}_{\text{新}} = \text{Work}_{\text{旧}} + \text{Allocation}[i]$$
   把 $P_i$ 记入安全序列，打钩标为已完成，拿变大后的 $\text{Work}$ 回第 2 步继续救下一家！
4. **第 4 步（下结论）**：
   - 若所有进程全部打钩完成 $\implies$ **处于安全状态**，按打钩顺序写出一条**安全序列**（安全序列往往不唯一，写出任意一条合法序列即满分）；
   - 若扫描一圈没有任何剩余未完进程满足 $\text{Need}[i] \le \text{Work}$ $\implies$ 雪球滚不动了，**处于不安全状态（不存在安全序列）**！

##### （2）如果题目追问“某进程 $P_i$ 此刻动态发来新请求 $\text{Request}_i$ 能不能批？”（资源请求四步法）
1. 合法检查：$\text{Request}_i \le \text{Need}[i]$？（超报最大额度直接报错）；
2. 库存检查：$\text{Request}_i \le \text{Available}$？（库存不够让 $P_i$ 阻塞等待）；
3. **试探性假装分配**（在草稿纸上改三个数）：
   $$\text{Available} \leftarrow \text{Available} - \text{Request}_i, \quad \text{Allocation}[i] \leftarrow \text{Allocation}[i] + \text{Request}_i, \quad \text{Need}[i] \leftarrow \text{Need}[i] - \text{Request}_i$$
4. 对试分配后的新表跑一遍上面的**安全性检查算法**：若**安全**则正式批准分配；若**不安全**则推翻刚才的试分配恢复原状，让 $P_i$ 等待！

##### （3）如果处于不安全状态，2023 卷要求“画出资源分配/等待图”怎么画？
- 把进程画成圆圈 $\bigcirc P_i$，把每类资源画成方框 $\square R_j$（里面点几个点代表总实例数，总实例数 $= \sum \text{Allocation} + \text{Available}$）；
- **已分配边（资源 $\to$ 进程）**：从资源框指向进程圈，标上 `Allocation[i][j]` 的数量；
- **申请等待边（进程 $\to$ 资源）**：从进程圈指向它当前不够满足的那类资源框，标上 `Need[i][j]` 的数量，直观展示循环等待关系。

> [!NOTE]
> **三步速记卡片**：① 算 $\text{Need} = \text{Max} - \text{Allocation}$ $\to$ ② 找全列满足 $\text{Need}[i] \le \text{Work}$ $\to$ ③ 回收 $\text{Work} = \text{Work} + \text{Allocation}[i]$ 循环滚雪球！

- **2018 真题速核**：$\text{Available} = (0, 2, 1)$。
  - 先选 $P_1$（$\text{Need}=(0,0,1) \le (0,2,1)$）$\implies \text{Work} = (0,2,1)+(2,0,0) = (2,2,1)$；
  - 再选 $P_4$（$\text{Need}=(2,0,0) \le (2,2,1)$）$\implies \text{Work} = (2,2,1)+(0,0,1) = (2,2,2)$；
  - 剩余 $P_2$（$\text{Need}=(1,3,2)$）和 $P_3$（$\text{Need}=(1,3,1)$）的 $R_2$ 均需 $3 > 2$，无法满足 $\implies$ **答：不处于安全状态（安全序列不存在）**。
- **2023 真题速核**：5 进程 $P_0 \sim P_4$，算出 $\text{Need}$ 依次为 $P_0(7,4,3), P_1(1,2,2), P_2(6,0,0), P_3(0,1,1), P_4(4,3,1)$。
  - 卷面印 $\text{Available} = (2, 3, 0)$：$P_0, P_1, P_3, P_4$ 均需 $C \ge 1 > 0$，$P_2$ 需 $A = 6 > 2$，**一步都走不动 $\implies$ 不处于安全状态**，可能卷入死锁的进程为 $P_0, P_1, P_2, P_3, P_4$。*(注：若考场把 Available 印为教材原值 `(3, 3, 2)`，则安全，序列为 `P1 -> P3 -> P4 -> P2 -> P0`)*。
  - **经典第 b 问：“当前不安全状态是否一定会发生死锁？为什么？”**
    - **答：不一定！** 不安全状态只代表存在导致死锁的潜在最坏请求序列（当各进程后续真的请求达到各自的 `Max` 时无法避免死锁）；如果各进程后续不再申请新资源或提前释放已占资源，系统并不会发生死锁。

## 五、考场 60 分钟冲刺与交卷前 5 分钟防丢分 Checklist

1. **【判断题】** 凡是打 **`×`** 的题，**100% 检查是否写了一句理由**（没写理由直接丢一半分！）。
2. **【判断题文字坑】** 看到 `$S = -6$` 看清写的是“等待**该信号量**的进程有 6 个”（√）还是“**全系统**共有 6 个等待进程”（×）。
3. **【选择题】** 先看大题标题是**单选**还是**不定项选择**；问“CPU 执行内核代码处于什么态”选**内核态**（别选执行态）；信号量初值 $2$ 当前值 $-1$，等待进程数是 **$|-1| = 1$ 个**（别选 $3$ 个！）。
4. **【CPU 调度题】** 交卷前重核四件事：
   - 甘特图末尾总长度是否等于 $\sum B_i$（无空闲段时）？
   - 优先级究竟是**小数字优先**（2019/2023）还是**大数字优先**（2018 / L5 P.36）？
   - 题目问的是**等待时间**（$C - A - B$）、**周转时间**（$C - A$）还是**响应时间**（$S - A$）？
   - RR 中多次运行的进程，是否用 $C - A - B$ 算齐了中途所有排队片段？
5. **【P/V 同步题】** 检查生产者和消费者是否都是**先 `P(资源 empty/full)`，再 `P(mutex)`**（顺序反了必死锁扣大分！）；检查消费者最后一行是否是 **`V(empty)`**（绝不是 `V(full)`！）。
6. **【条件变量题】** 检查 `wait` 外面套的是不是 **`while` 循环**（不能写 `if`），`pthread_cond_wait` 是否传了 `&mutex`，以及修改 `full` 标志后是否调用了唤醒**对方**条件变量的 `signal`。
