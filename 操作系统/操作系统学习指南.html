1️⃣ AI 时代，为什么还要学操作系统？

对应 lesson1 第 7–21 页 · 一个 save_config 函数引发的连环拷问

1.1 一道"简单"的编程题

假设你让 AI 帮你写一个函数 save_config(path, data)，把新配置保存到文件。AI 很快给出了代码，你运行一次、重新打开文件——内容确实更新了。看起来万事大吉？请试着回答下面三个问题：

  1. 如果写到一半程序退出了，原来的配置还在吗？
  2. 如果已经显示"保存成功"，此时机器断电，数据还在吗？
  3. 如果两个请求同时修改配置，会互相覆盖吗？

这三问的答案，不取决于你的 Python 代码写得好不好，而取决于程序究竟怎样执行、以及操作系统的接口到底向你承诺了什么。这就是 AI 时代依然要学操作系统的原因：AI 能生成代码，但判断代码在各种异常执行下是否仍满足要求这件事，需要懂底层机制的人来做。

核心直觉

把"从需求到执行"想成一条流水线：人的需求 → 程序员 → 软件基础设施 → 机器执行。程序员负责把"下次打开应用时记住我的设置"翻译成明确的保存逻辑；编译器/解释器负责翻译执行；运行库和操作系统提供文件、内存等支持；硬件最终改变内存与存储中的状态。AI 改变的只是"程序员"这一环，后面每一环的语义都没有变。

1.2 先补一课：LLM 到底是怎么"写代码"的？

要理解"为什么 AI 写的代码不能盲目信任"，先得知道大语言模型（LLM）的工作机制。以基于 Transformer 的自回归语言模型为例，整个过程分两步：

flowchart LR A["提示与已有代码"] --> B["Token 编号"] B --> C["嵌入向量
+ 位置信息"] C --> D["多层 Transformer
注意力 + 前馈网络"] D --> E["上下文表示 h"] E --> F["词表分数 → softmax
→ 条件概率分布"]

第一步：Token 与嵌入。文本被切成词元（token），每个词元有个编号，查表得到向量；再加上位置信息帮助模型区分顺序。

第二步：自注意力——匹配，再加权。每个位置的向量算出三个角色：Q（查询）、K（匹配特征）、V（待组合信息）。Q 与 K 做匹配，经 softmax 得到权重，再对 V 加权求和：

\[ z_i = \sum_{j \le i} \alpha_{ij}\, v_j, \qquad \sum_{j \le i} \alpha_{ij} = 1 \]

注意求和下标 \(j \le i\)：当前位置只能使用自身及前文（这叫因果掩码，防止"偷看未来"）。多头注意力则相当于从多个不同的投影角度同时组合信息。每层还有前馈网络、残差连接与归一化；多层堆叠后，最后一个位置的表示 \(h\) 被用来预测下一个 token。

预测的具体形式是词表上的一个条件概率分布：

\[ p_\theta(x_{t+1} = v \mid c,\; x_{1:t}) = \mathrm{softmax}(W_{out} h + b)_v \]

其中 \(c\) 是提示、要求与已提供的资料；\(x_{1:t}\) 是已生成的 token；\(\theta\) 是训练学到的参数。每生成一个 token 就把它追加到上下文，再预测下一步，逐步"写"出整段代码。

易错陷阱

概率模型无法提供正确性保证。预训练的目标只是"提高训练文本中实际后续 token 的概率"。也就是说，模型输出的是统计上最像正确代码的文本，而不是被证明满足需求的代码。"看起来会写文件"和"在断电时也保证不丢数据"之间，隔着整个操作系统的语义鸿沟。

1.3 "让 AI 再检查一遍"有用吗？

你可能会想：生成之后让它自查、修改、再自查，多迭代几轮总能改对吧？

flowchart LR A["生成代码"] --> B["「请再检查一遍」"] B --> C["修改代码"] C --> D["再次自查…"] D -.可能收敛，也可能原地打转.-> B

要清醒地认识到普通对话式自查的三个局限：

  • 自查只是增加上下文，通常不会更新模型参数——它没有真正"学到"什么；
  • 自查不自动带来执行证据——它说"没问题"不等于真的跑过异常路径；
  • 如果测试始终只检查"正常保存后能否读回"，那么反复修改仍可能漏掉写到一半退出这类情况。

研究也证实了这一点：Huang 等人（ICLR 2024）观察到，无外部反馈的自我纠错甚至可能让结果退步——模型可能发现错误，也可能重复遗漏，甚至把原本正确的部分改错。迭代次数本身不保证质量提升。

考点提示

使用 AI 编程时，人仍然要做的四件事（lesson1 第 13 页，简答题高频考点）：

  1. 把要求说清楚：正常写入就够，还是中途失败、断电、并发修改时也有要求？
  2. 看懂 AI 调用的操作系统接口：关闭文件、替换文件分别做了什么、能保证什么？
  3. 检查代码没考虑到的执行情况：正常运行通过后，再查半写退出、保存后断电、并发修改。
  4. 根据实际执行结果验证：核对 AI 生成的测试是否覆盖要求、修改是否真解决问题。

1.4 拷问一：写到一半失败了怎么办？

先看 AI 最常给出的"教科书式错误答案"：

def save_config(path, data):
    with open(path, "w", encoding="utf-8") as f:
        f.write(data)

这段代码在正常测试下毫无破绽：保存后重新读取，确实得到完整的新配置，with 还会帮你关闭文件。但请注意区分两个不同的要求：

  • 要求 A：正常结束时，文件内容更新——✅ 上面的代码做到了；
  • 要求 B：失败以后，仍有一份完整配置可用——❌ 上面的代码做不到。

问题出在 "w" 模式的语义上：打开文件的瞬间，原文件就被截断为长度 0。设想旧配置是 {"theme":"light","font":12}，新配置是 {"theme":"dark","font":14}：

flowchart LR A["📄 完整旧文件
theme=light, font=12"] -->|w 模式打开| B["💥 长度被截为 0"] B -->|只写入前缀| C["📝 写入前 12 字节"] C -->|发生异常| D["🗑️ 留下残缺文件
「#quot;theme#quot;: #quot;da」"]

如果程序在只写入前 12 字节后抛异常（比如磁盘满、进程被杀），重新打开文件你只能看到 {"theme":"da——旧配置已被破坏，新配置还未写完。这就是"原地覆写"策略的致命缺陷。

1.5 解法一：先写临时文件，再原子替换

业界标准解法是间接写入：先把完整新内容写到同目录下的独立临时文件，确认写完整后，再用 os.replace(tmp, path) 一次性替换目标路径：

flowchart LR subgraph 替换前 A["config.json
完整旧文件"] B["临时路径
完整新文件"] end B -->|"os.replace(tmp, path)
原子路径替换"| C["config.json
完整新文件"]

这个方案的美妙之处在于任意时刻都有一份完整文件：

  • 替换之前任何时刻失败：目标路径仍是完整旧文件，临时文件删掉即可；
  • 替换成功之后：新打开文件的读者得到新文件；已经打开旧文件的读者，可以继续读取旧对象（文件对象指向的是旧的存储内容，不受路径替换影响）。
易错陷阱

os.replace 解决的是可见性问题（读者要么看到完整旧文件、要么看到完整新文件，绝不看到残缺），但它不解决断电持久化，也不解决并发冲突。这两件事需要单独讨论——也就是下面两节。

1.6 拷问二：显示"保存成功"后断电，数据还在吗？

要回答这个问题，必须知道数据从你的程序到存储设备之间隔着几道"缓冲"：

flowchart LR A["🐍 Python 应用缓冲"] -->|"flush()"| B["🧠 内核页缓存
（内存中！）"] B -->|"fsync()"| C["💾 存储设备
（断电不丢）"]

f.write() 的数据可能只是进了 Python 的缓冲区；flush() 或 close() 把它推进内核页缓存——但页缓存仍在内存里，断电即失。只有 fsync() 才能强制内核把数据真正刷到存储设备。所以：close 成功、甚至路径替换成功，都不自动等于断电后数据仍在。

标准答案 · 背下来

若要求"成功返回后断电仍保留新配置"，完整序列是（每一步都要检查错误！）：

写临时文件 → flush → fsync(临时文件) → os.replace 替换路径 → fsync(父目录) → 返回成功

为什么最后还要 fsync 父目录？因为文件数据与目录项是不同的持久化对象——replace 修改的是目录里的"名字 → 文件"映射，这个映射本身也需要落盘。

1.7 持久化与性能的矛盾：合并同步

fsync 很慢（要等磁盘真正写完）。如果每个请求都立即同步，响应时间会明显增加。工程上的折中是合并同步（group commit）：

sequenceDiagram participant A as 请求A participant L as 追加日志 participant D as 磁盘 Note over A,D: 方案一：立即同步 A->>L: 写入 A L->>D: sync D-->>A: 确认 A Note over A,D: 方案二：合并同步 A->>L: 写入 A（等待收集） L->>D: 请求 B 到达，一次 sync 覆盖 A+B D-->>A: 确认 A、B

合并同步减少了同步次数，摊薄了磁盘开销；代价是较早到达的请求要等待收集时间。注意，如果你在同步完成之前就向用户确认"持久保存成功"，那改变的不是性能，而是承诺本身——你在宣称一个并未兑现的保证。

1.8 拷问三：两个请求同时修改会怎样？

初始配置 theme=light, font=12。请求 A 想把 theme 改成 dark，请求 B 想把 font 改成 14。两者都走"读出 → 修改 → 原子替换"流程：

sequenceDiagram participant A as 请求 A participant F as 配置文件 participant B as 请求 B A->>F: 读出 (light, 12) B->>F: 读出 (light, 12) A->>A: 改为 (dark, 12) B->>B: 改为 (light, 14) A->>F: 先替换：(dark, 12) B->>F: 后替换：(light, 14) Note over F: 最终 (light, 14)
❌ A 对 theme 的修改丢失！
易错陷阱

这一节最容易混淆的一句话：原子替换 ≠ 读取—修改—保存整体原子。os.replace 只保证"换名"这一个动作不可分割；但两个请求各自基于旧版本做修改再先后替换，后写者会整个覆盖先写者的结果——这就是经典的"丢失更新"（lost update）。

要修复它，必须显式定义冲突策略，常见三种：

  1. 整体加锁：读-改-写全程持锁，把三步合成一个临界区；
  2. 版本检查后提交（乐观并发）：提交时发现版本已被别人改过，就拒绝并重试；
  3. 按语义合并：识别 A 改 theme、B 改 font 其实不冲突，合并为 (dark, 14)。

1.9 怎么测试保存功能？

针对上面三类故障，测试也必须覆盖三类场景：

测试场景做法检查什么
部分写入写入前缀后抛异常，再重开文件是否仍有完整版本（旧或新）可用
并发修改让两个请求先读同一旧版本，再依次提交冲突策略是否生效、有无丢失更新
崩溃恢复在写入、同步、替换之间注入崩溃恢复后的状态、已确认操作是否兑现
易错陷阱

测试前必须明确故障模型：杀死应用进程 ≠ 整机断电。杀进程时内核还活着，页缓存里的数据之后仍可能被写回磁盘；而断电时页缓存直接蒸发。很多"崩溃测试"只模拟了前者，却声称验证了后者。另外请记住：测试通过只说明被覆盖的执行符合要求，未覆盖的执行与假设仍需分析。

1.10 没有"标准答案"，只有"设计判断"

同一个 save_config，放在不同场景，合理实现可能完全不同：

场景合理的设计
🗂️ 可重建缓存允许丢失最近结果，未必需要每次等待持久化——fsync 的开销不值得
⚙️ 用户确认的配置变更若承诺断电后保留，就必须有完整的同步与恢复语义
👥 多人共同修改还要定义冲突策略、协调提交，避免不符合要求的覆盖

理解了文件、缓存和并发的执行机制，你才有能力判断：AI 给的方案满足了哪些条件、遗漏了哪些条件、以及付出的代价是否值得。这就是这门课要给你的判断力。

Q1. 用 open(path, "w") 打开已有配置文件后直接写入，最大的风险是什么？

✔ 正确答案：B

B 对："w" 模式的语义是"先截断到长度 0 再写"，截断发生在打开时刻而非写入时刻，所以半写失败必然留下残缺文件。A 错：截断与速度无关。C 错：with 会正常关闭文件，这与数据损坏是两个独立问题。D 错：这是常规操作，OS 不会拒绝——危险恰恰在于它"合法但危险"。

Q2. 要求"返回成功 之后断电仍保留新配置"，下列哪个序列是完整且正确的？

✔ 正确答案：C

A 错：close 只把应用缓冲推入内核页缓存，页缓存仍在内存，断电即失。B 错：缺 fsync，数据可能从未离开内存；replace 只改目录项，更不能持久化数据。C 对：数据先随临时文件落盘，再做原子替换，最后把"目录项"这个独立的持久化对象也落盘。D 错：fsync 的是文件描述符，若数据还停在 Python 应用缓冲里没 flush 下去，fsync 无数据可刷；漏掉 fsync(父目录) 则文件名映射可能丢失，重启后找不到新文件。

Q3. 关于"原子替换 + 并发修改"，下列说法正确的是？

✔ 正确答案：A

A 对：原子的只是"换名"这一步；两个请求都基于旧版本修改再先后替换，后写覆盖先写，丢失更新依旧发生。B 错：正相反，课件例子中 A 的 theme 修改就丢了。C 错：等待收集时间的是较早到达的请求，方向记反了。D 错：杀进程时内核仍在运行、页缓存可能被后续写回；断电则页缓存直接消失——二者是不同的故障模型，不可互换。

闪卡：为什么"让 AI 反复自查代码"不能保证把 bug 改对？
  1. 采分点 1：普通对话中的自查只增加上下文，不更新模型参数——模型不会"长记性"；
  2. 采分点 2：自查不产生执行证据——若测试只覆盖正常路径，"写到一半退出"这类异常永远查不出来；
  3. 采分点 3：研究证据（Huang et al., ICLR 2024）表明无外部反馈的自我纠错可能退步，甚至把正确部分改错；迭代次数不保证质量提升；
  4. 采分点 4（升华）：正确做法是用真实执行结果作为外部反馈，并人工核对测试覆盖与修改效果。

2.2 从人工操作到分时：CPU 利用率驱动的一百年

操作系统不是被"发明"出来的，而是被CPU 太贵、不能让它闲着这个经济压力一步步逼出来的：

3.1 程序怎样使用操作系统：系统调用与两种状态

以"读取文件"为例，应用程序并不能自己碰磁盘，它走的是一条受控通道：

flowchart TB subgraph U["用户态（权限低）"] A["应用程序"] -->|"read(...)"| B["库封装"] end subgraph K["内核态（权限高）"] C["系统调用入口"] --> D["检查并处理请求"] end B ==>|"切换特权级"| C D ==>|"返回结果，切回用户态"| A
  • 系统调用（System Call）：应用请求内核服务的入口，例如文件读写、创建进程；
  • 用户态 / 内核态：两种执行权限不同的 CPU 状态；普通应用运行在用户态，不能随意执行特权操作（如直接访问磁盘硬件）；
  • 注意：应用调用的普通函数不一定触发系统调用（比如算个字符串长度，全程在用户态完成）——这个话题 lesson2 会展开。

3.2 操作系统何时获得控制：中断驱动

定义

An operating system is interrupt driven. 操作系统平时"沉睡"，CPU 在跑应用程序；只有当事件发生时，控制才转入内核。这些事件统称中断（广义），分两大类：

flowchart TB I["⚡ 中断（广义）"] --> H["🔌 硬中断 hardware interrupt
由硬件设备发出"] I --> S["💻 软中断 software interrupt
由程序执行引起"] H --> H1["时钟到期（定时器）"] H --> H2["设备完成 I/O"] S --> S1["系统调用：主动请求服务，如读文件"] S --> S2["异常：执行指令时被动触发，如除零、缺页"]

一个经典场景串起所有概念：时钟中断到期 → 内核获得控制 → 调度器决定哪个任务继续运行。正因为有定时器这个硬件，操作系统才能从"不听话"的程序手中定期夺回 CPU——这是多任务得以实现的硬件基础。

易错陷阱

三者经常被混为一谈，注意区分触发来源：硬中断来自外部设备（异步、不可预测）；系统调用是程序主动请求（同步、自愿）；异常是指令执行中被动触发（如除零、缺页，同步、非自愿）。判断题常把"系统调用是硬中断"作为错误选项。

3.3 多个程序怎样共享 CPU：进程、线程与调度

  • 进程（Process）：一个程序运行时的实例，包含运行状态和所使用的资源（内存、打开的文件等）；
  • 线程（Thread）：进程内的一条执行流；同一进程可包含多个线程，它们共享进程的资源；
  • 调度（Scheduling）：决定哪个可运行的线程获得 CPU、何时切换。
flowchart LR subgraph 单核CPU上的时间轴 direction LR A["A"] --> B["B"] --> A2["A"] --> C["C"] --> B2["B"] --> D["…"] end

以单核、单硬件线程为例：多个任务轮流执行，宏观上同时进行，这叫并发（concurrency）；若有多个核心，任务真正同时运行，这叫并行（parallelism）。并发是"逻辑上的同时"，并行是"物理上的同时"——单核也能并发。

3.4 并发程序如何协作：同步与死锁

还记得第 1 章两个配置请求互相覆盖的问题吗？共享访问必须协调，这就是同步：

  • 同步（Synchronization）：用互斥、等待与通知等机制，协调共享数据的访问和执行顺序；
  • 死锁（Deadlock）：多个执行者相互等待对方占用的资源，谁都无法继续。

最经典的死锁例子——两个线程按相反顺序获取两把锁：

flowchart LR A["🧵 线程 A"] -->|"已持有"| L1["🔒 锁 1"] B["🧵 线程 B"] -->|"已持有"| L2["🔒 锁 2"] A -.->|"等待 B 释放"| L2 B -.->|"等待 A 释放"| L1
易错陷阱

"加锁可以保护共享数据"只是上半句；下半句是"锁的使用方式也需要设计"。加锁引入了新资源（锁本身）的获取顺序问题。防范死锁的思路之一是规定所有线程按一致的全局顺序获取多把锁。这一主题会在同步与死锁章节（OSC 第 6–8 章）全面展开。

3.5 程序的内存如何管理

反直觉的事实：程序看到的地址，与数据在内存中的实际位置可以不同。两个进程可以使用同一个"地址" 0x1000，却被映射到物理内存中完全不同的位置：

flowchart TB PA["进程 A：地址 0x1000"] -->|"地址映射"| M1["📍 物理位置 甲"] PB["进程 B：地址 0x1000"] -->|"地址映射"| M2["📍 物理位置 乙"]

内存管理三件大事：

  1. 分配与回收：给程序提供内存，并在不再使用时收回；
  2. 地址映射与隔离：让程序使用各自的地址空间，限制相互访问——A 崩溃不会顺手踩坏 B 的内存；
  3. 虚拟内存：按需把内容调入内存；内存紧张时，可以把部分内容置换出去——让程序以为内存比实际更大。

3.7 资源如何受到保护

  • 一个程序不能随意改写另一个程序的数据 → 地址空间与访问权限限制内存访问；
  • 普通应用不能任意控制硬件或修改内核 → 用户态/内核态 + 受控入口限制特权操作；
  • 用户不能读取自己无权访问的文件 → 身份与访问控制决定谁可以读、写、执行。
考点提示

保护（Protection）≠ 安全（Security）：保护规定"谁能访问什么"（内部的访问规则）；安全还包括防范漏洞利用和其他攻击（外部的恶意威胁）。判断题高频考点。

闪卡：线程 A 持有锁 1 等待锁 2，线程 B 持有锁 2 等待锁 1。这是什么问题？成因是什么？给出一种预防思路。

采分点 1（识别）：死锁（Deadlock）——多个执行者相互等待对方占用的资源，均无法继续。

采分点 2（成因）：两个线程以相反顺序获取多把锁，且各自持有一把不放（持有并等待 + 循环等待）。

采分点 3（预防）：规定所有线程按一致的全局顺序加锁（如永远先锁 1 后锁 2），打破循环等待；或用一次性同时申请、超时释放重试等策略。（详细四条件会在死锁章节学习，此处答出"顺序一致"即可得分。）

闪卡：为什么说操作系统是"中断驱动"的？请结合时钟中断说明这一设计的意义。

采分点 1：OS 平时不占用 CPU，CPU 执行应用程序；只有事件（中断）发生时控制才转入内核，处理完再交还——故称中断驱动。

采分点 2：中断（广义）= 硬中断（设备发出，如时钟到期、I/O 完成）+ 软中断（程序引起：系统调用、异常）。

采分点 3（意义）：时钟中断保证内核能定期夺回 CPU 控制权，从而可以切换任务——这是多道程序与分时得以实现的基础；否则一个死循环程序将永久霸占机器。

4️⃣ 系统服务与用户界面

对应 lesson2 第 2–13 页 · 从一条 cp 命令看清操作系统要提供什么

4.1 一条 cp 命令背后的系统服务

执行 cp source.txt target.txt 看似简单，操作系统却在背后提供了五类服务：

  1. 启动程序：找到并运行复制工具（程序执行服务）；
  2. 访问文件：打开源文件、创建目标文件、读出并写入数据（文件系统服务）；
  3. 管理资源：提供 CPU、内存和设备访问（资源分配）；
  4. 处理失败：检查权限、文件是否存在、磁盘是否有空间（错误检测）；
  5. 报告结果：向用户返回成功状态或错误信息。
核心直觉

把这五件事记住，"操作系统服务"这张看似庞杂的清单就有了骨架：让程序跑起来、让数据进出、让多人共享、让失败可查。下面两节就是对这个骨架的官方展开。

4.2 支持程序运行的服务

  • 用户界面（User interface）：接收命令、点击或触控输入；
  • 程序执行（Program execution）：装入程序、开始运行、正常或异常结束；
  • I/O 操作（I/O operations）：读取输入、输出结果、访问设备；
  • 文件系统操作（File-system manipulation）：创建与删除、读写与定位、目录查询、属性与权限管理。

另外还有两类容易被忽略的服务：

  • 通信（Communication）：进程在本机或通过网络交换数据。两种模型——
    • 共享内存：访问约定的共享区域，速度快，但还需要自行同步（否则就是第 1 章的并发翻车现场）；
    • 消息传递：通过管道、套接字等接口发送/接收数据，内核做中转，天然有序但多了拷贝开销。
  • 错误检测（Error detection）：识别并处理程序、设备和硬件报告的错误（如非法访问、文件读取失败）。系统可以返回错误、记录日志或终止进程——但操作系统并不能自动恢复所有错误，处理方式取决于错误类型。

4.3 共享资源需要的服务

  • 资源分配（Resource allocation）：分配 CPU 时间、内存、文件空间和设备；
  • 记录与统计（Logging / Accounting）：记录资源使用、系统事件与故障信息（出问题时靠它追溯）；
  • 保护（Protection）：规定并检查谁能访问什么，避免相互干扰；
  • 安全（Security）：身份认证、防范攻击、保护数据与系统。

例子：两个用户同时复制文件，系统既要为双方分配资源，也要检查各自的访问权限——服务清单里的条目在现实中总是同时登场的。

4.5 命令由谁解释：Shell 的角色

在终端敲下 pwd、cd /tmp、/bin/ls，处理它们的 Shell 究竟是什么？

  • Shell 读取并解析命令，然后执行内建操作或启动外部程序；
  • 内建命令：例如 Bash 的 cd——它改变的是 Shell 自己的当前工作目录，所以必须由 Shell 亲自执行，不能外包给子程序（子程序改了它自己的目录，Shell 毫无变化）；

  • 记住结论：Shell 本身也是程序，在常见 Linux 桌面或服务器环境中运行于用户态，没有任何特权。

5️⃣ 系统调用深入剖析

对应 lesson2 第 14–32 页 · 本课程第一个"硬核"章节，考试重灾区

5.1 什么是系统调用

定义

System call：程序请求内核服务的受控接口——Programming interface to the services provided by the OS。读写文件、创建进程、建立通信等操作，都需要系统提供服务。

三条关键性质：

  • 应用通常不直接发起系统调用，而是调用库或运行时的 API，由它完成底层细节；
  • 用户程序不能把内核函数当普通函数随意跳转执行——进入内核必须走体系结构规定的专用入口；
  • 内核可以用 C 等高级语言实现，但"进入内核"这一步仍需要体系结构规定的入口指令。

5.2 API、库函数与系统调用：三个层次别混淆

概念约定的对象例子
API源代码怎样调用功能（源码层规范）POSIX read()、Windows API、Java API
库 / 运行时实现参数处理、缓冲、底层调用C 标准库（glibc）、JVM
系统调用用户程序怎样受控进入内核Linux 文件读写、进程操作
易错陷阱

一次 API 调用可能对应零次、一次或多次系统调用。例如计算字符串长度 strlen 通常完全在用户态完成，零次进入内核；printf 打印文件输出可能先攒在用户态缓冲区，多次 printf 才触发一次 write。所以"程序调用了一个函数"≠"发生了一次系统调用"——判断题常客。

5.3 手把手读懂 read(2) 接口

#include <unistd.h>
ssize_t read(int fd, void *buf, size_t count);

逐部分拆解：

  • fd：从哪个已打开的文件描述符读取（文件描述符是打开文件后内核发给你的"句柄编号"）；
  • buf：读到的数据放到哪里（你提供的缓冲区地址）；
  • count：最多读多少字节；
  • 返回值（对普通文件且 count > 0）：正数 = 实际读到的字节数；0 = 到达文件末尾（EOF）；-1 = 失败，由库设置 errno 说明原因。

两个使用提示：① 读得少不一定是出错——返回正数但小于 count 是合法的（短读）；② 查询接口用法用 man 2 read（第 2 节是系统调用）；注意 Shell 里同名的 read 是另一个命令，别混淆。

5.4 复制文件的完整调用过程

flowchart LR A["打开源文件
（不存在/无权限 → 报错）"] --> B["创建目标文件
（创建方式决定覆盖 or 拒绝覆盖）"] B --> C["循环：读取与写入"] C --> D{"读到末尾 or 读取失败？"} D -->|"read 返回 0 = EOF"| E["关闭并返回成功状态"] D -->|"read 返回 -1 = 失败"| F["报错并清理"]

真正的坑在循环内部：write 也可能"短写"——你让它写 n 字节，它可能只写 k < n 字节就返回。健壮的写法必须依据返回值循环推进：

n = read(in, buf, sizeof buf);
/* n > 0: 处理数据; n == 0: EOF; n < 0: 出错 */
ssize_t sent = 0;
while (sent < n) {
    ssize_t k = write(out, buf + sent, n - sent);
    if (k <= 0) { /* 重试或报错 */ break; }
    sent += k;   /* 只推进实际写成功的部分 */
}
考点提示

短读、短写：实际完成量可能小于请求量，必须依据返回值继续推进；失败与中断：先检查错误，再决定重试、退出或清理。另外记住与第 1 章的联动：写入成功不等于断电后一定保留——write 返回只表示内核接受了数据。

5.5 一次系统调用如何进入内核

sequenceDiagram participant A as 应用（用户态） participant L as 库封装（用户态） participant E as 系统调用入口（内核态） participant H as 处理函数（内核态） A->>L: 调用 read(fd, buf, count) L->>E: 置入调用号+参数，执行入口指令 E->>E: 切换特权级，保存必要状态 E->>H: 按调用号分派 H->>H: 检查并处理请求
（必要时等待/被调度） H-->>L: 结果与错误 L-->>A: 转换成程序可用的形式返回

内核如何知道你要执行哪个操作？靠调用号（system-call number）：

  1. 每个系统调用有一个唯一编号，标识所请求的操作；
  2. 入口代码读取调用号，检查范围（防止野号），然后分派到对应处理函数；
  3. 参数与返回值的约定由操作系统和体系结构共同规定；
  4. 库封装隐藏寄存器等硬件细节，并把结果转换成程序可用的形式。
易错陷阱

进入内核 ≠ 换了一个进程。系统调用只是同一进程切换了特权级（用户态→内核态）去执行内核代码，进程身份不变。这与 fork 创建新进程完全是两回事。

5.6 参数怎样传给内核：三种一般办法

方式做法需要注意
寄存器把参数值放入约定寄存器数量与布局受 ABI 约束（寄存器个数有限）
内存块把参数结构的地址传给内核，内核自己读内核必须检查地址合法性后才能读取内容
栈按约定把参数压入用户栈内核仍需检查长度与权限

这是三种一般办法，具体系统可以组合使用。Linux x86-64 的常见约定用寄存器传参；但要注意：指针指向的数据仍在内存中——寄存器里传的只是地址。

5.7 内核为什么还要"查户口"：参数检查

以 read(fd, buf, count) 为例，内核收到请求后必须验证四件事：

  1. 对象是否有效？fd 是否真的打开着？这个文件允许读吗？
  2. 内存是否可访问？返回数据时，内核是否可以写入那个用户缓冲区 buf？（应用可能传一个只读地址甚至野指针）
  3. 长度是否合理？检查范围、边界以及可能的整数溢出（比如 count 是个巨大的数，buf+count 绕回小地址）；
  4. 请求是否被授权？应用给出了路径或句柄，不等于自动获得权限。
核心直觉

为什么必须查？因为用户态程序是不可信的——它可能有 bug，也可能是恶意程序。系统调用是用户与内核之间的边界，内核若盲信参数，一个传错的指针就能让内核读写任意内存，整个系统的保护体系瞬间崩塌。信任止于系统调用边界。

分类帮助理解职责；注意一个接口可能同时涉及多个类别（比如创建设备文件既是文件管理又涉设备管理）。

▍进程控制四剑客：fork / exec / wait / exit

flowchart TB S["🐚 Shell（父进程）"] -->|"fork() 创建"| C["👶 子进程
（父进程的副本）"] S -->|"wait() 等待"| W["取得退出状态 → 结束"] C -->|"exec 系列：替换程序映像"| E["执行新程序

  • fork()：创建一个几乎与父进程一模一样的子进程；
  • exec 系列：把子进程的程序映像整个替换为新程序（注意：exec 不创建新进程！）；
  • wait 系列：父进程等待子进程结束并取回退出状态（父进程也可以选择不等待、继续干别的）；

▍文件与设备管理

  • 文件生命周期：创建、删除、打开、关闭；
  • 数据与位置：read()、write()、lseek()（移动读写位置）；查询或设置文件属性；
  • 设备操作：打开设备、读写或发出控制请求，查询和配置设备属性；
  • 共同点：都需要检查访问条件、处理错误并管理资源；
  • 不同点：设备可能不支持定位或某种读写——不能把所有设备当作普通磁盘文件（比如键盘没有"lseek"的意义）。

▍信息、通信与保护

  • 信息维护：查询时间、进程标识、文件或设备属性；修改通常受权限限制（不是谁都能改系统时间）；
  • 消息传递：建立管道或套接字，发送、接收并报告连接状态；
  • 共享内存：建立或映射共享区域，参与者另行协调访问；
  • 保护：查询与设置权限，允许或拒绝访问。文件读写、网络通信和共享内存都必须受到访问控制。

5.10 printf 是否就是 write？——缓冲的现场实验

setvbuf(stdout, NULL, _IOFBF, BUFSIZ);  // 标准输出设为全缓冲
printf("A");
printf("B\n");
fflush(stdout);                          // 此刻才把 "AB\n" 推给内核
write(STDOUT_FILENO, "C\n", 2);          // 直接系统调用

分析：

  • printf() 负责格式化，结果先进入 C 库的用户态缓冲区；全缓冲模式下，即便内容里有 \n 也不触发写出；
  • fflush() 把缓冲内容一次性推给内核——底层通常就是 write()；
  • 用 strace 观察，只能看到两次 write：write(1, "AB\n", 3) = 3 和 write(1, "C\n", 2) = 2——两次 printf 被合并成了一次系统调用；
  • write() 成功仅表示内核接受了相应数据，不保证磁盘持久化（呼应第 1 章！）。

5.11 用 strace 偷看系统调用

gcc -O0 -g -fno-builtin hello_io.c -o hello_io
strace -e trace=write ./hello_io
# 典型输出片段（参数与返回值）：
# write(1, "AB\n", 3) = 3
# write(1, "C\n", 2) = 2
  • 输出左侧是调用及参数，右侧是返回值；它不显示 printf() 等普通库函数——因为那些根本没进内核；
  • 常用选项：-f 跟踪子进程，-c 汇总各系统调用的次数和耗时；
  • 注意：跟踪本身也会影响运行（观测者效应），性能测量时要留心。

Q2. 关于系统调用进入内核的过程，下列说法错误的是？

✔ 正确答案：D（选"错误"项）

D 错（故为答案）：进入内核只是同一进程切换特权级执行内核代码，不创建新进程。A、B、C 均为正确陈述：A 是调用号分派的标准流程；B 是参数传递三种一般办法；C 对应课件"必要时也可能先等待或被调度"。注意审题——本题选"错误"项，考试中这类反向题干是常见失分点。

Q3. 内核处理 read(fd, buf, count) 时不需要检查的是？

✔ 正确答案：C（选"不需要"项）

C 对（为答案）：权限检查针对的是"能否访问该对象"（如文件权限位），而不是"用户名是不是 root"这种身份判断；给出句柄也不等于自动获得权限。A、B、D 正是课件列出的三类必查项：对象有效性、内存可访问性、长度合理性（含整数溢出）。

闪卡（课堂练习 1）：调用 printf() 是否一定立刻发生一次 write()？依据是什么？

采分点 1（结论）：不一定。

采分点 2（机制依据）：printf 是 C 库函数，格式化结果先进入用户态缓冲区；是否触发 write 取决于缓冲策略——全缓冲模式下要等缓冲满或 fflush 才写出，行缓冲遇换行写出，无缓冲才立即 write。

采分点 3（证据方法）：可用 strace -e trace=write 实测——课件实验中两次 printf 只产生一次 write(1, "AB\n", 3)，且 strace 根本不显示 printf 这类库函数。

闪卡（课堂练习 2）：一个函数参数是用户指针，内核为什么不能直接信任它？

采分点 1（信任边界）：用户态程序不可信——可能有 bug 或恶意；系统调用是用户与内核的边界，盲信参数会让内核读写任意内存，保护体系崩溃。

采分点 2（具体风险）：指针可能指向只读/未映射/其他进程甚至内核自身的地址；长度参数可能越界或整数溢出；句柄可能无效或未授权。

采分点 3（对策）：内核必须在使用前验证——对象有效、内存可访问、长度合理、请求已授权，四项检查缺一不可。

闪卡：写出健壮的"读若干字节并全部写出"循环框架，并说明为什么必须循环。 
n = read(in, buf, sizeof buf);   /* n>0 数据 / n==0 EOF / n<0 错误 */
ssize_t sent = 0;
while (sent < n) {
    ssize_t k = write(out, buf + sent, n - sent);
    if (k <= 0) { /* 重试或报错 */ break; }
    sent += k;
}

采分点 1：read/write 都可能短读/短写——返回值可能小于请求量，必须按返回值推进偏移；

采分点 2：循环终止要区分 EOF（n==0）与失败（n<0）；写失败（k≤0）先检查错误再决定重试或清理；

采分点 3：write 成功 ≠ 数据已持久化到磁盘（呼应第 1 章 flush/fsync 语义）。

6️⃣ 从源代码到运行：编译、链接与装载

对应 lesson2 第 33–40 页 · 你敲下的 .c 文件是如何变成一个"活着"的进程的？

6.1 三段旅程：编译 → 链接 → 装载

flowchart LR A["📄 源文件 .c"] -->|"① 编译 Compile"| B["🧩 目标文件 .o"] B -->|"② 链接 Link"| C["📦 可执行文件"] C -->|"③ 装载 Load"| D["🏃 进程开始执行"]
  • 编译（Compile）：把源代码转换成目标代码（机器指令 + 数据，但地址未定）；
  • 链接（Link）：合并多个目标文件，解析符号引用，并处理重定位（把"待定地址"填上）；
  • 装载（Load）：建立运行所需的地址空间、映射与初始状态。
易错陷阱

文件在磁盘上存在 ≠ 进程已开始执行。可执行文件只是"说明书+物料"，装载这一步才由内核据此在内存中搭出运行环境。同理：编译能过 ≠ 能链接（符号可能找不到）；链接成功 ≠ 能运行（库可能缺失）。三个阶段各有各的失败方式。

6.2 链接器到底在解决什么问题？

看这两个分开编译的源文件：

/* main.c */
int add(int, int);                          /* 只有声明：add 存在，但不知道在哪 */
int main(void) { return add(2, 3) == 5 ? 0 : 1; }

/* add.c */
int add(int a, int b) { return a + b; }     /* 真正的定义在这里 */
  • 编译 main.c 时，编译器可以生成"调用 add"的指令，而不必已知 add 的最终地址——先留个"欠条"（未定义符号 + 重定位项）；
  • 链接器的工作：找到 add 的定义，把多个目标文件的代码与数据组合起来，然后修正所有欠条（填入真实地址）；
  • 动手验证：nm main.o 查看未定义符号（能看到 U add），readelf -r main.o 查看重定位项。

6.3 静态链接 vs 动态链接

比较静态链接动态链接
库代码所需代码直接并入可执行文件运行时才装入/映射共享库
部署依赖通常减少外部库依赖，拷走就能跑需要目标机器有兼容的库与加载环境
更新影响库更新后通常需重新链接可独立更新共享库，但要保持兼容
空间使用不同程序可能包含重复代码，浪费磁盘/内存多个程序可共享同一份只读代码页

两种方式都在广泛使用，程序也可以混合使用（部分库静态、部分动态）。

易错陷阱

动态链接 ≠ 进程间共享全部内存。共享的只是库的只读代码页；共享库的可写数据（全局变量等）通常仍各自隔离——每个进程有自己那份拷贝。别望文生义。

6.4 装载后，程序在哪里？

进程启动后看到的是一片虚拟地址空间，里面大致分布着：

  • 程序自己的代码与数据；
  • 共享库映射（动态链接的库被映射进来）；
  • 堆、栈与初始参数。

三个关键认知：

  1. 可执行文件格式（如 Linux 的 ELF）说明需要映射哪些段、各段的权限（代码段只读可执行、数据段可写）及程序入口点；
  2. 内核与动态加载器（ld.so）协作准备运行环境；程序通常先经过一段启动代码才到达你写的 main()——main 不是真正的起点；
  3. 代码与数据可以按需调入内存，不要求一次性复制全部文件（这正是虚拟内存的用武之地，也是大程序能秒开的原因）。

6.5 同一程序为什么不能直接跨系统运行？

把 Linux 上编译的程序拷到 Windows 双击，为什么必然失败？障碍有四层：

  1. 指令集：二进制指令要能被目标 CPU 执行（x86 的指令 ARM 看不懂）；
  2. 文件格式：目标系统要认识可执行文件的格式和装载约定（ELF vs PE）；
  3. 系统与库接口：调用的功能、版本和运行时要匹配；
  4. ABI（Application Binary Interface）：二进制层面的调用约定、数据布局等（参数放哪个寄存器、结构体怎么对齐…）。
考点提示

API vs ABI 是必考辨析：API 面向源代码的使用约定（你写代码时调什么函数、传什么参数）；ABI 关系编译后的代码能否相互配合（二进制层的调用约定、数据布局）。源码兼容（API 相同）不代表二进制兼容（ABI 相同）——同一份 C 源码在 Linux 和 Windows 都要重新编译才能跑，就是这个原因。

6.6 跨平台有哪些办法？

办法程序怎样运行仍需满足什么条件
解释器Python 等由目标平台解释器执行依赖库、平台 API、路径等兼容
虚拟机 / 运行时Java 字节码由 JVM 等执行运行时版本与本地依赖兼容
分别编译C/C++ 源码针对各平台构建源码可移植，适配平台差异

一句话总结：跨平台需要可用的运行环境；语言相同不代表程序自动兼容。（一段调用 Linux 专有接口的 Python 代码，拿到 Windows 上照样跑不了。）

7️⃣ 内核结构设计：单体、分层、微内核与模块化

对应 lesson2 第 41–52 页 · 操作系统自己的"建筑学"

7.1 设计操作系统要权衡什么

  • 用户目标：方便使用、响应及时、运行可靠；
  • 系统目标：有效利用资源，便于维护、移植和扩展；
  • 实现约束：处理器、内存、设备、应用兼容性与开发成本；
  • 实现语言：高级语言便于组织复杂系统，但底层入口仍可能需要汇编（如特权级切换那几行）。

目标之间常常互相打架：更强的隔离可能增加通信开销；更丰富的功能也会增加维护成本。没有"最好"的结构，只有"适合场景"的结构。

7.2 机制与策略：一条重要的设计原则

定义 · 必考

机制（Mechanism）：提供"能够怎样做"的手段；策略（Policy）：决定"何时做、选谁、做多少"。把机制和策略适当分离，便于改变决策而少改动底层实现。

场景机制（怎么做得到）策略（做什么决策）
CPU 调度时钟中断、保存和恢复执行状态下一次运行哪个任务
内存分配页表与映射、分配和回收操作给谁多少、何时回收

直觉类比：机制是"电梯能上下运行、能停任意楼层"，策略是"先上后下还是先送顶楼的乘客"。换策略不用重造电梯。

7.3 四种基本结构思路

▍单体内核（Monolithic）

许多核心服务（调度、内存、文件系统、驱动…）位于同一内核地址空间，直接函数调用协作。

  • ✅ 优点：内部交互方便、开销小；
  • ❌ 缺点：一处错误可能影响整个内核（驱动写崩了，整机完蛋）；
  • 代表：传统 UNIX。注意：单体内核仍可以有清晰的模块和接口——"单体"说的是运行在同一地址空间，不是代码写得乱。

▍分层结构（Layered）

每层建立在较低层的服务之上，并向上提供接口：硬件 → 硬件相关机制 → 资源管理与抽象 → 用户接口与服务。

  • ✅ 优点：便于理解依赖、局部验证与维护；
  • ❌ 难点：合理划分边界很难；逐层调用可能增加开销或限制优化；
  • ⚠️ 澄清：分层描述的是依赖关系，不等于每层都有独立的进程或权限级别。

▍微内核（Microkernel）

把更多服务（文件系统、驱动等）从内核搬到用户空间，内核只留最基础的部分，服务之间通过 IPC（进程间通信）协作。

  • ✅ 优点：更小的内核有利于隔离和验证；服务可更独立地替换或重启（文件服务崩了可以只重启它）；
  • ❌ 代价：跨地址空间通信与切换有成本，具体性能取决于设计和实现；
  • 代表：Mach 是经典例子；
  • ⚠️ 澄清：较少的内核代码并不自动保证系统无漏洞——攻击面变小不等于没有攻击面。

▍模块化（Modular）与 Linux

以明确接口组织功能，部分组件（驱动、文件系统）可动态装入和卸载，无需重启。

  • Linux 内核 = 单体内核 + 模块化的结合：许多服务仍在内核空间运行，但驱动/文件系统可配置为可加载模块（.ko）；
  • ⚠️ 关键澄清：模块加载后拥有内核执行权限、跑在内核地址空间——模块化 ≠ 微内核的进程隔离。一个坏模块照样能搞垮整个内核。

7.4 混合结构：现实系统都是"混血儿"

结构思路主要关注什么
单体多数核心服务是否同处内核空间
分层功能依赖是否按层次组织
微内核哪些服务移到用户空间并经 IPC 协作
模块化功能能否通过明确接口组合、替换或加载

这四个维度可以组合，实际系统常采用混合设计。Windows NT 系列、Apple XNU 常用于讨论混合结构；分析一个真实系统时，应看实际的边界和调用路径，而不是它自称什么。

▍案例一：macOS / iOS 与 Darwin

  • Darwin = XNU 内核 + 基础系统组件；XNU 结合了 Mach（微内核血统）+ BSD（UNIX 血统）+ I/O Kit（驱动框架）——教科书级的混合结构；
  • macOS 与 iOS 共享底层技术，但不等于应用二进制兼容：平台框架、ABI 和设备能力仍不同；
  • 移动设备还要额外考虑触控、功耗与应用生命周期。

  • ⚠️ Android 使用 Linux 内核 ≠ 桌面 Linux 的完整软件环境——内核相同，但上层的库、运行时、应用框架完全是另一套。

7.5 一个最小的 Linux 内核模块

百闻不如一见，这就是一个可加载内核模块的全部骨架：

static int __init hello_init(void) {
    pr_info("lesson2: loaded\n");   /* 内核日志打印，不是 printf */
    return 0;                        /* 返回 0 表示初始化成功 */
}
static void __exit hello_exit(void) {
    pr_info("lesson2: unloaded\n");
}
module_init(hello_init);            /* 注册入口 */
module_exit(hello_exit);            /* 注册出口 */
MODULE_LICENSE("GPL");              /* 声明许可证，否则内核会"污染"警告 */
  • 入口函数完成初始化；退出函数负责释放初始化时取得的资源（有借有还）；
  • 通过内核构建系统编译生成 .ko 文件，需要匹配的配置、头文件和内核接口版本；
  • 再次体会：insmod 加载后，这段代码就以内核权限运行——模块化给了你便利，也给了你搞垮系统的能力。

B 对：XNU = Mach + BSD + I/O Kit，教科书级混合结构。A 错：内核相同不等于软件环境相同——上层库/运行时/框架完全不同。C 错：时代记反了——Dalvik 是早期实现，ART 是当前运行时。D 错：共享底层 ≠ 二进制兼容，平台框架、ABI、设备能力仍不同。

闪卡：从隔离性、性能、可维护性三个角度对比单体内核与微内核，并各举一个代表系统。

采分点 1（隔离性）：单体所有核心服务同处内核地址空间，一处错误可影响整个内核；微内核把服务放到用户空间，服务崩溃可独立重启，内核更小、更易验证（但内核代码少 ≠ 自动无漏洞）。

采分点 2（性能）：单体内部直接函数调用，开销小；微内核跨地址空间 IPC 与切换有成本，具体性能取决于设计与实现。

采分点 3（可维护性）：微内核服务可独立替换、边界清晰；单体通过良好模块与接口也能保持清晰（单体 ≠ 代码混乱）。

采分点 4（代表）：单体——传统 UNIX / Linux（单体+模块化）；微内核——Mach。

A. 可靠性与并发（第 1–6 题）

1. 关于 open(path, "w") 的截断行为，正确的是？

✔ 正确答案：B

截断是打开语义的一部分：文件以 "w" 打开的那一刻长度就被置 0。这正是"写到一半失败"之所以致命的原因——哪怕一个字节都还没写（A 错），旧内容已经没了。C 错：close 只是收尾，截断早已发生。D 错："w" 和 "w+" 都会截断，区别只在于是否同时允许读。

2. 某进程在 os.replace(tmp, path) 之前已打开旧配置文件，替换成功后它继续 read，读到的是？

✔ 正确答案：B

打开的文件描述符绑定的是存储对象（inode）而非路径名。replace 只改"路径 → 对象"的映射：新打开的读者得到新文件，已打开旧文件的读者继续读旧对象——这是原子替换方案天然提供的读写共存能力。A 错在把 fd 当成路径的别名；C 错：对象有引用就不会消失；D 错：不存在混合这种语义。

3. 为什么持久化序列最后还要 fsync(父目录)？

✔ 正确答案：A

fsync(临时文件) 保证数据落盘；但 os.replace 改的是目录项（名字到文件的映射），这个映射缓存在内核里，不 fsync 父目录，断电后可能出现"数据在盘上、名字却指回旧文件"的诡异状态。B 错：与缓存位置无关，是两类元数据。C 错：fsync 只刷该 fd 对应对象。D 错：这正是 OSTEP 第 42 章强调的现代实践。

4. 关于"合并同步（group commit）"，下列说法错误的是？

✔ 正确答案：D（选"错误"项）

D 错在"不改变承诺"：在同步之前确认持久保存成功，改变的正是承诺本身——你宣称了一个未兑现的保证，断电时用户会以为数据已安全。A、B、C 都是课件原文的正确描述。

5. 初始配置 (light, 12)。A 读旧版→改 theme 为 dark→先替换；B 也读旧版→改 font 为 14→后替换。最终配置是？

6. 做崩溃恢复测试时，"kill -9 杀掉应用进程"为什么不能替代"整机断电"场景？

✔ 正确答案：C

页缓存属于内核而非进程。进程被杀，内核活着，缓存数据可能被后续刷盘——测试"通过"可能只是侥幸；断电时内核一同消失，未 fsync 的数据必丢。所以二者是不同的故障模型，必须先明确再测试。A 错：kill -9 必终止。B 错：杀进程同样可能留下残缺文件（若在写入中途）。D 错：正是本题要破除的误解。

D. 核心职能（第 14–18 题）

14. 程序执行到"除以零"指令时，控制转入内核，这属于哪类事件？

✔ 正确答案：D

软中断 = 系统调用（主动请求）+ 异常（指令执行中被动触发，如除零、缺页）。A 错：硬中断来自外部设备（时钟、磁盘、键盘）。B 错：除零不是"请求服务"，程序并不想触发它。判断三类的钥匙：谁发起的、主动还是被动。

15. 一个陷入死循环的恶意程序为什么无法永久霸占 CPU？

✔ 正确答案：A

OS 是中断驱动的：定时器（时钟）到期产生硬中断，CPU 必然转入内核，调度器由此定期夺回控制权——这是多任务的硬件基础。B 错：编译器不做这种事。C 错：CPU 硬件不会自动销毁进程。D 错：地址空间隔离恰恰禁止这种操作。

16. 关于进程与线程，下列说法正确的是？

✔ 正确答案：B

17. 下列哪个场景构成死锁？

18. 关于虚拟内存，下列说法正确的是？

✔ 正确答案：A

虚拟内存 = 按需调入 + 紧张时置换，制造"内存比实际更大"的假象。B 错：正相反，按需调入才允许大程序快速启动。C 错：各进程地址空间相互独立（隔离是目标，共享是例外）。D 错：这是 OS 内存管理的核心职能之一。

F. 系统调用（第 21–24 题）

21. 程序调用 strlen(s) 计算字符串长度时，发生的系统调用次数通常是？

22. 对普通文件执行 read(fd, buf, count)（count > 0），返回 0 表示？

23. 关于 Linux x86-64 上系统调用的参数传递，正确的是？

✔ 正确答案：B

寄存器传的是值和地址，大块数据（如 read 的 buf）仍留在内存，内核必须验证地址合法性后才读写。A 错：寄存器数量受 ABI 限制，放不下大块数据。C 错：栈是三种一般办法之一，不是唯一。D 错：约定由操作系统和体系结构共同规定。

24. 用 strace 跟踪一个含 printf("A"); printf("B\n"); fflush(stdout); 的全缓冲程序，关于输出说法正确的是？

✔ 正确答案：D

全缓冲下两次 printf 都进了 C 库缓冲区，fflush 时才合并成一次 write 进入内核；strace 跟踪的是系统调用，不显示 printf 这类普通库函数。A、C 错在假设 strace 能看到库函数；B 错在假设逐 printf 写出（那是无缓冲模式）。

G. 编译链接、内核结构与构建调试（第 25–30 题）

25. "编译通过但链接失败"最可能的原因是？

✔ 正确答案：C

链接器的职责是解析符号引用：编译只需声明即可留下"欠条"，链接时必须找到定义，否则报 undefined reference。A 错：语法错误在编译阶段就失败。B 错：指令集问题要到运行时才暴露。D 错：那是装载阶段的问题。三个阶段各有各的失败方式——这正是 6.1 节的易错点。

✔ 正确答案：A

API 面向写代码的人（调什么函数、传什么参数）；ABI 管编出来的码（参数放哪个寄存器、结构体如何对齐）。B 错：源码兼容 ≠ 二进制兼容，这正是"同一源码要分别编译"的原因。C 错：ABI 由 OS 与体系结构共同决定。D 错：Java API 是源码层规范。

27. 下列哪个系统结构的说法正确体现了微内核的代价？

✔ 正确答案：B

隔离的收益（服务可独立重启、内核更易验证）以 IPC 与特权级/地址空间切换的开销为代价。A 错：那是单体内核的形态（且直接调用恰是其优点）。C 错：内核小 ≠ 无漏洞。D 错：服务在用户空间，崩溃通常可独立重启——这正是微内核的卖点。

28. 关于 Android 系统结构，下列说法正确的是？

✔ 正确答案：D

三个要点缺一不可。A 错：应用运行在 ART + Android 框架之上。B 错：时代颠倒——Dalvik 是早期实现。C 错：内核相同 ≠ 环境相同（库、运行时、框架完全不同），这与"同 CPU 也不能直接运行可执行文件"是同一道理。

29. 开机后屏幕上出现 "No working init found" 并卡死，说明启动链在哪一阶段失败？

✔ 正确答案：A

30. 程序响应很慢，top 显示 CPU 占用仅 5%。下列分析最合理的是？

✔ 正确答案：C

CPU 占用低 ≠ 没有瓶颈——等待 I/O、等待锁时线程不占 CPU。A 正是新手误判。B 错：瓶颈很可能根本不在 CPU。D 错：工具本身有开销（strace 会显著拖慢），观测会扰动被测系统，性能数字要在相同条件下比较。

LESSON 3 · 模块 10

10. 程序如何变成一个可管理的进程

对应 lesson3 第 2–6、9–13 页（按 PDF 页码）

先把“磁盘上的程序”和“正在运行的实例”分清，再看内存里有什么、内核用什么记住它。这是后面理解调度、fork 和线程的共同起点。

10.1 一份菜谱，可以有多次独立烹饪

程序（Program）是磁盘上的指令和初始数据，是静态对象；进程（Process）是程序的一次执行，有自己的身份、进度和资源。打开两个独立终端，可能是同一个 Shell 程序的两个进程。两者代码可以相同，却分别执行到不同位置，打开不同文件。进程可以暂时没有占用 CPU，等待中的它仍然存在。

定义

进程是执行中的程序及其运行状态和资源。PC（Program Counter，程序计数器）记录下一步执行位置；寄存器保存当前计算现场。仅有一份可执行文件，还不足以恢复一次执行。

10.2 地址空间：程序眼中的内存地图

地址空间是进程可以使用的地址及其映射规则。这里主要讲虚拟地址：相同数值的地址在不同进程里可以对应不同物理页。内核与硬件共同完成地址转换与访问保护。下面是教材的简化布局，实际布局受系统、架构、装载器和地址随机化影响。

#include <stdio.h>
#include <stdlib.h>
int x;            /* 全局未显式初始化：零初始化，常在 BSS */
int y = 15;       /* 全局已初始化数据 */
int main(int argc, char *argv[]) {
    int *values;  /* 指针变量本身是自动局部变量 */
    int i;
    values = (int *)malloc(sizeof(int) * 5);
    for (i = 0; i < 5; i++)
        values[i] = i;
    return 0;
}

这是第 6 页代码的文字还原。values 本身与 values 指向的 5 个整数要分开看：前者是局部指针，教材通常放在栈；后者是动态对象，通常在堆。编译器也可能把局部变量放在寄存器或优化掉。示例只用于位置辨认，实际程序应检查 malloc 是否返回 NULL，并在不再使用时 free(values)；本例返回 main 后进程退出，由系统回收地址空间。

10.3 PCB 是内核保存的“进程档案”

PCB 信息具体内容为什么需要
身份与状态PID、父进程关系、进程状态辨认任务，知道它在运行还是等待
执行上下文PC、寄存器、栈指针等暂停后能准确恢复
调度信息优先级、队列连接、使用统计选择下一个运行者并核算资源
内存信息地址空间、页表等关联信息恢复正确的地址解释与保护
资源与权限打开文件、身份、通信端点等正确使用与回收资源

PCB（Process Control Block，进程控制块）是内核数据结构，不是进程的全部内存。进程的代码、堆和栈通过管理信息关联起来，不会全部塞进 PCB。进程离开 CPU 后，PCB 仍然存在，否则就无从恢复。Linux 用 task_struct 等结构及其指向的对象表示任务与资源。

ps -o pid,ppid,stat,comm -p $$
cat /proc/$$/status

在 Linux Shell 中 $$ 是当前 Shell 的 PID。ps 看 PID、父 PID、状态与命令名；/proc 暴露内核提供的信息。R 同时包含正在运行和可运行，S 通常为可中断睡眠，Z 是僵尸。读取的是瞬间快照，两次结果可以不同。多线程进程里，每条线程各有 PC、寄存器与栈，通常共享进程资源，详见模块 16。

同一程序启动两个独立进程，哪项最准确？

B 对：同一个程序可以有多次独立执行。A 错：调度和输入使进度不同。C 错：只读代码页可以共享，独立地址空间不要求所有物理页独立。D 错：等待只是状态变化，进程仍存在。

局部指针 p 指向 malloc 得到的对象，教材模型中通常怎样放置？

C 对：区分指针变量和它指向的内存。A、B 把两者混为一谈，而且“必然”忽略优化。D 错：PCB 保存管理信息，不装载动态对象的全部内容。

为什么进程没有运行时仍要保留 PCB？

A 对：挂起期间仍需要身份、上下文与资源关系。B 错：非运行任务不占该 CPU 执行。C 错：代码属于地址空间。D 错：何时运行取决于调度与事件。

用“程序、地址空间、PC、PCB”四个词解释一次执行。

① 程序提供静态指令与初始数据。② 系统为一次执行建立地址空间和资源。③ PC 与寄存器描述执行进度。④ 内核通过 PCB 及关联结构管理和恢复这次执行。每点可作为一个采分点；不要把 PCB 等同于整个进程，也不要把虚拟地址等同于物理地址。

LESSON 3 · 模块 11

11. 状态、队列与上下文切换

对应 lesson3 第 7–8、14–20 页（按 PDF 页码）

想象单个 CPU 核是一张工作台：准备好的人排队，等材料的人暂时离开。调度解决谁来用工作台，上下文切换负责收拾旧现场并恢复新现场。

11.1 五态模型与六条关键转换

状态含义还缺什么
New 新建系统正在准备这个进程创建和接纳完成
Ready 就绪具备执行条件CPU 执行机会
Running 运行正在 CPU 上执行当前已经得到 CPU
Waiting 等待/阻塞等待 I/O、消息或其他事件所等待的事件完成
Terminated 终止执行结束，进入清理回收退出信息的最终回收
易错陷阱

就绪等的是CPU，阻塞等的是事件。I/O 完成只恢复执行条件，CPU 可能正被别人使用，因此通常先 Waiting → Ready，再经调度 Ready → Running。教材五态模型中不能把 Waiting → Running 当作无需调度的一步。

11.2 队列组织任务，调度策略决定先后

就绪队列组织所有可运行任务；设备、消息等等待队列组织正在等相应事件的任务。队列一般保存 PCB 或任务结构的引用、嵌入式链表节点等连接关系。任务本身不需要在内存中被整体搬进搬出。单链表只有后继，双链表有前后链接，循环链表把末尾连接到开头；Linux 常将链表节点嵌在对象内部。

“用链表还是树组织任务”和“优先调度谁”是两个问题。数据结构影响查找和增删效率，调度策略权衡响应、公平和利用率；队列这个词不保证所有系统都按先进先出运行。单核任一时刻至多执行一个普通线程，多核可同时执行多个可运行线程。

11.3 切换现场的完整逻辑

保存现场不是重新运行程序：恢复后从上次暂停的位置继续。直接开销包括保存、恢复和调度本身；间接开销可能来自缓存与地址转换状态的变化。切换期间不能推进被暂停任务的用户计算，但等待 I/O 时让出 CPU 可以提高整体利用率；时间片切换还能维持交互响应和公平。目标是减少无必要的频繁切换，而非消灭所有切换。

考点提示

进入内核 ≠ 一定切换进程。一个系统调用可以在当前进程的内核执行路径中完成，然后返回原来的任务。只有当内核决定让另一个任务运行时，才发生任务之间的上下文切换。

交互式检验区 · 先回忆，再作答

一个等待磁盘读的进程，其 I/O 完成后通常先进入什么状态？

B 对：事件完成恢复执行条件，仍要竞争 CPU。A 错：不是重新创建。C 错：忽略 CPU 是否可用和调度。D 错：I/O 完成不是退出。

LESSON 3 · 模块 12

12. fork、exec、wait 与进程的生命周期

对应 lesson3 第 21–33、69 页（按 PDF 页码）

Shell 运行命令，是理解创建、程序替换和退出回收的最好入口。先区分三个动作，再推导父子进程的执行顺序。

12.1 父子关系与进程树

系统初始化会建立早期进程，已有进程又能创建子进程。PID 标识进程，父子关系形成树；父子可以并发推进，也可以通过等待建立先后关系。不同创建接口可以选择复制、共享或替换不同资源，不能把一种接口的行为当成所有系统的规则。

12.2 fork：一次成功创建，父子各继续一次

pid_t pid = fork();
if (pid < 0) {
    /* 创建失败：只有原父进程继续，返回 -1 */
} else if (pid == 0) {
    /* 子进程：返回 0 */
} else {
    /* 父进程：返回值是子进程 PID */
}

成功时并不是一个进程里的同一函数先后普通返回两遍，而是系统创建了第二个执行实例，父、子各自得到返回值，并从 fork 之后继续。父子谁先运行没有默认保证。失败则没有子进程。只在每条执行路径都无条件成功调用 n 次 fork 时，才有总数 \(2^n\)，新增数 \(2^n-1\)：从 1 个开始，每轮翻倍，\(P_{k+1}=2P_k, P_0=1\)。条件分支、提前退出、exec 或失败会改变计数。

fork 后的对象关系推论
普通全局/局部变量初值相同，之后通常各自修改子进程改 x 不会自然修改父进程的 x
虚拟地址空间各自独立；Linux 常用写时复制 COW初期可共享物理页，写入时再分离，语义仍是独立
继承的文件描述符可指向相同的打开文件描述文件偏移、部分状态可共享；不能把所有资源都当作深拷贝
PID 与执行进度PID 不同，后续独立推进fork 返回值能区分父子分支
用户态 stdio 缓冲进程内存中的缓冲也可能被复制fork 前未刷出的内容可能由父子分别刷新
易错陷阱

相同虚拟地址、相同初值、相同物理页（写时复制初期）都不等于共享同一个可写变量。输出顺序还要区分 printf 的调用顺序与实际刷到终端/文件的顺序；需要时在 fork 前 fflush。

12.3 exec 替换程序，wait 等待并回收

接口做什么不应混淆
fork创建子进程子进程最初延续原程序
exec 系列当前进程装入并执行新程序，通常保留 PID成功不返回旧程序，失败才返回错误
wait / waitpid等待子进程状态变化，取得并回收退出信息不是创建进程，也不是让所有父子代码严格串行

12.4 课件第 27 页：把输出当作偏序推导

#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>
int main() {
    pid_t pid = fork();
    printf("[0] Hello from %d\n", pid); /* 0 */
    if (pid == 0) {
        printf("[1] [Child] before exec\n"); /* 1 */
        execlp("echo", "echo", "\033[31m[2] Hello from the echo command!\033[0m", NULL); /* 2 */
        printf("[3] [Child] after exec\n"); /* 3 */
    } else {
        int status;
        waitpid(pid, &status, 0);
        printf("[4] [Parent] child exited with code %d\n", WEXITSTATUS(status)); /* 4 */
    }
}

以上逐字还原课件图片中的主要代码。先假设 fork、exec、waitpid 成功，子进程正常退出，且输出及时刷新。记父进程的 [0] 为 P0，子进程的 [0] 为 C0。子进程内部 C0 → [1] → 新程序 [2]；父进程 P0 → waitpid 返回 → [4]。子进程退出后 [4] 才能执行，所以 [2] → [4]。没有默认的 P0 与 C0 先后关系。

考点提示

成功 exec 后，旧地址空间的代码被替换，因此 [3] 不会执行。例如 P0、C0、1、2、4 可以出现；C0、1、P0、2、4 也符合偏序。若重定向到文件，子进程 exec 前未刷新的 stdio 缓冲可能丢失，不能只凭换行推断可见输出。原图为教学简化：实际应处理 fork 失败、检查 waitpid、先判断 WIFEXITED；execlp 的可变参数结尾使用 (char *)NULL 更严谨。

12.5 正确读取退出状态

/* 完整 Linux/POSIX 示例：fork 后执行 echo，父进程读取退出结果。
   编译：cc -std=c11 -Wall -Wextra fork_wait.c -o fork_wait */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
int main(void) {
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return EXIT_FAILURE; }
    if (pid == 0) {
        execlp("echo", "echo", "hello", (char *)NULL);
        _exit(127); /* 只有 exec 失败才到这里，不刷新继承的 stdio 缓冲 */
    }
    int status;
    pid_t r;
    do { r = waitpid(pid, &status, 0); }
    while (r < 0 && errno == EINTR);
    if (r < 0) { perror("waitpid"); return EXIT_FAILURE; }
    if (WIFEXITED(status))
        printf("exit=%d\n", WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("signal=%d\n", WTERMSIG(status));
    return EXIT_SUCCESS;
}

status 是编码后的状态，不是直接的退出码。先检查等待是否成功，再以 WIFEXITED 判断正常退出，成立后才用 WEXITSTATUS；被信号终止则 WIFSIGNALED / WTERMSIG。EINTR 表示等待被信号打断，可按接口规则重试。正常返回 main 或调用 exit 会结束进程；未处理的致命信号也可能使它终止，其他进程在权限允许时能发送信号请求结束。

情形准确含义处理
僵尸 Zombie子进程已退出，退出信息还未被回收父进程 wait 系列回收，已释放大多数运行资源
孤儿 Orphan原父进程先结束，子进程仍存在Linux 中重新托管，由相应托管者负责后续回收
易错陷阱

“父进程没 wait”不意味着活着的子进程就是僵尸；判定还需要子进程已经结束。父亲退出也不意味着子进程必然跟着退出，是否终止取决于信号、系统与管理策略。

12.6 把生命周期放回手机和浏览器

手机屏幕上不可见的应用仍可能耗 CPU、内存和电量。课件介绍 Android 按前台、可见、服务、缓存等重要性及资源压力管理进程，iOS 提供受系统调度与条件限制的后台任务。应用必须保存可恢复状态，“在后台”不代表能够永久运行。浏览器采用多进程，将窗口协调、页面渲染、GPU、网络等工作分开，以资源和 IPC 成本换取故障隔离、安全边界与并行。

13. 共享内存与生产者—消费者

对应 lesson3 第 34–45 页（按 PDF 页码）

进程隔离保护了数据，也使协作必须经过明确机制。先用“一个人放视频帧，一个人取帧编码”理解缓冲，再把共享位置与同步顺序分开。

13.1 IPC 的两种基本思路

IPC（Interprocess Communication，进程间通信）支持信息共享、计算协作、模块化与隔离。生产者生成数据，消费者处理数据。共享内存让双方访问同一数据区域；消息传递通过发送、接收接口交换数据。无论哪种方式，都要管理权限、并发、格式和生命周期。

维度共享内存消息传递
数据位置共同映射的区域发送缓冲、通信通道与接收端
程序动作按约定读写数据结构按接口发送和接收
主要约定布局、读写顺序、同步格式、寻址、等待、容量
典型直觉本机大量数据协作边界明确的本机或跨机通信

13.2 缓冲区为何让双方不必同速

缓冲区暂存“已生产但还没消费”的数据，吸收短期速度差。有界模型容量固定，空时消费者不能取，满时生产者不能放；条件改变后通知等待方。无界模型忽略“满”，消费者仍可能等数据，真实机器当然仍受内存限制。若生产速度长期超过消费速度，任何有限缓冲最终都会满。

补充推导：环形缓冲

设数组有 N 个槽，in 指向下一写入位置，out 指向下一读取位置，每步按模 N 回绕。若约定 in=out 为空，并保留一个空槽区分满空，则满的条件为 \((in+1)\bmod N=out\)，有效容量为 N−1。若想存满 N 项，就需额外计数或其他判别状态。该补充模型帮助理解边界，不表示课件容量 4 的缓冲只能放 3 项。

读写索引、数量和数据必须一致。同步需要同时考虑：互斥（不能不受控地修改同一数据结构）与条件顺序（没数据不能取、没空位不能放）。简单忙等一个普通 ready 变量不自动获得跨进程可见性与排序保证；volatile 也不能替代同步。

13.3 POSIX 共享内存的四个阶段

两个进程的映射基址可以不同，但映射到同一组共享页。共享的是指定区域，不是自动共享整个堆、栈和全局变量。共享结构里宜保存数组索引或相对于共享区域的偏移，不能假定进程 A 的裸指针在进程 B 也有效。shm_unlink 去掉名称，现有映射按其生命周期继续存在，最后引用消失后对象资源才能最终回收。

13.4 还原第 44–45 页：先写完，再发布

/* 准备阶段，在 fork 前执行；需 sys/mman.h、sys/stat.h、fcntl.h、
   unistd.h、semaphore.h、stdio.h 等头文件。
   以下为课件两个片段的还原，不是独立完整程序。 */
struct message {
    sem_t ready;
    char text[128];
};
int fd = shm_open("/ipc_example", O_CREAT | O_EXCL | O_RDWR, 0600);
ftruncate(fd, sizeof(struct message));
struct message *shared = mmap(NULL, sizeof *shared,
    PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
close(fd);
sem_init(&shared->ready, 1, 0);

/* parent: producer */
snprintf(shared->text, sizeof shared->text, "hello");
sem_post(&shared->ready);

/* child: consumer */
sem_wait(&shared->ready);
printf("%s\n", shared->text);

两个尾部片段应分别放进 fork 后的父、子分支，不能顺次放在同一个执行路径来代替通信。sem_init(..., 1, 0) 的 1 是跨进程共享，0 是信号量初值，信号量对象本身必须位于共享区域。子进程若先到，会在 sem_wait 等；父进程先写完整字符串，再 sem_post；子进程在成功等待后才读。若父先发布，信号量保留可取得的通知，不要求子进程那一刻已经等待。

边界与清理

这里只有一次字符串传递。多次发送需要消费者确认已读或用空位/数据计数控制，防止覆盖尚未消费的数据。实际程序还需逐项检查 shm_open、ftruncate、mmap（失败为 MAP_FAILED）、sem_init 和 fork；sem_wait 遇 EINTR 可重试。结束时先确保无人再等待或使用信号量，再 sem_destroy、munmap，并由约定负责人 shm_unlink。

LESSON 3 · 模块 14

14. 消息传递、管道与通信边界

对应 lesson3 第 46–58、69 页（按 PDF 页码）

通信设计要同时回答：发给谁、是否等待、能暂存多少，以及一条消息在哪里结束。管道把这些抽象问题变成能直接观察的 read 与 write。

14.1 寻址：直接找人，还是发到邮箱

方式接口直觉需要明确的规则
直接通信send(P, message)，指定通信对方教材对称模型中双方相互命名，每对进程有链路
间接通信send(A, message)，指定共同邮箱/端口邮箱的创建、权限、收发、删除与接收者选择

邮箱让接收位置与具体接收者解耦，同一对进程可以使用多个邮箱，一个邮箱也可有多参与者。但共享邮箱不等于广播。若 P2、P3 同时接收同一邮箱，接口必须约定限制为一对一、同一时刻只允许一个接收者，或按规则选一个接收者；是否告知发送者也由协议确定。广播或发布订阅需要额外明确的复制和分发约定。消息还需约定固定或可变长度、格式、单向/双向以及连接参与方。

14.2 阻塞、非阻塞与缓冲容量是不同维度

操作阻塞方式非阻塞方式
接收没有可用消息时等待立即返回，报告暂无数据等状态
发送未达到接口完成条件时等待不能立即完成时返回当前状态，可能只完成部分

零容量不暂存消息，需要发送、接收配合交接，可形成 rendezvous（会合）；有界容量可暂存有限消息，满时可能等待、报错或丢弃，以接口为准；无界容量模型忽略满，真实系统仍有资源上限。阻塞发送不必等到对方完成业务，有缓冲时可能只要入队就返回。发送完成条件必须读接口约定。

14.3 普通管道：两个描述符，一条单向字节流

int fd[2];
pipe(fd); /* fd[0] 是读端，fd[1] 是写端 */

Linux 普通管道通常供能取得同一组端点的进程通信，常见做法是 pipe 后再 fork，让父子继承端点。它是单向字节流，一次 write 不保证对应一次 read。连续写入 hello 和 world，接收端可能分多次或一次读到组合字节；应用要用长度、分隔符等建立自己的消息边界。双向交流通常需两条管道或选用支持双向的其他机制。

14.4 带短读写与 EINTR 处理的完整管道例子

/* Linux/POSIX；编译：cc -std=c11 -Wall -Wextra pipe_demo.c -o pipe_demo */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
static int write_all(int fd, const char *p, size_t left) {
    while (left > 0) {
        ssize_t n = write(fd, p, left);
        if (n < 0 && errno == EINTR) continue;
        if (n <= 0) return -1;
        p += n;
        left -= (size_t)n;
    }
    return 0;
}
int main(void) {
    int fd[2];
    if (pipe(fd) < 0) { perror("pipe"); return EXIT_FAILURE; }
    pid_t pid = fork();
    if (pid < 0) {
        perror("fork"); close(fd[0]); close(fd[1]); return EXIT_FAILURE;
    }
    if (pid == 0) {
        close(fd[1]); /* 若漏关，自己的写端也会阻止 EOF */
        char buf[64];
        for (;;) {
            ssize_t n = read(fd[0], buf, sizeof buf);
            if (n < 0 && errno == EINTR) continue;
            if (n < 0) { perror("read"); close(fd[0]); _exit(1); }
            if (n == 0) break;
            if (write_all(STDOUT_FILENO, buf, (size_t)n) < 0) {
                close(fd[0]); _exit(1);
            }
        }
        close(fd[0]);
        _exit(0);
    }
    close(fd[0]);
    const char *msg = "hello\n";
    int failed = write_all(fd[1], msg, strlen(msg)) < 0;
    if (failed) perror("write");
    close(fd[1]); /* 在 wait 前关闭，让子进程读完后看见 EOF */
    int status;
    pid_t r;
    do { r = waitpid(pid, &status, 0); } while (r < 0 && errno == EINTR);
    if (r < 0) { perror("waitpid"); return EXIT_FAILURE; }
    return (!failed && WIFEXITED(status) && WEXITSTATUS(status) == 0)
        ? EXIT_SUCCESS : EXIT_FAILURE;
}

它扩展了第 56 页的父写子读片段：一次 read 实际返回 n 个字节，就只处理这 n 个；短写后继续发送剩余部分；信号打断时按条件重试。若所有读端关闭后仍写，POSIX 还涉及 SIGPIPE/EPIPE，通用程序需按需求设置处理策略；本例假设标准输出正常、读者按协议存活。

管道 EOF 的两个必要条件

read 返回 0 的条件是缓冲已空，并且所有写端都已关闭。有数据先读数据；无数据但仍有任何写端时，阻塞 read 通常继续等待。子进程忘关自己继承的写端也会等不到 EOF；父进程若等子退出后才关写端，可能双方互等。

14.5 命名管道 FIFO

FIFO 有文件系统路径，不相关进程可按名称打开同一通信对象。路径用来定位通道，传输字节不作为普通文件内容永久保存。Linux FIFO 的 I/O 语义类似普通管道，不能默认视为全双工。Windows 命名管道有可配置的方向与模式，不能将平台差异抹平。多读者、多写者仍需约定谁接收，以及如何划分消息。

LESSON 3 · 模块 15

15. Socket、RPC 与跨机器的不确定性

对应 lesson3 第 59–67、69–70 页（按 PDF 页码）

从管道走向网络，首先增加的是端点定位和连接管理；把收发包装成函数调用后，又必须面对数据格式、超时和重复执行。

15.1 Socket 是通信端点

Socket 可用于本机或跨机器 IPC。对 TCP/IP，要区分地址、端口与协议：IP 帮助找到主机/网络接口，端口帮助定位传输层端点，还需知道用 TCP 还是 UDP。127.0.0.1 是 IPv4 回环地址，指向本机。一个 TCP 连接通常由协议及两端 IP、端口共同区分，不能只用服务端端口当作所有连接的唯一编号。

TCP 提供有序字节流，仍需应用规定消息长度、换行分隔或其他帧格式。例如约定一条请求以换行结束，接收端就必须累积读取到换行再处理；一次 recv 不一定恰好是一条请求。send 成功不代表对方业务已经完成，它通常只说明满足了该发送接口的完成条件。

15.2 把 add(2,3) 包成 RPC，发生了什么？

RPC（Remote Procedure Call，远程过程调用）把远端请求包装成类似本地函数调用的接口。stub（存根）承担参数编码、发送与结果解码等工作，调用者仍需处理连接失败、超时、服务地址配置或发现。

15.3 机器之间必须约定数据表示

不同机器可能有不同字节序、整数宽度与结构体填充。序列化/编组（Serialization/Marshalling）将逻辑数据转成约定字节格式；接收端按相同格式还原。XDR（External Data Representation）是课件举出的外部数据表示标准。协议还应规定类型、长度、版本及错误表示。不能把本机指针值当作远端有效地址，要传对象内容或双方约定的标识。

15.4 超时后的两种世界

语义/性质含义边界
至多一次 At most once利用请求标识、去重等抑制重复执行允许没有完成，不能保证每个请求都成功
至少一次 At least once在相应故障与可恢复条件下重试争取完成一次逻辑操作可能执行多次，永久故障下不能保证成功
幂等 Idempotent重复执行产生的目标效果与一次相同如把目标状态设为固定值；不等同于操作毫无副作用
恰好一次需要定义跨重试、崩溃和业务提交的完整条件不能仅凭使用 RPC 或 TCP 得出保证
易错陷阱

“余额设为 100”可设计为幂等，“余额减少 100”通常非幂等。对非幂等业务，重试应复用同一逻辑请求 ID，并将去重记录与业务提交协调；每次重试随意生成新 ID 会失去识别同一请求的能力。超时意味着结果未知，不能直接推断失败或未执行。

15.5 选讲：/proc 如何把内核信息变成文本

自定义 /proc 条目也可以在回调中用 current 取得当前任务信息；proc_ops 指定文件操作回调，seq_file 帮助按读取位置分批生成文本。内核模块要按目标内核版本构建，不能把任意旧版本字段直接套到另一版本。本课以工作流程为目标，不要求运行自定义模块。

16. 线程：共享资源的多条执行流

16.1 一间工坊，多位工人

进程提供地址空间与资源，线程（Thread）是其中的一条执行流。同一进程可以有多个线程，它们通常共享代码、全局数据、堆与打开文件，每条线程各自保存执行进度和栈。进程侧重资源组织与隔离，线程侧重执行和调度。内核本身也会使用多线程或多个内核任务，让不同工作等待不同事件。

16.3 并发不等于并行

并发（Concurrency）表示多项任务在同一时间段内推进，可以交替也可以同时；并行（Parallelism）要求同一时刻实际执行多个任务。单核通过切换可形成并发，但同一时刻只能执行一个普通线程的指令；多核才提供线程计算并行的硬件机会。线程很多不等于当下正在并行的线程很多。

16.4 把任务拆开之前，先找依赖

多核编程要考虑任务划分、负载均衡、数据划分、数据依赖，以及不同调度下的测试与调试。图像处理可把像素分块，让每核对不同数据做相同操作，这是数据并行；也可拆成解码、滤镜、编码等不同功能，这是任务并行。任务并行可以处理相同或不同数据，二者也可组合使用。若滤镜依赖解码结果，就不能让同一帧的后续阶段无条件先运行；不同帧可按协议流水推进。

17. Amdahl 定律：更多核心能快多少

对应 lesson4 第 13–16、64 页（按 PDF 页码）

先固定同一份工作量，把单核耗时分成“必须串行”和“可以平分”两部分，再从时间相加推导加速比。公式记忆应建立在这条时间账上。

17.1 从执行时间一步步推导

设单核执行固定工作量用时 \(T_1\)，其中串行比例为 \(S\)，可并行比例为 \(1-S\)，使用 \(N\) 个核，\(0\leq S\leq1\)，\(N\geq1\)。先假设并行部分能均匀划分、所有核同速、没有额外通信和同步成本。

① 串行部分无法被分摊：\[T_{serial}=S T_1\]

② 可并行部分单核耗时：\[T_{parallel,1}=(1-S)T_1\]

③ 均分给 N 核后的理想耗时：\[T_{parallel,N}=\frac{(1-S)T_1}{N}\]

④ 两部分先后完成，总时间相加：\[T_N=ST_1+\frac{(1-S)T_1}{N}=T_1\left(S+\frac{1-S}{N}\right)\]

⑤ 加速比是旧时间除以新时间：\[Speedup(N)=\frac{T_1}{T_N}=\frac{1}{S+(1-S)/N}\]

串行部分像打包行李：即使有很多人帮忙并行清点不同物品，最后只有一个人核对并封箱的时间仍无法平分。加速比 2 表示同样工作用时减半，不是“时间增加两倍”。

17.2 课件算例与极限条件

课件例：\(S=0.25,N=2\)。先算 \(T_2/T_1=0.25+0.75/2=0.625\)，所以 \(Speedup=1/0.625=1.6\)。若 \(T_1=100s\)，串行 25s，另 75s 分为 37.5s，总共 62.5s。

当 \(S>0\)，\(N\to\infty\) 时，\((1-S)/N\to0\)，故 \[\lim_{N\to\infty}Speedup(N)=\frac1S.\] 当 \(S=0\)，理想模型中 \(Speedup=N\)，不存在固定的有限上限；当 \(S=1\)，加速比恒为 1；当 \(N=1\)，对任意 S，加速比也为 1。

题目若给的是“可并行比例 P”，先转换 \(S=1-P\)，再代入。S 是单核基准中的时间比例，不是某一段代码占源码行数的比例。固定工作量和理想均分是公式的前提。

17.3 为什么实测可能比理想值更慢

把额外开销记为 \(O(N)\)，可写成补充模型：\[T_{actual,N}=T_1\left(S+\frac{1-S}{N}\right)+O(N).\] 线程创建、调度、数据交换、锁等待、缓存竞争、内存带宽瓶颈、负载不均都可能让 \(O(N)\) 增大或破坏均分假设，因此核数更多甚至可能更慢。

Amdahl 定律固定问题规模；如果加核心时也增大数据量，必须重新定义基准，不能把不同工作量的总用时直接拿来当同一加速比。比较性能要记录工作量、核数、线程数、编译设置与运行条件。理想公式用于识别串行瓶颈，不能取代测量。

18. 用户线程到内核线程的映射

对应 lesson4 第 17–23、64 页（按 PDF 页码）

用户程序看到的“一个线程”，需要借助内核可调度实体才能运行。映射模型描述两层执行者之间的关系，不能直接用 API 名称或线程总数猜测。

18.1 两层管理者

用户级线程由用户空间的库或运行时管理；内核级执行实体由内核保存状态并调度到 CPU。接口规定“如何创建、等待”，实现决定“具体映射到谁”。Pthreads 是接口标准，Windows API 和 Java Thread 也不能仅凭名称就推导所有底层模型。Windows、Linux、macOS 都支持内核调度的线程。

18.2 四种模型，逐个看阻塞与并行

模型阻塞与并行成本与实例（依课件）
多对一 M:1唯一内核线程若真正阻塞，其上所有用户线程都无法继续；无法多核同时执行这些线程用户态切换可较轻；历史实例 GNU Pth，协作式调度，库可通过事件式 I/O 协调等待

多对一里“一个阻塞全受影响”特指唯一承载的内核执行实体被阻塞；若线程库将 I/O 等待转为事件并运行其他用户线程，则不必真的堵住它。多对多也不能凭模型名字保证任何阻塞都无影响，需要看运行时实现。Java 21 起正式支持虚拟线程，课件用它说明 JVM 层的调度可以与操作系统原生一对一线程同时存在。

三个不能画等号

一对一不等于一线程绑定一 CPU 核；内核调度可以迁移线程。两级模型中的绑定对象是内核线程/内核执行实体，不是固定物理核。用户线程数量也不等于可同时并行的数量：内核实体、可用核数、可运行状态和运行时限制都影响上限。

18.3 三个情境快速判断

  • 三个用户线程只共用一个内核线程：即使机器有 8 核，这三条执行流也不能同时占用多个核计算。
  • 三个原生一对一线程运行在 2 核：最多同时有两条执行流在这些核上计算，其余等待调度或事件。
  • 很多 goroutine 复用少量操作系统线程：用户任务多不要求同量内核线程，运行时负责复用；I/O 和 CPU 工作的实际表现仍需区分。

LESSON 4 · 模块 19

19. 显式线程编程：创建、传参、等待

对应 lesson4 第 24–29 页（按 PDF 页码）

读多线程代码时，分别检查参数是否仍有效、共享访问是否同步、最后是否等到了完成。这三个要求互相独立，sleep 和 join 各自都解决不了所有问题。

19.1 Pthreads 的创建与等待协议

pthread_create(&tid, attr, work, arg) 创建执行流，新线程从 work(arg) 开始，创建者继续；默认属性可传 NULL。线程函数返回或调用 pthread_exit 结束当前线程。pthread_join 等待指定可等待线程终止，并可取得其返回指针。多数 Pthreads 接口直接返回错误编号，与许多系统调用的返回 −1 并设置 errno 不同。

/* 课件第 25 页程序的完整补强版。Linux/POSIX：
   cc -std=c11 -Wall -Wextra -pthread threads.c -o threads */
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
static void *work(void *arg) {
    int id = *(int *)arg;
    for (int i = 0; i < 5; i++) {
        printf("Thread %d: iteration %d\n", id, i);
        sleep(1); /* 只模拟等待，不用它证明另一个线程已经完成 */
    }
    return NULL;
}
int main(void) {
    pthread_t tid[2];
    int ids[2] = {1, 2};
    int created = 0, failed = 0;
    for (int i = 0; i < 2; i++) {
        int rc = pthread_create(&tid[i], NULL, work, &ids[i]);
        if (rc != 0) {
            fprintf(stderr, "pthread_create: %s\n", strerror(rc));
            failed = 1;
            break;
        }
        created++;
    }
    for (int i = 0; i < created; i++) {
        int rc = pthread_join(tid[i], NULL);
        if (rc != 0) {
            fprintf(stderr, "pthread_join: %s\n", strerror(rc));
            exit(EXIT_FAILURE); /* 不再声称全部完成，终止整个进程 */
        }
    }
    if (failed) return EXIT_FAILURE;
    puts("All threads finished.");
    return EXIT_SUCCESS;
}

原图显式创建 t1、t2，并传入 id1、id2；这里用两个稳定数组元素表达同样关系并补了错误检查。ids 一直到 join 结束前都有效，工作线程先复制自己的 id。主线程等两个线程后才离开 main，避免参数所在栈帧提前消失。创建成功返回时，新线程可能已经运行，不存在创建者必先打印的保证。

19.2 第 26 页输出：局部有序，全局可交错

线程 1 自己按 0、1、2、3、4 输出；线程 2 也如此。两条线程之间的行可以有不同交错，“先创建 1”不能推出“1 的每一行先于 2”。只要两个 join 都成功返回，All threads finished. 就在两个工作线程终止之后。课件的两次输出用不同交错说明调度的不确定性。

一种允许的交错：T1:0  T2:0  T1:1  T2:1  T1:2  T2:2  T1:3  T2:3  T1:4  T2:4  完成
另一种允许的交错：T2:0  T1:0  T2:1  T1:1  T2:2  T1:2  T2:3  T1:3  T2:4  T1:4  完成
不允许的线程内部顺序：T1:2 在 T1:1 前（假设正常按循环执行且未改变输出机制）
三项检查不能互相替代

不要把不断变化的循环变量 &i 同时传给所有线程：多个线程可能读到变化后的同一值，还可能产生数据竞争。sleep 只延迟调用者，不能证明其他线程已经完成；join 等待终止，不能把运行期间的共享访问自动变成互斥。

19.3 count++ 为什么不是自动安全

把 count++ 拆成“读 count → 加 1 → 写回”。假设原值为 0，A 读 0，B 也读 0，A 写 1，B 再写 1，两次增加最终却是 1。这个交错帮助理解丢失更新；在 C/C++ 中，无同步地并发读写同一非原子对象还构成数据竞争，语言层面属于未定义行为，不能把结果简单限定为某几个整数。应使用互斥锁、原子对象，或各自计算后在同步点合并结果。

    }
    DWORD result;
    if (!GetExitCodeThread(h, &result)) {
        fprintf(stderr, "GetExitCodeThread: %lu\n", GetLastError());
        CloseHandle(h);
        return 1;
    }
    if (!CloseHandle(h)) { fprintf(stderr, "CloseHandle: %lu\n", GetLastError()); return 1; }
    printf("thread exit=%lu\n", result);
    return 0;
}

第 29 页讲的是线程句柄：等待句柄可确认线程结束，GetExitCodeThread 可读退出结果。CloseHandle 释放句柄，不等于终止线程。不同平台 API 的形状不同，但都需要正确安排创建、等待、结果和资源回收。

LESSON 4 · 模块 20

20. 线程池与 Fork–Join：从线程转向任务

对应 lesson4 第 30–41 页（按 PDF 页码）

线程是执行者，任务是待完成的工作。一条线程可以依次完成很多任务，一个大任务也可以拆成多项子任务。把两者分开，才好控制资源和计算粒度。

20.1 显式线程与隐式线程

显式编程中，程序自己创建线程、传参、等待和清理。隐式线程方法让程序描述任务、并行区域或队列，由运行时安排执行。线程池、Fork–Join、OpenMP、GCD 都减少线程管理负担，但并不自动消除数据共享和任务依赖问题。

线程池复用一组工作线程，减少反复创建的开销并限制同时存在的工作线程数。但限制线程数不等于限制任务队列占用的内存：请求持续堆积仍会撑大队列，需容量管理或背压。定时任务可由调度器到点后提交，线程池本身不一定自带定时功能。

20.2 还原 Python 六任务例子

from concurrent.futures import ThreadPoolExecutor, as_completed
import time

def work(task_id):
    print(f"Task {task_id} is running")
    time.sleep(1)
    print(f"Task {task_id} done")

with ThreadPoolExecutor(max_workers=3) as pool:
    tasks = []
    for i in range(0, 6):
        task = pool.submit(work, i)
        tasks.append(task)
    for f in as_completed(tasks):
        f.result()

print("All tasks finished.")

第 33 页完整文字还原。submit 返回 Future（未来结果对象）；as_completed 按完成顺序给出 Future；result 获取结果并重新抛出任务异常。with 退出会按默认规则等待已提交工作完成。最多三个工作线程，六次各约一秒的等待可重叠，粗略分两轮，理想约 2 秒加额外开销。不是 Task 3 必然由线程 1 执行，而是谁先空闲谁能取下一项，也不必等整批三个都完成才取后续任务。

Python 的等待并发与计算并行

启用 GIL 的 CPython 中，同一解释器通常一次只有一个线程执行 Python 字节码；sleep、网络等待等可重叠，因此此例约两秒不证明纯 Python 计算用上多个核。计算密集任务可考虑多进程。原生扩展释放 GIL、自由线程构建或不同解释器时需另行分析，不能泛化成“Python 永远不能多线程并行”。

20.3 Fork–Join 是拆分与合并计算的结构

Fork–Join 中的 fork 表示派生子任务，不必调用操作系统的 fork 创建进程。小问题直接算，大问题拆成独立子问题，等待子问题完成后合并结果。线程池回答谁执行，Fork–Join 回答工作如何拆、如何汇总，两个层次可以结合。

Task(problem):
    if problem is small enough:
        solve the problem directly
    else:
        subtask1 = fork(new Task(subset of problem))
        subtask2 = fork(new Task(subset of problem))
        result1 = join(subtask1)
        result2 = join(subtask2)
        return combined results

20.4 第 40 页递归代码与线程数量推导

from threading import Thread

def fork_join_sum(data, depth=0):
    if len(data) <= 1024 or depth >= 2:
        return sum(data)
    mid = len(data) // 2
    box = [None]
    def left():
        box[0] = fork_join_sum(data[:mid], depth + 1)
    t = Thread(target=left)
    t.start()
    right = fork_join_sum(data[mid:], depth + 1)
    t.join()
    return box[0] + right

if __name__ == "__main__":
    print(fork_join_sum(list(range(1, 10001))))

核心函数按第 40 页还原，补入 import 和调用。当前线程算右半，新线程算左半，join 后读取左边 box 再相加。每个递归调用有自己的 box，不是所有分支共同写一个累加器。小于等于 1024 或深度达到 2 就直接 sum，避免无限细分。切片本身也有复制开销；启用 GIL 时这段纯 Python 计算不应被当作多核加速保证。教学代码假设子任务正常返回；一般框架还应传播工作线程异常。

最大深度为 D 且数据足够大时：深度 0 有 1 个原始执行流，拆分后最多 2 个；再拆一层最多 4 个；故最多 \(2^D\) 条执行流（含原始线程）。实际新建线程数最多 \(1+2+\cdots+2^{D-1}=2^D-1\)。D=2 时是 3 个新线程、最多 4 条执行流；小数据可能提前停止而更少。这里原始调用线程也参与计算，没有额外一个只等待的主线程。

考点提示

线程数有上限还不够，任务粒度也要合适。不要机械地让固定小线程池的每个工作线程都提交子任务再同步等结果：若所有工作线程都等队列中的子任务，就可能没有空闲线程执行那些子任务。应使用能处理递归任务的调度框架，或避免池内这种阻塞等待结构。

21.2 parallel for 分配的是迭代，不是复制整个循环

#include <stdio.h>
#include <omp.h>
#include <unistd.h>
int main(void) {
    int a[5] = {1, 2, 3, 4, 5};
    int b[5] = {10, 20, 30, 40, 50};
    int c[5];
    #pragma omp parallel for
    for (int i = 0; i < 5; i++) {

        printf("%d\n", c[i]);

21.3 reduction：先私有累加，再合并

#include <stdio.h>
int main(void) {
    long long total = 0;
    #pragma omp parallel for reduction(+:total)
    for (int i = 1; i <= 10000; ++i)
        total += i;
    printf("total=%lld\n", total);
    return 0;
}

第 45 页核心片段补入 main。reduction(+:total) 为参与线程提供私有累加值，最后按加法规则合并，避免所有线程无同步更新同一 total。验证结果：令 \(A=1+2+\cdots+10000\)，倒序再写一次得到 \(A=10000+9999+\cdots+1\)，逐项相加有 \(2A=10000\times10001\)，故 \[A=\frac{10000\times10001}{2}=50005000.\] 浮点数的归约因结合顺序变化，可能出现舍入差异；本例整数范围足够时没有这一问题。

隐式线程仍需要显式理解依赖

去掉 reduction 却让所有线程写普通 total，会产生数据竞争。parallel for 不会自动证明每次迭代相互独立，也不会自动修复错误的共享变量更新。测试恰好得到正确值，不是无竞争的证明。

21.4 GCD：任务队列不是专属线程

/* 第 46 页核心调用补上 group 的创建，Apple 平台、Blocks 语法片段。
   work(1)、work(2) 是应用定义的具体任务函数。 */
dispatch_group_t group = dispatch_group_create();
dispatch_queue_t q = dispatch_get_global_queue(
    DISPATCH_QUEUE_PRIORITY_DEFAULT, 0);
dispatch_group_async(group, q, ^{ work(1); });
dispatch_group_async(group, q, ^{ work(2); });
dispatch_group_wait(group, DISPATCH_TIME_FOREVER);

GCD（Grand Central Dispatch）让应用提交任务，系统安排线程执行。串行队列一次执行一个任务；并发队列允许任务并发推进。队列和线程不是一一对应，同一队列不同任务可能由不同工作线程执行。dispatch group 用于等待一组任务完成。代码中的资源所有权/释放应遵守所用语言环境的规则；此处是 API 流程片段，不是跨平台独立程序。

LESSON 4 · 模块 22

22. 线程管理：fork、信号、取消与 TLS

对应 lesson4 第 47–55、64 页（按 PDF 页码）

一个线程“开始运行”只是生命周期的开头。要写可靠的多线程程序，还要明确复制后谁存在、事件给谁、何时允许退出，以及哪些数据随线程保留。

22.1 多线程进程 fork：复制内存，不复制所有执行者

在课件讨论的 POSIX 语义下，fork 后子进程只保留调用 fork 的那个线程。其他线程不会在子进程继续运行，但地址空间中它们留下的锁状态可能被复制。如果锁显示“已被线程 B 持有”，而 B 根本没被复制进子进程，子进程再去等待该锁就可能永远等不到。

多线程 fork 后的子进程在 exec 前，只能进行符合异步信号安全要求的操作，直到执行新程序。不能随意调用 printf、malloc 或依赖其他线程内部锁的普通库流程。成功 exec 会替换整个程序映像并终止同进程的其他旧线程；绝不是只给调用线程换一段函数。模块 12 的单线程教学例题不能不加分析地套入这里。

22.2 信号：处置属于进程，屏蔽字属于线程

信号用于通知事件发生。同步故障信号由当前执行触发，如非法内存访问；异步信号可源自外部事件。默认处置可能是终止、停止、继续或忽略；程序可为允许处理的信号注册处理函数或选择忽略。SIGKILL、SIGSTOP 不能捕获、阻塞或忽略。

情形接收规则
线程定向信号或线程触发的同步故障由指定线程或引发故障的线程接收
进程定向信号由一个符合接收条件的线程接收，不默认广播给每个线程
统一管理控制信号让其他线程阻塞该信号，由专门线程通过 sigwait 等待处理

信号处置（默认、忽略、处理函数等设置）通常在进程内共享，信号屏蔽字却由各线程分别维护。处理函数可能打断任意正常执行位置，只能调用符合异步信号安全要求的操作，不能像普通回调那样任意分配内存和打印。“信号定向”与“线程是否屏蔽它”是不同问题。

22.3 请求取消，不等于线程已经结束

pthread_cancel 发送取消请求；是否允许取消、何时响应，由目标线程的取消状态和取消类型决定。新线程默认允许取消（Enabled），类型为延迟（Deferred）。延迟取消到取消点才响应，pthread_testcancel() 可显式检查，部分阻塞接口也是取消点。异步取消可在任意允许位置生效，可能把锁、堆或共享结构留在不一致状态，清理更困难。

取消状态类型请求到来后
Disabled 禁用任意请求保留，暂不响应，继续执行
Enabled 允许Deferred 延迟到取消点响应
Enabled 允许Asynchronous 异步可以在任意允许位置响应
三层结束责任

停止计算、释放任务/应用资源、回收线程自身资源，是相关但不同的步骤。pthread_cancel 成功返回不证明目标已经退出。join 可等待可等待线程并回收其资源，分离线程按规则自动回收，但二者都不自动替应用释放所有堆对象和锁。

应用可以采用协作退出标志，但标志本身也需要原子操作、锁或其他正确同步。延迟取消可配合 pthread_cleanup_push/pop 注册清理动作，例如释放已持有的锁；这些接口需按作用域成对使用，且要在取消安全的位置管理资源。不能把“不取消线程”误解为“不需要退出协议”。

取消的完整最小示例：请求、清理、等待

/* Linux/POSIX：cc -std=c11 -Wall -Wextra -pthread cancel.c -o cancel */
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
static void *worker(void *arg) {
    (void)arg;
    void *buffer = malloc(128);
    if (buffer == NULL) return NULL;
    pthread_cleanup_push(free, buffer);
    for (;;) {
        pthread_testcancel(); /* 默认延迟取消：在此响应请求 */
    }
    pthread_cleanup_pop(1); /* 与 push 成对；本例正常路径不会走出循环 */
    return NULL;
}
int main(void) {
    pthread_t tid;
    int rc = pthread_create(&tid, NULL, worker, NULL);
    if (rc != 0) { fprintf(stderr, "create: %s\n", strerror(rc)); return 1; }
    rc = pthread_cancel(tid); /* 只发请求，不宣称线程已经结束 */
    if (rc != 0) { fprintf(stderr, "cancel: %s\n", strerror(rc)); return 1; }
    void *result;
    rc = pthread_join(tid, &result);
    if (rc != 0) { fprintf(stderr, "join: %s\n", strerror(rc)); return 1; }
    puts(result == PTHREAD_CANCELED ? "thread canceled" : "thread returned");
    return 0;
}

这个例子把课件第 51 页的 create → cancel → join 调用链补成独立程序：取消请求可能在线程第一次执行前就已挂起；线程先登记清理函数，再在取消点响应，取消退出时会 free(buffer)。如果分配失败而直接返回，则 join 可能取得普通返回结果。空循环仅用于最小演示，实际任务应在适当检查点协作或阻塞等待，避免长时间空转。它没有设置异步取消，因此不能把此资源登记方式原样套到任意时刻都可取消的线程。

    return NULL;
}

TLS 是 Thread-local storage，线程局部存储。同一变量名，每线程有自己的 counter。两条线程各调用一次该函数，可以各自输出 1、2、3；同一线程再次调用时会接着输出 4、5、6，因为 TLS 不随函数返回销毁。Pthreads 还提供 key 与线程特定数据接口，可注册线程退出时的析构函数。适用场景包括线程内缓存、错误信息和上下文。

线程池中的 TLS 陷阱

TLS 随工作线程存活，不自动随任务/请求重置。任务 A 留下请求编号，复用同一线程的任务 B 若不重新设置就可能读到旧编号；需在任务开始初始化、结束清理，或使用适合任务上下文的存储机制。

课件练习：pthread_cancel 成功返回后线程一定结束了吗？如何确认与回收？

① 不一定，它只请求取消。② Disabled 状态下请求可挂起；Deferred 类型到取消点才响应。③ 响应时执行已注册清理处理函数及线程退出清理。④ 对 joinable 线程可 join 确认退出，并检查返回结果（被取消时可得到 PTHREAD_CANCELED）。⑤ 应用自己负责堆内存、锁和任务资源的正确释放，分离线程也不能省去应用清理。

课件练习：在线程池中用 TLS 保存请求 ID，下一个任务要注意什么？

① 池内线程长期存活，TLS 也随线程保留。② 新任务可能复用上一请求的线程。③ 不初始化就可能泄漏旧请求上下文到新任务。④ 在任务边界显式设置、清理；区分线程身份与请求身份，异步任务跨线程时更不能仅凭 TLS 推导请求归属。

把抽象模型落实到 Windows 与 Linux 的数据结构，再回到浏览器讨论：何时选择共享带来的便利，何时值得支付隔离与 IPC 的成本？

23.1 Windows：线程对象与用户环境

常规 Windows 线程采用一对一映射。每线程有标识、寄存器现场、用户栈、内核栈及线程局部信息。ETHREAD 表示内核线程对象与管理信息；KTHREAD 保存调度、同步等低层线程信息；TEB 位于用户空间，保存线程环境信息，包括 TLS 等。知道这些结构分别服务什么目标，比死记字段布局更重要，具体字段依实现而变。

23.2 Linux：独立任务结构，共享资源对象

Linux 用 task_struct 管理任务，同一进程里的每个线程也有各自任务结构。clone/clone3 的标志描述新任务共享哪些资源；这不表示普通应用应该直接用 clone 手工实现线程库。pthread_create 还要处理栈、TLS 初始化和库内部管理，再请求内核创建执行实体。

clone 标志（课件第 60 页）共享/组织关系
CLONE_VM共享虚拟地址空间
CLONE_FILES共享文件描述符表
CLONE_FS共享当前目录、根目录等文件系统上下文
CLONE_SIGHAND共享信号处置表，不能推出共享每线程的屏蔽字
CLONE_THREAD加入同一线程组

同线程组的线程有不同 TID，通常共享 TGID。对用户常见的“进程 PID”，多线程组通常以 TGID 表示；主线程的 TID 通常等于 TGID。每线程有自己的 task_struct，不妨碍它们指向相同资源对象。这些标志存在组合约束，不应把表格理解成任意拼接都合法的底层编程配方。

# 把 1234 改成正在运行的目标进程 PID
ps -L -p 1234 -o pid,tid,stat,comm
ls /proc/1234/task
cat /proc/1234/status

ps -L 展示线程，/proc/PID/task 的各子目录对应线程，status 的 Threads 表示读取时的线程数量。观察的是快照，线程可能随时创建或结束，两次读取并不一定一致；PID 消失时文件也可能不存在。这个观察实验应在 Linux、虚拟机或合适的 Linux 环境中进行，不能把命令直接当作 Windows PowerShell 内置命令。

23.3 第 62 页讨论：浏览器若只有一个进程

角度每页面/插件一线程，全部放同进程多进程方案
资源与数据交换可直接访问共享对象，通常减少 IPC 与地址空间开销需定义 IPC，可能付出更多内存和通信成本

课堂讨论：若浏览器所有页面与插件都改用一个进程里的线程，有哪些好处与坏处？

① 好处：通常降低创建、地址空间与 IPC 开销；共享对象和数据交换更方便。② 坏处：共享地址空间扩大故障影响，一个越界写或严重错误可能破坏整个浏览器；不可信页面之间更难建立强隔离，且共享数据同步更复杂。③ 多线程仍可在多核上并行，不能把“少进程”直接等同于“不能并行”。④ 实际浏览器可混合多进程和多线程；“每标签页一个进程”只作为课件的讨论简化。
