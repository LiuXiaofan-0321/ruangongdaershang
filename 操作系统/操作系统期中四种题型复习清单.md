## Lesson 2　操作系统服务

### 1．从“复制文件”理解四层接口

你在终端输入 `cp a b`。**Shell** 解释命令并启动复制程序。程序使用**库提供的 API** 请求打开、读取、写入文件。库按约定准备调用号和参数，经**系统调用**进入内核。**内核**检查请求，访问文件系统、缓存或设备，再把结果返回。图形界面点击“复制”也能用到相同的底层服务。

- **用户态与内核态**描述执行权限。普通应用运行在用户态，特权操作通过受控入口交给内核。系统调用是程序主动请求服务。除零、缺页等异常由当前指令触发。时钟与设备完成 I/O 等硬件中断可异步到来。
- **一次 API 调用可能产生零次、一次或多次系统调用。** 计算字符串长度通常可在用户态完成。printf 可能只写入用户态缓冲，多次 printf 也可能在一次刷新时合并输出。
- **模式切换与上下文切换**回答两个问题。前者问“当前执行权限是否改变”。后者问“现在换谁执行”。线程进入内核完成一次 read 并返回，可以始终是同一个线程。若它阻塞等待磁盘，内核才可能转而运行其他线程。

### 2．能解释 read 的每个参数和返回值

`n = read(fd, buf, count)` 的含义是“从 fd 所指的打开对象中，最多读 count 字节到 buf”。内核要检查 fd 有效且可读、buf 所覆盖的用户地址可写、长度和边界合法。参数可按体系结构约定通过寄存器、内存参数块或栈传递，调用号用于选择相应的内核处理函数。

**具体例子。** 要求读普通文件 100 字节，本次返回 40，就只处理这 40 字节。随后往目标文件写这 40 字节，若 write 只返回 25，下一次应从 `buf+25` 写剩余的 15 字节。正数是实际完成的字节数。对正长度的普通文件读取，0 表示到了 EOF。返回 −1 时检查错误原因，再决定重试还是退出。

### 3．系统提供哪些能力，又是怎样组织的

| 知识点 | 复习内容 |
|---|---|
| 系统服务与系统调用分类 | 执行程序、文件与设备 I/O、通信、错误处理、资源分配、核算和保护。系统调用可按进程控制、文件管理、设备管理、信息维护、通信、保护分类。如 fork 创建进程，read 读取数据，pipe 建立通信通道。 |
| 机制与策略 | 机制提供手段，策略作出选择。时钟中断以及保存、恢复寄存器使换人执行成为可能。按时间片还是优先级选择下一个任务属于策略。 |
| 单体、分层、微内核、模块化 | 单体把多个服务放在同一内核空间。分层按依赖层次组织功能。微内核把更多服务放入用户空间，经 IPC（常见为消息传递）协作，改善隔离但引入通信成本。模块化支持按接口装入组件。Linux 可加载的内核模块仍在内核空间执行。 |
| 编译、链接、装载 | 编译得到目标文件。链接解决跨文件符号和重定位。装载建立进程映像并交到入口。静态链接把所需代码并入结果，动态链接依赖共享库。CPU 相同，仍可能因可执行格式、应用二进制接口（ABI）或库不兼容而无法直接运行。 |
| 从开机到 Shell | 固件初始化并选择启动目标，引导阶段装入内核，内核初始化内存、中断、调度和驱动，准备根文件系统、启动首个用户空间进程，再启动服务和登录环境。 |
| 怎样观察行为 | 计数回答“发生几次”，采样回答“时间多花在哪里”，跟踪回答“事件以什么次序发生”。strace 能观察系统调用。CPU 利用率低时，程序也可能在等 I/O 或锁。 |

## Lesson 3　进程

### 1．进程、地址空间与 PCB

磁盘上的程序是静态指令。**进程**是它的一次执行，有自己的身份、执行进度和资源。打开同一程序两次，可以产生两个不同 PID 的进程。典型地址空间有 text（指令）、data/BSS（静态存储期对象）、堆（动态分配对象）和栈（调用帧、自动局部变量等）。

**进程控制块（PCB）**，由内核保存。要让一个被换下 CPU 的进程稍后接着运行，内核需要知道它是谁、处于什么状态、下条指令在哪里、寄存器值是什么、地址空间和资源在哪里。它暂时离开 CPU 后，这些信息仍在。PCB 保存管理和恢复进程所需的信息，并引用相应资源。

### 2．把三态的四条箭头画全

| 转换 | 原因 | 要能举的例子 |
|---|---|---|
| 就绪 → 运行 | CPU 分给了它 | 调度器选中 P，分派程序恢复其执行现场。 |
| 运行 → 就绪 | 它还能运行，但 CPU 暂时分给别人 | 时间片到，或被更高优先级任务抢占。 |
| 运行 → 等待 | 某个事件尚未发生，给它 CPU 也做不下去 | 阻塞读正在等设备数据。 |
| 等待 → 就绪 | 所等条件满足，重新具备运行资格 | 设备完成 I/O，等待者被唤醒。 |

若题目问五态，再加**新建 → 就绪、运行 → 终止**。就绪队列里的任务等 CPU。等待队列里的任务等特定事件。切换时保存旧任务的 程序计数器（PC）、寄存器、栈指针等，再恢复新任务现场。跨进程还可能改变地址空间并影响缓存和 TLB。理解这四条箭头，后面才能分清调度等待和 I/O 阻塞。

### 3．fork、exec、wait 各改变什么

| 操作 | 执行后发生什么 |
|---|---|
| fork | 成功时，父子都从 fork 返回点继续。父进程得到子 PID，子进程得到 0。普通变量初始内容相同，之后独立修改。写时复制允许先共享物理页再按需复制。 |
| exec | 成功时用新程序替换当前进程映像，PID 保持。原程序位于 exec 后面的打印仅在调用失败并继续执行时才可能出现。 |
| wait / waitpid | 父进程等待子进程状态变化，常用于取得子进程退出结果并回收。子已退出、退出记录尚未被回收称为僵尸。父先退出而子还活着称为孤儿。 |

**2020 卷的文件题。** 初始空文件、无追加模式，两次写各一个字节且成功。若 fork **之后**父子各自 open，两次打开有独立偏移，两人都写偏移 0，最后只有 a 或 b。若**先 open 一次再 fork**，父子继承的 fd 指向同一个内核打开文件描述，偏移共享，两次写依次落在位置 0、1，结果是 ab 或 ba。父子普通变量是否共享和文件偏移是否共享，是两条独立的判断。

**练习。** 程序先 fork。子先打印 C1，再成功 exec 一个打印 C2 的程序。父先 waitpid 等子结束，再打印 P。若每次打印都及时可见，顺序为 **C1、C2、P**。若去掉 waitpid，只保留“C1 在 C2 之前”这条约束，P 的位置就可变化。

### 4．进程间通信（IPC）

| 机制 | 双方共享什么或传什么 | 关键边界 |
|---|---|---|
| 共享内存 | 不同进程映射同一片存储，直接访问其中的数据 | 映射地址可不同，宜在共享结构中传偏移。建立可见的数据区后，访问顺序和互斥仍由程序协调。典型过程为创建对象、设置长度、共享映射、同步读写、解除映射并清理。 |
| 消息传递 | send/receive 传送数据，可指定对方或经邮箱 | 区分阻塞和非阻塞。零容量需双方交接，有界通道满时如何处理看接口约定。无界模型仍可能因没有数据而等接收。 |
| 管道与 FIFO | 从写端到读端传字节流。命名管道可由无亲缘关系的本机进程按路径打开 | 管道有数据先读数据。若已空且仍有写端打开，阻塞读会等。只有已空且**所有**写端都关闭，正长度 read 才返回 0。子进程自己继承的写端也算。 |
| Socket 与 RPC | Socket 是通信端点。RPC 把调用参数编码发送，在服务端执行并返回结果 | TCP 是有序字节流，应用需约定消息边界。RPC 超时可能是请求没到，也可能是已执行但回复丢失。重试非幂等操作要防止重复执行。 |

**检查自己。** 父进程已关闭写端，子进程为何仍可能永远读不到 EOF？把父子各自继承的两个端点都画出来，就能看出子进程是否还保留写端。[状态与切换，第 7–20 页](<lesson3-processes.pdf#page=7>) · [进程创建，第 23–30 页](<lesson3-processes.pdf#page=23>) · [管道与 EOF，第 54–57 页](<lesson3-processes.pdf#page=54>)

## Lesson 4　线程与并发

### 1．一份资源由谁拥有，几条执行流共同用它

进程提供地址空间和资源边界，线程是其中一条执行流。在支持内核级线程的系统中，内核通常按线程调度。一个线程被换下后还必须能回到自己之前执行的位置，所以**每线程各有 PC、寄存器、栈、线程状态和线程局部存储（TLS）**。同进程内的线程**共享代码、全局数据、堆和打开文件表**。每线程各用自己的栈，但它们处在同一地址空间，传出仍有效的栈对象地址后，别的线程也可能访问它。

**并发与并行。** 单核在下载和处理图片之间切换，两件事在同一时间段都有进展，就是并发。两个核在同一时刻分别处理两张图，才是并行。数据并行把相同操作分到不同数据块。任务并行把不同类型的工作分开。多线程可以提高交互响应、复用进程资源、降低创建与通信成本，并利用多核。代价包括同步、调度和共享资源竞争。

### 2．用户线程怎样映射到内核线程

| 模型 | 阻塞与并行的后果 |
|---|---|
| 多对一 | 多个用户线程只对应一个内核线程。它进入阻塞系统调用，整组可能停住。该组同一时刻最多由一个核执行。 |
| 一对一 | 每个用户线程都对应一个内核线程。某个线程阻塞时，其他就绪线程可运行，多核上可并行。内核要管理更多线程。 |
| 多对多与两级模型 | 用户运行时把许多用户线程复用到多个内核线程上，在并行能力和管理成本之间折中。两级模型还允许特定用户线程绑定到内核线程。 |

### 3．创建、等待、取消和复用

- **create 与 join。** 创建顺序不能推出运行顺序。join 等待目标线程结束，可回收可等待线程的资源。join 本身不能保护两个线程正在共同修改的变量。给每个线程传独立且足够长寿的参数对象，避免把同一个仍在变化的循环变量地址反复传出。Java 的 start 启动新执行流，直接调用 run 是普通方法调用。
- **用写文件验证。** 主线程创建工作线程写 a，自己写 b 后从 main 返回，二者使用同一个 fd。在 2020 卷题设下，结果可能是 **b、ab、ba**。若主线程在写 b 前 join，则只能 ab。若写 b 后再 join，则 ab、ba 都可，单个 b 被排除。关键是区分“等待完成”与“先后次序”。
- **线程池与 TLS。** 线程池复用一组工作线程来执行一批任务。局部自动变量通常随函数调用建立和销毁，普通 static 对象由线程共享，TLS 则每个线程一份、可跨函数调用保留。若上一个任务在 TLS 写了请求编号，下一个复用此线程的任务要重设它。
- **取消、信号和 fork。** pthread_cancel 成功表示已提出取消请求，延迟取消要到取消点才响应。进程定向的信号由符合接收条件的线程之一处理，信号屏蔽字按线程保存。多线程进程 fork 后，子进程只保留调用者这一个线程，地址空间里却可能留有原来由其他线程持有的锁状态。
- **操作系统怎样表示线程。** Windows 把进程作为资源容器，调度其中的线程。Linux 用任务结构描述可调度任务，创建任务时可用 clone 的标志指定共享哪些资源，例如 CLONE_VM 共享地址空间、CLONE_FILES 共享文件描述符表。
- **组织计算。** Fork–Join 拆分任务、等待、合并结果。拆得太细会增加管理开销。OpenMP 的 parallel for 分配迭代，reduction 让每个线程先各自累加再合并。同名 critical 区域互斥。GCD 将任务提交到队列，由运行时安排执行。

### 4．Amdahl 定律要会算，也要能解释上限

固定工作量，设串行比例为 s，其余工作理想均分到 N 个核。将单核总时间记为 1，使用 N 核的时间就是 `s + (1−s)/N`。**加速比 = 1/[s + (1−s)/N]**。若 s=20%、N=4，总时间为 0.2+0.8/4=0.4，加速比为 2.5。只要 s>0，即使并行部分耗时趋近 0，总时间仍至少为 s，所以上限为 1/s，本例为 5。实际程序还需通信、加锁和调度。

## Lesson 5　CPU 调度

### 1．画图前先明确调度什么、比较什么

一个进程往往交替经历 CPU 执行段和 I/O 等待段。**调度器**从就绪任务中选下一位，**分派程序**完成现场切换，让选中的任务运行。当前任务阻塞或退出时必须另选。当前任务仍能运行却被换下，才叫抢占。时间片到期，或某个更高优先级任务从等待变为就绪，都可能触发抢占。

| 指标 | 计算方法 | 示例 |
|---|---|---|
| 周转时间 | 完成时刻 C − 到达时刻 A | 任务时刻 1 到达、10 完成，周转为 9。 |
| 响应时间 | 首次运行 S − 到达 A | 时刻 3 首次运行，响应为 3−1=2。 |
| 等待时间 | 把所有在就绪队列的时间段相加 | 若只在 3–5 和 8–10 运行，其余一直就绪，等待为 (3−1)+(8−5)=5。无 I/O 时也可用周转 9 减 CPU 时间 4。 |
| CPU 利用率、吞吐量 | 利用率看观察期内 CPU 的忙碌比例。吞吐量看单位时间完成多少任务 | 一组任务可能首次响应较快，却因频繁切换使整体吞吐量变低。 |

### 2．每种算法都要知道“按什么选、何时重选、谁可能吃亏”

| 算法 | 选择规则 | 为什么会有这种效果 |
|---|---|---|
| 先来先服务（FCFS） | 按就绪顺序，通常非抢占，当前任务阻塞或结束才换人 | 长任务排在队首会让一批短任务都延迟，叫护航效应。 |
| 短作业优先（SJF） | 非抢占，每次选预计**下一段 CPU 时间**最短者 | 同时到达且长度已知时可使平均等待最小。相邻长任务 a 在短任务 b 前，交换后，二者等待总和减少 a−b。短任务不断到来，长任务可能饥饿。 |
| 最短剩余时间优先（SRTF / STCF） | 可抢占，新任务就绪时比较**剩余时间** | 新到的任务比当前剩余段短才值得抢占。单 CPU、已知长度、忽略切换开销的单段模型下，可最小化平均周转和平均等待。 |
| 时间片轮转（RR） | 从队首取任务，每次最多运行 q，片尾还就绪则入队尾 | 小 q 通常给交互任务更早的响应，也可能增加切换开销。q 足够大时接近 FCFS。只有自己就绪时可以继续运行。 |
| 优先级 | 每次选最高优先级，可抢占也可非抢占。同级按给定规则 | 先看题目是大数字优先还是小数字优先。持续有高优先级工作时，低优先级可能饥饿，老化可逐步提高久等任务的优先级。 |
| 高响应比优先 HRRN（旧卷） | 一般非抢占，选择 (等待时间+服务时间)/服务时间 最大者 | 同时照顾短任务和已经等了很久的任务。这个比值与“首次响应时间”含义不同。 |
| MLQ 与 MLFQ | 多级队列 MLQ 中任务通常按固定类别入队。多级反馈队列 MLFQ 允许按运行行为升降队列 | 课件例子 Q0 用 RR 8 ms，Q1 用 RR 16 ms，Q2 用 FCFS。独自运行、需要 30 ms 的任务依次用 8、16、6 ms。若低层长期得不到 CPU，可设计定期提升。 |

### 3．同一组进程，亲手做四种算法

2019、2023 卷均出现过这组数据。设 P1–P4 在 0 时刻按编号入队，运行时间分别是 **9、2、3、2 ms**，优先级为 **3、1、2、4，小数字优先**。同长按编号，RR 取 q=1 ms，忽略切换开销。

| 算法 | 甘特图（相邻数字之间是执行者） | 各进程等待，按 P1–P4 | 平均等待 |
|---|---|---|---|
| FCFS | `0 P1 9 P2 11 P3 14 P4 16` | 0，9，11，14 | 8.5 ms |
| 非抢占 SJF | `0 P2 2 P4 4 P3 7 P1 16` | 7，0，4，2 | 3.25 ms |
| 非抢占优先级 | `0 P2 2 P3 5 P1 14 P4 16` | 5，0，2，14 | 5.25 ms |
| RR | `0 P1 1 P2 2 P3 3 P4 4 P1 5 P2 6 P3 7 P4 8 P1 9 P3 10 P1 16` | 7，4，7，6 | 6 ms |

**RR 怎么一步步算。** 第一轮每人用 1 ms，时刻 4 的剩余量为 (8,1,2,1)。第二轮依次还是 P1、P2、P3、P4，P2 在 6 完成、P4 在 8 完成。第三轮只剩 P1、P3，P3 在 10 完成，P1 在 16 完成。按编号写完成时刻 (16,6,10,8)，分别减各自 CPU 时间即可得到等待。P1 响应为 0，等待却有 7 ms。2019 旧参考表把 P1 的等待写成了 6。

**改成分批到达。** L5 第 23 页给到达时刻 (0,1,2,3)，长度 (8,4,9,5)。SRTF 在时刻 1 比较“P1 剩 7”与“新来的 P2 需 4”，所以换成 P2。时刻 2、3 的新任务都比当时的 P2 剩余时间长。最终为 `0 P1 1 P2 5 P4 10 P1 17 P3 26`，等待为 (9,0,15,2)，平均 6.5。若用非抢占 SJF，时刻 1 仍运行 P1。画图前写清到达、平局规则和时间片，最后逐人核对运行段之和。

### 4．把计算扩展到预测、多核、实时和性能评估

- **预测长度。** 指数平均 `下次预测 = α×本次实际 + (1−α)×原预测`。α 越大，最近一次观察权重越大。α=0.5、实际 6、原预测 10，新预测为 8。
- **多核。** 共享就绪队列便于均衡负载，每核队列能减少争用。推或拉任务能均衡，但迁移可能损失缓存和 NUMA 本地性。CPU 亲和性强调继续在同一核或指定核上运行。四核八硬件线程共享部分执行资源，吞吐量需看工作负载。进程竞争范围（PCS）关注同一进程的用户线程如何获得运行时分配的执行机会。系统竞争范围（SCS）关注内核可见的线程如何竞争 CPU。
- **实时。** 硬实时关注错过截止时间是否破坏功能，软实时可容忍部分延迟。速率单调调度（RM）优先选周期最短的任务，最早截止时间优先（EDF）优先选绝对截止时间最早的当前作业。在独立周期任务、单 CPU、可抢占、无开销与阻塞、截止期等于周期的模型中，令 `U=Σ(Cᵢ/Tᵢ)`。EDF 可调度条件为 U≤1。RM 的充分界是 `n×(2^(1/n)−1)`。超过 RM 的界还需进一步判断。若两任务为 (C=1,T=4)、(C=2,T=5)，U=0.65，小于两任务 RM 界约 0.828。
- **实际系统。** 按本课讲法，Linux 普通任务 nice 越小权重越高。实时 FIFO/RR 的用户优先级通常越大越高。CFS 用按权重累计的虚拟运行时间衡量已获服务。EEVDF 在合资格任务里比较虚拟截止时间。普通任务的虚拟截止时间与实时任务的实际期限含义不同。Windows 示例先选高优先级线程，同级采用轮转。
- **评估。** 同一组任务手算是确定性比较。仿真使用到达、完成等事件。实测要控制负载和环境。稳定系统中 Little 定律为 `Lq=λWq`，平均队列长 14、每秒到达 7 个，平均排队时间为 2 秒。统计若包含正在服务者，应对应到系统内逗留时间。

## Lesson 6　同步工具

### 1．竞争条件、临界区和正确性的三个要求

两个线程要把 count 从 5 加到 7。若各做一次普通的“读、加一、写回”，一种可能的交错是 **甲读 5，乙读 5，甲写 6，乙写 6**，结果只加了一次。这叫丢失更新。把单次读和单次写各自做成原子操作仍容许这种交错。可以让整个加一成为原子读改写，或让所有访问者都用同一把锁保护完整更新。

| 要求 | 准确含义 | 反例 |
|---|---|---|
| 互斥 | 同一时刻至多一个执行者在受保护的临界区内 | 两人同时改同一个队列下标。 |
| 前进 | 临界区空着且有人想进入时，选谁进入不能无限推迟 | 严格轮换只看 turn。轮到乙但乙根本不想进，甲仍被挡住。 |
| 有限等待 | 某人提出申请后，别人先于它进入的次数有上界 | 即使每次都有一人成功，新来者仍可一再抢在同一等待者之前。 |

**Peterson 双进程算法。** flag[i] 表示 Pi 想进入，turn=j 表示若两人都想进，Pi 愿意让 Pj 先走。初始两个 flag 都为 false。Pi 的进入协议为 `flag[i]=true → turn=j → 当 flag[j] 且 turn==j 时等待`，退出时令 flag[i]=false。如果对方没有申请，自己可以直接进。如果双方都申请，最后写 turn 的一方让行。经典论证依赖原子读写和顺序一致等假设。

### 2．硬件如何支持互斥，为什么还要管内存顺序

- **屏蔽中断的边界。** 单核内核可以在合适条件下短暂屏蔽本地中断，避免某些交错。在多核上 CPU0 关中断时，CPU1 仍能同时读写同一数据，因此需要对各核有效的原子操作或锁。
- **Test-and-Set（TAS）。** 一条指令取出锁的旧值并设为 true。旧值为 false 的调用者成功占用。其余人可以自旋等待。临界区很短、持锁者能在另一核继续时，自旋能省去睡眠唤醒开销。等待较长时，阻塞能让出 CPU。
- **Compare-and-Swap（CAS）。** 仅当当前值等于 expected 时才换成 new。课件伪代码返回旧值，据此判断成功。例如不停尝试把“读到的旧值”改为“旧值+1”，失败就重读并重试。朴素 CAS 锁能互斥，但未规定轮到谁。课件的有限等待版用 waiting[i] 登记，退出者环形扫描并交给下一位等待者，可以限制插队次数。
- **原子性与可见顺序。** 一个线程先写 x=100，再发布“准备好”。另一个线程收到标志后读 x。要建立这种顺序，写者对原子标志做 release 存储，读者用 acquire 读取到**这一次发布的 true**，才有相应的先行关系，能观察此前对 x 的写入。内存屏障约束访问顺序。对一个字段的原子更新也不会自动把一组字段包成整体。

### 3．互斥锁、信号量、条件变量分别解决什么

| 工具 | 什么时候用 | 谁能使等待结束 |
|---|---|---|
| 互斥锁 mutex | 多个执行者都要访问共享状态，某段代码一次只允许一人执行 | 正常用法由持锁线程解锁，别人才有机会取得锁。 |
| 信号量 semaphore | 限制 k 个并发名额，或规定 A 完成后 B 才能开始 | P/wait 申请许可，V/signal 发放许可。申请和发放可以由不同线程执行。 |
| 条件变量 condition variable | 要等的是“队列非空”“已有空位”等共享条件 | 一方在锁内改状态并通知，等待者重新持锁后再检查。无人等待时，通知不会留下供将来消费的许可。 |
| 管程 monitor | 集中封装共享数据、访问过程和同步协议 | 进入受管程的互斥规则约束。在管程内等条件时要让出管程，其他人才能进入并改变条件。 |

**用初值区分三种 P/V 题。** 互斥用初值 1，进临界区前 P、离开后 V。允许 k 人同时使用则初值 k。要求 S1 在 S2 前完成时初值 0，甲执行 `S1 → V(done)`，乙执行 `P(done) → S2`。甲先做完留下一个许可，乙先到则等待。

**计数怎么读。** 在课件的记录型实现里，P 原子处理“减 1 并在结果 <0 时排队阻塞”，V 原子处理“加 1 并在结果 ≤0 时唤醒一个等待者”。初值 1，甲 P 后为 0 可进入，乙 P 后为 −1 被阻塞，丙再 P 后为 −2。甲 V 后值回到 −1，唤醒一人，仍有一人等待。负数绝对值统计的是**等待这个信号量的人数**。

### 4．四种“等待”放在一起记

| 代码 | 到底在等什么 | 一个决定性细节 |
|---|---|---|
| waitpid(child, …) | 父进程等目标子进程报告状态，常用于退出回收 | 成功取得的是子进程的状态。 |
| pthread_join(t, …) | 调用者等目标线程结束 | 可以约束 join 后的程序顺序。两线程同时运行时的共享访问仍要同步。 |
| P(s) 或 sem_wait(&s) | 等到一个能拿走的许可 | 另一方先 V 也能留下许可。调用时若持有其他锁，阻塞可能造成循环等待。 |
| wait(not_empty, mutex) | 等“可能有菜了”的通知 | 调用前持有 mutex，等待时原子地放锁并进入等待。返回时已重新持有 mutex。真正的条件由受这把锁保护的 full 或 count 表示。 |

**区分两种通知语义。** 在 L6 第 50–55 页的“唤醒并等待”管程中，有人等条件时，被通知者先在管程中运行，通知者暂时挂起。可以用入口 mutex=1、通知者等待的 next=0 和每个条件自己的等待信号量来交接。L7 的 POSIX 和 Java 例子中，通知者仍可继续持锁。被通知者要重新得锁，随后重查条件。看清题干采用哪种接口。

## Lesson 7　把同步工具用到具体问题

### 1．生产者与消费者怎样协调空位、产品和互斥访问

设缓冲区容量 N，初始为空。生产者需要一个空位，消费者需要一个产品，两者修改缓冲区、下标等状态时还要排他访问。由此分别定义 **empty=N、full=0、mutex=1**。这里的 empty、full 是**计数信号量**，每次成功 P 会用掉一个许可。

```text
生产者（反复执行）                 消费者（反复执行）
    item = 在锁外生产                 P(full)
    P(empty)                          P(mutex)
    P(mutex)                          item = 从缓冲区取一个产品
    把 item 放入缓冲区                 V(mutex)
    V(mutex)                          V(empty)
    V(full)                           在锁外消费 item
```

**逐条解释生产者。** P(empty) 先预订空位，有了空位还可能有其他人在改队列，所以再 P(mutex)。放好后归还互斥权，并 V(full) 表示多了一个可取产品。消费者镜像执行，最后 V(empty) 把空位还给生产者。

**怎样检验 P 的先后。** 若缓冲区已满，生产者先 P(mutex) 再 P(empty)，就会拿着锁等空位。消费者必须拿这把锁才取走产品，双方都无法推进。在空缓冲区里让消费者先拿锁再等 full，也能构造对称的死锁。2019、2023 卷中的单槽题代 N=1 即可。2018 售票厅只限制“厅内最多 20 人”，直接用 seats=20，进厅前 P，离厅后 V。

### 2．同一传菜位，改写成条件变量

本题恰有一个位置。改用布尔变量 `full` 记录台上是否有菜，初值 false。一把 mutex 保护这个变量和传菜位。not_empty、not_full 是两个条件变量。

```text
厨师放一份菜                        服务员取一份菜
lock(mutex)                         lock(mutex)
while (full)                        while (!full)
    wait(not_full, mutex)               wait(not_empty, mutex)
放菜                                取菜
full = true                         full = false
signal(not_empty)                   signal(not_full)
unlock(mutex)                       unlock(mutex)
```

**服务员先到。** ① 持锁见 full=false，进入 wait，原子地释放 mutex 并等待。② 厨师取得 mutex，放菜并设 full=true，然后 signal(not_empty)。此刻厨师仍持锁。③ 厨师解锁。④ 服务员重新拿到锁后，wait 才返回。while 再看 full，若有菜就取走，改为 false，并通知可能等待空位的厨师。

**厨师先到。** 他可以先放菜，即使发通知时无人等待，full=true 仍然保存在共享状态里。服务员随后拿锁就看到已有菜，直接跳过 wait。**为什么用 while？** 当服务员甲获通知后，服务员乙可能先拿到锁并取走菜。甲真正得到锁时货位又空了。也可能发生虚假唤醒。两种情况下都要重新检查。

### 3．为什么由第一个读者申请资源、最后一个读者归还

允许读者同时读，写者则必须独占。把所有正在读的人看作一组，共用一次资源使用权。设 `read_count=0`，另设两个初值为 1 的**信号量**，分别用 count_lock 保护读者计数、用 rw 保护共享资源。第一个和最后一个读者可能是不同线程，所以 rw 要允许跨线程申请和归还。

```text
读者：
    P(count_lock)
    read_count += 1
    if read_count == 1: P(rw)
    V(count_lock)

    读取共享数据

    P(count_lock)
    read_count -= 1
    if read_count == 0: V(rw)
    V(count_lock)

写者：
    P(rw)
    修改共享数据
    V(rw)
```

**推一遍人数。** R1 来使计数 0→1，申请 rw。R2 来使 1→2，可以与 R1 同时读。R1 离开使 2→1，还不能还 rw。R2 离开使 1→0，写者才有机会进入。若 R2 离开前又有 R3 加入，后续总是如此，写者就可能一直等待。此时读者一直在工作，正好说明**饥饿**与**死锁**的区别。

### 4．哲学家、锁顺序与死锁

五位哲学家各需左右两根筷子。若五人都先取左筷，并在拿着左筷时等右筷，就形成闭环。经典死锁的四个必要条件是**互斥、占有并等待、资源不可抢占、循环等待**。统一按筷子编号从小到大取，能破坏循环等待。也可限制最多四人同时尝试，或在管程里一次检查并授予两根筷子。

**课件的管程解法。** 每人有 THINKING、HUNGRY、EATING 三种状态。pickup 登记 HUNGRY。test(i) 在自己饥饿且左右邻居均未 EATING 时，把自己设为 EATING 并通知。若未获准，就在自己的条件变量上等。putdown 将自己改为 THINKING，并检查左右两位是否可以进餐。检查与改状态都在管程内完成，真正吃饭在管程外进行，因此不相邻者可以同时吃。没有人拿一根等另一根，仍可能因左右邻居交替进餐使某人饥饿。

**2020 锁代码题与此同理。** a 按 y、z 加锁，b 按 z、x 加锁，c 按 x、y 加锁，拿齐才释放。分别让 a 先拿 y、b 拿 z、c 拿 x，再各自申请第二把，就得到 `a 等 b → b 等 c → c 等 a`。修改解锁顺序救不了这条交错，因为没有线程能走到第一条解锁语句。让所有线程按同一全序申请自己需要的锁，可消除这个环。抢占 CPU 也不会自动收走线程已经持有的互斥锁。

### 5．同一思想在系统接口中叫什么

| 环境或工具 | 对应关系 |
|---|---|
| POSIX | pthread_mutex_lock/unlock 管互斥，sem_wait/post 管许可，pthread_cond_wait/signal 管条件等待。有名信号量可用名字找到。无名信号量跨进程使用时，要设置相应的 pshared，且对象本身处在共享内存。 |
| Java | synchronized 使用对象锁，wait 会释放对应对象锁，notify/notifyAll 后等待者重新竞争锁。ReentrantLock 可关联多个 Condition 来分开等待条件。Semaphore.acquire 成功后才应归还许可，等待被中断且未取得许可时，多做一次 release 会平白增加名额。 |
| 内核 | 修改单个计数可用原子操作，短且不能睡眠的临界区可用适当自旋锁，允许睡眠的线程上下文可用互斥锁。Windows 的互斥对象、信号量、事件等也可使线程在条件满足前等待。 |
| 其他思路 | 事务内存可使一组更新整体提交，发生冲突时撤销重试。不可变数据、各自独立计算后再合并，可减少对共享写入的协调。 |

## Lesson 6–7 专题　算法性质、CAS 读码与三个经典问题

### 一、三条性质分别排除哪一种错误

- **互斥（mutual exclusion）**看“能不能两人同时进”。同一时刻至多一个执行者处在同一受保护的临界区。它约束安全性。
- **前进（progress）**看“空着时，想进的人里能不能选出一个”。临界区为空且有人申请时，不想进入的人不能无限拖住决定。它关注整体能否推进。
- **有限等待（bounded waiting）**看“已经申请的这个人，最多还会被超几次”。提出申请后、获准进入前，其他人先进入的次数有上界。这里数**进入次数**，而非多少毫秒。

比较时采用教材模型：临界区会执行完，参与者能继续获得执行机会，需要的共享读写满足相应原子性和顺序要求。

| 临界区方案 | 互斥 | 前进 | 有限等待 | 优点与代价 |
|---|---|---|---|---|
| 严格轮换（两人只看 turn） | 满足 | **不满足** | 按超越次数，对方至多先行一次；仍可能空等 | 最简单。若轮到乙而乙根本不申请，甲会在空临界区外一直等。这个反例直接违反前进。 |
| Peterson 双进程算法 | 满足 | 满足 | 满足，对方至多先行一次 | 在经典顺序一致模型中可证明三项。局限是基础版本只处理两人、会忙等、正确性依赖内存顺序。 |
| 朴素 TAS 自旋锁 | 满足 | 满足 | **不保证** | 一条原子指令取旧值并置位，可用于多核。等锁者持续轮询，释放后新来者可以抢先。 |
| 朴素 CAS 自旋锁 | 满足 | 满足 | **不保证** | 仅一个执行者能把锁从 0 改成 1。CAS 决定谁这一次改成功，没有排队次序。 |
| CAS + waiting 数组 + 环形交接 | 满足 | 满足 | 满足，至多 n−1 次 | 已登记者依编号接替，避免反复插队。代价是每人一个标志、退出时最坏扫描 O(n)、申请者依然忙等。 |

**锁、信号量和管程也要看具体用法。** 初值为 1 的信号量配对 P/V 可以互斥，初值为 3 的计数信号量则允许三个执行者同时使用。阻塞锁可以减少等锁时浪费的 CPU，但挂起、唤醒有成本。锁或管程能让临界区互斥，能否有限等待取决于排队与唤醒策略。不恰当的加锁顺序也可能造成死锁。[L6 第 7–15 页](<lesson6-synchronization.pdf#page=7>) · [L6 第 23–33 页](<lesson6-synchronization.pdf#page=23>)

### 二、Peterson 为什么成立，又为什么直接照抄会出问题

```c
// Pi 的代码。j 是另一个进程。初始两个 flag 都为 false。
// 教材假设下的伪代码：共享读写原子且顺序一致。
flag[i] = true;                   // 我想进
turn = j;                         // 如果我们都想进，我让你
while (flag[j] && turn == j) { }  // 你也想进，并且轮到你，我才等待
critical_section();
flag[i] = false;                  // 我退出
```

**手推一遍。** 两人的 flag 都为 true。若 P0 先写 turn=1，P1 后写 turn=0，最终 turn=0。P0 的等待条件为假，P0 进入；P1 的等待条件为真，P1 留在循环。由此理解互斥。只有 P0 想进时，flag[1] 为 false，P0 可直接进入，这解释前进。若 P1 正等，P0 退出后又申请，必须写 turn=1 把机会让给 P1，因此 P0 无法连续超越它。

**为什么工程上有局限？** 一是经典代码为两个参与者设计。二是 while 空转仍占 CPU。三是普通变量在现代 C/C++ 多线程程序中无同步并发读写会产生数据竞争，不能直接套用上述证明。硬件上，若“我想进”的写入未及时被另一核观察到，对方可能依据旧 flag 进入，使互斥的论证失效。按教学模型实现时可用顺序一致的原子读写；只给普通变量加 volatile 不足以建立线程间同步。课件展示的 release/acquire 发布数据例与完整 Peterson 算法要分别分析。[L6 第 16–21 页](<lesson6-synchronization.pdf#page=16>)

### 三、CAS 代码题先确定返回值

**课件约定：CAS 返回操作前的旧值。** `CAS(&x, expected, desired)` 原子地读出 x。若旧值等于 expected，就把 x 改成 desired；无论是否修改，都返回旧值。C11 的 `atomic_compare_exchange_*` 接口返回布尔成功标志，做题以题面给的函数定义为准。

| 代码符号 | 读成中文 |
|---|---|
| `&x`、`*p` | 取变量 x 的地址；访问指针 p 指向的值。两个符号本身都不提供原子性。 |
| `=`、`==`、`!=`、`&&` | 赋值、相等比较、不等比较、逻辑“且”。while 后表达式为真，就继续循环。 |
| `atomic_int` / `_Atomic int` | 原子整数类型。课件 C11 例子通过 `<stdatomic.h>` 使用相关接口。 |
| `atomic_load(&x)`、`atomic_store(&x,v)` | 一次原子读、一次原子写。把两者前后拼起来仍允许别人插入操作。 |
| `atomic_fetch_add(&x,1)` | 原子地取出旧值并加一，返回旧值。若原来为 5，返回 5，x 变为 6。普通 int 上的 `x++` 无此保证。 |
| `test_and_set(&lock)` | 原子地取旧值并置 true；旧值 false 表示此次拿到了锁。CAS 则按 expected 决定是否写。 |

**题型 A · 填空与跟踪锁值**（共享 lock 初始为 0）

```c
while (CAS(&lock, 0, 1) != 0) { }
critical_section();
atomic_store(&lock, 0);
```

若甲先 CAS，返回 0，锁变 1，`0 != 0` 为假，甲进入。乙随后 CAS，返回 1，锁仍为 1，乙继续循环。甲退出置 0 后，乙和刚来的丙都可争锁。丙可以先成功，于是得出**能互斥、能前进、不能保证有限等待**。若题目把 `!= 0` 改为 `== 0`，取得锁的人反而继续循环，看到锁被占用的人却能跳出，互斥协议就错了。

**题型 B · 用 CAS 实现原子加一**

```c
do {
    old = atomic_load(&count);
} while (CAS(&count, old, old + 1) != old);
```

初值 5，两人都先读到 5。甲执行 CAS(5→6)，返回 5，成功退出。乙也尝试 CAS(5→6)，实际值已经是 6，所以返回 6、本次不写。乙重读 6，再尝试 CAS(6→7)，返回 6，成功退出。**最终为 7。** 若把 load 移到循环外，失败者可能始终拿过期的 expected=5 重试。

**题型 C · 有限等待版的两种进入方式**（初始 lock=0，各 waiting=false，key 和 j 是私有变量；共享读写按课件顺序一致模型执行）

```c
waiting[i] = true;
key = 1;
while (waiting[i] && key == 1)
    key = CAS(&lock, 0, 1);
waiting[i] = false;
critical_section();

j = (i + 1) % n;
while (j != i && !waiting[j])
    j = (j + 1) % n;
if (j == i)
    lock = 0;                // 环扫一圈，无人等待，开放竞争
else
    waiting[j] = false;      // 有指定接班人，lock 保持 1
```

Pi 能跳出进入循环有两个原因：① CAS 返回 0，自己抢到空闲锁；② 上一位令 waiting[i]=false，把资格直接交给了自己。例：P0 正在临界区，P1、P2 已登记，P0 退出时先找到 P1，清 waiting[1]，**保持 lock=1**。P1 可以退出循环，即便它自己的 CAS 一直返回 1。其他人仍不能抢这把锁。若在直接交接时还把 lock 清成 0，新来者就可能与指定接班人同时进入。环形依次寻找等待者，让已登记者最多被其他 n−1 人先行。[CAS 锁，第 25–26 页](<lesson6-synchronization.pdf#page=25>) · [有限等待版，第 27–29 页](<lesson6-synchronization.pdf#page=27>) · [原子加一，第 30–31 页](<lesson6-synchronization.pdf#page=30>)

### 四、Lesson 7 三个经典问题分别要求什么

| 算法 | 哪些必须互斥，哪些可以并发 | 好在哪里 | 可能坏在哪里 |
|---|---|---|---|
| 有界缓冲区（生产者—消费者） | 放、取以及更新下标需互斥。锁外的生产与消费可并行。空时消费者等产品，满时生产者等空位。 | 用 empty/full 管数量，mutex 管共享数据；耗时处理可放锁外。 | 先拿 mutex 再等资源可死锁。只保证数量和互斥并不自动保证每个同类等待者公平获准。 |
| 读者—写者（课件的读者优先版） | 读—读可并发，读—写和写—写互斥；读者计数更新也要互斥。 | 首位读者 P(rw)，末位读者 V(rw)，读者组可共同读。 | 新读者可以不断加入，只要人数不归零，写者就可能饥饿；写者无有限等待保证。 |
| 哲学家就餐 | 每根筷子一次只能一人用。相邻两人不能同时吃，不相邻者可并行。 | 管程内统一检查左右邻居，两根一起授予，可消除人手一根的死锁。 | 朴素“先左后右”会成环；管程方案虽无这种死锁，左右邻居仍可能交替抢先，使同一人饥饿。 |

**三个最短反例，闭卷能写出来。**

1. **缓冲区。** 初始为空。消费者先拿 mutex 再 P(full)，生产者拿到空位却进不了缓冲区。正确写法是消费者先 P(full) 再 P(mutex)，取完 V(mutex)、V(empty)。生产者对应 P(empty)、P(mutex)、放、V(mutex)、V(full)。
2. **读者写者。** R1 读，W 等；R1 离开前 R2 加入，R2 离开前 R3 加入。读者持续完成工作，W 却可能一直等。这是整体有进展、个体饥饿。
3. **哲学家。** 五人各拿一根左筷，下一根在右邻手里，所有人同时等，形成死锁。可改为按筷子编号递增取、五人最多四人同时尝试，或管程内判断两根都可用才授予。要进一步保证有限等待，还需明确的公平授予规则。
