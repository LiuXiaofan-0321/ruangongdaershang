1.1 为什么要学 OS：一道“保存配置”的题

老师用一个例子开课：实现 save_config(path, data)，把新配置写进文件。正常跑一次没问题，但有三个追问：

① 写到一半程序崩了
用 "w" 打开文件会先把它截成 0 长度，再写。写一半退出，旧配置没了，新配置也不完整，只剩 {"theme":"da。
② 显示“保存成功”后断电
数据可能还在 Python 缓冲区或内核的页缓存里，没真正落到磁盘上。
③ 两个请求同时改
A 改主题、B 改字号，都先读旧版本再各自写回，后写的会覆盖先写的，A 的修改丢了。

正确思路：先写到同目录的临时文件 → flush → fsync(临时文件) → os.replace(tmp, path) 原子替换 → fsync(父目录) → 才返回成功。并发修改要再定义冲突策略（加锁、版本检查、合并）。

这一节想说明什么

程序到底会不会出错，取决于操作系统接口到底保证了什么。AI 能写代码，但要判断它考虑漏了“中途失败、断电、并发”哪种情况，就得懂文件、缓存和并发的机制。大模型是按概率生成下一个 token，概率模型给不了正确性保证；没有外部反馈的反复“自查”也不保证变好。

1.2 什么是操作系统★★

教材定义：操作系统是管理计算机硬件的程序。它还为应用程序提供运行基础，并且是用户与硬件之间的中介。

两个角度理解：

  • 资源管理者：CPU、内存、磁盘、设备都有限，OS 决定谁用、用多少、什么时候用。
  • 扩展机器 / 抽象：把难用的硬件包装成好用的概念（文件、进程、地址空间），程序员不用直接操作磁盘扇区。
真题 · 2020 选择

“哪个组件定义了使用系统资源解决计算问题的方法？”原卷答案是 B 操作系统。注意教材原文的分工是：应用程序定义用资源解决用户问题的方式，操作系统控制和协调硬件在各应用之间的使用。考试遇到原题按老师答案选 B，但要知道这个分工。

1.5 用户态、内核态、系统调用与中断★★★

  • 系统调用：应用请求内核服务的入口，例如读写文件、创建进程。
  • 用户态与内核态：执行权限不同，普通应用不能执行特权操作，也不能访问别人的内存。
  • 应用调用的普通函数（如 strlen）不一定触发系统调用。

OS 什么时候拿到 CPU 的控制权？中断！

教材原话：An operating system is interrupt driven. OS 平时并不一直在跑；应用正在执行时，是中断让控制权转到内核。

硬中断 hardware interrupt
由硬件设备发出：时钟到期（时间片用完）、磁盘/网卡完成 I/O。异步发生，与当前指令无关。
软中断 software interrupt（trap）
由程序执行引起：
· 系统调用：主动请求服务，如读文件；
· 异常：执行指令出错，如除零、缺页。

例：时钟中断 → 内核获得控制 → 决定哪个任务继续运行。这就是防止一个程序霸占 CPU 的方法。

考点 · 三年真题
  • 2018 选择：OS 提供给程序员的接口是 → 系统调用（不是库函数、不是 Shell；Shell 是给用户的命令接口）。
  • 2018 简答：比较核心态和用户态 → 核心态是 OS 内核执行时的受保护状态，可执行特权指令、访问全部内存；用户态是用户进程执行的状态，只能访问自己的地址空间；用户态要通过中断或系统调用才能进入核心态。
  • 2019 选择：CPU 执行操作系统代码时处于 → 内核态。
  • 2018 不定项：中断优先级由硬件规定 ✓；中断是多道并发的必要条件 ✓；“只有硬件中断发生时内核才运行” ✗（系统调用、异常也会进入内核）。
  • 2018：单处理机系统里操作的“原子性”可通过屏蔽中断实现（关了中断就不会被切走）。但多处理器上关中断不能保证互斥（2019、2020 判断题都考了，只关了自己这颗 CPU 的中断，别的 CPU 照样跑）。

2.1 操作系统提供哪些服务★★

以 cp source.txt target.txt 为例，复制一个文件就要用到：启动程序、访问文件、分配 CPU 和内存、处理失败（没权限、文件不存在、磁盘满）、报告结果。

对用户有帮助的服务
  • 用户界面 UI：命令行、图形、触控
  • 程序执行：装入、运行、正常或异常结束
  • I/O 操作：读输入、写输出、访问设备
  • 文件系统操作：创建删除、读写定位、目录、权限
  • 通信：进程间交换数据（共享内存或消息传递）
  • 错误检测：发现并处理程序/设备/硬件错误
保证系统本身高效、安全的服务
  • 资源分配：CPU 时间、内存、文件空间、设备
  • 记录与统计（logging / accounting）
  • 保护：谁能访问什么，避免相互干扰
  • 安全：身份认证、防范攻击

2.2 用户界面：Shell、GUI、触控

  • Shell（命令解释器）读取并解析命令，然后执行内建命令或启动外部程序。
    • 内建命令：如 Bash 的 cd，因为它要改变 Shell 自己的工作目录，必须由 Shell 本身执行。
    • 外部程序：如 /bin/ls，增加新命令不用改 Shell。
  • Shell 是普通程序，运行在用户态，不是内核的一部分。
  • GUI：窗口、图标、菜单 + 鼠标键盘，重要早期研究来自 Xerox PARC。触控界面：手势、虚拟键盘、语音。
  • 界面怎么变，程序访问资源的基本路径不变：都要经过系统提供的接口。

2.3 系统调用★★★

系统调用（System call）：程序请求内核服务的受控接口。用户程序不能把内核函数当普通函数随便跳过去执行，必须走体系结构规定的入口（trap 指令）。

API、库函数、系统调用：三个层次

概念规定什么例子
API源代码怎样调用功能POSIX read()、Windows API、Java API
库 / 运行时参数处理、缓冲、发起底层调用C 标准库、JVM
系统调用用户程序怎样受控进入内核Linux 文件读写、进程操作

为什么程序员一般用 API 而不直接用系统调用？可移植（同一套 API 在不同系统上都能编译）、好用（隐藏寄存器等细节）。strlen 这种函数根本不进内核；printf 先进 C 库缓冲区，不一定立刻 write。

读懂 read 接口

ssize_t read(int fd, void *buf, size_t count); /* fd：从哪个已打开的文件描述符读；buf：放到哪；count：最多读多少字节 返回 > 0：实际读到的字节数（可能比 count 少，叫“短读”，不是错误） 返回 0 ：到达文件末尾 EOF 返回 -1 ：失败，错误原因在 errno */

一次系统调用怎样进入内核

  1. 库把系统调用号和参数放到约定位置，执行 trap 指令。
  2. CPU 切换到内核态，保存必要状态，跳到系统调用入口。
  3. 入口按调用号查表分派到对应处理函数（系统调用表）。
  4. 内核检查参数后处理；完成后返回用户态，返回值交给程序。必要时中途会等待或被调度。

“进入内核”不等于“换了一个进程”，还是同一个进程，只是在内核态执行。

参数怎么传给内核（教材经典考点）

① 寄存器
把参数值放进约定寄存器。最快，但数量受限。Linux x86-64 常用。
② 内存块（表）
参数放在内存里一个块/表中，把块的地址放进寄存器传给内核。参数多时用。
③ 栈
程序把参数压入栈，内核从栈中弹出。

后两种方式不限制参数个数和长度。不管哪种，内核都必须检查参数：fd 是否有效、缓冲区地址是否属于这个进程且可写、长度是否越界/溢出、有没有权限。用户给的指针不能直接信任，否则恶意程序可以让内核替它改写内核内存。

2.4 系统程序；编译、链接、装载

系统程序（文件管理、编辑器、编译器、Shell、日志服务……）一般运行在用户空间，通过系统调用使用内核服务，它们不是内核本身。

静态链接动态链接
库代码并入可执行文件运行时装入或映射共享库（.so / .dll）
部署依赖少需要兼容的库
更新库要重新链接换共享库即可，但要保持兼容
空间多个程序各存一份重复代码多个进程可共享只读代码页（可写数据仍各自隔离）

为什么同一个程序不能直接跨系统运行？即使 CPU 相同，还要看：指令集、可执行文件格式（Linux 用 ELF，Windows 用 PE）、系统调用和库接口、ABI（应用二进制接口：二进制层面的调用约定、数据布局）。API 面向源代码，ABI 关系到编译后的代码能否配合。跨平台办法：解释器（Python）、虚拟机（Java 字节码 + JVM）、针对各平台分别编译（C/C++）。

2.5 设计目标；机制与策略

用户目标（方便、响应快、可靠）和系统目标（高效利用资源、易维护、易移植扩展）常常冲突，要权衡。例如隔离越强，通信开销可能越大。

场景机制 Mechanism：“能怎样做”策略 Policy：“何时做、选谁、做多少”
CPU 调度时钟中断、保存和恢复执行状态下一次运行哪个任务
内存分配页表与映射、分配和回收操作给谁多少、何时回收

把机制和策略分离，改决策时不用动底层实现。（定时器是机制，“给每个用户多长时间片”是策略。）

考点 · 三年都考微内核
  • 2018 不定项：“进程间通信机制是微内核的一部分” → ✓。
  • 2019 判断：“微内核结构中，虚拟内存管理在微内核内部” → ✗。按答案：只有 CPU 调度和进程间通信是必须在微内核内部的（虚存的分页策略等可以放在用户态服务里）。
  • 2020 判断：“微内核中进程间通信可以不在微内核内” → ✗。IPC 是微内核的核心功能。2020 选择：微内核中使用的 IPC 方式 → 消息传递。
  • “Linux 可以加载模块，所以是微内核吗？” → 不是。模块加载后在内核空间、拥有内核权限，没有微内核那种进程隔离；Linux 是单体内核 + 模块化。

2.8 课堂练习参考答案

调用 printf() 是否一定立刻发生一次 write()？

不一定。printf 先格式化并放进 C 库的用户态缓冲区，缓冲区满、遇到换行（行缓冲时）、调用 fflush 或程序退出时才调用 write。所以 0 次、1 次或几次 printf 合并成 1 次 write 都可能。依据：stdio 缓冲机制，用 strace 观察。

一个函数参数是用户指针，内核为什么不能直接信任它？

指针可能无效、指向别的进程无权访问的区域，甚至指向内核内存。若内核直接写入，恶意程序就能借内核之手改写内核数据、提权。所以内核要检查地址是否属于该进程、是否可读写、长度是否越界。

两台机器 CPU 相同，为什么仍可能不能运行同一个可执行文件？

还取决于可执行文件格式（ELF/PE）、系统调用接口、所依赖的库及版本、ABI（调用约定、数据布局）。指令集相同只是必要条件。

Linux 可以加载模块，是否就属于微内核？

不是。判断依据是服务运行在哪里、怎样协作：Linux 的模块加载后运行在内核空间、拥有内核权限、通过函数调用协作；微内核把服务放到用户空间独立进程、经 IPC 协作。Linux 是单体 + 模块化。

从按下电源到出现 Shell，至少经过哪些阶段？

固件初始化 → 引导程序装入内核 → 内核初始化子系统 → 挂载根文件系统、运行第一个用户进程 init（如 systemd）→ 启动系统服务 → 提供登录 / Shell。

3.1 程序与进程★★

教材定义：A process is a program in execution. 进程是执行中的程序。

程序 Program
磁盘上的指令和数据，是静态的文件（被动实体）。像一份菜谱。
进程 Process
程序的一次执行，有运行状态和资源，是动态的（主动实体）。像照着菜谱做菜的过程。

同一个程序可以对应多个进程，各有自己的 PID 和执行进度（开两个终端 = 同一个 Shell 程序的两个进程）。

一个进程包含：执行进度（程序计数器 PC、寄存器）、代码与数据、栈、堆、系统资源（打开的文件、身份、通信端点）。

3.2 进程的地址空间★★

#include <stdlib.h> int x; // 未初始化全局 → bss int y = 15; // 已初始化全局 → data int main(int argc, char *argv[]) { // argc、argv → 最高处 int *values; // 局部变量 → 栈 int i; // 局部变量 → 栈 values = malloc(sizeof(int)*5); // 5 个 int 本体 → 堆 for (i = 0; i < 5; i++) values[i] = i; return 0; // main 的机器指令 → text }
真题 · 2020 选择

“下面哪一个包含可执行代码？” → A 文本（text）部分。data 放全局变量，heap 放动态分配，stack 放函数调用的局部数据。

易错：values 这个指针变量本身在栈上，它指向的 5 个 int 在堆上；static 局部变量在 data/bss，不在栈上。

3.3 进程的五种状态★★★★

状态含义比喻（排队打饭）
New 新建正在创建刚进食堂
Ready 就绪万事俱备，只差 CPU排在窗口队伍里
Running 运行正在 CPU 上执行（单核同一时刻只有一个）正在窗口打饭
Waiting 等待（阻塞）在等 I/O 或某个事件，给它 CPU 也没用饭卡没钱，去充值了
Terminated 终止执行结束，等待清理回收打完饭离开
状态机模拟器：点事件，看进程能不能这样走
当前：New。点一个事件试试。
转换典型原因
New → Ready创建完成，被系统接纳（admitted）
Ready → Running调度程序从就绪队列选中它（scheduler dispatch）
Running → Ready时间片用完，或被更高优先级抢占（中断）
Running → Waiting请求 I/O、等待事件（如等子进程、等消息、等锁）
Waiting → ReadyI/O 完成或事件发生
Running → Terminated执行完毕（exit）或出错被终止
易错 · 不可能的转换
  • Waiting → Running 不可能：事件完成后必须先回到就绪队列，再等调度程序选中（2018 选择）。
  • Ready → Waiting 不可能：就绪的进程没在执行，不会发出 I/O 请求。
  • New → Running 不可能：要先进就绪队列。
考点 · 三年真题
  • 2019：正在运行的进程时间片用完，挂到 → 就绪队列。
  • 2020 判断：“进程请求打开的文件打开后，进程从运行态变为就绪态” → ✗。请求打开文件时它进了等待态，文件打开（I/O 完成）后是 等待态 → 就绪态。
  • 2020 不定项：哪些情况可能让进程离开 CPU？I/O 请求、创建子进程（父进程可能被放回就绪或等待子进程）、中断或时间片到期 → ABCD 全选。
  • 2020 简答：线程有 Ready、Running、Waiting 三态，列出所有可能转换和条件 → 就是上表中间 4 行。
  • 调度时机（详见 5.2）：Running→Waiting、Running→Terminated 时调度是非抢占的；Running→Ready、Waiting→Ready 时调度是抢占式的（2020 选择：抢占式调度可发生在 等待→就绪 时）。
  • 2018 判断：“进程执行的相对速度不能由进程自己控制” ✓（取决于调度和资源）。2019 判断：“进程执行的相对速度与资源无关” ✗（资源不够就得等）。

3.4 PCB、调度队列与调度程序★★★

PCB（进程控制块）是内核为每个进程保存的数据结构，是进程存在的唯一标志。进程不在 CPU 上时，靠 PCB 记住它的一切，以便之后恢复。

PCB 里有什么
进程状态（new/ready/running…）
标识：PID、父进程
程序计数器 PC：下一条指令地址
CPU 寄存器
CPU 调度信息：优先级、队列指针
内存管理信息：页表、基址/界限
记账信息：CPU 用时、时间限制
I/O 状态信息：打开的文件列表、分配的设备

Linux 用 task_struct 结构表示进程，用双向链表把它们串起来；current 指向当前正在运行的任务。

观察：ps -o pid,ppid,stat,comm、cat /proc/$$/status。状态字母：R 运行或可运行、S 可中断睡眠（等待）、Z 僵尸。

三级调度（2018 判断题）

调度别名做什么频率
长程调度作业调度、高级调度决定哪些作业从外存进入内存、创建为进程；控制多道程度低（分钟级）
中程调度中级调度把进程暂时换出到外存（swap），内存宽松时再换入中
短程调度CPU 调度、进程调度、低级调度从就绪队列选一个进程分配 CPU非常高（毫秒级），必须快

2018 判断“作业调度是高级调度，进程调度是低级调度” → ✓。

3.5 上下文切换★★★

  • 切换的时间是纯开销，速度取决于硬件（寄存器数量、是否有多组寄存器）和内存速度；切换后缓存、TLB 失效还带来后续开销。
  • 但不能“避免所有切换”：等 I/O 时切换能让别人用 CPU；时间片切换保证交互响应、防止独占。
  • 进入内核 ≠ 切换进程：系统调用处理完可以直接返回原进程（只是模式切换，开销小得多）。
真题 · 2020 简答：列举 3 种减少上下文切换开销的方法
  • 使用较少的内核线程（事件驱动编程、有界线程池）。
  • 减少模式切换次数（用户级线程/用户级调度，切换不进内核）。
  • 使用切换较少的调度算法（如 FIFO 而不是时间片很小的 RR；适当增大时间片）。
  • 硬件支持：多组寄存器，切换时只换寄存器组指针。

另见 2018 判断：“时间片越小，响应时间越小，系统效率越高” → ✗。响应快了，但切换开销占比增大，效率降低。

3.6 进程创建：fork、exec、wait★★★★

已有进程（父进程）可以创建新进程（子进程），形成进程树。Linux 中根是 systemd（PID 1）。

pid_t pid = fork(); if (pid < 0) { /* 创建失败，只有父进程得到 -1 */ } else if (pid == 0) { /* 子进程：fork 返回 0 */ } else { /* 父进程：fork 返回子进程的 PID */ }
为什么 fork “返回两次”

调用一次 fork，内核复制出一个几乎一样的子进程。从这一刻起有两个进程，都从 fork 返回的地方继续往下跑，只是拿到的返回值不同：子进程拿到 0，父进程拿到子进程 PID。父子谁先执行没有保证。

fork 之后父子关系
普通变量初值相同，之后各改各的，互不可见（地址空间独立，Linux 用写时复制 COW 实现）
继承的文件描述符指向同一个打开文件描述，共享文件偏移量
PID、执行进度PID 不同，之后独立推进
  • exec 系列（execlp、execve…）：在当前进程中装入新程序，替换掉代码、数据、栈。成功后不返回，原程序 exec 之后的代码不会执行；PID 不变。
  • wait / waitpid：父进程等待子进程状态变化，取得并回收其退出信息。
  • exit：结束进程，退出码交给系统。
  • Shell 的套路：fork 子进程 → 子进程 exec 命令 → 父进程 wait（前台）或继续（后台 &）。
fork 进程树：for (i = 0; i < n; i++) fork();
例题 · 课件第 27 页：打印顺序可能是什么？
pid_t pid = fork(); printf("[0] Hello from %d\n", pid); if (pid == 0) { printf("[1] [Child] before exec\n"); execlp("echo", "echo", "[2] Hello from echo", NULL); printf("[3] [Child] after exec\n"); } else { waitpid(pid, &status, 0); printf("[4] [Parent] child exited with code %d\n", WEXITSTATUS(status)); }
  • 父、子各打印一次 [0]（父的 pid 是子进程号，子的是 0），两者先后不定。
  • 子进程依次：[0] → [1] → echo 打印 [2]。
  • [3] 永远不会打印：exec 成功后原程序被替换（除非 exec 失败）。
  • [4] 一定最后：父进程 waitpid 等子进程结束才打印，退出码 0。
  • 可能顺序：[0]父 [0]子 [1] [2] [4]、[0]子 [0]父 [1] [2] [4]、[0]子 [1] [0]父 [2] [4]、[0]子 [1] [2] [0]父 [4]。
真题 · 2020 综合（10 分）：file.txt 最终可能是什么？

前提：file.txt 初始为空，open(..., O_WRONLY) 不清空不追加，从偏移 0 开始写；调度顺序不定。

程序一：fork 之后父子各自 open，子写 "a"，父写 "b"

两次 open 得到两个独立的打开文件描述，各自偏移都从 0 开始，都写在第 0 个字节，后写的覆盖先写的。

结果：B（a）或 C（b）。

程序二：先 open 再 fork，子写 'a'，父写 'b'（buffer 是全局变量）

fd 继承自同一次 open，父子共享文件偏移：先写的写在位置 0，偏移变 1，后写的写在位置 1。全局 buffer 在 fork 后各自独立，子的是 'a'，父的是 'b'，不会互相影响。

结果：E（ab）或 F（ba）。

程序三：open 后 pthread_create，新线程写 "a"，主线程写 "b"

线程共享 fd 和偏移，所以两者都写了就是 ab 或 ba。但主线程写完后 main 返回 → 整个进程退出，新线程可能还没来得及写，此时只有 b。

结果：C（b）、E（ab）、F（ba）。

3.7 进程终止；僵尸与孤儿★★

  • 正常结束：从 main 返回或调用 exit，把退出状态交给系统。异常终止：收到未处理的致命信号（如段错误 SIGSEGV、被 kill）。
  • 内核释放大部分资源，但保留 PCB 中的退出信息，等父进程来取。
  • 取退出码要先判断：WIFEXITED(status) 为真才用 WEXITSTATUS(status)；WIFSIGNALED 为真用 WTERMSIG。status 是编码过的，不能直接当退出码。
含义处理
僵尸进程 Zombie子进程已结束，但父进程还没 wait 回收它的退出信息（ps 显示 Z）父进程调用 wait 后彻底消失
孤儿进程 Orphan父进程先结束，子进程还在运行Linux 中被重新托管（由 init/systemd 或指定的收养进程接管，它会定期 wait）

有些系统采用级联终止：父进程结束，子进程也被强制结束。Linux 默认不这样。

手机为何限制后台
看不见的应用仍耗 CPU、内存、电量。Android 按重要性（前台、可见、服务、缓存）回收进程；iOS 只允许受限的后台任务。应用要保存可恢复状态：在后台 ≠ 一直运行。
浏览器为何多进程
Chrome：浏览器进程（界面与协调）+ 渲染进程（每个页面，在沙箱里）+ GPU/网络等服务进程。好处：故障隔离、安全边界、并行；代价：更多内存和 IPC。

3.8 进程间通信 IPC★★★

进程彼此隔离，要合作就得约定怎样共享或传递信息。为什么要合作：信息共享、计算加速、模块化、方便。

比较共享内存消息传递
数据在哪多个进程共同映射的区域发送缓冲、通道、接收端
怎么用像读写普通内存一样调用 send / receive 接口
速度快：建立后不用每次进内核较慢：每条消息都要系统调用
麻烦在哪要自己约定布局，并自己做同步要约定格式、寻址、等待和容量
适合本机大量数据少量数据、跨机器（分布式）通信；无需避免冲突

生产者-消费者与有界缓冲区（同步章节的伏笔）

生产者生成数据放进缓冲区，消费者取出处理。缓冲区空时消费者要等，满时生产者要等。两者速度可以不同，缓冲区吸收差异。比如摄像头产生视频帧，编码进程取出处理。

有界缓冲区模拟器（容量 4）
考点
  • 2019/2020 判断：“生产者-消费者问题只要解决互斥访问即可” → ✗。还要解决同步：缓冲区空时消费者必须等生产者生产出产品，满时生产者要等。
  • 模拟器里的 empty、full 就是以后 P/V 操作要用的两个信号量：值为负时，绝对值 = 正在等待的进程数。

POSIX 共享内存的步骤

fd = shm_open("/ipc_example", O_CREAT | O_EXCL | O_RDWR, 0600); // ① 创建共享对象 ftruncate(fd, sizeof(struct message)); // ② 设置大小 shared = mmap(NULL, sizeof *shared, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0); // ③ 映射 sem_init(&shared->ready, 1, 0); // 第 2 个参数 1 = 进程间共享；初值 0 = 消费者先等 /* 父进程（生产者）*/ snprintf(shared->text, …, "hello"); sem_post(&shared->ready); /* 子进程（消费者）*/ sem_wait(&shared->ready); printf("%s\n", shared->text); // ④ 用完 munmap，shm_unlink 删除

要点：共享的只是映射的那块区域，不是整个堆栈；各进程映射到的地址可以不同，所以共享区里别存指针，存偏移；必须先写完整再通知，否则消费者会读到一半的数据。

消息传递的三个设计问题

① 寻址：直接 vs 间接
直接：send(P, msg) 指名道姓发给进程 P，每对进程一条链路。
间接：send(A, msg) 发到邮箱/端口 A，多个进程可共用一个邮箱；一条消息被谁取走要有规则。
② 同步：阻塞 vs 非阻塞
阻塞发送：等对方收到才返回；非阻塞发送：发出就返回。
阻塞接收：没消息就等；非阻塞接收：没消息立即返回“暂无”。发送和接收都阻塞叫会合 rendezvous。
③ 缓冲：容量
零容量：不暂存，发送者必须等接收者。
有界：满了发送者阻塞/报错。
无界：理论上发送者从不等（实际仍受内存限制）。

3.9 管道、Socket 与 RPC★★

机制怎样找到对方用途
普通管道继承文件描述符（一般父子进程）本机相关进程，单向字节流
命名管道 FIFO文件系统路径名本机不相关进程按名字通信
SocketIP 地址 + 端口（或本机路径）本机或跨机器通信
  • pipe(fd)：fd[0] 是读端，fd[1] 是写端。Linux 普通管道是单向字节流，没有消息边界；双向通信要两条管道。
  • 什么时候 read 返回 0（EOF）：管道空了并且所有写端都关闭。只要还有一个写端开着（包括子进程自己忘了关的那个继承来的写端），读端就会一直阻塞等待。
  • 命名管道有路径，但数据不存进普通文件；Linux FIFO 也是半双工。
  • Socket = 通信端点，由 IP 地址 + 端口 标识；127.0.0.1 是本机回环地址。TCP 服务端：socket → bind → listen → accept → 收发；客户端：socket → connect → 收发。accept 返回一个新的已连接 socket，监听 socket 继续监听。TCP 是有序字节流，应用要自己定消息边界（如以换行分隔）。

RPC 远程过程调用

  • RPC 把“编码请求 → 传输 → 解码 → 执行 → 返回”封装成像本地函数调用一样的接口。stub（存根）负责编组。
  • 编组 / 序列化（marshalling）：不同机器字节序（大端/小端）、类型宽度不同，要编码成统一格式，如 XDR（外部数据表示）。不能把本机指针直接发过去。
  • 超时与重试：超时不能说明服务端没执行（可能执行了但回复丢了）。至多一次：带请求编号去重，可能没完成；至少一次：重试直到成功，可能重复执行。幂等操作重复执行效果相同；扣款、下单不是幂等的，需要去重。RPC 本身不保证“恰好一次”。

3.10 课堂练习参考答案

I/O 完成后，进程为什么通常先回到就绪状态？

I/O 完成时 CPU 可能正被其他进程使用，由调度程序决定谁运行；该进程只是重新具备了运行条件，所以进入就绪队列等待调度，而不是直接抢 CPU。

fork 后子进程修改普通变量，父进程能看到吗？

不能。fork 后父子地址空间独立（写时复制），子进程修改的是自己的副本。要共享数据需用共享内存等 IPC。

exec 成功后，为什么原程序后面的打印没有执行？

exec 用新程序替换了当前进程的代码、数据和栈，原程序已不在内存中，exec 成功不会返回。只有 exec 失败时才会继续执行后面的语句。

管道中已经没有数据，read 为什么仍可能等待？

只要还有任何进程持有该管道的写端（可能是自己忘关的继承副本），内核就认为以后可能还有数据，阻塞读会继续等。只有所有写端都关闭，read 才返回 0（EOF）。

RPC 调用超时，能认定服务端没有执行吗？

不能。可能是请求没到，也可能是已执行但回复丢失或太慢。所以非幂等操作重试前要用请求编号去重。

4.1 线程：共享什么、私有什么★★★★

只有一个线程时，一个操作阻塞就卡住整个进程。编辑器要同时响应按键、检查拼写、自动保存；服务器在等一个请求的数据时还要接收别的请求。所以把一个进程拆成多条执行流，就是线程。

同一进程内的线程共享每个线程私有
代码段、全局数据、堆程序计数器 PC、寄存器
地址空间、打开的文件栈、线程 ID
进程的其他资源和属性（信号处置等）调度状态、线程局部存储 TLS、信号屏蔽字
考点 · 必背
  • 2020 判断：“线程都保存有各自的栈、CPU 状态、堆信息、打开文件列表” → ✗。线程只保存栈和 CPU 状态；堆和打开文件列表是进程的（线程实现了资源单位与调度单位的分离）。
  • 2018 简答：进程与线程的关系 → 单线程进程中，进程既是资源管理单位也是调度单位；多线程进程中，线程是调度（CPU 分配）的单位，进程是资源分配的单位。线程相关的是寄存器和栈，进程相关的是栈以外的内存、打开文件列表等。
  • 2019 选择：线程控制块（TCB）中包含 CPU 寄存器状态 ✓；在支持核心态线程的系统中，CPU 调度单位仍是进程 ✗（是线程）。

4.2 多线程的四个好处；进程 vs 线程★★★

线程默认共享进程的内存和文件，不用像进程那样专门建 IPC。
经济 Economy
创建线程、切换线程比进程便宜（不用切地址空间）。
可扩展性 Scalability
多个线程可以在多核上并行。

4.3 并发与并行；多核编程★★★

真题 · 2018 简答：比较并发与并行

并发（concurrency）：一段时间间隔内有多个任务都在推进（宏观上“同时”，单核轮流也算）。

并行（parallelism）：同一时刻有多个任务在执行（微观上同时，必须有多个处理器/核）。

并行一定是并发，并发不一定是并行。

多核编程的五个挑战：任务划分（哪些可独立执行）、负载均衡（别让有的核早早闲着）、数据划分、数据依赖（必须等别人的结果）、测试调试（不同调度顺序结果还对不对）。

数据并行
把数据分成几份，每个核对自己那份做相同操作。例：4 个线程各调整图片的 1/4 像素。
任务并行
把任务（操作）分给不同核，各做不同操作。例：一个线程解码、一个加滤镜、一个编码。

4.4 Amdahl 定律★★★

就算一部分能并行，必须串行的部分会卡住整体加速比。设串行比例为 S，核数为 N：

加速比 ≤ 1 / ( S + (1 − S) / N ) N → ∞ 时，加速比趋近 1/S。串行 25% 的程序，再多核也快不过 4 倍。
Amdahl 计算器与曲线
例题
  • 课件：S = 0.25，N = 2 → 1/(0.25 + 0.75/2) = 1/0.625 = 1.6。
  • 课堂练习：S = 0.2，N = 4 → 1/(0.2 + 0.8/4) = 1/0.4 = 2.5。
  • 100 核：S = 0.10 → 9.17（上限 10）；S = 0.25 → 3.88（上限 4）；S = 0 → 100。

Amdahl 是理想模型，没算线程创建、同步、通信、缓存竞争、负载不均的开销，实际更低。它假设问题规模固定。2020 选择：计算“给有串行和并行部分的程序加核能提升多少” → Amdahl 定律。

4.5 用户线程、内核线程与映射模型★★★

  • 用户级线程：由用户空间的线程库管理，内核不知道它们的存在。切换快（不进内核）。
  • 内核级线程：内核保存状态并直接调度。Windows、Linux、macOS 都支持。
  • 用户线程最终要映射到内核线程上才能被 CPU 执行。Pthreads、Java 线程只是接口，看名字判断不了底层模型。
多对一
多个用户线程 → 1 个内核线程（GNU Pth）。
一个线程阻塞，全部阻塞；不能利用多核。
一对一
每个用户线程 → 1 个内核线程（Linux NPTL、Windows）。
并发性好、能多核；线程数受限（每个都要内核资源）。
多对多
多个用户线程复用较少的内核线程（Go goroutine、Java 虚拟线程）。
能多核，又控制内核线程数。
两级
多对多 + 允许某个用户线程绑定到专用内核线程（Solaris 8）。
考点 · 2019 不定项
  • “用户态线程（没有核心态线程或 LWP 支持）阻塞，可能会阻塞整个进程” → ✓。因为内核只看到一个执行实体，它一阻塞，所有用户线程都停了。
  • “多处理器环境下，线程间同步不能使用关中断实现” → ✓。
  • 一对一模型里一个线程等 I/O，不会让整个进程停住，其他线程照样被调度。

void *work(void *arg) { int id = *(int *)arg; for (int i = 0; i < 3; i++) { printf("Thread %d: iteration %d\n", id, i); sleep(1); } return NULL; // 线程函数返回 = 线程结束（或调用 pthread_exit） } int main(void) { pthread_t t1, t2; int id1 = 1, id2 = 2; pthread_create(&t1, NULL, work, &id1); // 新线程从 work(&id1) 开始 pthread_create(&t2, NULL, work, &id2); pthread_join(t1, NULL); // 等 t1 结束 pthread_join(t2, NULL); printf("All threads finished.\n"); }

输出顺序：同一线程自己的 iteration 0→1→2 一定按顺序；两个线程之间的交错每次可能不同；All threads finished. 一定在最后（两次 join 之后）。

创建线程后要保证的三件事
  • 参数有效：线程用参数期间，参数对象必须还活着；别把循环变量 &i 传给多个线程（i 会被改掉）。

  • 等待完成：用 join 等线程结束，不要用 sleep 猜。join 只保证“等结束”，不保证执行期间的互斥。

4.8 多线程带来的问题★★

多线程进程调用 fork / exec

  • fork()：子进程只保留调用 fork 的那个线程，其他线程不会被复制。但地址空间被复制了，别的线程持有的锁状态也被复制，持锁者却不在了，可能永远等不到解锁。
  • exec()：替换整个程序映像，所有线程都被终止。所以 fork 后马上 exec 时，只复制调用线程就够了。

信号

信号通知进程发生了某事件。同步信号由当前执行引起（除零、非法访问），递送给引发它的线程；异步信号来自外部（Ctrl+C、kill）。默认处置可能是终止、停止、继续或忽略；SIGKILL、SIGSTOP 不能被捕获、阻塞或忽略。

4.10 课堂练习与讨论

一个线程有自己的栈，是否意味着其他线程绝对不能访问它？

不是。线程栈在进程共享的地址空间里，别的线程只要拿到指向它的指针就能读写，没有硬件隔离。“私有”指每个线程有自己的一份，不是受保护。

串行部分占 20%，用 4 个核，理想加速比？

1 / (0.2 + 0.8/4) = 1 / 0.4 = 2.5。

一对一模型中一个线程等待 I/O，整个进程都无法运行吗？

不会。每个用户线程有自己的内核线程，内核只把等 I/O 的那个阻塞，其他可运行线程照样被调度。多对一模型才会全部阻塞。

在线程池中用 TLS 保存请求编号，下一个任务开始时要注意什么？

TLS 属于工作线程而不是任务，上一个任务的请求编号还留着。每个任务开始时要重新设置，结束时要清理，否则会串号。

pthread_cancel 成功返回后，目标线程一定结束了吗？

不一定。它只是发出取消请求；默认是延迟取消，要等目标线程到达取消点才响应，取消也可能被禁用。要确认结束得 pthread_join。

讨论：如果 Chrome 只用一个进程，每个页面和插件用一个线程，好处和坏处？

好处：线程创建和切换开销小；共享地址空间，页面间通信和共享缓存方便；总内存占用更少。

坏处：一个页面或插件崩溃（如非法访问内存）会让整个浏览器崩溃；无法给每个页面单独的沙箱权限，恶意网页利用漏洞后能访问其他页面的数据，安全性差；一个页面的内存泄漏或死循环拖累所有页面；共享数据需要大量同步，容易出竞争和死锁。

5.1 调度是什么：CPU 区间与 I/O 区间★★

上一讲说线程可以独立执行。可是就绪的线程常常比 CPU 多，总得有人决定下一个让谁上 CPU，这就是 CPU 调度。

  • 就绪队列（ready queue）：已经具备运行条件、只差 CPU 的任务排在这里。正在等 I/O 的任务不在就绪队列里，I/O 完成后才回来排队。
  • 本讲说的“任务”可以是进程，也可以是线程（支持内核线程的系统里，CPU 调度的单位是线程，见 4.1）。
比喻

CPU 是医院里唯一的医生，就绪队列是候诊区，去拍片（I/O）的病人不在候诊区。调度算法就是“叫号规则”：先来先看？病情轻的先看？每人先看 5 分钟轮流来？

程序运行时总是算一会儿、等一会儿交替进行：连续用 CPU 计算的一段叫 CPU 执行区间（CPU burst），等输入输出的一段叫 I/O 区间（I/O burst）。调度关心的是下一段 CPU 区间有多长，而不是整个程序要跑多久。

调度器的三个层次在 3.4 讲过：长程（作业调度，高级）、中程（换入换出）、短程（CPU 调度，低级）。本讲讲的都是短程调度，它非常频繁（几十毫秒一次），所以必须快。

5.4 先来先服务 FCFS 与护航效应★★★

FCFS（First-Come, First-Served）：按进入就绪队列的顺序执行，新来的排队尾，CPU 空了取队首；非抢占，一直跑到这段 CPU 区间结束或阻塞。

课件例子：P1=24、P2=3、P3=3，都在时刻 0 到达。只是换了排队顺序，结果天差地别：

算一遍

顺序 P1、P2、P3：等待 0、24、27，平均 (0+24+27)/3 = 17。
顺序 P2、P3、P1：等待 0、3、6，平均 (0+3+6)/3 = 3。
总工作量都是 30，只是短任务不再被长任务挡住。

护航效应（Convoy effect）

一个长的 CPU 密集型任务占着 CPU，一群 I/O 密集型的短任务只能在后面干等，就像一辆慢车后面排起的车队。短任务拿不到 CPU 就发不出下一次 I/O，于是I/O 设备闲着；等长任务去做 I/O 了，短任务一拥而上、很快又都去等 I/O，CPU 又闲着。CPU 和 I/O 交替空闲，利用率下降。

考点 · 2020 选择

可能出现护航效应的调度算法 → FCFS。FCFS 的优点：简单、公平（按顺序）、切换少；缺点：平均等待时间往往很长、对短任务和交互任务不友好。

5.5 短作业优先 SJF 与最短剩余时间优先 SRTF★★★★

SJF（Shortest-Job-First）：每次从就绪队列中选下一段 CPU 区间最短的任务。课件里的 SJF 默认是非抢占的：一旦开始就跑完，后来的再短也不抢。

P1=6、P2=8、P3=7、P4=3 同时到达：顺序 P4→P1→P3→P2，等待 3、16、9、0，平均 7。

为什么短的先跑，平均等待最小？（课件 P21 的证明）

两个任务从时刻 t 开始跑，长度 a > b。
长的先：两者等待之和 = t + (t + a) = 2t + a；
短的先：两者等待之和 = t + (t + b) = 2t + b，少了 a − b。
后面任务的开始时间不变。所以只要发现“长的排在短的前面”就交换，一直换到按长度从小到大排列，平均等待最小。

结论：一组任务同时到达、执行时间已知、忽略切换开销时，SJF 的平均等待时间最小（最优）。

SRTF：SJF 的抢占版

SRTF（Shortest-Remaining-Time-First，也叫抢占式 SJF、STCF）：每当有新任务到达，就拿新任务的执行时间和当前任务的剩余时间比，新的更短就抢占。

课件 P23 · 一步步来

到达 0、1、2、3；执行 8、4、9、5。

  • t=0：只有 P1，开跑。
  • t=1：P2 到（需 4），P1 还剩 7 → P2 抢占。
  • t=2、3：P3（9）、P4（5）到，都比 P2 剩下的长，P2 继续，到 t=5 完成。
  • t=5：剩 P1(7)、P3(9)、P4(5) → P4；t=10 → P1；t=17 → P3，t=26 结束。
  • 等待：P1 = 17−0−8 = 9，P2 = 0，P3 = 26−2−9 = 15，P4 = 10−3−5 = 2 → 平均 26/4 = 6.5。（同一组数用非抢占 SJF 是 7.75。）
考点
  • 2020 简答：SRTF 在哪个指标上最优？→ 平均等待时间（平均响应时间）最优。FCFS 在什么指标上优于 RR？→ 吞吐量（没有频繁的上下文切换开销）。
  • 课堂练习：新任务到达时，非抢占 SJF 不管它，等当前任务跑完再按长度选；SRTF 立刻比较“新任务长度”和“当前任务剩余”，更短就抢。
  • SJF/SRTF 的两个问题：① 下一段 CPU 区间有多长事先不知道，只能预测；② 短任务源源不断来时，长任务可能饥饿。

怎么预测下一段 CPU 区间：指数平均

τn+1 = α·tn + (1 − α)·τn　　0 ≤ α ≤ 1 tn：第 n 次实际长度；τn：对第 n 次的预测；τn+1：对下一次的预测。
课件例：α = 0.5，τn = 10，tn = 6 → τn+1 = 0.5×6 + 0.5×10 = 8。
α = 0：只用旧预测，新数据不起作用；α = 1：只看最近一次；0 < α < 1：越早的数据权重按 (1−α) 的幂衰减。
拖一拖：α 越大，预测越“跟得紧”

5.6 高响应比优先 HRRN★★

课件没有单独讲，但 2019 判断题考过，国内教材常见。

响应比 R = (等待时间 + 服务时间) / 服务时间 = 1 + 等待时间 / 服务时间 非抢占。每次 CPU 空出来时，给就绪队列里每个任务算一次 R，选最大的。
  • 服务时间短 → R 大 → 优先（像 SJF）；
  • 等得越久 → R 越大 → 长任务也终会轮到（像 FCFS，不会饥饿）。
考点 · 2019 判断

“RR、短进程优先、FCFS 及高响应比优先调度算法都没有综合考虑进程等待时间和执行时间” → ✗。高响应比优先综合考虑了等待时间和执行时间。

例题：A(到达 0, 服务 3)、B(2, 6)、C(4, 4)、D(6, 5)、E(8, 2)，用 HRRN 求执行顺序

t=0 只有 A，A 跑到 3。t=3 只有 B，B 跑到 9。

t=9：C 等了 5 → R = (5+4)/4 = 2.25；D 等了 3 → (3+5)/5 = 1.6；E 等了 1 → (1+2)/2 = 1.5 → 选 C，跑到 13。

t=13：D 等了 7 → (7+5)/5 = 2.4；E 等了 5 → (5+2)/2 = 3.5 → 选 E，跑到 15；最后 D 跑到 20。

顺序 A B C E D，等待 0、1、5、9、5，平均 4.0（FCFS 是 4.6，SJF 是 3.6）。在下面的模拟器里选“高响应比 HRRN 例”可以看到甘特图。

5.7 时间片轮转 RR★★★★

RR（Round Robin）：就绪队列当成一个循环队列，每个任务最多连续跑一个时间片 q：

  • q 内跑完或阻塞 → 提前让出 CPU；
  • q 用完还没跑完 → 被抢占，回到队尾；
  • 它是抢占式的，专为分时、交互系统设计。
课件 P29（q=4）P1P2P3平均
首次运行时刻047
完成时刻30710
响应时间04711/3 ≈ 3.67
等待时间30−24 = 64717/3 ≈ 5.67
易错 · 画 RR 甘特图的三条规矩
  1. 时间片用完的任务排到队尾；如果同一时刻有新任务到达，惯例是新任务先入队，被换下的再排在它后面（题目另有说明时按题目）。
  2. 任务剩余时间不足 q，跑完就走，不必用满 q，下一个立刻接上。
  3. 队列里只剩它自己时，时间片到了也不会换人，它接着跑（课堂练习：RR 时间片到期不一定切换）。

时间片 q 选多大

q 太大
每个任务都能在一个时间片里跑完 → 退化成 FCFS，响应变慢。
q 太小
切换太频繁，上下文切换的开销占比变大，CPU 大量时间花在“换人”上 → 效率下降。

经验：q 要比一次上下文切换的时间大得多（q 常取 10–100 ms，切换不到 10 μs）；让大约 80% 的 CPU 区间短于 q。固定 n 个任务都一直就绪时，每个任务最多等 (n−1)·q 就能再轮到。

考点
  • 2018 判断：“时间片越小，系统的响应时间就越小，系统的效率就越高” → ✗。时间片小能缩短响应时间，但切换开销占比增大，效率降低。
  • 2019 选择：运行进程时间片用完 → 挂到就绪队列。
  • 2020 判断：RR 不需要预知任务运行时间，且不会出现长任务饥饿 → ✓。
  • RR 的平均等待时间往往比 SJF 长，但响应时间短；首次响应快 ≠ 总等待少。

5.8 优先级调度；饥饿与老化★★★

给每个任务一个优先级，每次选优先级最高的。可以是抢占式（更高优先级的到了就抢），也可以是非抢占式。同级之间再用 FCFS 或 RR 决定先后。

易错 · 先看清“数字大还是数字小优先”

课件例题数字越小优先级越高；2018 期中题和课堂练习是数字越大越高（“这里 5 为最高优先级”）。题目没说时按教材默认“数字小 = 优先级高”，并在答案里写明你的假设。

课件 P33（数字小优先）：顺序 P2→P5→P1→P3→P4，等待 6、0、16、18、1，平均 8.2。

SJF 其实是优先级调度的特例：把“预测执行时间越短”定为“优先级越高”。

饥饿（Starvation）与老化（Aging）

饥饿
高优先级任务源源不断，低优先级任务一直就绪却总轮不到。（传闻 1973 年拆 MIT 的 IBM 7094 时，发现一个 1967 年提交的低优先级任务还没跑。）
老化
等得越久，逐步提高它的优先级（数字小优先时就是把数字减小），总有一天它会变成最高。也可以周期性把所有任务提到高队列，或给低优先级预留份额。

优先级 + 轮转

先选最高优先级，同一优先级内用 RR 轮流。课件 P35（数字小优先，q=2）：

P4（优先级 1）先跑完；再轮转 P2、P3（优先级 2）；最后轮转 P1、P5（优先级 3）。

5.9 多级队列与多级反馈队列★★★★

多级队列 MLQ（Multilevel Queue）

系统里既有交互任务又有后台计算，一条队列一个规则不合适。于是按任务类型或优先级分成几条队列（如实时 > 系统 > 交互 > 批处理），每条队列用自己的算法（交互用 RR，批处理用 FCFS），队列之间用严格优先级（高队列空了才轮到低队列）或按比例分时间（如前台 80%、后台 20%）。

关键：任务进了哪条队列就固定在那里，不会根据运行情况换队。

多级反馈队列 MLFQ（Multilevel Feedback Queue）

允许任务根据运行行为在队列间移动：用满时间片还没完（像 CPU 密集型）就降级；等太久就升级（老化）。越高的队列优先级越高、时间片越短。

5.11 多核调度★★

有多个 CPU 时，调度器不仅要选“谁跑”，还要选“在哪个 CPU 上跑”。

线程竞争范围

范围和谁抢 CPU谁来调度
PCS 进程竞争范围同一进程内的用户线程之间线程库（多对一、多对多模型中把用户线程排到 LWP 上）
SCS 系统竞争范围系统里所有内核线程之间内核

POSIX 用 PTHREAD_SCOPE_PROCESS / PTHREAD_SCOPE_SYSTEM 设置。Linux NPTL 是一对一模型，只支持 SYSTEM（对照 4.5）。

就绪队列怎么组织

  • 负载均衡：把任务从忙的 CPU 迁到闲的 CPU。推迁移（push）：定期检查，从忙的往外推；拉迁移（pull）：闲的 CPU 主动去别人队列里拿。负载不只看任务个数，还看优先级、可运行时间、CPU 能力。
  • 处理器亲和性（affinity）：任务在某个 CPU 上跑过，那个 CPU 的缓存里有它的数据，迁走就要重新加载。软亲和：调度器尽量留在原 CPU；硬亲和：限定只能在某些 CPU 上跑（但不保证独占）。亲和性和负载均衡是互相拉扯的。
  • NUMA（非一致内存访问）：每个 CPU 访问“自己那块”内存快，访问别的节点慢，所以迁移还要考虑内存在哪。

硬件多线程（超线程）

课堂练习

“四核八线程”是否等于八个独立物理核？→ 不等于。OS 看到 8 个逻辑 CPU，但同一核上的两个硬件线程共享执行单元和缓存，两个都满负荷时性能远不到两个核。

5.12 实时调度：RM 与 EDF★★

实时系统关心能不能在截止时间（deadline）前完成，而不是平均多快。

硬实时
错过截止时间 = 系统失败（如刹车、心脏起搏器）。

某任务首次运行很早，总等待时间一定很短吗？

不一定。响应时间只看第一次，等待时间要把每次回到就绪队列后的排队都加起来。RR 中的长任务第一次很快就上 CPU，但会反复排队，总等待可能很长（如 P12 的例子，响应 2、等待 5）。

新任务到达时，非抢占 SJF 与 SRTF 的选择有什么区别？

非抢占 SJF：当前任务继续跑完，新任务进就绪队列，下次 CPU 空出来时再按长度选。SRTF：立刻比较新任务的执行时间和当前任务的剩余时间，新任务更短就抢占。

RR 时间片到期，一定会切换到另一个进程吗？

不一定。如果就绪队列里没有别的任务，时间片到了它被放回队尾，又是队首，于是继续运行（不发生真正的进程切换）。

四核八线程是否等于八个独立物理 CPU 核？

不等于。8 个是逻辑 CPU，同一物理核上的两个硬件线程共享执行资源和缓存，只是利用访存停顿的空隙交替执行。

Linux 的 nice、实时优先级与 EEVDF 虚拟截止时间各表示什么？

nice：普通任务的调度权重，越小分到的 CPU 份额越大。实时优先级：SCHED_FIFO/RR 任务的优先级（1–99，越大越先），高的严格先跑。EEVDF 虚拟截止时间：公平调度类内部为兼顾公平和延迟而算出的排序依据，不是应用要求的真实截止时间。

同一算法在一个固定例题中表现最好，是否足以证明它适合所有工作负载？

不能。确定性建模的结论只对那组输入成立；要用排队模型、仿真、真实测量在多种负载下比较，并且看清目标指标（吞吐量、响应、截止时间）。

B 错：MLFQ 的队列之间就是按优先级排的。D 不是 MLFQ 的定义性特征（课件的 MLFQ 例子 Q0、Q1 都是 RR、Q2 是 FCFS，但各队列完全可以用不同算法）。

C 需要注意：本学期课件 P39 原话是 MLQ “任务按固定类别入队，不根据运行行为自动换队”，P42 是 MLFQ “任务可以在队列之间移动”，这正是 C 的意思。按课件，C 也成立，我认为选 AC 更符合今年的讲法。不定项选择少选多选都不给分，如果遇到原题，按课件理解写 AC；拿不准就在考前问一下老师或助教。

简答：SRTF 在什么指标上是最优的？在什么指标上 FCFS 优于 RR？（5 分）2020

SRTF 的平均等待时间（平均响应时间）最优。FCFS 在吞吐量上优于 RR，也省去了频繁上下文切换的开销。

辨析：多级反馈队列调度与 FCFS（5 分）2019

FCFS：按到达就绪队列的先后顺序分配 CPU，非抢占，一个任务运行到结束或阻塞。实现简单、切换少，但短任务排在长任务后面会等很久（护航效应），不适合交互系统。

多级反馈队列：设置多个优先级不同、时间片不同的就绪队列；新任务进最高队列，用完时间片未完成就降级，等待过久可升级；高队列空了才调度低队列，可抢占。短任务和交互任务响应快，长任务也不会饿死，不需要预知运行时间。

联系：MLFQ 的最低一级队列常用 FCFS；若 MLFQ 只有一个队列且时间片无穷大，就退化成 FCFS。区别：FCFS 单队列、非抢占、不看任务行为；MLFQ 多队列、抢占式、按运行行为动态调整。

综合：举例说明什么是多级反馈队列调度算法，其有哪些优点（10 分）2019

举例：三级队列 Q0（RR，q=8 ms）、Q1（RR，q=16 ms）、Q2（FCFS），高队列优先。新任务进 Q0；在 Q0 用完 8 ms 未完成降到 Q1；在 Q1 再用完 16 ms 未完成降到 Q2；一个需要 30 ms 的任务依次运行 8、16、6 ms 后结束。

优点（原卷答案要点）：① 交互型短作业通常在第一队列的时间片内就能完成，终端用户满意；② 短批处理作业在第一或第一、二队列各执行一个时间片就能完成，周转时间短；③ 长批处理作业依次在各队列获得时间片运行，不会得不到处理；④ 不需要事先知道作业运行时间，能自动区分 I/O 密集与 CPU 密集任务。

综合：5 个任务 A–E 运行时间 10、6、2、4、8 ms，优先级 3、5、2、1、4（5 最高），几乎同时到达，求 FCFS、优先级、RR(q=2) 的平均周转时间（15 分）2018

FCFS：完成时刻 10、16、18、22、30 → 平均周转 (10+16+18+22+30)/5 = 19.2 ms。

优先级（B、E、A、C、D）：完成时刻 6、14、24、26、30 → 平均 (6+14+24+26+30)/5 = 20 ms。

RR：轮次 (A,B,C,D,E)(A,B,D,E)(A,B,E)(A,E)(A)；完成 C=6、D=16、B=22、E=28、A=30 → 平均 102/5 = 20.4 ms。

先看个大概

判断：资源分配图中存在环时，系统（中某些）进程处于死锁状态。2018·2020

✗ 每类资源只有一个实例时，有环才一定死锁；资源有多个实例时，有环不一定死锁。

判断：A、B 共享 S1 需互斥，B、C 共享 S2 需互斥，所以 A 与 C 也必须互斥。2018

✗ 互斥没有传递性。

判断：信号量 S 当前值 −6，表示系统中共有 6 个等待的进程。2020

✗ 表示有 6 个进程在等待这个信号量（对应的临界区），不是全系统。

判断：取值为 0 或 1 的信号量只能实现互斥。2020

✗ 二值信号量也能实现同步（如初值 0 用于“先后顺序”）。

判断：管程中条件变量的 signal() 与信号量的 signal() 效果相同。2020

✗ 条件变量的 signal 在没有等待者时什么都不做；信号量的 signal 一定会把值加 1。

选择：P/V 信号量 S 初值 2，当前 −1，表示有几个等待进程？2019

1 个（负值的绝对值）。

综合：售票厅最多容纳 20 人，用 P/V 操作管理（15 分）2018

信号量 S 初值 20。S>0：还能进的人数；S=0：厅内已满 20 人；S<0：|S| 是在外等待的人数。

每个购票者：P(S); 进入售票厅; 购票; 退出; V(S);

若最多 n 人购票：S 最大 20，最小 20 − n。

综合：银行家算法，可用 (0,2,1)，求安全序列（10 分）2018

P1 需 (0,0,1) 可满足 → 释放后可用 (2,2,1)；P4 需 (2,0,0) 可满足 → 可用 (2,2,2)；P2 需 (1,3,2)、P3 需 (1,3,1)，R2 都不够。不存在安全序列，系统处于不安全状态。

综合：一个缓冲区、多个生产者、多个消费者，用 PV 写代码（10 分）2019
semaphore mutex = 1, empty = 1, full = 0; Producer: while (1) { P(empty); P(mutex); 放产品; V(mutex); V(full); } Consumer: while (1) { P(full); P(mutex); 取产品; V(mutex); V(empty); }

要点：先 P 资源信号量（empty/full），再 P mutex，顺序反了可能死锁。

综合：三个线程 a、b、c 分别按 (y,z)、(z,x)、(x,y) 加锁，分析死锁（25 分）2020

(1) 死锁顺序：a 获取 y，b 获取 z，c 获取 x，然后 a 申请 z、b 申请 x、c 申请 y，循环等待。

(2) 第一个不安全状态：a 持 y、b 持 z、c 持 x，出现在前三步之后。

(3) 改变解锁顺序不能解决，死锁发生在任何解锁之前。

(4) FCFS 调度下不会死锁：每个线程一直运行到结束，锁不会被竞争。

(5) 抢占式调度不能消除死锁：它抢占 CPU，但不抢占线程持有的锁。

辨析：死锁与饥饿；互斥量与信号量2019

死锁：多个进程循环等待对方占有的资源，都无法继续。饥饿：某些进程长时间得不到资源而无法执行。发生死锁的进程必然饥饿，饥饿不一定是死锁。

互斥量用于互斥，值只有 0/1，必须由加锁的同一线程解锁；信号量可用于同步和互斥，值可以是非负整数（计数多个同类资源），可由一个线程 V、另一个线程 P。
