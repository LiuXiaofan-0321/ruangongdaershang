Lab2  Ethernet 以太网帧的捕获与分析
一、实验目的
本实验以 ICMP Echo 流量为切入点，用 Wireshark 捕获并逐字段拆解以太网帧，掌握 DIX Ethernet（Ethernet II）的帧格式与地址作用范围，并回答广播地址与IEEE 802.3 的相关问题。具体目标如下：
1. 掌握在 Wireshark 中选择捕获接口、设置捕获过滤器、关闭混杂模式以及开启 MAC 地址解析的方法，并能保存可复核的 pcapng 迹线。
2. 依据协议详情面板与原始字节，确认目的 MAC、源 MAC 和 Type 字段的偏移与长度，并由实测长度验证帧结构与理论模型的差异（FCS、填充、前导码为何不可见）。
3. 结合本机 IP、默认网关与 ARP 缓存，解释访问远程主机时目的 MAC 为什么指向下一跳，并区分 MAC 地址与 IP 地址的作用范围。
4. 捕获广播与组播流量，写出以太网广播地址的标准形式，并明确指出判断单播/组播的究竟是以太网地址的哪一位（本次实测以字节级证据纠正了常见的 MSB 误判）。
5. 分析 IEEE 802.3 与 Ethernet II 的格式差异，理解 LLC 在上层协议解复用中的作用。
二、实验内容与实验步骤
实验按实验手册的五个 Step 推进：先用 ping 产生单播 ICMP 流量并捕获，再检查帧内各字段；其次绘制帧结构图与地址范围图；随后用 ether multicast 过滤器捕获广播/组播背景流量；最后完成手册的 Turn-in 题与 IEEE 802.3 拓展题。
需要特别区分两种过滤器：捕获过滤器（capture filter）在开始抓包前决定记录哪些帧，使用 BPF 语法，例如 icmp、ether multicast；显示过滤器（display filter）在抓包后筛选已记录的帧，使用 Wireshark 语法，例如 eth.dst == ff:ff:ff:ff:ff:ff、eth.dst.ig == 1。把 ether multicast 填进显示过滤器是常见错误，它不是显示过滤器语法。
本实验的三次抓包及其用途如下表。前两次为本机实测数据，第三次是为回答IEEE 802.3 拓展题而构造的样例（原因见 4.5 节）。

4.1  单播迹线的获取与定位
先用 ping 验证目标可达，再开始抓包，可以避免把网络不通误判为抓包失败。本次 ping www.baidu.com (www.a.shifen.com)，解析到 IPv4 地址 180.101.51.73，4 次请求全部收到回复，丢失 0%，往返时间约 14–180 ms。
ping -4 -n 4 www.baidu.com
参数 -4 把查询固定在 IPv4。若不加 -4，域名可能先解析出 IPv6 地址，此时用 icmp 作为捕获过滤器将抓不到任何帧，这是初学者最常见的空迹线原因之一。
抓包参数按手册要求设置：捕获接口选实际的联网物理接口 WLAN，链路层类型为 Ethernet，捕获过滤器为 icmp，关闭混杂模式（只记录本机收发的帧），并开启 MAC 地址解析以便识别厂商。随后在捕获过程中重新执行上面的 ping 命令，结束后停止捕获并保存为 pcapng。
本次捕获共 8 帧，恰好对应 4 个 Echo Request 与 4 个 Echo Reply。Wireshark 中显示过滤器 icmp 生效后（绿色表示语法有效），列表、协议详情与原始字节三个面板的关系如图 1 所示。图中帧 1 为请求帧，源 IP 为本机、目的 IP 为远程服务器，长度均为 74 字节。
图 1  单播迹线（Lab2_刘小凡_单播.pcapng）：显示过滤器 icmp 生效，共 8 帧，Frame 1 为 Echo (ping) request，长度 74 B
图 2  连通性验证：ping -4 -n 4 的 4 次请求全部收到回复，丢失 0%，并记录目标地址与往返时间（baidu 的 A 记录会轮转，此处地址与抓包时不同属正常）
关于请求与回复的配对：ICMP 的 Identifier 在本次抓包中恒为 1，而 Sequence Number 依次为 6、7、8、9，恰好与 ping 的 4 次请求一一对应，因此可以通过这两个字段确认请求与回复属于同一次 ping 过程。TTL 的差异也值得注意：本机发出的请求 TTL 为 128（Windows 默认值），而回复的 TTL 为 52，说明服务器端以 64 起跳、报文经过约 12 跳到达本机，这一差值本身不参与以太网帧结构分析，但它证明回复确实来自远端而不是本地伪造。

要判断目的 MAC 到底属于谁，必须把抓包结果与本机接口配置、ARP 缓存对照起来。本机 WLAN 接口的配置如下（ipconfig /all 实测）：

4.6  广播帧的地址与 I/G 判断位（重点）
广播帧的原始字节如下（帧 1，42 B）。可以看到前 6 个字节全为 ff，紧随其后是源 MAC、类型字段 0x0806（ARP），再往后是 ARP 报文：
0000  ff ff ff ff ff ff 14 ac 60 56 df 85 08 06 00 01
0010  08 00 06 04 00 01 14 ac 60 56 df 85 c0 a8 1f 87
0020  00 00 00 00 00 00 c0 a8 1f 01
该 ARP 报文的 Opcode 为 1（request），Sender IP 为 192.168.31.135，Target IP 为 192.168.31.1，Target MAC 为全零，说明这是本机在询问网关的 MAC 地址，属于普通的地址解析请求，而不是「免费 ARP（Gratuitous ARP）」。免费 ARP 的特征是发送方通告自己的地址（Sender IP 等于 Target IP）或目标 MAC 为广播，两者含义不同，不能仅凭「目的 MAC 是广播」就把所有 ARP 帧都归为免费 ARP。本机未出现 ARP 冲突检测流量，因为网关的 ARP 记录一直有效。
以太网广播地址的写法为 ff:ff:ff:ff:ff:ff，即 48 位全为 1。判断一个以太网地址是单播还是组播/广播，看的是地址第一个字节的最低有效位（Least Significant Bit，LSB），也就是 bit 0，称为 I/G 位：该位为 0 表示 Individual（单播），为 1 表示 Group（组播，广播是其中的特例）。紧邻的 bit 1 是 U/L 位，用于区分全球唯一地址与本地管理地址，它判断的是地址的管理属性，与收发对象无关，两者不可混淆。
图 11  目的 MAC 首字节中 I/G 位（bit 0）与 U/L 位（bit 1）的位置及本次实测地址的取值
这里需要特别强调一个容易出错的地方：I/G 位是第一个字节的最低有效位，而不是最高有效位。教材中文译本中曾把该位描述为「最左侧的第一位」，这容易被理解为 MSB，从而得出相反结论。本次实测给出了直接的字节级反证：广播地址首字节为 0xFF，其二进制为 1111 1111，最低位为 1；普通组播地址 01:00:5e:00:00:fb 的首字节为 0x01，二进制 0000 0001，最低位同样为 1；而两个单播地址 28:d1:27:df:d4:95（首字节 0x28 = 0010 1000）与 14:ac:60:56:df:85（首字节 0xAC = 1010 1100）的最低位都是 0。若按最高位判断，0xAC 的最高位为 1，就会被错误判为组播地址，这与实际抓到的单播流量直接矛盾。此外，以太网在发送每个字节时先发送最低位（LSB first），因此手册所说的「先发送的第一位」与这里的 bit 0 是同一个位。
补充一点观察：NBNS 的 9 个广播帧源 MAC 都是本机 14:ac:60:56:df:85，说明这些名称查询是本机发出的（本机设置了系统代理，因而主动查询 WPAD）。这提醒我们，广播流量并不只来自路由器或其他设备，本机自身也是常见的广播源。
4.7  IEEE 802.3 拓展：格式对照与 LLC 解复用
手册的拓展题要求观察 IEEE 802.3 帧。我在本机全部迹线中用显示过滤器 llc 检索，结果为零：单播迹线（8 帧）、广播组播迹线（110 帧）以及此前实验累积的lab1.pcapng（144509 帧）中都没有 LLC 帧。这也符合手册的说明 —— IEEE 802.3 格式在现代网络中已很少见到，抓不到属于正常现象。因此在下面的分析中，格式结论给出原理推导，字段数值则用一份按标准构造的IEEE 802.3 + LLC 样例来验证，该样例文件已在附录中标注来源，不与本机实测统计混用。
构造样例的第 1 帧（IEEE 802.3 + LLC，25 B）原始字节如下：
0000  aa bb cc dd ee ff 11 22 33 44 55 66 00 0b 42 42
0010  03 4c 4c 43 2d 44 45 4d 4f
Wireshark 对该帧的解析为「IEEE 802.3 Ethernet」，偏移 12–13 的两字节显示为 Length: 11，随后是 Logical-Link Control，DSAP/SSAP 均为 0x42，Control 为 0x03（无编号信息 UI 帧）。对照样例的第 2 帧为 Ethernet II，同样的 12–13 偏移处显示 Type: IPv4 (0x0800)。同一个 16 位字段位置，在两种格式下含义完全不同，这正是区分二者的关键。
三个拓展问题的回答如下：
问题 1：IEEE 802.3 与 LLC 组合的首部比 DIX Ethernet 长多少？两者的 MAC 首部都是 14 B（6 B 目的地址 + 6 B 源地址 + 2 B 长度/类型）。IEEE 802.3 在其上还有 LLC 首部：当 Control 字段为单字节的 UI 格式时，DSAP、SSAP、Control 共 3 B，因此合计 17 B，比 DIX Ethernet 长 3 B。若 LLC 之上再带 SNAP，则要追加 5 B（3 B OUI + 2 B 协议标识），合计 22 B，比 DIX Ethernet 长 8 B。样例帧的 Length 字段为 11，正好等于 LLC 首部 3 B 加上有效数据 8 B，可以直接验证长度字段的含义。需要注意 Trailer/Padding 与 FCS 位于帧尾，不应计入首部长度。
问题 2：接收方如何判断帧是 DIX Ethernet 还是 IEEE 802.3？读取源地址之后的 16 位字段：若其值不小于 1536（0x0600），则按 EtherType 解释，属于 DIX Ethernet；若其值不大于 1500（0x05DC），则按长度解释，其后跟随 LLC，属于 IEEE 802.3。1501–1535 这一段两个标准都不使用，因此不可能出现。样例中 0x000B 落在长度区间，Ethernet II 样例中 0x0800 落在类型区间，Wireshark 也正是据此把两帧分别标注为 IEEE 802.3 和 Ethernet II。
问题 3：IEEE 802.3 没有 Type 字段，上层协议是如何确定的？由 LLC 首部中的服务访问点字段解复用，接收端主要看 DSAP。DSAP 指明上层协议或协议族，SSAP 指明发送方，Control 指明 LLC 帧类型（0x03 为无编号信息的 UI 帧，常用于承载上层协议数据）。当 DSAP 与 SSAP 均为 0xAA 时表示使用 SNAP 扩展：Control 通常为 0x03，其后 3 B 为 OUI、2 B 为协议标识；当 OUI 为 0x000000 时，该 2 B 协议标识沿用 EtherType 的编号，例如 IPv4 为 0x0800，从而实现与 DIX Ethernet 的兼容。在构造样例中 DSAP=0x42，Wireshark 据 SAP 值将其识别为生成树 BPDU，这就是「用 DSAP 作为解复用键」的直接体现。

5.1  Turn-in 题回答
题目 1：绘制 ping 报文以太网帧结构图。见 4.2 节图 3。目的 MAC、源 MAC 与 Type 字段的长度分别为 6 B、6 B、2 B，以太网首部共 14 B；IPv4 数据报与 ICMP 报文整体作为它的有效载荷，实测载荷为 60 B，抓包记录总长 74 B。标准帧末尾另有 4 B FCS，由网卡处理，抓包中通常不可见，图中以虚线框表示其存在。
题目 2：绘制地址范围图。见 4.4 节图 5。本机 （192.168.31.135，14:ac:60:56:df:85）与默认网关（192.168.31.1，28:d1:27:df:d4:95）处于同一链路，远程服务器（180.101.51.73）经 Internet 到达。请求帧的以太网目的地址是下一跳网关的 MAC，而 IPv4 的目的地址才是远程服务器；回复帧在本地链路上以网关为源 MAC、以本机为目的 MAC。
题目 3：以太网广播地址是什么？判断位是哪一位？广播地址为 ff:ff:ff:ff:ff:ff，即 48 位全为 1。判断单播与组播/广播的位是目的 MAC 第一个字节的最低有效位（bit 0），称为 I/G 位：0 表示单播，1 表示组播或广播。本次实测的字节证据为：广播 0xFF（最低位 1）、组播 0x01 与 0x33（最低位 1）、单播 0x28 与 0xAC（最低位 0）。需要强调的是该位不是最高有效位，若按最高位判断，首字节 0xAC 的本机单播地址会被误判为组播，与实测矛盾。
5.2  实测结果汇总
5.3  实验体会
这次实验最大的收获是「用字节说话」。教材与网络资料对判断单播/组播的位位置存在不一致的说法，有的写「最左侧第一位」容易被读成最高位。只要把原始字节调出来逐位核对 —— 广播 0xFF、组播 0x01、单播 0xAC —— 结论就没有歧义。这也说明抓包实验的价值不仅在于验证理论，更在于当资料表述含糊时能够自己取得判据。
其次是理解了「观测位置决定观测结果」。同一个以太网帧，在主机上抓到的是 74 B 而没有 FCS 和填充；ARP 帧只有 42 B，低于标准最小帧长 64 B。如果不知道 FCS 由网卡剥离、填充在抓包点之前已经完成，很容易误判为帧不符合标准。抓包看到的是「操作系统能看到的那一部分」，而不是线上传输的全部比特，这一点对后续分析无线帧和隧道流量同样重要。
最后是抓包口径要一致。广播/组播数量完全取决于网络环境和观测时长，本次 60 秒得到 110 帧，其中广播 11 帧。报告如实记录时长与数量，并注明本机因配置系统代理而主动发送 NBNS WPAD 查询，而不是照搬他人报告的数值。这样得到的数据才能经得起复核。
