一、实验目的 
本实验通过真实 HTTP 流量和逐 TTL 的 ICMP 探测，分析 IPv4 首部结构、分片判据与网络
路径，并独立验算接收报文的首部校验和。具体目标如下。 
1. 掌握在 Wireshark 中选择联网接口、设置 tcp port 80 捕获过滤器、开启网络名称解析并关闭
混杂模式的完整抓包流程，能够保存可复核的 pcapng 迹线； 
2. 能够把 IPv4 首部各字段与被高亮的原始字节逐一对应，理解哪些字段共享同一个字节，并
据此还原首部长度字段 IHL 的编码方式； 
3. 通过实测数据总结 Total Length、Identification、TTL 以及分片标志的变化规律，并区分“未
分片”的判据与 IP 校验和卸载等容易误判的现象； 
4. 使用 traceroute 类探测发现从本机到远端服务器的路由器级路径，理解星号跳的含义，并能
借助地址登记信息为每一跳标注归属组织； 
5. 独立完成一次 IPv4 首部校验和的 1 的补码求和验算，把 10 个 16 位字与对应字段一一列
出，验证结果等于 0xffff。 
二、实验内容与实验步骤 
实验按手册的五个步骤进行：捕获 HTTP 迹线；展开 IPv4 首部并核对字节；绘制字节布局并
回答六道问题；根据同一目标服务器的逐跳探测绘制路径；选取接收方向、首部 20 B 且校验和非零
的报文完成验算。 
提交内容分别为 IPv4 结构图和六题答案、网络路径图及实际探测输出、校验和的十个 16 位字
与求和过程，均在第四节及附录中给出。

4.1 HTTP 流量的获取与定位 
本次使用 curl 获取网页。参数 -4 强制使用 IPv4，--resolve 固定 www.baidu.com 的服务器地
址，--interface 绑定 WLAN 源地址，--noproxy 禁用 curl 的显式代理；这些参数并不关闭系统 
TUN，路径探测的影响另见 4.5 节。命令按 Windows PowerShell 的续行语法书写如下。 
curl.exe -4 --noproxy "*" --interface 172.31.165.86 ` 
  --resolve www.baidu.com:80:182.61.200.108 ` 
  -o baidu.html -w "%{http_code} %{size_download} %{time_total}\n" ` 
  http://www.baidu.com/ 
curl 返回 HTTP 200，实际下载 2381 B，用时约 0.855 s；保存的响应首部包含 Content-Length: 
2381，与下载文件大小一致。随后在 Wireshark 选择 WLAN、Ethernet 链路层和 tcp port 80 捕获过
滤器，关闭混杂模式并启用网络名称解析。tcp port 80 本身不限定 IP 版本，本次由 curl -4 产生 
IPv4 流量。

1 本机与远端 IPv4 地址 
本机 WLAN 地址为 172.31.165.86，目标服务器为 182.61.200.108；收发方向由源、目的地址的

2 Total Length 的统计范围 
Total Length 包含 IPv4 首部及其载荷，不含以太网首部。第 4 帧：117 B = 20 B IP 首部 + 20 
B TCP 首部 + 77 B HTTP 请求；帧长 131 B 与 IP 总长度之差为 14 B，恰好是本次 Ethernet II 首
部。 
3 Identification 字段的变化 
本机方向依次为 0xedbe 至 0xedc7，逐包加 1；接收方向为 0xedbe、0xb73c、0xb73e、
0xb73f、0xb740、0xb741、0xb744、0xb745、0xb746，存在跳号。两方向在第 1、2 帧还出现了相同
值。因此本次 ID 不在连接内恒定，也不保证双向不同；不能把观察到的递增趋势推广为协议要求。
ID 用于分片重组，不是 TCP 连接号。RFC 6864 所称 atomic datagram 满足 DF=1、MF=0、
Offset=0，允许其 ID 重复[2]；本次 19 帧满足这一条件。 
4 发送方向 TTL 的初值 
本次 HTTP 连接的 10 个发送包在 WLAN 抓包处 TTL 均为 128，低于 8 位字段的最大值 
255。路径探测则故意使用 TTL 1–17。接收 SYN/ACK 的 TTL 为 45，其余接收包为 40；未确认
对端初始 TTL，不能用 64−接收 TTL 直接推断路由跳数。

5 未分片报文的判据 
MF=0 且 Fragment Offset=0 表示本包未分片。19 帧均满足该判据。DF=1 是禁止后续分片的指
示，不是判断未分片的必要条件；DF=0 的短包也可能不分片。MF=0 但 Offset>0 是最后一片。
Fragment Offset 以 8 B 为单位；图 7 的 Offset=0 在两种单位下数值相同。 
6 IHL 的长度编码 
本次目标连接首部均为 20 B。首字节 0x45 的高 4 位 0100 表示 Version=4，低 4 位 0101 
表示 IHL=5。IHL 以 32 位字即 4 B 为单位，5×4=20 B；合法的最小值为 5，4 位最大值 15 对应 
60 B，选项与填充最多共 40 B。 
4.5 Internet 路径与隧道影响的排查 
首先对与 HTTP 相同的服务器运行 tracert -4 -h 30 -w 700 182.61.200.108，原始输出只显示两
跳： 
1    *        62 ms    *        182.61.200.108 
2    33 ms    32 ms    33 ms    182.61.200.108 
两跳结果本身不能证明异常，因为目标也可能离源很近；关键证据是对应 WLAN 迹线中 Echo 
Request 的 TTL 全为 128，未体现 tracert 的逐 TTL 探测。结合 singbox_tun 的默认路由指向 
172.18.0.2，可判断该结果受到本机隧道影响，不能据此描述 WLAN 的逐跳转发路径。排查未修改 
VPN 或系统路由。

测，单次超时 900 ms。保存 API 返回结果，并在 WLAN 抓包核对实际 TTL。下文称其为“绑定

五、实验结果总结 
5.1 实验结论 
关于 IPv4 首部：本次所有报文首部长度均为 20 B，无选项字段；首字节 0x45 同时编码版本
号与首部长度，IHL 以 4 字节为单位，最大值 15 对应 60 B。Total Length 统计 IP 首部与载荷之
和，不含链路层首部。 
关于标识与分片：本机方向 Identification 逐包递增，接收方向存在跳号，说明它只是分片重组
时用于归组同一数据报的标识，并非连接号；19 个包全部满足 MF=0 且 Offset=0，因此都未分
片，其中 DF=1 是发送方的策略选择而不是未分片的判据。 
关于 TTL：本机普通数据流的 TTL 初值为 128，低于 8 位字段上限 255；接收方向报文 TTL 
为 40，首个响应为 45。这里只报告观测值——由 64 减 TTL 直接推算跳数是不严谨的，因为无法
确认对端的初始 TTL 一定是 64，而且双向路由可能不同。

获值为零与校验和卸载现象相符，不能据此判定线上错误。 
关于与教材的差异：结构上没有发现差异，但有一处实现层面的现象值得记住——协议规定的字
段未必在抓包点就已填好，校验和卸载就是典型例子。这提醒我们在用抓包结论判断“对错”之前，要
先确认抓包位置相对于协议栈处理的位置。 
5.2 实验体会 
本次实验中，发送包的零校验和和 tracert 的两跳结果都需要结合抓包位置分析。前者应与校验
和卸载区分，后者需检查实际发出的 TTL。把工具提示与独立字段验证相结合，才能避免把本机处
理现象误写为网络结论。 
另一处体会是描述数据时要留有余地。Identification 在本机方向确实逐包递增，但接收方向有跳
号，因此报告里只写“呈递增趋势”而不断言每包加一；星号跳也只写“规定时间内无应答”，不推断该
路由器关闭了 ICMP。把结论限制在证据支持的范围内，比给出一个漂亮但过度的断言更可靠。 
最后是独立复核的价值。校验和既可以让 Wireshark 判定，也可以自己按 1 的补码算一遍；两
条路径得到同一个结果，才算真正验证。本报告的字段与统计量均由脚本从 pcapng 原始字节重新解
析，与界面显示互为交叉验证，而不是从截图抄写。
