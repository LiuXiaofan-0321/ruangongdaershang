四、实验过程与分析 
本次实验围绕 IPv4 协议展开，目的是通过抓取并逐字段检查真实的 IPv4 数据报，掌握 IP 首部的
结构与各字段含义，并学会用抓包证据回答关于寻址、长度、标识、生存时间与分片的问题。具体目标如
下： 
1. 掌握在 Wireshark 中选择联网接口、设置 tcp port 80 捕获过滤器、开启网络名称解析并关闭混杂
模式的完整抓包流程，能够保存可复核的 pcapng 迹线； 
2. 能够把 IPv4 首部各字段与被高亮的原始字节逐一对应，理解哪些字段共享同一个字节，并据此
还原首部长度字段 IHL 的编码方式； 
3. 通过实测数据总结 Total Length、Identification、TTL 以及分片标志的变化规律，并区分“未分片”
的判据与 IP 校验和卸载等容易误判的现象； 
4. 使用 traceroute 类探测发现从本机到远端服务器的路由器级路径，理解星号跳的含义，并能借助
地址登记信息为每一跳标注归属组织； 
5. 独立完成一次 IPv4 首部校验和的 1 的补码求和验算，把 10 个 16 位字与对应字段一一列出，
验证结果等于 0xffff。 
实验按手册的五个 Step 推进：先用 curl 抓取同一远端服务器的网页并用 tcp port 80 过滤器捕获，
再做 traceroute 探测路径；随后在 Wireshark 中展开 IPv4 首部逐字段核对；接着绘制 IP 包结构图并回
答六道问题；之后依据路径探测结果绘制网络路径图；最后选取一个接收方向、非零校验和、20 字节首
部的包完整验算 IP 首部校验和。 
本次实测使用 curl 代替手册中的 wget，两者都是命令行取回工具，作用等价。为避免域名解析或
代理影响结果，抓包时用 --resolve 把目标域名固定到一个已知的服务器地址，并显式指定出口接口、禁
用代理、强制 IPv4： 
curl -4 --noproxy "*" --interface 172.31.165.86 \ 
     --resolve www.baidu.com:80:182.61.200.108 \ 
     -o baidu.html -w "%{http_code} %{size_download} %{time_total}\n" \ 
     http://www.baidu.com/ 
命令返回 HTTP 200，Content-Length 2381 字节，实际下载 2381 字节，全程耗时约 0.855 秒，与
抓到的报文长度一致。抓包参数按手册设置：接口选实际联网的 WLAN，链路层 Ethernet，捕获过滤器 
tcp port 80，关闭混杂模式，勾选网络名称解析。这一步对应手册的 Turn-in 第 1 项。 
需要说明的是，原始迹线 Lab3_HTTP.pcapng 共 108 帧，其中包含其他应用程序的背景 HTTP 流
量。为避免把无关连接混入分析，本次按 tcp.stream == 0 导出目标连接为 Lab3_HTTP_target.pcapng（19 
帧：本机发送 10 帧、接收 9 帧）。导出过程未改写任何报文，帧号仍为 1–19，后续分析均以该文件为
准。

5.2  必做题目二：IPv4 六道问题 
题目原文（Step 3）：结合迹线中的 IP 包回答以下六个问题。逐题作答如下。 
问题 1：本机与远端服务器的 IP 地址是什么？本机 WLAN 接口地址为 172.31.165.86，远端服务
器为 182.61.200.108。这两个地址可以从迹线中任一收发方向报文的 Source Address 与 Destination 
Address 字段直接读出，方向由地址顺序即可区分。 
问题 2：Total Length 包含 IP 首部还是仅包含 IP 载荷？两者都包含，即 IP 首部长度加上 IP 载
荷长度，但不包含以太网首部。以第 4 帧为例，Total Length = 117 B，而首部为 20 B、TCP 首部 20 
B、HTTP 请求 77 B，20 + 20 + 77 = 117，正好吻合。该帧的以太网帧长为 131 B，131 − 117 = 14 B 恰
好是以太网首部，可见链路层首部不计入 Total Length。 
问题 3：Identification 字段如何变化？本机发送方向按顺序为 0xedbe、0xedbf、0xedc0、0xedc1、
0xedc2、0xedc3、0xedc4、0xedc5、0xedc6、0xedc7，逐包递增 1；接收方向依次为 0xedbe（第 2 
帧）、0xb73c、0xb73e、0xb73f、0xb740、0xb741、0xb744、0xb745、0xb746，存在跳号。因此可以说：
同一方向、由同一台主机产生的报文其 Identification 常呈递增趋势，但两方向的取值互相独立，且接收
方向出现跳号，所以既不能说它在整个 TCP 连接中保持不变，也不能断言两方向绝无重复。需要强调的
是 Identification 不是 TCP 连接号，它服务于分片重组：同一原始数据报拆成的多个分片共享该值，接
收端依据源/目的地址、Protocol 与 Identification 等把它们归到一组。对未分片的 atomic datagram，RFC 
6864 并不要求每个包的取值都不相同。 
问题 4：本机发出的报文 TTL 初值是多少？是最大值吗？本机发送的所有报文 TTL 均为 128，不
是 8 位字段的最大值 255。这说明发送方主动选择了一个较低的初值（Windows 的 IPv4 默认值）。需
要与路径探测区分：在绑定源地址的 traceroute 中，探测报文被故意设置成 TTL = 1、2、3……17，那是
为了实现逐跳探测，与本机普通数据流的 TTL 初值不是一回事，两者不能混为一谈。 
问题 5：如何判断一个包没有被分片？关键在于 Fragmentation 相关的三个信息：MF（More 
Fragments）标志为 0 且 Fragment Offset 为 0。本迹线 19 个包全部满足 MF=0、Offset=0。需要注意 
DF（Don't Fragment）位在本迹线中虽然都是 1，但 DF=1 并不是“未分片”的必要条件：一个报文完全可
以是 DF=0 却因为长度未超过 MTU 而没有分片。反过来，若 MF=0 但 Offset>0，则说明它是某个已分
片数据报的最后一片。因此判据应是 MF=0 且 Offset=0。另外 Fragment Offset 的单位是 8 字节而不是 
1 字节。 
问题 6：IP 首部长度是多少，在首部长度字段中如何编码？本次所有报文的首部长度都是 20 B，
即不含选项的最小首部。首部的第 0 字节为 0x45，高 4 位是版本号（0100 = 4），低 4 位是 IHL
（0101 = 5）。IHL 表示的是“以 4 字节为单位的首部长度”，因此实际字节数 = IHL × 4 = 5 × 4 = 20 B。
正因为只有 4 位，IHL 的最大值为 15，对应首部最长 60 B，这既是选项字段长度受限的原因，也是首
部长度必须以 4 字节对齐的原因。 
5.3  必做题目三：Internet 路径图与组织标注 
题目原文（Step 4）：依据 traceroute 输出绘制网络路径示意图，标明本机与远端服务器的 IP 地
址，以及路径上路由器的跳数编号；并利用域名信息标注每一跳所属的真实组织；无法解析的跳留空。

六、实验结果总结 
6.1  实验结论 
关于 IPv4 首部：本次所有报文首部长度均为 20 B，无选项字段；首字节 0x45 同时编码版本号与
首部长度，IHL 以 4 字节为单位，最大值 15 对应 60 B。Total Length 统计 IP 首部与载荷之和，不含
链路层首部。 
关于标识与分片：本机方向 Identification 逐包递增，接收方向存在跳号，说明它只是分片重组时用
于归组同一数据报的标识，并非连接号；19 个包全部满足 MF=0 且 Offset=0，因此都未分片，其中 
DF=1 是发送方的策略选择而不是未分片的判据。 
关于 TTL：本机普通数据流的 TTL 初值为 128，低于 8 位字段上限 255；接收方向报文 TTL 为 
40，首个响应为 45。这里只报告观测值——由 64 减 TTL 直接推算跳数是不严谨的，因为无法确认对
端的初始 TTL 一定是 64，而且双向路由可能不同。

关于校验和：接收方向首部校验和经两次独立计算确认正确；本机方向校验和为 0 是校验和卸载造
成的观测现象，不代表线上首部有误。 
关于与教材的差异：结构上没有发现差异，但有一处实现层面的现象值得记住——协议规定的字段
未必在抓包点就已填好，校验和卸载就是典型例子。这提醒我们在用抓包结论判断“对错”之前，要先确认
抓包位置相对于协议栈处理的位置。 
6.2  实验体会 
这次实验最主要的收获是意识到“看到的”和“实际发出的”可能不是一回事。本机 IP 校验和全为 0，
如果只看抓包就下结论，会误判为协议实现错误；同样，直接运行 tracert 得到“两跳到达”，如果照抄就
成了错误结论，实际原因是隧道接管了探测流量。两处都说明：异常现象要先定位到观测位置和处理时
序，再谈结论。 
另一处体会是描述数据时要留有余地。Identification 在本机方向确实逐包递增，但接收方向有跳
号，因此报告里只写“呈递增趋势”而不断言每包加一；星号跳也只写“规定时间内无应答”，不推断该路由
器关闭了 ICMP。把结论限制在证据支持的范围内，比给出一个漂亮但过度的断言更可靠。 
最后是独立复核的价值。校验和既可以让 Wireshark 判定，也可以自己按 1 的补码算一遍；两条路
径得到同一个结果，才算真正验证。本报告的字段与统计量均由脚本从 pcapng 原始字节重新解析，与界
面显示互为交叉验证，而不是从截图抄写。
